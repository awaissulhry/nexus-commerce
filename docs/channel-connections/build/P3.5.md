**P3.4 already built the alert**, so this package did not invent a sixth path: it reads
the headers and calls `raiseChannelAlert`. That was the point of leaving the shape
behind in P3.4.

### 2.1 Read on a SUCCESS, not in the error path

`Sunset` rides on a **200** for months before anything starts failing. That is the whole
value of the header — it is a warning, not a symptom — so the watch sits on the success
path of the gateway. Putting it beside the error classifier would have meant learning
about a retirement on the day it broke.

---

## 3. The three rules that are about not crying wolf

### 3.1 🔴 `Deprecation`'s date is NOT the shutdown date

They answer different questions:

- `Deprecation` says **it is deprecated**, and its date is when it *became* so — usually
  in the past.
- `Sunset` says **when it stops working**. That is the date an operator plans around.

`Deprecation: @1688169599` is 2023-07-01. Reading that as the shutdown date would tell
someone their integration died three years ago. The shutdown date comes from `Sunset`
alone; when there is none, the alert says *"It has not said when it stops working"*
rather than inventing one, and stays at `info` instead of `warn`.

### 3.2 🔴 `Deprecation: false` is believed

RFC 9745's field is a boolean. `false` / `?0` is the channel saying the **opposite** of
a notice, and reading "the header is present" as "it is deprecated" would raise an alarm
about an endpoint that was just confirmed fine. A `Sunset` arriving beside a false
`Deprecation` is still reported, because the shutdown date is the one that costs money.

### 3.3 🔴 A MOVED sunset date is news

This was found by a failing test, not by design.

P3.4's dedupe keys on `(kind, entityType, entityId)`, and `deprecationAlert`'s entity
was `channel:endpoint`. So a channel that **moved its shutdown date earlier** was folded
into the unread notice that still named the old date — and the operator would keep
reading a date that was no longer true while planning around it.

The date is now part of the identity. An endpoint whose date never moves still gets
exactly one notice; a moved date gets a second one, and both are readable, which is
itself the news.

### 3.4 An unparseable date is shown as the channel wrote it

A `Sunset` we cannot parse keeps its raw string. Showing nothing would be worse: an
operator can act on "whatever eBay said", and cannot act on a blank.

## 4. The proof

**`src/services/cx/deprecation-watch.p35.vitest.test.ts` — 22 tests.** The pure reader
is tested without a database; the watch on a real PostgreSQL with the generated schema
and the real profile policies, profiles ON.

The done-when is a test by that name: a fixture with the header raises **one** alert,
carrying the parsed date and the sentence *"Nexus still calls it"*.

### 4.1 Mutation checks — 6 rules broken, 6 named tests failed

| # | Mutation | Result |
|---|---|---|
| 1 | `Deprecation`'s date used as the shutdown date | ✅ failed |
| 2 | an explicit `Deprecation: false` read as a notice | ✅ failed |
| 3 | an unparseable `Sunset` dropped instead of shown | ✅ failed |
| 4 | the quiet period removed | ✅ failed **after a fix — see §4.2** |
| 5 | the sunset date leaves the alert identity | ✅ failed |
| 6 | the watch's memory grows without limit | ✅ failed |

All three touched files restored and compared byte for byte.

### 4.2 Mutation 4 proved the test was asserting the wrong guard

Deleting the in-process quiet period left the test *"one deprecated endpoint answering
many times is ONE alert"* **passing**. That was correct behaviour and a wrong test.

There are **two guards here and they are not the same guard**:

- **P3.4's database dedupe** is the correctness one. It is what makes 51 calls into one
  notice, and it holds with the in-process set gone entirely.
- **The in-process quiet set** is the *cheapness* one: without it, 51 answers from a
  deprecated endpoint do 51 `Notification` lookups per owner. The Amazon Ads
  `PUT /sp/keywords` in this ledger alone has **26,838 calls**.

An efficiency guard has to be asserted by counting the **work**, not the outcome. The
test now asserts 1 raise and 50 quiet alongside the 1 notice, and the mutation fails.

The quiet set has a TTL and is bounded at 500 endpoints, so it can only ever *delay* a
re-alert, never suppress one — the database stays the authority on whether anyone has
been told.

## 5. Still open

1. **No channel has ever sent one of these headers to this installation**, so nothing
   here is proven by real traffic. The first real notice is worth reading — it will say
   which spelling a channel actually uses.
2. **`Link: <...>; rel="deprecation"`**, RFC 9745's companion pointing at the
   documentation, is **not** parsed. It would add a link to the notice, not a fact. Out
   of scope and named rather than silently skipped.
3. **The alert only fires where a business profile is in context.** `raiseChannelAlert`
   needs one to find the owners; a gateway call made outside any profile logs and
   raises nothing. Every scheduled job enters a profile, so this is the platform-level
   boot path only.
