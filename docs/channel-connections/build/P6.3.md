# P6.3 — Etsy: a rotated refresh token is never lost

State: **BUILT (2026-09-19), committed locally (not pushed, not deployed).** Run under the Owner's "Start to implement the whole plan" (FINAL-PLAN 14.3). Taken out of order (small, independent) while the P1 gateway survey ran.

Plan row (FINAL-PLAN.md section 6, P6): save the rotated refresh token safely before using it, so it can never be lost.

## 1. Evidence (2026-09-19)

- Only Etsy rotates refresh tokens (`rotatesRefreshToken: true` in `services/cx/connectors/etsy/spec.ts:198`; the other four specs say false). Etsy invalidates the old refresh token when it answers.
- `services/cx/token.service.ts` `refreshOwned` already refused to use a response without the rotated token, and saved before returning the access token. But the save is one compare-and-set against a snapshot of the row that includes `authStatus` and `consecutiveFailures`-adjacent fields (`refreshSnapshot`, `:219-225`). If anything else wrote the row between the read and the save — the heartbeat moving the status, for example — the save was refused (`RefreshContended`) and the rotated token was dropped: the account then needed a reconnect. A failed database write dropped it the same way.

## 2. Change

`services/cx/token.service.ts` — `saveRefreshedCredentials`: for a ROTATED token only, when the save is refused or fails, re-read the row; if the grant itself is unchanged (same stored credentials, still active, not disconnected or revoked), save against the fresh row; up to 3 attempts (a short wait after a write error). A grant replaced meanwhile (a reconnect) or an account disconnected meanwhile still wins, as before. After three failures: a `refresh_failed` ledger row, an alert ("a new refresh token could not be saved"), and the error surfaces. Every other refresh keeps the strict one-shot compare-and-set.

## 3. Proof

- `services/cx/token.service.vitest.test.ts` (+6; 85 pass): the heartbeat changes the status mid-refresh → the rotated token is saved and the status is `connected` (before: refused, token lost); control: the same interruption on a non-rotating channel is still refused and the old grant kept; a reconnect mid-refresh wins; a disconnect mid-refresh is not undone; two failed writes → saved on the third; three failed writes → alert + `refresh_failed`, no token material in events or alerts.
- Mutation check: rule switched off → 3 fail; grant check removed → 4 fail.
- `tsc` (apps/api): 0 errors. Full API suite: **9578 passed, 6 failed** (the two known Amazon local-account files).

## 4. Production proof — OPEN

Etsy is connected only locally today (09-10 note). After Etsy goes live on production (P6.8): `ConnectionEvent` rows `refresh` with `rotated: true` keep appearing every hour with no `refresh_failed`.
