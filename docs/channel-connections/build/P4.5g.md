# P4.5g — "reconnect once for a true expiry date" is the wrong instruction

State: **BUILT 2026-09-21**, committed locally. Part of P4.5 (advertising).
**Recommendation to the Owner: do NOT reconnect Amazon Ads.**

Plan row (FINAL-PLAN.md §6, P4.5): *"reconnect once for a true expiry date"*.
Deadline row: *"Refresh tokens issued **on or after 2026-07-30** expire 365 days after
consent; tokens issued **before** that date are **not affected**. **CONFIRMED** (Amazon
Ads release note of 2026-05-26). … If our grant predates 2026-07-30, it has no 365-day
expiry at all, and a reconnect would START one. → P4.5: decide from the grant date."*

P0.8 spotted the inversion and wrote *"P4.5 must decide from the grant date"*.
**This is that decision.**

## 1. Evidence (measured 2026-09-21, development database)

| Fact | Value |
|---|---|
| `AmazonAdsConnection.tokenIssuedAt`, all 9 rows | **2026-05-17T02:45:45Z** (sub-second apart — one backfill) |
| `tokenIssuedAtIsEstimate`, all 9 rows | **true** |
| Amazon's cut-off | 2026-07-30 |
| Grant predates the rule | **YES** |

🟢 **The estimate's direction supports the conclusion rather than weakening it.** The
schema records that the backfill used `createdAt` as a **conservative floor** — consent
happened at or before the row existed — so the true consent date is **≤ 2026-05-17**,
and earlier than the cut-off whichever way the estimate is wrong.

That is worth saying out loud because the same reasoning in the other direction would
be invalid: a floor cannot prove a date is *after* anything.

**Therefore: this refresh token has no expiry. A reconnect would create one**, turning a
token that does not die into one that dies 365 days later.

## 2. 🔴 The defect that made the screen agree with the wrong instruction

`ChannelConnection.refreshTokenExpiresAt` reads **2027-09-08T09:00:02.920Z** — exactly
365 days after `lastRefreshAt` (2026-09-08T09:00:02.920Z), to the millisecond.

**Amazon did not report it.** Traced in the source:

1. `token.service.storeGrant`:
   `refreshLife = grant.refreshExpiresInSec ?? spec.auth.refreshTokenLifetimeSec ?? null`
2. The Ads connect flow builds its `GrantResult` **without** `refreshExpiresInSec`
   (asserted by a test, sliced out of the real file).
3. `services/cx/connectors/amazon-ads/spec.ts` declares
   `refreshTokenLifetimeSec: 365 * 86_400` — **our own constant**.
4. LWA has no `refresh_token_expires_in` field at all. That is eBay's.

And `routes/advertising.routes.ts` read that column as `measuredExpiry`, preferred it
over the row, and set **`isEstimate: false`** from it — over a comment reading *"The
grant reported a real refresh-token lifetime, which is on the connection."*

**Two banked traps in one place:** a derived number wearing a measurement's badge
(`reference_a_banked_rule_can_go_false`), and a comment asserting a property the data
does not have (`reference_comment_asserts_property_code_lacks` — the same shape as
P4.4a's *"EU marketplaces all use EUR"*).

The visible result: a confident, unflagged expiry date for a token that has none — and
that date is exactly what makes "reconnect once for a true expiry" look sensible.

## 3. Changes

1. **New** `services/ads-core/ads-token-expiry.ts` — `adsRefreshExpiry()` decides from
   Amazon's published rule and returns **where the answer came from**:
   `channel` (Amazon told us — nothing produces this today, it is the seam for when it
   does) · `derived` (our rule + the consent date) · `none` (the rule does not apply) ·
   `unknown` (no consent date, so nothing can be said).
2. `routes/advertising.routes.ts` — uses it. New fields `tokenExpiryProvenance` and
   `tokenExpiryNote`; `tokenExpiryStatus` gains **`no_expiry`**, which is a different
   answer from `unknown` and from `ok`. P3.6's rule applied to a date. The response
   shape only **grew**, so the nine existing web call sites are untouched.
3. `apps/web/.../channels-data.ts` — the status union and the two new optional fields.
4. `apps/web/.../ConnectTab.tsx` — the **Renewal** line read *"Sign-in lasts about 12
   months, then you reconnect."* from the catalogue's declared lifetime. That is what
   the spec declares, not what this grant has. When every ads connection reports
   `no_expiry`, the card now shows the account's own sentence instead.

**Not changed:** `spec.auth.refreshTokenLifetimeSec` and `storeGrant`. That constant is
a reasonable default for a *new* grant, and `storeGrant` is shared by every channel —
changing it to satisfy one would be the widest possible fix for the narrowest problem.
The route is where the claim was made, so the route is where it is corrected.

## 4. Proof

## 5. The decision, in one line

**Do not reconnect Amazon Ads.** The grant predates 2026-07-30, so it has no expiry; a
reconnect would start a 365-day clock for no gain. The plan row is answered by
measuring, not by acting.

**When to revisit:** if Amazon ever forces a re-consent, the new token *will* carry a
365-day life, and the connect callback already stamps the real consent date
(`tokenIssuedAtIsEstimate: false`, AX-IE.0). From that moment the screen's countdown is
a real one, derived from an observed date — and `adsRefreshExpiry` switches to
`provenance: 'derived'` on its own.
