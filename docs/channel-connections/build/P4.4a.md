# P4.4a — a currency per market, from the data

**Date** 2026-09-21 · **Package** P4.4 (Price), first slice · **Size** L

The plan row: *"A currency per market from data, not a hard-coded GBP/EUR
(Sweden SEK, Poland PLN, Turkey TRY)."* §4.3 names one line:
*"Price currency is hard-coded: GBP for UK, EUR for every other Amazon market
(`services/outbound-sync.service.ts:310`). … If we ever push a price there, it
is wrong. (PROD? — do we have priced listings in SE/PL/TR?)"*

---

## 1. What was measured

### 1.1 🟢 The data was right the whole time

`Marketplace.currency` is a **required** column. On the development database all
**20 rows** carry one, and every one is correct:

| | |
|---|---|
| EUR | AMAZON BE DE ES FR IE IT NL · EBAY DE ES FR IT · ETSY/SHOPIFY/WOO GLOBAL |
| GBP | AMAZON UK · EBAY UK |
| **PLN** | **AMAZON PL** |
| **SEK** | **AMAZON SE** |
| **TRY** | **AMAZON TR** |
| USD | AMAZON US (inactive) |

The hard-coded rule (`UK/GB → GBP, else EUR`) disagrees with the table on
**4 of 20 rows** — exactly the three the plan named, plus US.

Several screens already read the column (`insights-summary`,
`channel-reconciliation`, the marketplaces and syndication routes). **Every
outbound price write ignored it.**

### 1.2 🔴 The finding is bigger than the row: one fact, EIGHT implementations

The plan names one line. A derived census found the same decision re-implemented
across **8 files / 16 lines**, and none of them read the table:

| Where | Shape |
|---|---|
| `outbound-sync.service.ts:213` | `marketplaceId === "EBAY_GB" ? "GBP" : "EUR"` |
| `outbound-sync.service.ts:313` | `code === "UK" \|\| code === "GB" ? "GBP" : "EUR"` |
| `ebay-variation-push.service.ts` ×2 | `mp === 'UK' ? 'GBP' : 'EUR'` |
| `ebay-shared-listing-push.service.ts:26` | a 5-market map + `?? 'EUR'` |
| `amazon/flat-file.service.ts:65` | `CURRENCY_MAP`, 5 markets, `?? 'EUR'` at 3 sites |
| `listing-wizard/submission.service.ts:148` | an 11-market map + **`?? 'USD'`** |
| `field-resolution/propagation-fill.ts:15` | `currencyForMarket()` |
| `listing-automation/triggers.ts:67` | **`currencyForMarket()` — the same name, byte for byte, in a second file, neither importing the other** |
| `listing-wizard.routes.ts:5539` | `currencyForMarketplace()` |
| `ebay-flat-file.routes.ts` ×2, `ebay-cockpit.routes.ts`, `listings-syndication.routes.ts` ×2 | ternaries |
| `marketplaces/ebay.service.ts:21` | 🔴 `process.env.EBAY_CURRENCY ?? "EUR"` — **ONE currency for every market**, on 3 live price writes |

They agree on EUR and GBP and disagree on everything else — **they do not even
agree on what to do when they do not know**: ten fall back to EUR, one to USD.

### 1.3 🔴🔴 Two comments that write the false fact down

This is the sharpest thing in the package, and it is a new shape of a banked
trap. The usual version is *"a comment asserts a property the code never had"*.
Here the comments assert a property of **the world** and of **our own database**,
and the code is wrong for exactly as long as they are believed:

```ts
// listing-wizard.routes.ts
// EU marketplaces (IT, DE, FR, ES, NL, BE, SE, PL) all use EUR
// when listing on Amazon.
```
SE is SEK. PL is PLN. Both are named in the list.

```ts
// listings-syndication.routes.ts
// Currency is marketplace-driven; keep simple for v1 (EU = EUR, GB = GBP,
// US = USD). Could read from Marketplace.currency when that becomes a real field.
```
`Marketplace.currency` **is** a real field, and always was: a required column
with correct values, read by four other services in this repo.

### 1.4 The census was wrong twice before it was right

- **v1** used "a currency literal on a market-ish line" → **91 files, 243 lines**,
  almost all of them display defaults and stored-order fallbacks. Useless.
- **v2** narrowed to market→currency shapes → **8 files, 16 lines**, and had
  **two holes**: `EBAY_GB` (a channel-prefixed code) and a two-line
  `if (m === 'UK' || m === 'GB') return 'GBP'`. Both are real sites.
- **v3** scans a 3-line window and accepts prefixed codes, and **carries a
  positive control for each of the two blind spots v2 had** — it fails if either
  is missed.

*A hole in the denominator is not a pass.* The gate below inherits all of it.

## 2. What was built

### 2.1 One accessor

`services/pim/market-currency.ts`, modelled exactly on `market-languages.ts`
next door, which already reads a different column of the same table:

- `marketCurrency(channel, code)` → `Promise<string>`, or a sync form taking
  rows the caller loaded once (`marketCurrencyRows`, `allMarketCurrencyRows`);
- `marketCurrencyAcrossChannels(code, rows)` for callers that know a market but
  not a channel (the propagation preview, the automation rule context). **Every
  channel configuring that market must agree; a disagreement is refused, not
  resolved by picking one** — picking one is how a guess becomes a fact;
- `GB` normalises to `UK`, and `EBAY_GB` to `UK`;
- **it REFUSES**, `statusCode: 400`, `code: 'market_currency_unconfigured'`, the
  same shape `marketLanguages` uses. A missing row, a blank currency and a
  non-ISO value are all refusals. A wrong currency is a money defect that no
  channel reports — Amazon accepts a number.

### 2.2 Every producer converted — 16 sites across 13 files

All eight implementations are gone. Where a builder is **pure**
(`buildSharedListingInput`, `buildJsonFeedBodyWithReport`, `buildCollapsedAttrs`,
`buildCoordinateEntries`, `guardCurrency`) the currency is an **argument**
resolved by the caller, so the builder stays pure — and each of them **refuses a
missing currency** rather than defaulting.

`ListingCoord.currency` and the propagation guard's currencies are now
`string | null`, and **null is treated as "not the same currency"** everywhere:
an unconfigured market drops out of the `=== 'EUR'` price-divergence filter and
is flagged as a cross-currency mismatch in the propagation preview. That is the
fail-closed direction.

### 2.3 The ratchet, with its own controls and checked exemptions

`apps/api/scripts/check-market-currency.mjs`, wired into the pre-push hook.

🔴 **It runs its own detector against four synthetic violations before it
reports a pass**, and exits 2 if any is missed. A pattern gate that finds nothing
is indistinguishable from a broken one: *"could not measure" reads exactly like
"measured clean"*. It also has a negative control (the accessor's own call shape
must not trip it) and refuses to report on a scan of fewer than 500 files.

Three exemptions, each with a written reason **that the gate checks**:

| File | Reason | Checked by |
|---|---|---|
| `services/pim/market-currency.ts` | the accessor itself | — |
| `routes/marketplaces.routes.ts` | the SEED list that WRITES the rows — the authority's source, not a reader | it must actually carry `SE: SEK` and `PL: PLN`, or it is not the authority it claims to be |
| `services/ai/listing-content.service.ts` | a JSON example inside an AI prompt | it must still be a prompt (`"recommendedPrice"`) and must not have become a caller |

*An exemption whose reason has gone stale reads exactly like a valid one*, so
each one is re-derived on every run.

## 3. Proof

**`market-currency.p44.vitest.test.ts` — 24 tests.** The value table (including
`EBAY_GB`, `GB`, and case); the four the old code got wrong asserted BOTH as
their real currency **and** as `not.toBe('EUR')`; refusals for a missing row, the
right market on the wrong channel, and blank / whitespace / non-ISO / null
currencies; the coordinate normalisation asserted on the query itself; and the
cross-channel form, including **a disagreement being refused with both
currencies named**.

**Existing tests: fixtures corrected, propositions kept.** 19 files failed on the
first full run, every one because its db double had no `Marketplace` row — the
honest cost of moving a fact out of code and into data. Two propositions moved
rather than changed: "UK → GBP" now belongs to the accessor's test, and the
builders' tests assert that a builder **carries the currency it is given** and
**refuses to invent one**. One test gained a new arm the change earns: *an
UNCONFIGURED target currency is a mismatch, never a match.*

**Mutation checks — 8 of 8 convicted**, six on the rule and **two on the gate**:

| Mutation | Red |
|---|---|
| an unconfigured market falls back to EUR | `a market with no row is REFUSED, not defaulted` |
| a blank currency on the row is accepted | the same |
| `GB` is not normalised to `UK` | `AMAZON/GB → GBP` |
| the channel prefix is not stripped | `EBAY/EBAY_IT → EUR` |
| two channels disagreeing picks the first | `two channels disagreeing is REFUSED` |
| the shared eBay builder invents EUR again | `UK market uses GBP` |
| **GATE:** a new UK ternary appears in a service | `1 market→currency decision(s) outside …` |
| **GATE:** an exemption goes stale (`SEK` → `EUR` in the seed) | `the exemption for routes/marketplaces.routes.ts is STALE` |

**Gates.** `tsc --noEmit` clean. market-currency ✓ (1,618 files, 0 outside the
accessor). Gateway ratchet all zeros; queue rows outside `outbound-rows.ts`: 0.
`check-push-lock.mjs`: 1 FAIL, the pre-existing one. **profiles-ON ratchet ✓** —
836 files, none new, none worse. **Full API suite: 6 failed / 10,396 passed**,
the documented baseline.

### 3.1 🔴 Two existing tests caught me putting a database read too early

Both are the same lesson, and it is the one this package keeps re-learning from
the other direction:

- `product-presets-submission-patch` asserts that a destination-bound wizard is
  refused **before any resolver, database or publisher work** — it hands the
  service a prisma proxy that throws. My `marketCurrencyRows()` at the top of
  `composeMultiChannelPayloads` was a read before that refusal. Moved to just
  before the (sync) channel map, past every early guard.
- `flat-file.push-lock` asserts that an omitted attribution is refused **before
  any listing read or write**. Same defect in `syncRowsToPlatform`; the load is
  now **lazy and memoised**, taken only when a row actually reaches the
  attribute builder.

*Placing a new refusal too early masks the ones behind it — and placing a new
READ too early breaks the promise that nothing happens before them.*

## 4. What this does NOT do

- **It does not change any currency on the development database**, where the
  only markets in use are EUR and GBP ones and the old rule agreed. The change
  bites the moment a price goes to PL, SE, TR or US.
- **Production is unmeasured.** The plan's own question — *"do we have priced
  listings in SE/PL/TR?"* — is still open; Railway database reads are not
  available to this session. The done-when is a price push to one of those
  markets carrying its own currency.
- **It does not fix `marketplaces/ebay.service.ts`'s real shape.** That service
  is single-market by construction: `updatePrice`, `createOffer` and
  `updateVariantPrice` take no market and read one env var. The currency is no
  longer a guess, but threading a market through is its own decision.
- **It does not touch price VALUES**, min/max guards or the eBay price push.
  Those are the rest of P4.4.
