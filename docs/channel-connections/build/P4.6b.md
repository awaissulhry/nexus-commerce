# P4.6b — the Etsy write client

**Package:** P4.6 (Etsy writes). **Slice:** b of f. **State:** BUILT, local, green.

Until P4.6, the connected-account Etsy client could only `GET`. This is the writer every
following slice uses.

## 1. What was built

| File | What |
|---|---|
| `services/etsy/account.ts` | **new** — one place that turns an account id into *which shop, with what headers* |
| `services/etsy/write-client.ts` | **new** — `etsyWriter(accountId)` on the gateway |
| `services/etsy/read-client.ts` | moved onto `account.ts`; behaviour unchanged (its P1.2 test still passes untouched) |

The client is transport only. It does **not** decide whether a write may be sent — the gateway
does (publish mode, sign-in state, push lock, rate bucket, ledger). A second opinion here is how
the two drift.

## 2. 🔴 Three spellings of one header, and one of them is wrong

The reader built `x-api-key` inline. Before copying that into a writer, it was checked — and the
repo turned out to hold **three** versions:

| site | value | verdict |
|---|---|---|
| `etsy/read-client.ts` | `clientId:clientSecret` | ✅ |
| `cx/connectors/etsy/spec.ts` | `clientId:clientSecret` | ✅ |
| `marketplaces/etsy.service.ts:273` | **`this.accessToken`** | ❌ the OAuth token, in the API-key header |

**Verified against Etsy, not against ourselves** (developer.etsy.com → Essentials → Requests,
read 2026-09-21): *"Every request to a v3 endpoint must include an `x-api-key` header containing
your keystring and shared secret separated by a colon"*, example
`x-api-key: 1aa2bb33c44d55eeeeee6fff:a1b2c3d4e5`. So the colon form is right and the third site is
wrong.

That matters beyond tidiness: the legacy service's standing description is *"it works, it is just
inert in production"*. It is **not** inert-but-correct — every call it made would be refused by
Etsy on the header alone. A fourth builder was not an option, so both clients now share
`account.ts`. (Banked: *two column builders drift, and the drift is silent*.)

Etsy's bearer is also `{user_id}.{access_token}` — the numeric user id is part of the token
string, so the token service's stored value already carries it and `Bearer ${token}` is correct.
The test pins a token in that shape so a future "clean-up" of the dot does not pass quietly.

## 3. The two Etsy rules that ARE in this file

### `kind` is chosen per operation, not per file

The gateway's contract: the publish mode and the push lock apply to `kind: 'write'`; a `kind:
'action'` owns its own switch at the call site (the P0.1 pattern, `NEXUS_ENABLE_*_SHIP_CONFIRM`).

A listing change is a `write`. **Marking a receipt shipped is an `action`** — it is not publishing
a listing, and one switch must not silently govern both. A test proves a shipment notice is sent
while listing publishing is gated.

### Only PUT and DELETE repeat — Etsy has no idempotency key

`idempotent` and `maxTransientRetries` are set from the method:

| method | retried after a transport failure? | why |
|---|---|---|
| PUT, DELETE | yes | repeatable by HTTP's own rule |
| POST, PATCH | **no** | a retried `uploadListingImage` is a duplicate image; a retried `createReceiptShipment` is a **second tracking number on a buyer's order** |

A transport failure is an **unknown** outcome, not a failure (banked, P4.5). With no idempotency
key there is nothing to make a second POST safe, so it stops.

Note the gateway retries a **429** whatever the method, because a throttle means nothing was
done. That is its rule, not this file's, and §4 records how the test for it was wrong at first.

## 4. Proof — `services/etsy/write-client.p46.vitest.test.ts`, 22 tests, green

Every case drives a real `gatewayCall`, so what is proven is the pair, not the client's intentions.

- the header set, the URL, the body, and one ledger row per **operation** (ids replaced)
- gated → nothing leaves; push-locked → `PUSH_SYNC_PAUSED` before the call
- an `action` is sent while `write` is gated
- POST and PATCH are **not** retried; 🟢 **positive control:** a PUT **is** (2 calls)
- Etsy's own words become the operator sentence; a non-JSON body does not become a broken one
- a non-Etsy account, six unusable shop identities and four hostile paths are each refused
- FormData passes through and the client does **not** set `Content-Type` (fetch owns the boundary)

### ⚠️ A test that passed the wrong proposition

The 429 case first pushed **one** 429 and expected the error. It passed nothing: the gateway
retried, got the default 200 from the stub, and the call **succeeded**. The assertion was
`.rejects`, so it failed loudly — but had the default answer been an error, it would have gone
green for the wrong reason. It now pushes three 429s and asserts `h.calls` is 3.

## 7. What P4.6c must handle — measured from Etsy's documentation, 2026-09-21

`updateListingInventory` (`PUT /listings/{id}/inventory`) is the stock **and** price endpoint, and
it is a **full replace**. Three traps, all confirmed, none of them ours:

1. **No partial update exists.** Etsy staff: *"You cannot update a single ListingInventory record;
   you must perform a PUT and include the entire dataset of your inventory."* So a quantity change
   is read-modify-write over the whole listing.
2. **A GET response cannot be PUT back as it stands.** The JSON is strictly interpreted, and
   read-only keys are rejected: `"Array contains invalid keys: product_id,is_deleted"`. At least
   `product_id`, `offering_id`, `is_deleted` and `scale_name` must be stripped. And `price` comes
   back as an **object** (`{amount, divisor, currency_code}`) but must be sent as a **float** —
   the shape changes between the read and the write of the same field.
3. 🔴 **A listing with domestic + international pricing loses its domestic price.** The PUT
   disables regional pricing and blanks the domestic price field. Reported repeatedly since 2023
   and **still unresolved in August 2026**; Etsy staff do not read that board.

Trap 3 is a money-path data loss that a correct, successful write would cause. P4.6c's design is
therefore **refuse rather than destroy**: a listing with regional pricing is held and alerted, the
way P4.3b's EU quantity guard fails closed. *Restraint is a deliverable* (P4.5c/f), and this is
the clearest case of it this programme has met: the write would succeed, and that is the problem.
