# P3.2 — every channel error lands on its listing

**Built 2026-09-20.** Plan row: *every channel error lands on its listing in
`ListingIssue`, with an as-of time: Amazon put/patch issues, previews, feed reports,
issue notifications and suppression (add a scheduled job); eBay bulk, feed and Trading
errors; Shopify `userErrors`.*
Done when: *a rejected change shows on the listing within one minute, in the channel's
words.*

## 1. What was measured first

All counts from the local development database (`127.0.0.1:55439`, printed before every
query), which carries the real call history.

| Measurement | Result |
|---|---|
| `ListingIssue` rows | **0** |
| `ChannelListing` rows | 1,003 (AMAZON 725, EBAY 274, ETSY 2, SHOPIFY 2) |
| `OutboundApiCallLog` rows | 469,462 |
| …of which name a `listingId` | **0** |
| Stored `AmazonFlatFileFeedJob` rows | 25, all DONE |
| Real Amazon rejections inside them | **140, on 48 SKUs**, all marketplace IT |
| …that name an attribute | **0 of 140** |

So the table the plan row is about was **empty**, the column that would join a call to a
listing had **never been filled**, and 140 real rejections sat in a JSON column that
nothing joined to a listing.

### 1.1 The flat-file grid was already reading it

`services/amazon/flat-file.service.ts:2231` batch-reads open `ListingIssue` rows per
listing and builds `_issueCount` / `_issueSeverity` / `_issueFields` for the grid's
per-row health chip. **That chip has been reading an empty table since it was written.**
Wiring the writer lights up a screen that already exists.

### 1.2 Only two things had ever written the table

`mirrorListingIssues` had exactly two call sites — `amazon-cockpit-publish.routes.ts`
and `preflight-report.service.ts` — and both write source `validation-preview`, which is
Amazon's *pre-check*, not a rejection. Nothing carried a real channel refusal to a
listing on any channel.

### 1.3 Parts of the plan row describe code that does not exist

Measured, not assumed:

- **`putListingsItem` / `patchListingsItem`: 0 occurrences in `apps/api/src`.** Amazon
  single-item Listings writes are not built. Amazon content publishes go out as
  `JSON_LISTINGS_FEED`, and that path lives in the flat-file service. "Amazon put/patch
  issues" therefore has no producer to hook; it is P4.1's to build.
- `OutboundApiCallLog` confirms it: the only SP-API listings operation ever logged is
  `getListingsItem` (1,712 calls, all reads).
- `AmazonSuppression` holds **0 rows** and had no scheduled job — the plan row's
  "(add a scheduled job)" is accurate.

### 1.4 A measurement that turned out to be un-measurable

A first pass looked for errors hidden inside 200 responses (Amazon returns issues in a
200; eBay returns `<Ack>Failure</Ack>` in one) and found none. The positive control
said why:

```
statusCode>=400 : 184 rows, 184 with a responsePayload
statusCode< 400 : 468,185 rows,  0 with a responsePayload
```

**`responsePayload` is stored only on failures.** That result was "could not measure",
not "measured empty", and it is recorded here as such.

## 2. The four defects

### 2.1 The attribute is lost on 140 of 140 real rejections

Two independent causes, both real:

1. `amazon-flat-file-feed.service.ts:192` guarded the message fallback with
   `Array.isArray(i?.attributeNames)`. Amazon sends `attributeNames: []` on every real
   rejection, and `Array.isArray([])` is **true**, so the fallback never ran.
2. The fallback itself, a private `extractFields`, matched only English phrasings
   (`attribute - x`, `attribute 'x'`) with straight quotes. Every stored rejection is
   **Italian** with typographic quotes: `“outer” è obbligatorio ma mancante.`

### 2.2 …and that silently destroys 57% of them

`ListingIssue`'s identity is `code + sorted attributeNames`. With no attribute, all five
"X is required but missing" rejections on one SKU share the fingerprint `90220::`.
Measured over the whole real population:

```
REAL issues           : 140
OLD distinct rows     : 60  -> LOST 80
NEW distinct rows     : 140 -> LOST 0
issues with NO attribute after the fix: 0 / 140
```

Worst single SKU, `GALE-JACKET-BLACK-MEN-XXS-REAL`: **5 rejections → 1 row.** An
operator would have been told "closure is missing" on a listing missing five attributes.

**Mirroring the real data without fixing this first would have been the defect.**

### 2.3 A blanket resolve sweep would close issues a feed never mentioned

`mirrorListingIssues` resolved every open issue from the same source that was absent
from the fresh set. That is right for a full-state sync. It is wrong for a feed:
`flat-file.service.ts:2859` defaults `operationType` to **PARTIAL_UPDATE** (a full
UPDATE drops attributes the row did not resend — the bug that sank the DE feed), so a
feed report speaks only about the attributes that feed carried.

### 2.4 A flat-file feed finishing was pushed to us and ignored

`amazon-sqs-poll.job.ts` handles `FEED_PROCESSING_FINISHED` by resolving
`AmazonImageFeedJob` only. A `JSON_LISTINGS_FEED` result was learned solely from the
poll cron, whose backoff grows with the poll count — which is what stood between this
package and its "within one minute" done-when.

### 3.1 The design decision worth naming

`ListingIssue.source` scopes the resolve sweep, and each source declares whether its
report is the listing's **full current state** (`replace`) or only **what it touched**
(`merge`):

| Source | Mode | Why |
|---|---|---|
| `listings-api`, `validation-preview` | replace | a full sync / pre-check states the listing's current issues |
| `amazon-suppression` | replace | suppression is a whole-listing state; the resolve half is what stops the job becoming a wall of stale red |
| `amazon-feed`, `amazon-notification`, `ebay-write`, `shopify-write` | merge | each speaks about one submission or one SKU |

## 4. The proof

**`src/services/channel-issue-attributes.p32.vitest.test.ts` — 27 tests.** All 12
distinct real Amazon messages verbatim, plus the collapse check, plus the apostrophe
guard (pairing Italian `l'attributo` with the next quote would return a 60-character
"attribute").

**`src/services/listing-issue-recorder.p32.vitest.test.ts` — 16 tests**, on a real
PostgreSQL with the generated schema and the real profile policies, profiles ON. The
Amazon fixtures are **REAL** — copied verbatim from `AmazonFlatFileFeedJob.perSkuResults`
— for the reason P2.2 taught: a hand-written fixture can agree with the bug.

**Whole-population check.** Running all 140 stored rejections through the new accessor:
140 issues → 140 distinct fingerprints, 0 lost, 0 without an attribute.

|---|---|---|
| 1 | drop the snake_case pass in the extractor | ✅ failed |
| 2 | restore the `Array.isArray` guard | ✅ failed |

All three source files restored and compared byte for byte.

### 4.2 Mutation 7 found a defect in the test, and then one in the code

At first, mutation 7 **passed** — the rule was not load-bearing. The cause: the test
asserted "nothing on the DE listing" as a bare read, and when run alone under `-t` no
record call had happened, so it was green either way. A green that proved nothing.

Making it self-contained (record inside the test, plus a positive control that IT *did*
get the rows) exposed a real defect behind it: the SKU→listing map was
`new Map(listings.map(l => [sku, id]))`, which keeps the **last** listing when a SKU has
more than one on the same channel and marketplace — an alias row is exactly that shape.
Now it is `Map<sku, listingId[]>` and the rejection lands on every listing carrying the
SKU.

### 4.3 A 2-hour discrepancy that was a read, not a write

Two as-of assertions failed by exactly 2 hours. `occurredAt` is `TIMESTAMP(3)` without a
zone, and node-pg builds a `Date` from it as if it were local time (UTC+2 here). The
stored value was correct. The test now reads through Prisma, as the app does, **and**
asserts the raw stored text via `TO_CHAR` so the assertion cannot pass on a client's
timezone interpretation of a wrong value.

## 6. Still open

1. **No eBay caller passes `ctx.listingId`.** The plumbing is in and tested; the
   publication paths (`studio-publication-ebay.ts`, `ebay-shared-fanout.service.ts`)
   still call `callTradingApi` without it, so an eBay rejection reaches the ledger and
   not the listing. Threading it is a small, separate change and belongs with P4.1,
   where those builders are rewritten anyway. **Named here so it is not mistaken for
   done.**
2. **`OutboundApiCallLog.listingId` is still 0-filled for every other sender.** eBay
   Trading now passes it; nothing else does.
3. **Amazon put/patch issues have no producer** until P4.1 builds the Listings API path.
4. **The screens are P3.3.** The flat-file grid's health chip reads this table already;
   the studio "Errors & Sync" console and the Channels Diagnostics panel are P3.3.
5. **Not verified by real traffic.** Nothing in this package has been exercised by a
   real event in production. The first real feed rejection after the deploy is the
   thing to read.
