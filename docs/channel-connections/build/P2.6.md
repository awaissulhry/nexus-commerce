# P2.6 — Account lifecycle

**Built 2026-09-20.** Plan row: *every revoke signal (eBay revocation, Shopify uninstall,
Amazon `invalid_grant`, Etsy refresh 401) sets `revoked`, pauses writes and alerts.*
Done when: *each signal proven with a test; one proven on production.*

---

## 1. What was measured first — and most of this already worked

This is the first package in the series where the measurement mostly found **working
code**, and establishing that before writing anything is the whole value of the step.

| Already true | Where |
|---|---|
| Writes are **already paused** for a revoked account | `gateway.ts:207` refuses any call whose account is inactive or whose `authStatus` is `needs_reauth` / `revoked` / `disconnected`, and **holds** it rather than sending |
| A **state machine already exists** | `transition()` in `cx/token.service.ts`: guards terminal states, writes with a compare-and-set so two racing signals cannot both win, records a `ConnectionEvent`, and raises a `CONNECTION_HEALTH` alert for `needs_reauth` and `revoked` |
| **Amazon `invalid_grant`** already reaches it | `catalog.ts:212` classifies it `auth_revoked`; `statusAfterConnectionFailure` maps that to `needs_reauth`; `failRefresh` announces the transition |
| **Etsy refresh 401** already reaches it | `catalog.ts:214` — `status === 401` → `auth_revoked`, same path |

So two of the plan's four signals were already done, and the "pauses writes" half was
already done for all four.

### 1.1 The two that did not

- **eBay `AUTHORIZATION_REVOCATION`** — P2.3 subscribed the topic and recorded the
  event, explicitly leaving the action to this package.
- **Shopify `app/uninstalled`** — **P2.4, in this same programme**, wrote
  `authStatus: "revoked"` with a raw `updateMany`. That skips the compare-and-set, the
  `ConnectionEvent` and, above all, **the alert**. An account that revokes itself in
  silence is precisely the failure this package exists to end, so introducing one inside
  it was the wrong shortcut however narrow the write looked.

A sweep of every `authStatus:` write confirmed those were the only two off the machine;
the others write `disconnected` on an explicit operator disconnect, or `unknown` when a
connection is created.

## 2. What changed

| File | Change |
|---|---|
| `migrations/20260920c_p26_ebay_inbound_alias/` | eBay's username and user id join `inboundAliases`, so a revocation naming `xaviaracing` finds its connection |
| `services/cx/account-lifecycle.service.ts` (new) | `revokeChannelConnection(connectionId, reason, source)` — one way in, through `transition()` |
| `routes/ebay-notification.routes.ts` | The revocation is acted on: routed by username, revoked inside its own workspace |
| `routes/shopify-webhooks.ts` | The uninstall goes through the lifecycle, and is handed the connection the receiver already routed to |
| `scripts/check-inbound-ledger.mjs` | A fourth rule: no code writes `authStatus` by hand |

### 2.1 The decisions worth keeping

- **No new state machine.** The one that exists is good; the defect was two signals
  going around it. Building a second would have been the drift this programme keeps
  finding.
- **`revokeChannelConnection` takes a connection ID and nothing vaguer.** A revoke that
  has to work out WHICH account it means cuts off the wrong seller the day a second one
  is connected — the MAP.3 ratchet refuses those lookups, and a revocation is the most
  damaging place to get one wrong. Callers resolve through the routing index first,
  which matches the names the **channel** sends.
- **`isActive` is written AFTER the transition.** It is not part of the state machine,
  and it is what the routing trigger keys on — so leaving it true would keep a revoked
  account in the inbound index after its grant is gone. Reversed, a failed transition
  would leave an account inactive while still reading as connected: invisible to the
  operator and dead to the channel. A test pins the order.
- **The eBay revoke only happens on the verified path.** The endpoint is reachable by
  anyone who can attempt a signature; only a verified notification, routed to a real
  connection, revokes anything.

## 3. The proof

### 3.1 Mutation checks

| # | Mutation | Test that went red |
|---|---|---|
| AE | Write `authStatus` by hand again | guard: *"writes authStatus: "revoked" directly … skips the compare-and-set, the ConnectionEvent and the alert"* |
| AF | Skip the state machine in the lifecycle | `goes through the state machine, which is what raises the alert` (+2) |
| AG | Stand the account down before the transition | `writes the stand-down AFTER the transition, never before` |
| AH | Revoke an already-terminal account again | `does nothing to an account that is already terminal` |

Every file restored byte-for-byte.

**The guard failed on its own comment first.** Rule 4's explanation quotes the literal it
forbids, so the first run went red on prose. Comments are now stripped before matching —
a guard that can be tripped by a comment can also be silenced by one, which makes both
its red and its green worth less than they look. Re-mutated afterwards to confirm it
still catches a real raw write.

### 3.2 A test was changed, and why that is not a weakening

`app/uninstalled revokes the shop the notice NAMES` asserted a `where` clause narrowed
by shop domain — P2.4's mechanism. P2.6 removed the lookup entirely: the revoke is handed
the connection id the receiver already resolved. The assertion now pins **that** —
`revoked === [{ connectionId: 'conn-1', source: 'shopify_app_uninstalled' }]` — which is
a stronger claim about a better mechanism, not a relaxed one about the same.

A load failure was also diagnosed rather than worked around: mocking all of
`token.service.js` removed `statusAfterConnectionFailure`, and the file reported
`Tests no tests` — a suite that failed to LOAD, not a suite that passed. It is now a
partial mock, so the Amazon/Etsy assertions exercise the **real** mapping instead of this
file's own stub.

## 4. Still open

1. **"One proven on production" is not met.** No revoke signal has fired in production:
   no Shopify webhook has ever been recorded, and eBay's subscriptions do not exist yet.
   The Amazon and Etsy paths run on a real refresh failure, which has not occurred since
   the deploy. All four are proven by test only.
2. **`app/scopes_update` records the granted scopes; it does not react to them.**
   Deciding what a reduced scope set means per feature is a design question, not a
   mechanical one, and is not attempted here.
3. **Nothing un-revokes.** `transition` leaves a terminal state only through `storeGrant`
   or an explicit disconnect, which is correct — but there is no operator path that says
   "this shop was reinstalled, try again" other than reconnecting.
4. **`jobs/cx-heartbeat.job.ts:157` is an INDIRECT connection lookup** the MAP.3 audit
   flags for a human to read. Untouched here; it predates this programme.
