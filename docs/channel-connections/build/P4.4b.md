# P4.4b — a price push must name its listing too

**Date** 2026-09-21 · **Package** P4.4 (Price), second slice · **Size** S

The row: the one `build/P4.3c.md` §5 left pre-measured — `syncPayload.price` in
`PATCH /api/catalog/products/:id` is the identical duplicate producer that P4.3c
removed for stock.

---

## 1. What was measured

### 1.1 The pre-measured row holds, and it is worse than the stock one

`masterPriceService.update` (`services/master-price.service.ts:264`) cascades a
price **per listing** inside the same transaction, through
`computeListingPrice(rounded, pricingRule, followMasterPrice,
priceAdjustmentPercent)`, and queues one `PRICE_UPDATE` row per listing naming
its listing. The catalog PATCH calls it — and then queued a **second**,
product-level row carrying the **raw master price**.

That second row knows none of the per-listing rules. It is worse than the stock
twin in two ways:

- a listing with `followMasterPrice: false`, or a `pricingRule` / a
  `priceAdjustmentPercent`, is **deliberately** at a different number, and the
  product-level row overwrites it with the master's;
- with no listing, `syncToAmazon` cannot read the stored sale window
  (`payload.price !== undefined && … && queueItem.channelListingId && cl.salePrice != null`),
  and `buildAmazonListingPatch` emits `op: replace` on `purchasable_offer` — so
  the push **wipes a scheduled sale**. That is MX.1 / D-MX4's defect, reached
  through the one door it does not guard.

### 1.2 🔴 The census found a second producer, with two defects of its own

Scanning for product-level `PRICE_UPDATE` creators, `jobs/repricing-evaluator.job.ts`:

```ts
await createOutboundRow(prisma, {
  data: {
    productId: rule.productId,
    targetChannel: rule.channel as never,
    targetRegion: rule.marketplace ?? listing.marketplace ?? 'IT',
    syncType: 'PRICE_UPDATE',
    payload: { newPrice: result.price, ruleId: rule.id },
    syncStatus: 'PENDING',
  },
}).catch(() => { /* Non-fatal */ })
```

1. **It names no listing — while holding one.** `listing.id` was selected four
   lines earlier and `listing.marketplace` is read on the very next line.
2. 🔴 **The payload key is `newPrice`. The dispatcher reads `payload.price`.**
   `newPrice` appears **nowhere** in `outbound-sync.service.ts`. So the row
   dispatches with no price at all: `buildAmazonListingPatch` emits no
   `purchasable_offer`, and the row reports **SUCCESS**. *A repricer that records
   a live reprice and sends nothing.*
   `SyncPayload` carries `[key: string]: any`, so TypeScript never said a word.
3. And the failure was swallowed by a bare `.catch(() => {})`, so a failed
   enqueue and a successful one looked identical.

**It is gated behind `NEXUS_REPRICER_LIVE=1` and is off**, which is the only
reason none of it has cost anything. The P4.3a shape again: *ask whether "never
ran" means harmless or means **not yet***.

## 2. What was built

### 2.1 The engine rule widened from quantity to any NUMBER

`outbound-rows.ts` now refuses a row that carries a **price** and names neither a
listing nor a shared eBay ItemID, exactly as it does for a quantity. The verdict
type is `OutboundRowTarget` (`NOT_A_NUMBER_ROW` / `LISTING` / `SHARED_ITEM` /
`UNNAMED`).

Either half counts, as with quantity: `syncType === 'PRICE_UPDATE'` **or**
`payload.price !== undefined` — because a price can ride a `FULL_SYNC` or a
`CONTENT_UPDATE`, and a `price: 0` is a real price.

**The sentence follows the row's kind.** `unnamedRowKind()` decides, and a price
row is told its *"pricing rule, its market and its scheduled sale"* cannot be
applied — not the stock buffer. An operator told the stock buffer could not be
applied to a price change learns nothing.

### 2.2 Both producers

- `catalog.routes.ts`: no `syncPayload.price`; the cascade owns it. With neither
  the quantity nor the price reaching the payload, what is left is always
  attributes and title, so the syncType is plainly `ATTRIBUTE_UPDATE`.
- `repricing-evaluator.job.ts`: names `listing.id`, sends `price` (the key the
  dispatcher reads), tags `source: 'REPRICER'`, and **logs** a failed enqueue
  instead of swallowing it.

## 3. Proof

`unnamed-quantity-row.p43.vitest.test.ts` grew to **37 tests**: a bare
`PRICE_UPDATE`, a price on a `CONTENT_UPDATE`, a **price of zero**, and a
`PRICE_UPDATE` naming its listing; the sentence per kind, with `unnamedRowKind`
tested by value including a row carrying both; and the producer arm now asserts
`catalog.routes.ts` names no `PRICE_UPDATE` and assigns no `syncPayload.price`.

**Mutation checks — 5 of 5 convicted:**

| Mutation | Red |
|---|---|
| a price row no longer has to name its listing | `bare PRICE_UPDATE → UNNAMED` |
| only the syncType counts, not a payload price | `a price on a CONTENT_UPDATE → UNNAMED` |
| a price row gets the stock sentence | `a price row earns the price sentence` |
| the price sentence loses the pricing rule | `the sentence … says what cannot be applied` |
| the catalog PATCH puts the master price back | the producer arm |

**Two fixtures corrected, no proposition changed.** The P1.3
ambiguous-destination case is an `ATTRIBUTE_UPDATE` now — it can no longer be
posed with a quantity *or* a price, because neither shape exists product-level
any more. The W1.9 publisher control's price row names its listing, and its
double gained the `channelListing.findUnique` that a named row needs.

**Gates.** `tsc` clean · market-currency ✓ · gateway ratchet all zeros, 0 rows
outside `outbound-rows.ts` · **profiles-ON ratchet ✓** (836 files, none new) ·
full suite **6 failed / 10,403 passed**, the documented baseline.

## 4. What this does NOT do

- **It does not verify the repricer end to end.** `NEXUS_REPRICER_LIVE` is off,
  and turning it on is a live price write — the Owner's. The done-when is one
  repriced listing whose queue row carries a `price` and a `channelListingId`.
- **It does not add a min/max guard**, build the eBay price push, or read a
  price back. Those are the rest of P4.4.
- **Production is unmeasured** for how many product-level price rows are sitting
  in the queue right now; the dispatch refusal will report them as they are
  drained.
