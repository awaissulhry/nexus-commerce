## 1. What was measured first

P2.1 had just made every Amazon notification's raw payload readable in the ledger. So
this package could be measured against **real Amazon traffic** rather than against the
plan's description or the code's comments.

```
AMAZON event types in the ledger:
  ANY_OFFER_CHANGED    2823
  ORDER_CHANGE         1413
  ORDER_STATUS_CHANGE  1013   (Amazon retired this type on 2026-07-29)
```

### 1.1 The order-change parse was reading one level too high

Amazon nests an order's own details under `Summary`. The parser read them directly off
`OrderChangeNotification`. Running **the parser's own expressions** over all 1,413
stored ORDER_CHANGE payloads:

| What the code computed | Result | What was really there |
|---|---|---|
| `payload.OrderStatus` | undefined — **1413 / 1413** | `Summary.OrderStatus` = "Shipped", … |
| `payload.MarketplaceId ?? ''` | empty — **1413 / 1413** | `Summary.MarketplaceId` = A1PA6795UKMFR9 |
| `payload.FulfillmentType ?? payload.OrderType ?? 'MFN'` | `"MFN"` — **1413 / 1413** | **AFN 1071**, MFN 342 |

Only `AmazonOrderId` and `SellerId` sit at the top level, so only those two ever parsed.

### 1.2 The defect had switched off a branch nobody knew was off

The poller carried `if (fulfillmentType === 'AFN') { skip }`, with the comment *"FBA
orders are managed by Amazon's warehouse — no stock action needed here."* Because the
parse always answered `'MFN'`, **that branch had never executed in production.** Every
FBA order has been synced on its notification since the day the branch was written.

Fixing the parse in isolation would have switched the skip on for **1,071 of 1,413**
notifications, and FBA orders would have stopped appearing in Nexus until the next cron
tick. That is a silent operational change hiding inside a two-line bug fix.

**Owner's decision (2026-09-20): keep syncing them.** The branch is deleted rather than
left to spring into life. `fulfillmentType` is still parsed, and now correctly; nothing
reads it. Skipping FBA to save SP-API quota remains available as its own decision.

### 1.3 A test was green about behaviour that had never happened

`amazon-sqs-poll.p06.vitest.test.ts` asserted *"an FBA order is recorded, closed done
and deleted **without a sync**"* — and passed. Its fixture put `FulfillmentType` at the
top level, the same wrong place the parser read. **The fixture and the parser agreed
with each other and neither agreed with Amazon.**

### 1.4 One payload version for every type

`payloadVersion: '1.0'` was hardcoded for all types. Amazon **withdrew version 1.0 of
`LISTINGS_ITEM_ISSUES_CHANGE` on 2024-09-25**; the correct version is `2023-12-13`. The
constant would have been refused outright for one of the types the plan names.

### 1.5 Two of the plan's seven types cannot reach an SQS destination

- `LISTINGS_ITEM_STATUS_CHANGE` — subscribing it to the SQS destination returned
  **400 InvalidInput** (this repository's own 2026-07-20 boot self-report). The SQS
  poller already parses this type, so only a destination is missing.
- `BRANDED_ITEM_CONTENT_CHANGE` — SP-API's notification-type-values page states the
  **Amazon EventBridge workflow** for it.

`LISTINGS_ITEM_ISSUES_CHANGE` is delivered on **both** EventBridge and SQS.

For `LISTINGS_ITEM_MFN_QUANTITY_CHANGE`, `REPORT_PROCESSING_FINISHED`, `PRICING_HEALTH`
and `ITEM_PRODUCT_TYPE_CHANGE` the documentation page returned by fetch is truncated
before their entries. **Their destination support and payload version are not
established, and are not guessed here.**

### 1.6 Nothing reconciled the subscriptions

`ensureAmazonNotificationSubscription()` runs once, at boot, fire-and-forget. Between
two deploys nobody checked. That failure is silent by nature — notifications simply
stop arriving, which looks like a quiet day.

## 2. What changed

| File | Change |
|---|---|
| `services/amazon-sqs.service.ts` | ORDER_CHANGE is read from `Summary`, with the flat shape kept as a fallback so the retired ORDER_STATUS_CHANGE (1,013 stored rows) still parses |
| `jobs/amazon-sqs-poll.job.ts` | The dead AFN skip is removed (Owner's decision). The ledger row is keyed on Amazon's `NotificationMetadata.NotificationId`, falling back to the SQS `MessageId` |
| `services/amazon-notifications-boot.service.ts` | `NEXUS_SP_API_NOTIFICATION_SPECS`: per type, its payload version, the destinations it supports, and how well that is known. `payloadVersionFor()`. `sqsNotificationSpecs()`. `NEXUS_SP_API_NOTIFICATION_TYPES` is now derived |
| `jobs/amazon-notification-reconcile.job.ts` (new) | Nightly reconcile at 03:40 UTC, platform-scoped |
| `index.ts` | Starts the reconcile cron |
| `jobs/amazon-sqs-poll.p06.vitest.test.ts` | The order fixture now uses the shape Amazon actually sends; the FBA assertion is inverted to the decided behaviour |

### 2.1 Why the new types are not subscribed yet

Creating a subscription is a **live channel call and a production write**, and both need
the Owner's yes. So the specs ship complete and **gated**:
`NEXUS_AMAZON_SUBSCRIBE_NEW_TYPES` is **off** by default, and with it off both the boot
path and the admin endpoint subscribe exactly the six types that are live today — the
behaviour before P2.2, unchanged.

**No handlers were written for the new types.** Their payload shapes have never been
seen here, and a handler written from a guess is a fixture pinned to a belief — which is
precisely how 1.3 happened. P2.1 made the honest order possible: an unhandled
notification is now recorded in the ledger **with its payload** and dead-lettered
visibly, so subscribing first and writing each handler from a real payload costs nothing
and guesses nothing.

## 3. The proof

### 3.1 The parse, against a payload Amazon actually sent

The fixture in `amazon-sqs.p22.vitest.test.ts` is a real ORDER_CHANGE notification taken
verbatim from the ledger (2026-09-08). Parsed through the real `pollSqsMessages`:

```
amazonOrderId   303-3208227-5274706
orderStatus     Shipped              (was undefined on 1413/1413)
marketplaceId   A1PA6795UKMFR9       (was empty on 1413/1413)
purchaseDate    2026-09-07T14:52:42.220Z
fulfillmentType AFN                  (was 'MFN' on 1413/1413)
```

### 3.2 Mutation checks — five rules broken on purpose

| # | Mutation | Test that went red |
|---|---|---|
| J | Read the payload one level too high again | `parses a real notification: status, marketplace and AFN all arrive` |
| K | Hardcode the payload version back to `1.0` | `uses the version Amazon requires, not a constant` |
| L | Let an EventBridge-only type onto the SQS destination | `never offers an EventBridge-only type to the SQS destination` |
| M | Subscribe the unverified types without the Owner's switch | `does not subscribe an unverified type until the Owner turns it on` |
| N | Restore the original parse bug, run **p06** | **Nothing failed — see below** |

Every file restored byte-for-byte (`cmp -s` → YES).

**Mutation L found a weak test and it was strengthened, not accepted.** The first run was
caught only by a neighbouring test: the dedicated one exercised the arm with the gate
OFF, where an EventBridge-only type is excluded by its evidence anyway, so the
destination filter could be deleted without it noticing. It now runs both arms, and the
mutation turns it red.

**Mutation N is reported as a negative result.** Correcting p06's fixture to Amazon's
real shape makes the file honest, but it did **not** add coverage of the parse: with the
skip removed, both MFN and AFN take the same path, and p06 asserts nothing about
`orderStatus`. The parse is covered by 3.1 alone. Stated rather than counted as a win.

## 4. Still open

1. **The plan's done-when is not met and cannot be met from here.** *"Each type seen
   arriving on production"* needs the subscriptions created (a live channel call, Owner's
   yes) and then real Amazon traffic of each type. What is built is everything up to
   that call.
2. **Four types have unverified destination support and payload version**:
   `LISTINGS_ITEM_MFN_QUANTITY_CHANGE`, `REPORT_PROCESSING_FINISHED`, `PRICING_HEALTH`,
   `ITEM_PRODUCT_TYPE_CHANGE`. They are declared `evidence: 'unknown'`. Amazon's answer
   to a subscribe is the measurement, and `setupAllAmazonNotifications` records it per
   type — a 400 InvalidInput is the finding "not available on an SQS destination".
3. **Two types need an EventBridge destination**, which does not exist here:
   `LISTINGS_ITEM_STATUS_CHANGE` (already parsed by the poller) and
   `BRANDED_ITEM_CONTENT_CHANGE`. That is a separate piece of work.
4. **No handlers for the new types** — deliberately, see 2.1. They land in the ledger
   and dead-letter visibly until each is written from a real payload.
5. **The 1,013 stored ORDER_STATUS_CHANGE rows** parse through the flat fallback. Amazon
   retired the type, so no new ones arrive.
6. **Production proof** — taken after the push; limited to the parse and the reconcile,
   since no new subscription is created.
