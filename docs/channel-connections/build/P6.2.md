# P6.2 — the eBay signing key has a death date, and now something knows it

State: **BUILT 2026-09-21**, committed locally. Includes an **additive migration**
(`20260921a_p62_signing_key_expiry`), applied locally only.

Plan row (FINAL-PLAN.md §6, P6.2): *"Rotate app secrets and the eBay signing key too,
not only account tokens."*
Plan §4.1 gap: *"Key rotation covers account tokens only. App secrets and the eBay
signing key are never rotated."*

## 1. Evidence (measured 2026-09-21)

| fact | state |
|---|---|
| `ChannelApp` EBAY/production signing key | **exists** — `signingKeyEnc` and `signingKeyId` both set |
| its expiry | **unknown** — no column existed |
| `createEbaySigningKey` → `expirationTime` | read, put into a `signing_key_created` event's detail, **dropped** |
| `getEbaySigningKey` — a **read** that returns it | exists, has a passing test, **zero production callers** |
| `secretExpiresAt` and `rotatedAt`, all **5** `ChannelApp` rows | **NULL** — nothing has ever rotated |
| the alert sweep's query | `where: { secretExpiresAt: { not: null } }` — a row whose only date is the signing key's **was never selected** |

🔴 **The key that signs eBay refunds and finances calls will expire on a date nothing
recorded.** P0.3 made refunds signed precisely because eBay requires it for EU/UK
sellers; the first symptom of expiry is every signed call failing with a **215xxx**
signature error — an error class `EbayApiError.isSignatureError` already knows by name
(215000–215122), and which nothing anticipated.

**You cannot rotate on a schedule you cannot see**, so the date comes first. And
`getEbaySigningKey` is the fourth accessor this programme has found that exists, is
tested, and has never once run.

## 2. Changes

1. **Migration `20260921a_p62_signing_key_expiry`** — two nullable columns on
   `ChannelApp`: `signingKeyExpiresAt` and `signingKeyCheckedAt`. Additive, no backfill,
   no default. `secretExpiresAt` beside them is the **client secret's** date (P6.1) and
   stays a separate fact: two credentials, two lifetimes, two remedies.
2. `apps.service.ts` — `storeSigningKey` takes the expiry and writes both columns;
   **new** `recordSigningKeyExpiry` updates them without touching the key.
   `ChannelAppCreds` exposes `signingKeyId`, `signingKeyExpiresAt`, `signingKeyCheckedAt`.
3. `connectors/ebay/client.ts`
   - `signingKeyFor` stores `created.expirationTime`, and **replaces a key inside a
     7-day window** instead of returning the stored one forever. Creating a key at eBay
     is additive (the old one lives to its own expiry), so replacing early costs
     nothing and replacing late costs a refund.
   - A key with **no recorded date is still used** — absence is not expiry. The
     opposite mistake would fire a live eBay call to replace a healthy key every time
     we simply had not asked yet.
   - **New** `recoverEbaySigningKeyExpiry` — the call that finally uses
     `getEbaySigningKey`. It **reports** a failure instead of throwing: a metadata read
     failing is not a reason to take eBay signing down.
4. **New** `services/cx/signing-key-expiry.ts` — `refreshEbaySigningKeyExpiry`, run by
   the 15-minute heartbeat, asking **at most once a day**.
   - `signingKeyCheckedAt` is the discriminator: *"eBay named no expiry"* and *"we have
     never asked"* both leave the date null and are different facts. Keying on
     `checkedAt` stops the first becoming 96 calls a day and stops the second being
     mistaken for a settled answer. P3.6's rule, applied to a date.
5. `channel-alerts` — **new** `signingKeyExpiryAlert`, its own kind
   (`channel-signing-key-expiry`) and its own `entityId` suffix so it cannot dedupe
   against the app secret's alert. The sweep's `where` became an `OR`.
   - 🔴 **The wording matters.** An expired app secret is replaced by a human in eBay's
     console; an expired signing key is replaced by us automatically on the next signed
     call. Telling an operator to go and fix something the system fixes itself is how
     alerts get ignored, so this one says the replacement is automatic and that its
     presence *after* that is the news.

## 4. What P6.2 does NOT cover

**App-secret rotation beyond Amazon.** P6.1 built automatic rotation for the Amazon
app secret (off until the Owner registers the queue). eBay, Shopify and Etsy client
secrets have `secretExpiresAt` columns that are **NULL** — no date is recorded, so
nothing can alert or rotate. Those channels do not publish a secret expiry through an
API the way Amazon does; the date would have to be entered when the secret is created
in each developer console. That is an **operator-entry** problem, not a code one, and
it belongs with P6.8 (the production app set-up) rather than here.

## 5. Production proof — OPEN

After the deploy, on the next heartbeat:

- `[cx-ebay] recorded the signing key expiry {"signingKeyId":"…","expiresAt":"…"}` —
  **the first time this system has ever known that date.**
- Then `ChannelApp.signingKeyExpiresAt` is set for EBAY/production, and
  `signingKeyCheckedAt` stops it being re-asked for 24 hours.
- If `expiresAt` comes back **null**, eBay reports no expiry for this key and the
  alert will never fire — `signingKeyCheckedAt` being set is how you tell that from a
  check that never ran.
- 🔴 **If the recovered date is within 7 days, the next signed eBay call replaces the
  key.** That is a live channel call (`createSigningKey`), it is additive, and it is
  the intended behaviour — but it is worth knowing it may happen on the first day.
