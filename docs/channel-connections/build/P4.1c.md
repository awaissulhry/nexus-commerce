## 1. The measurement, and it is a COUNTERWEIGHT

The plan row reads as a gap. **It is not one.** Every eBay builder that sends a
description a buyer can see already runs it through
`renderListingDescriptionSafe`, on **both** channel models:

| Path | Where |
|---|---|
| Trading | `services/ebay-shared-listing-push.service.ts:401` |
| Trading | `services/pim/studio-publication-ebay.ts:199` |
| Trading | `services/ebay-description-push.service.ts:355` |

| Trading | `routes/ebay-flat-file.routes.ts:2313, 2681` |
| Inventory | `services/images/ebay-inventory-image-publish.service.ts:317` |

One engine, one definition (`services/ebay-description-theme.service.ts:360`).

**Say so and mark the row.** That is P2.6's lesson and the third time this
programme has hit it — after P2.6 itself and P3.3's two "apparent gaps that were
correct behaviour".

### 1.1 But the rule lived in the CALLERS, which is the drift shape

`pushVariationGroup` (`services/ebay-variation-push.service.ts`, 2,900 lines) is
the Inventory-API group publisher. It took the parent's content as an optional
argument and, when omitted, fell back to:

```ts
description: opts?.parentContent?.description ?? parentRow.description ?? ''
```

— the **raw** body, with no theme around it. Its own doc comment said so:
*"When omitted, the group falls back to the parentRow.* values (byte-identical to
pre-P9e)."*

Both of its callers render first, so the fallback was dead. **Dead only until
somebody writes a third caller.** That caller would publish an unthemed listing
to eBay with no error, nothing unusual in the ledger, and a listing that simply
looks wrong. Nobody would find it from a log.

That is exactly the banked lesson *"two column builders DRIFT — put the rule in
the ENGINE, assert parity in the gate."*

### 1.2 What is safely NOT covered, and why

`pushVariationGroup` also sends a **per-variant** `description` (line 1396). It
is deliberately unthemed and that is correct: on a grouped eBay listing the
per-variant description **never surfaces** — the group's is what buyers see. The
existing comment records the incident that established this (eBay 400s the whole
publish on an empty variant description, so it falls back through the group
description → title → SKU). Left alone.

`pushOffersOnly` sends **no** description at all. Measured, not assumed.

## 2. What was built

`parentContent` is required now, held twice because one way is not available:

- **Compile time.** It is no longer optional inside `opts`, so `opts: {}` will
  not compile. Both callers already pass it, so nothing changed for them.
- **Run time.** `opts` itself cannot be made a required *parameter* —
  `TS1016: A required parameter cannot follow an optional parameter`, because
  five optional parameters sit before it. So omitting `opts` altogether is
  **refused**, one `EBAY_WRITE_REFUSED` row per SKU, in the same idiom this
  function already uses for a disallowed publish host.

Refused rather than published raw, deliberately: an unthemed live listing is
worse than a push that did not happen, and it is silent.

The runtime fallback stays as belt and braces. It is no longer the contract.

### 🔴 2.1 The ordering defect the existing tests caught

The refusal was placed **first**, before the publish-mode check, the push lock,
the presentation lock and the review gate. **14 existing tests failed
immediately**, and they were right: a paused listing reported *"no theme-rendered
parent content"* instead of reporting the pause.

```
FAIL legacy-ebay-variation-push-lock > refuses both eBay direct publishers for {"syncPaused":true}
FAIL legacy-ebay-variation-push-lock > refuses both eBay direct publishers for {"presenceIntent":"HELD"}
… 11 more
```

**A new refusal placed too early MASKS every refusal behind it.** The most
important reason has to win. Moved after all four; its position is now asserted
by index, and a mutation that moves it back reproduces those failures.

### 2.2 One existing test fixture was made representative

`pim/publish-review-gate.vitest.test.ts`'s positive control called
`pushVariationGroup` with eight arguments and no `opts`, relying on a stubbed
`fetch` throwing further down to prove *"the gate let it through"*. With the
refusal in place it returns before reaching that `fetch`.

The fixture now passes `opts.parentContent`, as **every real caller does**. Its
assertions are byte-for-byte unchanged — the test still proves the review gate
lets a reviewed row past. This is *"a fixture must be representative"*: no real
writer ever omits it. It is **not** a weakened test, and it is recorded here so
that claim can be checked.

## 3. The proof

**9 tests green** (`services/ebay-description-engine.p41.vitest.test.ts`), with
the builder census and the caller census both derived from source.

**4 mutations, 4 named tests failed, every file restored byte for byte.**

```
✅ parentContent goes back to optional (compile-time rule removed)
✅ the runtime refusal is deleted (an unthemed push goes out)
✅ a caller stops rendering the theme
✅ ORDERING: the refusal moves back to the top and masks the push lock
4 guarded, 0 not guarded
```

🔴 **The behavioural test's arm was WITNESSED before its assertions were
written.** The first draft had an escape hatch — *"if a lock threw first, accept
that instead"* — which would have made the test pass without ever reaching the
refusal. A probe wrote the actual outcome to a file:

```
RETURNED: [{"sku":"A-1","market":"DE","status":"ERROR","message":"EBAY_WRITE_REFUSED: this push has
no theme-rendered parent content. Resolve it with renderListingDescriptionSafe and pass it as
opts.parentContent; nothing was sent."}, …]
```

The refusal arm is the one that runs, so the escape hatch was removed and the
test made unconditional. A branch that never runs turns a test into a pass that
proves nothing.

- Gateway ratchet — `{"EBAY":0,...}` (exempt 47), unchanged.
