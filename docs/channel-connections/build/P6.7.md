User access token with an `IAF ` prefix and requires **no OAuth scope**. Read in a browser; see

Plan row (FINAL-PLAN.md §6, P6.7): *"eBay: probe the keyset for returns, cancellation

*"Reconnect is yours"* already marked as the Owner's.
Plan §4.1: *"eBay has no returns, cancellation or inquiry scopes in its 20."*

## 1. 🔴 The two halves of this row must not happen together

eBay refuses the **whole** consent request when one scope is outside the app's keyset,
and **names none of them** — the operator sees only
`{"error_id":"invalid_scope","http_status_code":400}`.

That is not hypothetical. `sell.logistics` and `commerce.catalog.readonly` sat in the
list from **2026-08-29 to 2026-09-16** and **no eBay account could be connected** for
those nineteen days. Nothing in the tree could see it: the list is valid TypeScript and
the OAuth tests stub eBay. `scopes.ts` now carries the rule it cost:

> *"Add a scope only after the deploy check passes with it."*

So **probe** and **add** are separate steps, and only the first is safe to do without
the answer in hand.

## 2. What was built

`scripts/check-ebay-consent-scopes.mts` — which already runs in
`.github/workflows/deploy-api.yml` before every Railway deploy — gained an optional
**candidate pass**:

```
EBAY_CANDIDATE_SCOPES='https://api.ebay.com/oauth/api_scope/…,…'
```

Each candidate is asked **alone, beside the base scope**, and reported:

| answer | line |
|---|---|
| accepted | `✓ ACCEPTED — safe to add to the consent list in scopes.ts` |
| refused | `✗ refused (invalid_scope) — do NOT add it` |
| neither | `? could not measure — <detail>` |

Three properties make it safe:

1. **A candidate never enters `EBAY_REQUIRED_SCOPES`.** It cannot affect whether anyone
   can connect.
2. **A refused candidate does not fail the deploy.** It is a scope we do not have and
   do not use; blocking a release on it would be a gate with no subject.
3. **"Could not measure" is its own answer**, not folded into "refused" — otherwise a
   quiet network reads as *"you do not have this scope"*.

With `EBAY_CANDIDATE_SCOPES` unset the check behaves exactly as before.

## 3b. ✅ 2026-09-21 (later) — READ IN A BROWSER, and the answer is THERE IS NOTHING TO ADD

§4 below says the row needs *"the scope names, read in a browser (it blocks automated fetches, not
people)"*. That was done, with Chrome, and it closes the row in a direction §4 did not anticipate.

**First, §4's blocker is confirmed and narrower than it looked.** `developer.ebay.com` answers
**403 to WebFetch** and serves a **real browser normally** — so the obstacle is bot-blocking, not
authentication. The scopes URL redirects to *Authorization | eBay Developers Program*, which
explains how scopes work and **lists none**. It does say where a list lives:

> *"To discover the scopes you need, refer to the **OAuth scope section of the API documentation
> for each method** you use."*

**So the method pages were read. Returns, cancellation and inquiry are the Post-Order API — and
it does not use OAuth scopes at all.** From eBay's *Making a Call* page, the Authorization header:

> *"The Post Order API accepts both OAuth and Auth'n'Auth tokens as input for this header.
> Auth'n'Auth – Prefix a valid eBay token with the word `TOKEN `.
> **OAuth – Prefix a valid User access token with the string `IAF `**."*

No scope is named there, and the `Get Cancellation` reference page carries **no OAuth scope
section** — which, by the Authorization guide's own rule above, is where one would be if it
existed.

### What that means for this row

| the plan said | measured |
|---|---|
| §4.1: *"eBay has no returns, cancellation or inquiry scopes in its 20"* | **True — and not a gap.** Those scopes do not exist to have |
| P6.7: *"probe the keyset for returns, cancellation and inquiry scopes; add the accepted ones"* | **The probe has no subject.** Every candidate would have to be invented |
| *"reconnect both accounts once"* | **Not needed for this row.** A reconnect exists to grant new scopes, and there are none to grant |

🔴 And inventing one is the outage. P6.7 §1 says it plainly: `sell.logistics` and
`commerce.catalog.readonly` were plausible-looking names that broke **every** eBay connect for
nineteen days. A probe fed invented strings would return `✗ refused` for all of them, and that
reads as *"we do not have this scope"* when the truth is *"it is not a scope"* — a false negative
dressed as a measurement.

This is **P4.5f's shape a second time**: a plan row asking for a value that cannot be established
because the thing does not exist, and the correct deliverable is **restraint**. Nothing was added.

### What we already hold, which is the part that matters

`EBAY_REQUIRED_SCOPES` already contains **`sell.fulfillment`** and **`sell.fulfillment.readonly`**
— the scopes eBay's *modern* Fulfillment API uses for order and return work. So the capability the
plan row was reaching for is already granted by a scope we have; the Post-Order path needs only a
valid user token, which every connected account has.

### Confidence, stated honestly

This rests on **two** eBay pages (the Post-Order *Making a Call* auth section, and one method
reference with no scope section) plus the Authorization guide's rule about where scopes are
documented. That is strong, not conclusive.

**One page would make it conclusive, and it needs the Owner's login:** *Your Account → Application
Keys → **OAuth Scopes*** lists exactly which scopes this keyset holds. If no returns / cancellation
/ inquiry scope appears in that list, the matter is closed by eBay's own answer. **The probe
apparatus stays** — it costs nothing switched off, and it is the right instrument the day eBay
does publish such a scope.

## 4. 🔴 Why the row WAS open (superseded by §3b — kept as the record)

Two things could not be obtained in this session, and neither may be guessed:

1. **The scope strings.** eBay's OAuth scope reference
   (`developer.ebay.com/api-docs/static/oauth-scopes.html`) answers **HTTP 403** to an
   automated fetch, and a web search returned the Post-Order user guide with no scope
   list. Inventing `…/sell.item.return` or similar and adding it **is** the 2026-09-16
   outage.
2. **The credentials to run the probe.** It needs `EBAY_CLIENT_ID` and `EBAY_RUNAME`
   — the production keyset. They are **not in the local environment**, and Railway
   variable reads were refused by the auto-mode classifier again this session.

**What closes it, in order:**

1. Read the scope names off eBay's OAuth scopes page in a browser (it blocks automated
   fetches, not people), or off the Post-Order API reference's *OAuth scope* section.
2. Set `EBAY_CANDIDATE_SCOPES` in the deploy workflow's environment and read the next
   deploy's output. No code change, no risk to connecting.
3. Add only the `✓ ACCEPTED` ones to `EBAY_REQUIRED_SCOPES`. The existing full-list
   check then guards the result on the same deploy.
4. **Then** the reconnect of both accounts — which the plan already marks as the
   Owner's, and which a new scope genuinely requires: eBay grants scopes at consent.
