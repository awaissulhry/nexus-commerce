## 1. 🔴 The two halves of this row must not happen together

eBay refuses the **whole** consent request when one scope is outside the app's keyset,
and **names none of them** — the operator sees only
`{"error_id":"invalid_scope","http_status_code":400}`.

That is not hypothetical. `sell.logistics` and `commerce.catalog.readonly` sat in the
list from **2026-08-29 to 2026-09-16** and **no eBay account could be connected** for
those nineteen days. Nothing in the tree could see it: the list is valid TypeScript and
the OAuth tests stub eBay. `scopes.ts` now carries the rule it cost:

> *"Add a scope only after the deploy check passes with it."*

So **probe** and **add** are separate steps, and only the first is safe to do without
the answer in hand.

## 2. What was built

`scripts/check-ebay-consent-scopes.mts` — which already runs in
`.github/workflows/deploy-api.yml` before every Railway deploy — gained an optional
**candidate pass**:

```
EBAY_CANDIDATE_SCOPES='https://api.ebay.com/oauth/api_scope/…,…'
```

Each candidate is asked **alone, beside the base scope**, and reported:

| answer | line |
|---|---|
| accepted | `✓ ACCEPTED — safe to add to the consent list in scopes.ts` |
| refused | `✗ refused (invalid_scope) — do NOT add it` |
| neither | `? could not measure — <detail>` |

Three properties make it safe:

1. **A candidate never enters `EBAY_REQUIRED_SCOPES`.** It cannot affect whether anyone
   can connect.
2. **A refused candidate does not fail the deploy.** It is a scope we do not have and
   do not use; blocking a release on it would be a gate with no subject.
3. **"Could not measure" is its own answer**, not folded into "refused" — otherwise a
   quiet network reads as *"you do not have this scope"*.

With `EBAY_CANDIDATE_SCOPES` unset the check behaves exactly as before.

## 4. 🔴 Why the row is still OPEN

Two things could not be obtained in this session, and neither may be guessed:

1. **The scope strings.** eBay's OAuth scope reference
   (`developer.ebay.com/api-docs/static/oauth-scopes.html`) answers **HTTP 403** to an
   automated fetch, and a web search returned the Post-Order user guide with no scope
   list. Inventing `…/sell.item.return` or similar and adding it **is** the 2026-09-16
   outage.
2. **The credentials to run the probe.** It needs `EBAY_CLIENT_ID` and `EBAY_RUNAME`
   — the production keyset. They are **not in the local environment**, and Railway
   variable reads were refused by the auto-mode classifier again this session.

**What closes it, in order:**

1. Read the scope names off eBay's OAuth scopes page in a browser (it blocks automated
   fetches, not people), or off the Post-Order API reference's *OAuth scope* section.
2. Set `EBAY_CANDIDATE_SCOPES` in the deploy workflow's environment and read the next
   deploy's output. No code change, no risk to connecting.
3. Add only the `✓ ACCEPTED` ones to `EBAY_REQUIRED_SCOPES`. The existing full-list
   check then guards the result on the same deploy.
4. **Then** the reconnect of both accounts — which the plan already marks as the
   Owner's, and which a new scope genuinely requires: eBay grants scopes at consent.
