# P6.2b — P6.2 was 0% working in production, and its tests said it was fine

**Found by:** the handover's own instruction — *"§0b. Verify on the next deploy: `[cx-ebay]
recorded the signing key expiry {"signingKeyId":…,"expiresAt":…}` — the first time this system
has ever known that date."* It never appeared. What appeared instead was a warning, four times
in two minutes.

## 1. What production said

Deployment `5e51055d` (commit `6e9cdd0fd`) — the deploy P6.2 shipped on — reached SUCCESS at
09:12:12 UTC and applied `20260921a_p62_signing_key_expiry`. Then:

```
[cx-ebay] could not read the signing key expiry
  {"signingKeyId":"828aad3f-487a-4fef-b06e-8bcb0646b34f",
   "error":"Invalid `prisma.channelApp.update()` invocation:
     data: { signingKeyExpiresAt: new Date(\"Invalid Date\"), signingKeyCheckedAt: … }
     Invalid value for argument `signingKeyExpiresAt`: Provided Date object is invalid."}
```

at **09:12:58, 09:13:07, 09:15:02, 09:15:09**. The design asks eBay once a day.

## 2. Two defects, and the second is the worse one

### D1 — epoch seconds handed to a date-string parser

`key-management.ts` normalises eBay's `expirationTime` with `optionalString`, so the number
`1731536000` becomes the string `'1731536000'`. Both consumers then did
`new Date(created.expirationTime)`.

```
new Date('1731536000')   →  Invalid Date     ← what production ran
new Date(1731536000)     →  1970-01-21       ← also wrong, quietly
ebayEpochToDate('1731536000') → 2024-11-13T22:13:20.000Z
```

🔴 **The repo already knew.** `key-management.ts`'s own type comment says *"eBay returns epoch
seconds; normalised to a string here"*, and its own fixture (`signing.vitest.test.ts:271`) uses
`expirationTime: 1731536000`. The fact was written down one file away from the code that
ignored it. *A comment can be right and still not be read.*

### D2 — one bad value took the whole row, and the throttle with it

`recordSigningKeyExpiry` writes **two** columns in one `update`: the expiry, and
`signingKeyCheckedAt`. Prisma refuses the whole statement for one invalid Date. So:

| what should have happened | what happened |
|---|---|
| expiry recorded | never recorded |
| `signingKeyCheckedAt` set | **never set** |
| `shouldAskForSigningKeyExpiry` sees a fresh check → waits a day | sees `checkedAt: null` → **asks again** |

**The write that stores the throttle was the write that failed.** So the sweep asked eBay's Key
Management API on every heartbeat, forever — a live channel call on a loop, at our expense and
eBay's rate limit. Four calls in two minutes, measured.

## 3. 🔴 Why P6.2's own tests passed the whole time

```ts
expect(client).toContain('created.expirationTime ? new Date(created.expirationTime) : null')
```

The claim was *"the expiry that was dropped is now stored"*. That assertion pins the
**characters**, and the claim is about the **value**. It would have passed just as happily if
`new Date` had been spelled correctly and eBay had returned nothing at all.

This is the banked rule — *a control must target the LAYER and the BRANCH* — and this is what
it looks like when it is not followed. Every new test below runs the code and reads the result.

A second assertion in the same file was brittle in the other direction: it sliced **1800
characters** from the function and looked for a `return` inside the window. Adding two comment
lines above that return broke it. A control a *correct* change can break is measuring the
wrong thing; it is now bounded by the function's own end.

## 4. The fix

| # | File | Change |
|---|---|---|
| 1 | `cx/connectors/ebay/key-management.ts` | **new** `ebayEpochToDate(value)`. Seconds and milliseconds told apart by **magnitude** (< 1e11 is seconds); an ISO string still parses; anything unusable is `null`; a result outside **2000–2100** is `null`, because a key expiry in 1970 is a parse failure wearing a date |
| 2 | `cx/connectors/ebay/client.ts` | both call sites use it — the create path and the recover path. The recover path records **either way** and warns with the **raw** value, so a shape eBay changes to is named in a log rather than guessed at |
| 3 | `cx/apps.service.ts` | **`usableDate()`** guards both writers. An invalid Date degrades to "we asked, there is no date" and **never takes `signingKeyCheckedAt` with it** |
| 4 | `recoverEbaySigningKeyExpiry` | returns `unreadable: boolean` — *"eBay named no expiry"*, *"eBay named one we cannot read"* and *"we never asked"* are three different facts |

`usableDate` guards `storeSigningKey` too, and that is the worse path: it writes the **private
key**, which eBay never hands back a second time. A row refused because the date beside it was
unusable would have lost the only copy of the key.

## 5. Proof — 28 new tests, all green

- `cx/signing-key-expiry.p62b.vitest.test.ts` (22) — the parser table, the guard, and the
  throttle demonstrated in both directions.
- `cx/connectors/ebay/signing-key-recover.p62b.vitest.test.ts` (6) — **the production path end
  to end**, with eBay's real answer shape, and a stub that refuses an invalid Date exactly as
  Prisma does. Positive controls: the stub really does refuse; a real date survives; no key
  means no call.

| # | Mutation | First run | Now |

| M2 | parser's `isNaN` guard removed | 🔴 **SURVIVED** | KILLED |
| M3 | year bounds removed | KILLED | KILLED |

### What the three survivors were worth

- **M7 was the production defect itself.** Putting the exact broken line back broke no test,
  because P6.2 had covered that function with source text only. **The arm that would have
  failed was the one never run.** It now has an end-to-end test.
- **M2 was a second real hole,** not just a coverage gap. `new Date(1e300)` is an Invalid Date,
  and an Invalid Date's `getUTCFullYear()` is **NaN** — so `NaN < 2000` and `NaN > 2100` are
  **both false** and the year bound waves it through. The `isNaN` check before it is the only
  thing that refuses it. Same family as the banked `Array.isArray([])` trap: *a range check is
  not a validity check, because every comparison with NaN is false.*
- **M6** was a coverage gap on the higher-stakes path (the private key).

## 7. Verify on the next deploy

1. `[cx-ebay] recorded the signing key expiry {"signingKeyId":"828aad3f-…","expiresAt":"…"}` —
   an **info**, with a real ISO date. **Prediction, written before the deploy:** a date roughly
   two years after the key's creation; eBay's Key Management keys are long-lived.
2. It appears **once**, not every heartbeat. If the warning returns instead, read
   `rawExpirationTime` in it — that is the value eBay actually sends, which nothing has ever
   seen, and the parser is wrong about its shape rather than its unit.
3. `expiresAt: null` with `unreadable: false` would mean eBay genuinely names no expiry. That
   is a real answer, and `signingKeyCheckedAt` now records that we asked.
