# P3.4 — alerts that reach a person

**Built 2026-09-20.** Plan row: *alerts: dead-letter growth, signature failures, feed
rejections over a threshold, secret expiry, deprecation headers — to the owning
profile's owners.*
Done when: *each alert fired once in a test.*

---

## 1. What was measured first — the alert path reached nobody

There **is** an alert service, `services/monitoring/alert.service.ts`, and P0.5's
app-secret-expiry alert already calls it. Its in-app channel is this:

```ts
private async createInAppAlert(alert: Alert, destination: string): Promise<void> {
  // Store in database for in-app notification
  console.log(`[IN_APP] Alert for ${destination}:`, alert.title)
}
```

The comment says "store in database". It writes a console line. The `destination` is
the string `'admin'`, which is not a user id.

`CONNECTION_HEALTH` — the type every channel alert uses — has exactly two channels:
that stub, and EMAIL guarded by
`enabled: !!process.env.NEXUS_CONNECTION_ALERT_EMAIL`.

**`NEXUS_CONNECTION_ALERT_EMAIL` is not set in production.** Checked against the live
Railway variable list, 2026-09-20: 96 variables, and it is not among them.

So **every CONNECTION_HEALTH alert in production has gone to a log line and stopped** —
including the secret-expiry alerts this programme shipped in P0.5. The ConnectionEvent
row it writes first is real and useful; the notification is not.

### 1.1 The thing that does deliver was sitting beside it

| Path | Rows | Used by |
|---|---|---|
| `alertService` in-app | — | nothing; it is a `console.log` |
| `Notification` + the bell | **391,197** | the ads programme, only |

`Notification` is per-user, scoped by business profile, and the bell reads it. It is a
proven path with six figures of traffic. Nothing in the channels programme used it.

### 1.2 What each alert actually has to work with

| Alert | Source | Rows today |
|---|---|---|
| dead-letter growth | `WebhookEvent.status = 'dlq'` (P2.1) | **0** — nothing has ever reached dlq |
| signature failures | `WebhookEvent.signatureOk = false` | **7**, real, and nothing had ever looked at them |
| feed rejections | `ListingIssue` (P3.2) | 0 locally; the store went live with P3.2 |
| secret expiry | `ChannelApp.secretExpiresAt` | **0** — no app has a date set |
| deprecation headers | — | **no producer; P3.5 builds it** |

Two things follow, and both are said plainly rather than left to be assumed:

- **P0.5's secret-expiry alert has never fired, for two independent reasons**: it
  reaches nobody, *and* no `ChannelApp` has an expiry date to fire on.
- **The 7 signature failures are the only real fuel any of these five has today.**

`alert.service.ts` is **not** changed. Its stub is a real defect and it is named here,

do. The channel alerts route around it.

### 2.1 Two rules taken from this codebase's own notifier

Both from `publish-refusal-notify.service.ts`, which records why:

🔴 **Recipients are THIS business's people.** `ads-automation-notify.service.ts` fans
out to every login on the system. Under business profiles that delivers one business's
problem — naming another business — to people who belong to neither. Recipients here
are the actor, if there is one, plus the **active OWNERs of the business in context**.

🔴 **Deduped, or it floods.** That same notifier measured **41,466 notifications a day**
before its caps. A dead-letter backlog is the same fact every fifteen minutes until
someone acts on it. One unread notice per kind per subject per person; **once it has
been read, a recurrence is new information and notifies again.**

### 2.2 Thresholds, and why none of them is 1 except one

A notice an operator learns to dismiss is worse than no notice, so a threshold of 1 on
a retrying system is a mistake. Each has an env override.

| Alert | Default | Env |
|---|---|---|
| dead letters | 5 in the window | `NEXUS_ALERT_DLQ_THRESHOLD` |
| signature failures | **1** | `NEXUS_ALERT_SIGNATURE_THRESHOLD` |
| feed rejections | 10 in the window | `NEXUS_ALERT_REJECTION_THRESHOLD` |
| secret expiry | 30 days | `NEXUS_ALERT_SECRET_EXPIRY_DAYS` |
| window | 24 hours | `NEXUS_ALERT_WINDOW_HOURS` |

Signature failures fire on one because a payload we could not verify is already a fact
worth saying. Its wording is deliberately careful: **it does not claim an attack.** A
rotated secret and a forged payload look identical from here, and naming one would be a
guess presented as a finding. It says to check the signing secret first.

## 3. The proof — each alert fired once

**`src/services/cx/channel-alerts.p34.vitest.test.ts` — 29 tests**, on a real
PostgreSQL with the generated schema and the real profile policies, profiles ON. Five
tests are literally the done-when, one per alert kind, each asserting the notice
reached both owners with the right severity and wording.

The sweep is tested over real sources too: dead letters per channel (and a third
channel *below* its threshold, which must not be folded in), the window boundary, a
verified event not being read as a failure, feed rejections counted through the listing,
and a secret with months left staying quiet.

### 3.1 Mutation checks — 8 rules broken, 8 named tests failed

| # | Mutation | Result |
|---|---|---|
| 1 | recipients become every user, not this business's owners | ✅ failed |
| 2 | the OWNER role filter is dropped | ✅ failed |
| 3 | the dedupe is removed | ✅ failed |
| 4 | the dedupe ignores `readAt` | ✅ failed |
| 5 | the dead-letter threshold becomes 1 | ✅ failed |
| 6 | the sweep stops filtering by time window | ✅ failed |
| 7 | the sweep counts never-checked as a failure | ✅ failed |
| 8 | the sweep groups every channel together | ✅ failed |

Both source files restored and compared byte for byte.

### 3.2 A mutation that did not mutate

Mutation 7's first form was `signatureOk: { not: true }`, and the test kept passing.
That is not a weak test: in SQL, `!= true` **already excludes NULL**, so the mutation
changed no behaviour at all — the exact "a mutation that does not mutate" trap.

To genuinely fold the never-checked rows into the failure count you have to ask for
null explicitly (`OR: [{ signatureOk: false }, { signatureOk: null }]`), and that form
fails the test immediately. It matters: there are **5,249 rows with `signatureOk = null`
against 7 with `false`**, so a truthy read would have turned every event ever received
into a signature alarm.

**A second lesson from the same check.** The mutation *script* was edited by a `replace`
that matched nothing, so it silently kept running the old mutation, and the ❌ looked
like a weak rule for two rounds. The fix was to assert the line changed rather than
trust the edit — `assert 'not: true' in lines[81]`.

### 3.3 And a suite that failed to LOAD

The first run of this test printed `19 skipped`, not `19 failed`. The cause was in the
seed, which invented three table names: `User`, `WorkspaceRole`,
`WorkspaceMembershipRole`. The real ones are **`UserProfile`**, **`Role`** and
**`WorkspaceMemberRole`**, and they were read out of the schema rather than guessed the
second time. `'N skipped'` with a Failed Suites block is a load failure wearing a green
hat.

## 4. What does NOT work yet, said plainly

1. **`channel-deprecation` has no producer.** P3.5 is the package that teaches the
   gateway to read `Deprecation` and `Sunset` headers. Its shape and wording live in
   the service so P3.5 raises it through the same path instead of inventing a sixth,
   and it is tested through that shape only. **It will not fire today.**
2. **Three of the four live alerts have no fuel.** Dead letters: 0 ever. Feed
   rejections: 0 until a feed runs after P3.2. Secret expiry: no `ChannelApp` has a
   date, so an Owner must set one (`PUT /api/cx/apps/:channelKey/secret-expiry`) before
   it can ever fire.
3. **Signature failures are the one that can fire now** — 7 real rows are waiting, and
   the first sweep after deploy is the test of that.
4. **`alert.service.ts`'s in-app channel is still a `console.log`.** Other programmes
   still call it and still reach nobody. Named here, not fixed here.
5. **Email is not wired.** These notices go to the bell. An email path would need
   `NEXUS_CONNECTION_ALERT_EMAIL` or a per-owner preference, and neither exists.
