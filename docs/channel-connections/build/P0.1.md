# P0.1 — No dry run or sandbox write reaches a live channel

State: **BUILT (2026-09-19), not committed, not deployed.** The Owner said "go" on 2026-09-19. Section 7 is the build record.

## 1. The rule this package enforces

A write to a channel happens only when that channel's publish mode is `live`.

| Mode | What a write does after P0.1 |
|---|---|
| `gated` | 0 calls. Clear refusal message. |
| `dry-run` | 0 calls. Clear refusal message, or the existing dry-run result where one exists. |
| `sandbox` | The sandbox host, only where the path already has one. Otherwise 0 calls. |
| `live` | Unchanged. |

Etsy stays read-only (decision D6): every Etsy listing write refuses in every mode.

A "would send" record for dry runs comes with the gateway (P1.1). P0.1 only makes sure nothing is sent.

## 4. Exact changes

### 4.1 Shared helpers (2 small additions)
- `services/ebay-publish-gate.service.ts`: add `ebayWriteRefusal(host: 'production' | 'sandbox'): string | null`. Allowed: mode `live` + production host, or mode `sandbox` + sandbox host. Otherwise it returns one plain sentence, e.g. "eBay publishing is in dry-run mode. Nothing was sent to eBay." Plus `assertEbayWriteAllowed(host)` that throws it.
- `services/shopify-publish-gate.service.ts`: add `assertShopifyWriteAllowed()` (throws unless `live`).

### 4.2 Amazon
1. `clients/amazon-sp-api.client.ts` — the 3 methods treat `sandbox` like `dry-run` (0 calls, warning log, `dryRun: true`). This is the same pattern AS.5 already uses in `submitListingPayload` in the same file.
2. `routes/marketplaces.routes.ts` — when `spResult.dryRun` is true: do **not** mark the listing published/ACTIVE and do **not** start the stock sync. The answer stays `DRY_RUN` (both screens already show "dry run" apart from "published").
3. `services/images/amazon-media-client.ts` — `patch(..., preview=false)` throws unless mode is `live`. The `VALIDATION_PREVIEW` call (writes nothing) is unchanged.
4. `services/images/amazon-media-publish.service.ts` — `approveAmazonMediaRun` refuses (422, plain sentence) unless `live`. The worker checks the mode **before** it marks a SKU `SENDING`, so a refused SKU is recorded as `NOT_SENT`, not `UNKNOWN`.

### 4.3 eBay
5. `services/ebay-trading-api.service.ts` `callTradingApi` — for listing-write call names only (`AddItem`, `AddItems`, `AddFixedPriceItem`, `ReviseItem`, `ReviseFixedPriceItem`, `ReviseInventoryStatus`, `EndItem`, `EndItems`, `EndFixedPriceItem`, `RelistItem`, `RelistFixedPriceItem`, `UploadSiteHostedPictures`): call `assertEbayWriteAllowed` just before the `fetch`. Reads (`Get…`, `Verify…`) and order/feedback calls keep their own flags. The existing dev "fake success" branch is not touched.
6. `routes/ebay-flat-file.routes.ts` — push :1515 and publish :3329 refuse unless `live` (sandbox too: this path has production tokens and host only). `DELETE /ebay/flat-file/offer` gets the same check. Each refusal is one plain sentence and 0 calls.
7. `services/ebay-variation-push.service.ts` — `pushVariationGroup` and `pushOffersOnly` call `assertEbayWriteAllowed` for the host of their `apiBase` at entry (belt and braces for every caller).
8. `services/channel-batch/ebay-parallel-batch.service.ts` — dry run unless mode is `live`. The **stock** and **price** operations refuse per operation ("Use the stock sync / price sync; this bulk path would overwrite the listing"). They never send a partial `inventory_item` or offer. A correct bulk path comes later (P4.3 / P4.4).
9. `services/marketplaces/ebay.service.ts` — every write method calls `assertEbayWriteAllowed('production')` first. (P1.6 retires this file.)
10. `services/images/ebay-inventory-image-publish.service.ts` — refuse at entry unless `live`, **before** the job row is marked running, so no job reads "DONE" for a refusal.

### 4.4 Shopify and Etsy
11. `services/marketplaces/shopify.service.ts` `makeRequest` — non-GET calls `assertShopifyWriteAllowed()`.
12. `services/marketplaces/shopify-enhanced.service.ts` — `updateVariantPrice` and the `inventoryAdjust` write call `assertShopifyWriteAllowed()`. Fulfillment, cancel and refund are order writes with their own flags; not touched.
13. `services/channel-batch/shopify-bulk-mutation.service.ts` — dry run unless mode is `live` (the env flag can still force a dry run).
14. `services/marketplaces/etsy.service.ts` `updateVariationQuantity` — always refuses: "Etsy is read-only in Nexus. Nothing was sent to Etsy."

### 7.2 What was built

All 15 changes in section 4, as written, with these differences:

1. **Placement.** Each mode check sits where section 4 says. Where a path also has the push lock, the mode check comes first (plan section 5 order: mode, then lock) — except the eBay bulk stock/price refusal, which runs after the lock so a held listing still names its hold.
2. **`services/bulk-action.service.ts` (not in the list).** The eBay `CHANNEL_BATCH` branch ignored the batch result and always said `processed`. It now throws the first failed operation's message, so a refusal shows as a failed item. Without this, change 8 would have been silent.
3. **Change 13 (Shopify bulk).** Outside `live` it now **refuses** (throws) instead of returning a dry-run result. A dry-run result reads as `processed` in bulk actions, which would claim work that never happened. `NEXUS_SHOPIFY_BULK_DRYRUN=1` still gives the explicit rehearsal.
4. **Change 4 (Amazon image approval)** answers 409, not 422 (same code as the other state refusals in that service).
5. **Change 8.** The batch-level refusal returns failed rows with `EBAY_WRITE_REFUSED: …`, never synthesised success. `NEXUS_EBAY_BATCH_DRYRUN=1` keeps its old rehearsal behaviour.
