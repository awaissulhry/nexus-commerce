# P4.3e — the shared eBay fan-out coalesces its own superseded rows

**Date** 2026-09-20 · **Package** P4.3 (Stock), fifth slice · **Size** S

The plan row: *"Coalesce shared eBay rows."*

---

## 1. What was measured

### 1.1 The row is true — and the reason it had not bitten is a counterweight

`coalescePendingQuantityRows` (`services/sync-coalesce.ts`, P1) cancels stale
PENDING quantity rows before the cascade writes fresh ones, scoped by
`channelListingId IN (…)`. **A shared eBay SKU is not a `ChannelListing`**, so
its rows carry `channelListingId: null` and that scope has never matched one.
`enqueueSharedTradingFanout` inserted a fresh row beside every superseded one.

🔴 **The ChannelListing lane learned this in P1; the shared lane did not.** Same
waterfall, same rule, applied in one of the two builders — the shape this package
has now found five times.

**But the stale number does not reach eBay**, and that is a real counterweight.
`syncSharedTradingQuantity` re-reads the pool at dispatch (RT.4): it
re-derives every SKU's quantity through `resolveMembershipIntended` from the
CURRENT ledger, drops SKUs already at `lastQtyPushed`, and returns SUCCESS
**without spending a revise** when nothing is left. Its own comment names this
very gap — *"superseded row that outran coalescing"*. So the eBay ~250
revises/listing/day budget was already protected.

### 1.2 🔴 What coalescing actually buys: the re-read has a `catch`, and it fails open

```ts
} catch (err) {
  // Re-read is an accuracy upgrade, not a gate — fall back to the
  // enqueue-time quantities on any read failure.
  logger.warn("syncSharedTradingQuantity: dispatch re-read failed — using enqueue-time quantities", …)
}
```

That sentence is the same shape as the one P4.3b removed from the EU guard
(*"Guard infrastructure failing must not stop legitimate pushes"*). **The fifth
fail-open found in this package.**

And here is the thing worth writing down: **the fallback is not wrong — its
premise was.** An enqueue-time quantity came from the resolver a moment earlier,
so pushing it when the ledger is unreadable is a reasonable answer *for a current
row*. It is only wrong for a **superseded** row, where the enqueue-time number is
stale by definition and pushing it is the lost update the whole P1 ordering work
exists to stop.

So the right fix is not to harden the `catch`. It is to **make its premise true**:
with the superseded rows cancelled, the only row that can reach that `catch` is
the current one, and falling back to its own quantity is correct. The `catch` is
left exactly as it is, and it is now safe. *Ask what a failure path's premise is
before hardening it.*

### 1.3 A second thing the coalesce repairs

The fan-out re-reads its own rows back to return their ids:

```ts
where: { productId, channelListingId: null, syncType: 'QUANTITY_UPDATE', syncStatus: 'PENDING' },
orderBy: { createdAt: 'desc' }, take: rows.length,
```

With superseded rows sitting in that same scope, `createdAt desc` ordering was
the only thing separating the rows just written from older ones — and the code's
own comment admits a same-millisecond tie is possible. After the cancel, the
PENDING shared rows for that product **are** the rows just written, so the
read-back is exact rather than probable.

### 1.4 The hazard the scope has to avoid

**One shared ItemID can carry SKUs belonging to several products**, and each
product's fan-out writes a row covering only its own SKUs. Cancelling by ItemID
alone would throw away another product's pending update to the same listing. The
scope is therefore `productId` **and** the ItemIDs being replaced — both halves,
each asserted by value in the tests.

Neither caller passes `args.sku` today (`stock-movement.service.ts:944`,
`ebay-inventory-readback.service.ts:520`), but if one did, its run would cover
only that SKU's memberships and could not claim to supersede a row carrying the
product's others. That run does not coalesce.

## 2. What was built

`coalescePendingSharedQuantityRows(tx, productId, itemIds)` in
`services/sync-coalesce.ts`, beside its sibling, cancelling
`productId + channelListingId: null + externalListingId IN itemIds +
QUANTITY_UPDATE + PENDING`. PENDING only — never an in-flight row, never a
non-quantity sync, the same limits as the sibling.

`enqueueSharedTradingFanout` calls it **before** `createOutboundRows`, in the
caller's transaction, for exactly the ItemIDs it is about to write
(cancel-scope == replace-scope), skipped on a narrowed run and behind the same
kill-switch as the sibling (`NEXUS_SYNC_ORDERING_V2=0`).

`SharedFanoutDeps` now declares `outboundSyncQueue.updateMany`, so a narrow test
double cannot silently skip the coalesce and read as "nothing to cancel".

## 3. Proof

`src/services/shared-fanout-coalesce.p43.vitest.test.ts` — **12 tests**:

- the cancel's `where` asserted **by value**, whole, with `toHaveBeenCalledExactlyOnceWith`;
- `productId` present (the several-products hazard), `channelListingId: null`
  (so it cannot reach into the ChannelListing lane), `PENDING` and
  `QUANTITY_UPDATE` each asserted on their own;
- no items / blank items / no product each write **nothing at all**;
- duplicate ItemIDs collapse;
- the fan-out's call **order** — `['updateMany', 'createMany']`, because
  cancelling after the insert would cancel the fresh rows;
- cancel-scope == replace-scope, derived: the ItemIDs cancelled equal the
  ItemIDs written;
- a run that writes nothing cancels nothing;
- a run narrowed by `args.sku` does not coalesce;
- the kill-switch turns it off and the insert still happens.

**Mutation checks — 7 of 7 convicted**:

| Mutation | Red test |
|---|---|
| the coalesce is never called | `cancels the superseded rows … BEFORE the insert` |
| the narrowed-run guard dropped | `a run narrowed to one SKU does NOT coalesce` |
| the coalesce runs AFTER the insert | `… BEFORE the insert` |
| `productId` drops out of the scope | `productId is part of the scope` |
| the cancel widens past the replaced items | `cancels only this product's PENDING shared quantity rows` |
| an IN_PROGRESS row can be cancelled | `it never touches an IN_PROGRESS row` |
| an empty item list still writes | `no item ids: writes nothing at all` |

🔴 **The IN_PROGRESS mutation passed GREEN on the first run**, and the reason is
a banked trap in a new place: its marker, `syncStatus: 'PENDING',`, appears in
**both** coalescers and `String.replace` takes the first — so it mutated the
**ChannelListing** function and convicted nothing here. *Mutate inside the thing
you are convicting.* The marker is now anchored on the shared function's own
`externalListingId: { in: targets }` line.

**Gates.** `tsc --noEmit` clean. Gateway ratchet all zeros, queue rows outside
`outbound-rows.ts`: 0. `check-push-lock.mjs`: 1 FAIL, the pre-existing one.
**Full API suite: 6 failed / 10,344 passed** — the documented baseline.

One existing test double (`ebay-shared-fanout.service.vitest.test.ts`) gained
`updateMany`. No proposition changed.

## 4. What this does NOT do

- **It does not change the dispatch `catch`.** That was the decision, and §1.2
  is the reasoning: the fallback is right for a current row, and coalescing is
  what guarantees the row is current.
- **It cannot cancel an IN_PROGRESS row**, the same limit the ChannelListing
  lane has had since P1. A row already in flight finishes; its re-read is what
  keeps it honest.
- **No production measurement.** Railway reads are blocked for this session, so
  how many superseded shared rows exist in production right now is unmeasured.
  The done-when is a second stock movement inside the grace window leaving
  exactly one PENDING shared row per ItemID instead of two.
