# P4.3a — Etsy does not get to write our stock

**Date** 2026-09-20 · **Package** P4.3 (Stock), first slice · **Size** S

---

## 1. What was measured

The P4.3 row says *"Remove the Etsy inbound stock write."* It was there, and it
was worse than the row suggests.

`services/sync/etsy-sync.service.ts → syncInventoryFromEtsy(productId)` read an
Etsy listing and wrote **Etsy's numbers straight into our database**:

```ts
await prisma.productVariation.update({ where: { id: variant.id }, data: { stock: estyVariation.quantity } })
…
await prisma.product.update({ where: { id: productId }, data: { totalStock } })
```

Directly, with `prisma.update`, bypassing every rule that owns a quantity here:

- **the stock resolver** — the one place a quantity is decided;
- **the shared-stock POOL** — a pooled product's own stock is deliberately `0`
  and `StockLevel` holds the truth, so writing `totalStock` from a channel makes
  every screen that reads it lie;
- **any audit** — nothing recorded that a channel had moved our stock.

Inbound stock from a channel is backwards. Nexus owns the quantity and pushes it
**out**; a channel telling us what it thinks it has is at best stale and at worst
a silent overwrite of a pool that several listings share. D6 also keeps Etsy
read-only.

## 2. Had it ever run? — and why the answer made it MORE dangerous

Almost certainly not:

- `etsy-sync` is **registry-only** — a manual trigger, never scheduled. It
  appears in `CRON_REGISTRY` and in no `cron.schedule` call.
- Both entry points need `ConfigManager.getConfig('ETSY')`, and production boots
  with `[ConfigManager] ⚠ Etsy configuration incomplete (missing env vars)`, so
  the job returns at `if (!config)`.
- P2.5 separately measured that **no Etsy order had ever entered Nexus by any
  route**.

This is the P2.1 – P2.5 shape once more — referenced by working code, never once
executed. **But this one is not harmless dead code.** It is a manual trigger
nobody had pulled, one environment variable away from overwriting pooled stock
with no audit trail and no error. The usual finding is "it never ran, so the
feature does not exist"; here it is "it never ran, which is the only reason
nothing is broken yet".

⚠️ And the Owner says Etsy may be connected through the **Channels** screen. That
is a CX OAuth connection, which this legacy env-based job does not read — so it
stays unable to run. That is luck, not design, and it is why this is removed now
rather than noted.

## 3. What was built

The function is a **refusal**. It writes nothing, reads nothing from Etsy, and
returns `success: false` with a sentence naming the reason and the alternative.

Deliberately a refusal rather than a deletion: two callers exist
(`jobs/etsy-sync.job.ts`, `routes/etsy.ts`). They keep working and now get an
answer that explains itself — **a silently removed feature is how the next person
rebuilds it**.

`success: true, updated: 0` was available and is wrong: it would read as "ran,
nothing to do", which is the false green this programme keeps finding. It
refused, so it says so, and it logs — a pulled trigger must be visible.
