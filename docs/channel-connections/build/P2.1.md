# P2.1 — the incoming event ledger

**Built 2026-09-20.** Plan row: *a ledger that works for every channel: status lifecycle,
dedupe on the channel's delivery id, rejects recorded in every mode, retry worker,
dead-letter queue, replay button, archive instead of delete.* Decision D8 is settled:
**archive, never delete.**

---

## 1. What was measured first

The plan's reading was from 2026-09-19 and assumed the ledger had to be built. It did
not: **CX.4a already built the table**. `WebhookEvent` carries `status`, `attempts`,
`nextAttemptAt`, `signatureOk`, `verifiedBy`, `payloadDigest`, `lastError`, `archivedAt`
and `archiveUri`, all added by migration `20260901a_cx4a_inbound_ledger`, and
`services/cx/ingress/ledger.ts` is a single writer for every channel.

What was missing was the behaviour, and two of the gaps were live production defects.

### 1.1 The ledger's contents (local database, 2026-09-20)

```
AMAZON  done     5158
AMAZON  pending    91
EBAY    failed      7
SHOPIFY             0     ← no Shopify event had ever been recorded
attempts = 0 on all 5256 rows; nextAttemptAt set on 0 rows; status 'dlq' never written
```

### 1.2 Shopify recorded nothing — and the measurement that says so

The first probe used a bare `new PrismaClient()` and reported "the compound key is
missing `workspaceId`". **That measured the wrong layer** and the conclusion was wrong
in its mechanism. The app uses a scoping client which completes compound keys itself.

Re-measured through `apps/api/src/db.js`, the app's real client, on the branch a Shopify
webhook actually takes — no workspace context, `NEXUS_WORKSPACES_ENABLED=1`:

```
workspaces flag: 1
CONTROL count() THREW -> Select a business profile.
isWebhookProcessed returned: false
after markWebhookProcessed, rows found: []
```

And the second arm, the one that decides what the fix is — the same two calls inside a
workspace:

```
WITH workspace — isWebhookProcessed after write: true
```

So: `WebhookProcessor` worked perfectly well; the **routes had no business profile**.
Both methods threw `WorkspaceError: Select a business profile` into their own catch
blocks. `isWebhookProcessed` swallowed it and returned `false`, so no delivery was ever
recognised as a duplicate. `markWebhookProcessed` swallowed it and returned, so no
Shopify event was ever written. Seven routes read as if both worked.

### 1.3 The defect the first one was hiding

`externalId` was `String(payload.id)` — the **product's** id, the **order's** id —
against a unique `(workspaceId, channel, externalId)`. Had the ledger write worked, the
first change to a product would have been handled and **every later change to that same
product dropped as "Already processed", permanently.** Repairing 1.2 alone would have
turned a silent gap into silent data loss, so the two are one change.

### 1.4 eBay rejects were not recorded in production

`ebay-notification.routes.ts:373` wrote the rejected-signature row only when
`NEXUS_WORKSPACES_ENABLED !== '1'`. Production runs with profiles on. So the one mode
where a forged notification mattered was the one mode that recorded nothing, and
`signatureOk = false` could not occur in production however many arrived. The gate came
from a bulk checkpoint commit (`f212c2348`), not from a decision.

### 1.5 Two dispatch tables that had already drifted

`dispatchShopifyWebhook` listed `'refund/create'`; the route wrote `'refunds/create'`.
Replaying a refund threw `Unknown Shopify eventType` and nothing said so.

### 1.6 Nothing deletes an inbound event

`/usr/bin/grep` over `apps` and `packages` for `webhookEvent.delete`, `deleteMany` and
`DELETE FROM "WebhookEvent"`: **zero hits.** D8 was already held; it now has a guard.

### 2.1 Design notes worth keeping

- **The worker is per-workspace, not platform.** `cron.schedule` already visits every
  active profile and runs the handler inside it. The first end-to-end run used
  `$queryRawUnsafe`, which the scoping client cannot see into, and the sweep read **zero
  rows while a due event sat in the table** — a worker that looked idle and was in fact
  blind. `dueInboundEvents` now uses the model API. A test asserts it never uses raw SQL.
- **An unverified body is recorded against the platform's workspace**, never a business.
  Attributing it to a business would let anyone who can reach the endpoint write rows
  into that business's ledger.
- **A rejected event never names itself.** `externalId: null` keys it on the body digest,
  so a forged delivery id cannot occupy the unique slot and suppress the genuine
  delivery as a duplicate.
- **Only a `done` duplicate short-circuits.** A channel resends the same delivery id both
  when it never heard an answer and when we answered with a failure; treating the second
  as handled would drop the retry we asked for.
- **Shopify routing has a safe fallback.** If the domain matches no alias, the
  channel-only lookup answers *only* when exactly one active Shopify route exists. It
  recovers a connection saved before its domain was captured and cannot guess between
  two businesses.

  after replay        status=pending attempts=0 due=yes
  sweep: due=1 ok=1 failed=0 unreplayable=0

Probe rows and the Order row that ARM 3's replay really created were cleaned up **by
value**; the ledger is back to its starting 5158 / 91 / 7.

The retry in ARM 3 SUCCEEDED, so exhaustion is proven through `completeInbound` — the
function the worker calls on every failure — rather than through a handler that keeps
throwing. The Shopify handlers are resilient enough that no payload tried would make one
throw. Stated plainly rather than dressed up as a handler failure.

| # | Mutation | Test that went red |
|---|---|---|
| A | A failure stops scheduling (the CX.4a state) | `sets a time to try again and spends one attempt` |
| B | The dead-letter cap slips by one | `becomes a dead letter once the attempts run out…` |
| C | A redelivery spends the retry budget | `counts a duplicate arrival as a delivery…` |
| D | Replay forgets to give the budget back | `gives a dead letter a full budget back and queues it` |
| E | The worker looks at failures only | `selects on the TIME, so a replayed event is collected…` |

Every file restored byte-for-byte afterwards (`cmp -s` → YES in each case).

## 4. Still open

1. **Amazon and eBay events cannot be replayed from the ledger.** Amazon's handling lives
   inside the SQS poll loop and eBay's inside the live notification envelope; neither can
   be re-run from a stored payload without being split out first. They are named in the
   guard's `UNREPLAYABLE` map with that reason, and the worker dead-letters them on the
   first sweep instead of retrying five times to reach the same place eight hours later.
   The replay endpoint still handles both channels its own way (re-sync).
2. **The 91 AMAZON rows stuck at `pending`** are untouched by this package. They carry no
   `nextAttemptAt`, so the worker does not see them. `replayInbound` deliberately accepts
   a `pending` row with no time on it, which is the shape they have — but nothing sweeps
   them automatically yet.
3. **The archiver does not exist.** `archivedAt` / `archiveUri` are written by nothing;
   `replayInbound` and the worker both honour them. D8 is held by the guard, not by an
   archiver.
4. **Amazon dedupes on the SQS `MessageId`, not the SP-API `NotificationId`** the plan
   names. Stable across SQS redeliveries of one send, but two sends of the same
   notification would be two rows. A small fix, deliberately not bundled here.
5. **Amazon dedupes on the SQS `MessageId`.** See section 5 — P2.2's measurement
   confirmed `NotificationMetadata.NotificationId` is present on **1413 of 1413** stored
   ORDER_CHANGE payloads, so the plan's key is there and unused.
