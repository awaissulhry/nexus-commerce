# P0.7 — Wrong-account guard: a change for a second account's listing is refused, never sent to the first

State: **BUILT (2026-09-19), committed locally (not pushed, not deployed).** Run under the Owner's "Start to implement the whole plan" (FINAL-PLAN 14.3).

Plan row (FINAL-PLAN.md section 6): until P1.3 is done, refuse (loudly) any eBay or Amazon write whose listing belongs to a non-primary account, instead of sending it to the primary. Done when: a test with a second-account listing is refused with a clear message and 0 calls.

## 1. Evidence (census 2026-09-19, one read-only helper, every claim re-read)

- **eBay:** 12 listing-write paths pick the account with `{ channel: 'EBAY', primary: true }`, or with a resolver scope (`{ itemId }`, `{ listingId }`) that itself falls back to the primary when the recorded account is null (`services/connection-resolver.service.ts:198, 209, 224`). Among them: the outbound queue (`services/outbound-sync.service.ts:1323`, shared Trading `:1746`), the flat-file push, publish, offer delete, shell auto-heal, reconcile / convert / relabel routes (`routes/ebay-flat-file.routes.ts`), flat-file variation removal, the listing wizard and cockpit (`services/listing-wizard/ebay-publish.adapter.ts:306`), both eBay image publishers, and bulk actions (`services/bulk-action.service.ts:2439`). The publish and offer-delete loops also took "the first" listing of a product in a market, which with two accounts can be the other account's.
- **Amazon:** the default seller does not fall back to a primary: with two or more active Amazon accounts `amazonAccount()` throws (`lib/amazon-sp-client.ts:13-16`), so those paths fail closed. The misroute is the one-active-account case: a listing recorded for another (e.g. disconnected) account is written through the active one. Already account-bound and not changed: delist, recovery, market offer close/reopen, the studio, the media client.
- A listing records its account in `ChannelListing.channelConnectionId`; a shared eBay variant in `SharedListingMembership.channelConnectionId`.

## 2. Changes

1. **New** `services/write-account-guard.ts`:
   - `assertWriteAccount(channel, usedConnectionId, target)` — `target` names listing ids, product ids (+ market), SKUs (+ market) or eBay ItemIDs. It refuses with `WrongAccountWriteError` (`WRONG_ACCOUNT_WRITE`, 409) when everything the write touches is recorded for OTHER accounts. A listing with no recorded account, or a target no listing names, passes (nothing to contradict). If the ownership lookup fails, it refuses (fail closed). The message names both accounts and says nothing was sent.
   - `assertWriteAccountPerSku` — the batch form: each SKU on its own, so one foreign SKU refuses the batch and is named (the union rule would let it through; a test shows both).
   - `ownListingFor` — the account's own listing of a product in a market (moved here so the route gains no direct DB access; the route-prisma ratchet refused that).
   - Market codes: `EBAY_IT`, `IT` and Amazon marketplace ids all read as `IT`.
2. **eBay paths:** the outbound queue (by the row's listing, else SKU + market; refusal is FAILED, not retryable) and the shared-Trading lane (by ItemID); the flat-file push (per SKU, every target market; 409); publish and offer delete (use this account's own listing of the product; if it has none, the row is `REFUSED`); the four item routes and the save-time shell auto-heal (by ItemID); flat-file variation removal; the wizard and cockpit adapter (by SKU + market); the inventory image publisher (by product, before any job row); the shared image publisher (each target's ItemID, since one token is used for all); bulk actions (by listing).
3. **Amazon paths:** every listing write on the shared `amazonSpApiClient` proxy (`submitListingPayload`, `…Batch` per SKU, `putListingsItem`, `patchListingPrice`, `patchPurchasableOffer`, `deleteListingsItem`) is checked against the account the proxy binds, in both profile modes; reads are not checked. Explicit checks with a terminal answer: the outbound queue, the flat-file feed submit (per SKU, 409), bulk actions and the image feed (per SKU, before the job row).
4. **Census test:** every source file that picks the primary eBay account must call the guard, or be listed as not writing listings, with a reason (17 listed: reads, Nexus-only rows, ads, feedback, refunds). The list is also checked for stale entries.

Not changed: the old app-token `EbayService` and old `AmazonService.updateVariantPrice` (no account at all; already refused outside `live` by P0.1; on the P1.6 delete list). eBay Promoted Listings writes (ads, not listings; P4.5).

## 4. Production proof — OPEN

After a push: with one eBay account, nothing changes (every listing belongs to it; the guard only adds one read per write). With the second eBay account connected, a stock change for one of its listings shows on the queue row as FAILED with the "Nothing was sent to eBay … second account" sentence, and `OutboundApiCallLog` shows no call for it. P1.3 then removes the need for this guard.

## 5. Found, but NOT in this package

- Flat-file variation removal logs a refusal and reports `failed`; the operator sees "failed", not the sentence. The delete result could carry the reason (P3).
- The census works per file: a second write path added inside a file that already calls the guard is not caught. The P1.2 gateway ratchet replaces it.
- `resolveConnection({ listingId | itemId | variantListingId })` still falls back to the primary when the recorded account is null. Every listing write that uses it is now guarded; the fallback itself goes with P1.3.
