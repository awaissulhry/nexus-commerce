# P4.6f — closing Etsy's six-hour rule

**Package:** P4.6. **Slice:** f. **State:** BUILT, local, green.

P4.6e measured Etsy's six-hour content rule and found it **had never been met**. This closes it.

## 1. The gap, restated

FINAL-PLAN §13: *"Etsy's terms: listing content at most 6 hours stale. **Required.**"* The job
that was meant to keep it was dead three times over (`build/P4.6e.md` §3):

1. `etsy-sync` is **registry-only** — a manual "Run now", never scheduled;
2. its client needs **env credentials production does not have**;
3. and its `x-api-key` is the **OAuth access token**, so Etsy would refuse the call anyway.

This slice replaces that path with the **connected-account reader**, which works and is already on
the gateway.

## 2. 🔴🔴 What it writes — a closed set of three

| written | why it is allowed |
|---|---|
| `listingStatus` | **the channel's own fact about its own listing**, and Nexus already keeps a column for it. The push lock reads it (P1.7), so a listing Etsy has ended stops being written to |
| `lastSyncedAt` | the freshness stamp the rule is about |
| `lastSyncStatus` | so a failed sweep does not read as a successful one |

**Never written:** quantity, price, stock, `totalStock`, title, sku, salePrice, stockBuffer.

That is P4.3a's ruling, and it is the whole shape of this job. `syncInventoryFromEtsy` wrote
Etsy's quantities straight into `ProductVariation.stock` and `Product.totalStock` — past the
resolver, past the shared-stock pool, past the audit. **A refresh job written to "fix staleness"
by copying Etsy's numbers back in would be that defect rebuilt with a better excuse.**

The test asserts the written columns as a **derived closed set** (`Object.keys(update.data).sort()`),
not as spot checks, so a field added to that write fails the test. A second case feeds Etsy a
payload that *does* carry `quantity`, `price`, `title` and `sku`, proves none reaches the write,
and 🟢 proves with a positive control that the write happened at all.

## 3. 🔴 Why it sweeps six states

`getListingsByShop` takes **one `state` per call and offers no "all"** — and its default is
`active`. A sweep that asked once would see only the listings that are fine and would **never
notice the one that went `expired`**, which is the population the push lock exists for.

Etsy's own enum is the list, read from its OpenAPI document rather than typed from memory:

| Etsy `state` | → `listingStatus` |
|---|---|
| `active` | ACTIVE |
| **`sold_out`** | **ACTIVE** |
| `inactive` | INACTIVE |
| `draft` | DRAFT |
| `expired` | ENDED |
| `removed` | ENDED |

**`sold_out` → ACTIVE is deliberate.** On Etsy it means *listed and visible, quantity 0*. The
listing is present, and its quantity is a fact this job is forbidden to write. Calling it INACTIVE
would make the push lock refuse a live listing that only needs restocking — the opposite of what
an operator wants. A test pins it, and a mutation flipping it is killed.

## 4. Four hours, not six

The rule is a **six-hour ceiling**, so scheduling at exactly six meets it only if no run is ever
late or slow. `20 */4 * * *` leaves a whole run's headroom. `NEXUS_ETSY_CONTENT_REFRESH=0` turns it
off; `NEXUS_ETSY_CONTENT_REFRESH_SCHEDULE` overrides the cadence.

It ships **on**, not dark. It is a **read** — no publish gate applies, nothing is sent to Etsy,
and the alert P4.6e added will keep firing until it has run.

## 5. Failure is partial, never total

- An account whose shop identity cannot be read is **recorded and skipped**; the other shops are
  still swept.
- One state failing does not lose the other five.
- The run summary names the error count, so *"freshened nothing because every call failed"* does
  not read like *"freshened nothing because there was nothing to do"* (P3.6 — `no_data` is never a
  pass). A test drives a total failure and asserts the summary says `6 error(s)` and `0 freshened`.

## 7. Verify on the next deploy

1. `etsy-content-refresh cron: scheduled {"schedule":"20 */4 * * *"}` at boot.
2. Its first run's summary: `N account(s), M listing(s) seen, … 0 error(s)`.
3. Then the alert P4.6e added should **stop firing**, because `lastSyncedAt` is being stamped.
   **Prediction, written before the deploy:** the first `[channel-alerts] etsy freshness` line
   shows `stale === total` (nothing has ever refreshed), and the first line **after** a successful
   sweep shows `stale: 0`. If `total` is 0 there are no Etsy `ChannelListing` rows and the rule is
   vacuously met — a different answer, and worth knowing.
