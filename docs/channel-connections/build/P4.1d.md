# P4.1d — eBay business policies: one reconciliation, both builders

**Date** 2026-09-20 · **Package** P4.1 (Publish / content), fourth slice · **Size** S

---

## 1. The plan row, and where the defect actually was

> *eBay: … business policies per account …*

**Per ACCOUNT was already right**, and better than the row asks:

- the ids come from `ChannelConnection.connectionMetadata.ebayPolicies` for the
  **resolved connection**, not from a global default;
- P0.7's wrong-account guard (`assertWriteAccount` / `assertWriteAccountPerSku`)
  is called at five places in the push route, so a write that would reach a
  different account than the listing's is refused before it sends;
- and both publishers additionally reconcile per **marketplace**, because eBay
  business policies belong to one market and a foreign id is the classic **25007**.

**Per MARKET is where the defect was, and it is a DRIFT, not a gap.** Both
publishers ran the *same* three-tier waterfall and the *same* "replace any id not
in this market's list" rule. They disagreed on the one case that matters:

| Builder | On an unavailable account snapshot |
|---|---|
| `ebay-variation-push.service.ts` (group) | 🔴 **REFUSES.** `FFP.12`: *"NEVER proceed with UNVERIFIED policy ids. The old fallback ('keep whatever ids we have') is exactly how another market's policy got written onto DE offers — creating unpublishable drafts that then failed EVERY publish of the family with a mixed-locale 25007."* |
| `routes/ebay-flat-file.routes.ts` (single SKU) | 🔴 **WARNED and CONTINUED**, writing the unverified ids. `Audit R12`: *"silent skip left cross-market policy IDs unvalidated and eBay later failed with an opaque 25007. **Warn once per push.**"* |

**R12 made it warn. FFP.12 made the other one refuse. The single-SKU path was
left with the exact behaviour FFP.12 exists to prevent** — it could still write a
wrong-market policy id onto an offer whenever eBay's account API was briefly
unavailable, producing an unpublishable draft that then fails every later publish
with an error naming the wrong thing.

That is the banked *"TWO column builders DRIFT — put the rule in the ENGINE,
assert parity in the gate"* lesson in its exact shape: a rule learned in one
builder and never carried to the other, silent, and visible only by reading both.

### 1.1 It was three copies, not two

Replacing the block found **two** occurrences inside the group publisher —
`pushVariationGroup` **and** `pushOffersOnly` — plus the one in the route. Three
copies of one rule across two files, which is how the versions diverged.

## 2. What was built

`services/ebay-policy-reconcile.service.ts` — one accessor, called by both sides,
stating the rule once:

1. **The waterfall**: the row's own flat-file column, then the account's stored
   default, then this market's first policy.
2. **REPLACE, don't top up.** An id absent from THIS market's list is *wrong*,
   not merely unconfirmed — a DE id on an IT offer is a 25007 whether or not an
   IT id was also configured.
3. **An unverifiable snapshot is a REFUSAL, never a warning.** Retrying in a
   minute is cheap; an unpublishable draft carrying another market's policy is
   not.

Both publishers now report the refusal in their own idiom — the group returns an
`ERROR` row per SKU, the route pushes a `perRowResult` and moves to the next SKU
— and neither sends anything.

### 🔴 2.1 A discriminated union does NOT narrow in `apps/api`

The result was first typed as `{ ok: true; policies } | { ok: false; message }`.
It does not work here: `apps/api/tsconfig.json` sets `"strict": false`, and
without `strictNullChecks` TypeScript never eliminates the `{ ok: true }` member,
so `resolution.message` after `if (!resolution.ok)` is a compile error. The union
compiles and gives **no** safety in this package.

Two nullable fields say the same thing and actually work:
`{ policies: EbayPolicyIds | null; message: string | null }`. Worth banking — the
`ok`-flag result type is a reflex that silently buys nothing in `apps/api`.

## 3. The proof

**14 tests green** (`services/ebay-policy-reconcile.p41.vitest.test.ts`), each
rule with its own arm and a positive control (a *correct* id for this market must
be KEPT, not overwritten — otherwise "replace everything" would pass too).

**5 mutations, 5 named tests failed, every file restored byte for byte.**

```
✅ refusal becomes a warning again (the FFP.12 regression)
✅ REPLACE becomes top-up (a DE id survives on an IT offer)
✅ the waterfall inverts: the account default beats the row
✅ the snapshot is asked for the wrong market
✅ the single-SKU caller continues past a refusal
5 guarded, 0 not guarded
```

**The parity gate**, derived from source, asserts three things that together stop
the drift coming back: no file builds a Set of this market's policy ids on its
own; both publishers call the accessor (and the group file calls it **twice**, so
`pushOffersOnly` is counted); and **every** call site checks the refusal — with a
regex **backreference**, so `a.message || !b.policies` does not count as a check.

The parity test caught its own first version: the check regex assumed one
variable name (`sPolicies`) and the group publisher uses `resolution`, so it
reported `2 call(s), 0 refusal check(s)`. Fixed by matching any name with a
backreference rather than by loosening the pattern.

**Gates**

- `tsc --noEmit` — clean.
- Full API suite — `Tests 6 failed | 10182 passed | 127 skipped`; the documented baseline, attributed at clean `HEAD` in `build/P5.1.md` §3.
- Gateway ratchet — `{"EBAY":0,...}` (exempt 47), unchanged.
- Push-lock gate — 1 missing guard, the pre-existing `studio-publication-amazon.ts:164`.

## 4. What is still open

1. **Not proven by real traffic.** The refusal only fires when eBay's account API
   is unavailable, which is by definition rare. The done-when is one push
   refusing with this sentence instead of publishing unverified ids.
2. **A second, smaller drift is NAMED and NOT changed.** After reconciliation the
   two builders apply different "missing field" rules: the group refuses when
   `merchantLocation`, `fulfillmentPolicy` **or** `returnPolicy` is missing; the
   single-SKU path refuses only on a missing `merchantLocation`. Both then fail at
   eBay, so this is a question of which error the operator sees, not of what is
   written. Left to its owner rather than changed quietly inside this slice.
3. **`resolvePolicyDisplayNames`** still runs its own snapshot read for the
   display names in the description theme. It is display-only and fails open, so
   it is deliberately outside the accessor.
