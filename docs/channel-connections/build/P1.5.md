# P1.5 — eBay headers from one builder (EBAY_IT sends it-IT, not en-US)

State: **BUILT (2026-09-19), committed locally (not pushed, not deployed).** The Owner included the flat-file routes (FINAL-PLAN 14.3).

Plan row (FINAL-PLAN.md section 6, P1): one header builder in the gateway (language, marketplace id); fix `EBAY_IT → en-US`. Done when: a test for every eBay market sends the right three headers.

## 1. The defect

`toListingLanguage` (ebay-variation-push) mapped `IT → it-IT` but anything else to `en-US`, and `pushOffersOnly`, the cross-market draft delete and two flat-file routes passed the **full id** `EBAY_IT` → `en-US`. eBay stores listing content in the write's language, so Italian aspects ("Colore", "Taglia") met English names ("Color", "Size"), error 25013. The same map was the one language-guard violation left (LX finding F-LX-6, baselined because its fix touched the flat-file routes).

## 2. Change

- **The builder** (gateway, P1.1 `ebayMarketHeaders`): the three headers from the Marketplace row — `X-EBAY-C-MARKETPLACE-ID` from the row, the language from `Marketplace.languages` (first = default), with a hyphen (`it-IT`, `en-GB`, `fr-BE`).
- **A listing write** gets all three from the row. A language the call sends is kept only when it is one of that market's languages (Belgium in Dutch stays `nl-BE`); `en-US` for Italy is replaced. A caller's differently-cased copy of a header is removed, so eBay never gets two values joined. A write to a market Nexus has no row for → refused `MARKET_UNCONFIGURED` (nothing sent); a failed row read → `MARKET_LOOKUP_FAILED` (503, retry later).
- **Every other call** (reads, order actions, setup) keeps what it sends and gets only the headers it left out — a read may ask for English labels on purpose (the category service does).
- **The moved eBay calls** (`ebaySend` / `ebayTransport`, P1.2) now use the builder (they kept their own headers until now). Trading calls are unaffected (their site id decides).
- **`toListingLanguage` is deleted.** Its 13 uses (variation push, flat-file routes ×4, inventory drift, the queue's `ebayInventoryHeaders`, now async) read `ebayListingLanguage(market)` — the same row; `en-US` only for a market with no row (a read can still go; a write is refused by the gateway).
- Language guard: the violation is gone; `scripts/market-languages-baseline.json` loses its entry (17 → 16) and the guard test now expects none.

## 3. Proof

- `services/gateway/ebay.p12.vitest.test.ts` (+10): **every configured market** (IT, DE, FR, ES, UK/GB, BE) sends the right marketplace id and language in all three headers although the caller sent `en-US`, one value per header; Belgium's Dutch kept; a write to an unconfigured market refused, 0 calls; a failed market read is `MARKET_LOOKUP_FAILED`, 0 calls; the helper reads the same row (`EBAY_IT`, `IT`, `EBAY_GB`, `UK` right; `en-US` only for an unknown market); a read keeps its own `Accept-Language: en-US` and only gains the missing `Content-Language`.
- `outbound-sync.ebay-headers.vitest.test.ts` now reads the Marketplace row (async).
- Fixtures: two test database stand-ins gained the Italian Marketplace row; one mock dropped the deleted helper.
- Mutation checks 5/5 caught (the caller's en-US wins, a read overridden, the helper always en-US, a lookup failure reported as unconfigured, moved calls keep their own headers). Full API suite: **9734 passed, 6 failed** (the two known Amazon local-account files). Market-languages script and guard test pass; ratchets 0.

## 4. Production proof — OPEN

After a push: a flat-file or queue eBay write for an Italian listing leaves with `Content-Language: it-IT` (the call ledger shows the operation; eBay's 25013 "aspect name" errors on IT listings stop). No `MARKET_UNCONFIGURED` refusals for the five configured markets.
