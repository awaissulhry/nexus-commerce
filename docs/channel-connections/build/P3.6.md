## 1. What was measured first

### 1.1 There was no target to be "against"

`slo` appears **once** in `apps/api/src`, in a comment on an unrelated route. No
concept of a target level existed, so "against a target" had nothing to compare to.

The four numbers themselves existed, scattered and uncompared:

| Number | Where it lived | Compared to anything? |
|---|---|---|
| error rate | `/sync-logs/api-calls`, by channel | no |
| slow calls | `/admin/outbound-latency`, queue latency only | no |
| backlog age | nowhere | — |
| dead letters | Ingress tab, counted | no |

And the backlog is real: **1 PENDING row, 227 hours old** (SHOPIFY). A nine-day-old
queued change, and nothing was showing it.

### 1.2 🔴 The trace followed a RUN, not a change

`requestId` exists, is well filled (455,896 of 459,724 cron calls) and **works for what
it was built for** — the module's own header says so: *"Cron ticks: `recordCronRun()`
opens a fresh context with a generated tickId so per-tick API calls share a correlation
ID."*

That is a **run** id. Measured over the real population:

```
calls sharing one requestId:  1243  ×2 traces
                               682  ×1
                               656  ×1
                               315  ×1
```

**One id covering 1,243 calls answers "what did this tick do" and can never answer
"what happened to my change".**

And the change's own id died at the queue: `OutboundSyncQueue` had **no id column at
all**, so when the worker picked a row up it was inside its own cron tick, and the
tick's id went onto the channel call.

This is not the usual "never ran" finding — it is the P2.6 counterweight in a new
shape: the thing works, for a different question than the one asked.

### 1.3 🔴 The honest denominator

Of the 395 calls since the gateway landed, **only the 48 Shopify ones are real
traffic** — every eBay row is a test artefact (a `conn-1` account, a sandbox host, no
status code) and Amazon has 2. A dashboard "verified" against that is verified against
nothing. It is stated **on the screen**, not only here.

### 2.1 Two names, because they are two facts

`requestId` stays exactly what it was. `traceId` is new and different:

- **`requestId`** — this process RUN. A cron tick. Answers *"what did this run do"*.
- **`traceId`** — this CHANGE. Minted on the operator's request, stored on the queue
  row, re-bound by the worker. Answers *"what happened to my edit"*.

`getTraceId()` falls back to `requestId` **on an HTTP request only**: a change made
directly in a request, with no queue row between, *is* that request. It deliberately
does **not** fall back on a cron — returning a tick id would make 1,243 calls look like
one change, which is worse than admitting there is no trace.

## 3. The three rules that stop a false green

### 3.1 🔴 `no_data` is its own verdict, and never a pass

A metric with nothing behind it renders **neutral with its reason**, never green.
`rollUp` is worst-wins and `no_data` can only ever be the answer when *every* metric has
none — one real pass beside it is `meeting`, one real miss is `missing`.

The screen counts channels with no data in its own tile, so "everything is green" can
never quietly mean "we measured nothing".

### 3.2 🔴 Zero dead letters is a MEASUREMENT; zero calls is an ABSENCE

They must not look alike. The ledger was *asked* about dead letters and answered none —
that is a pass, with a sample size of 1 (the window). No calls at all is a question that
could not be asked, and that is `no_data`.

### 3.3 🔴 A target is a number someone agreed, not one we computed

An SLO derived from recent behaviour ("p95 of the last week") always says the system is
fine, because it moves with the system. These are fixed defaults with env overrides — a
number that **can be missed** is the only kind worth showing.

| Metric | Target | Env |
|---|---|---|
| error rate | ≤ 2% | `NEXUS_SLO_ERROR_RATE_PCT` |
| slow calls | ≤ 5% over 5,000 ms | `NEXUS_SLO_SLOW_CALL_PCT`, `NEXUS_SLO_SLOW_CALL_MS` |
| backlog age | ≤ 1 h | `NEXUS_SLO_BACKLOG_AGE_HOURS` |
| dead letters | 0 | `NEXUS_SLO_DEAD_LETTERS` |

### 3.4 Two measurement choices worth naming

- **Backlog is an AGE, not a count.** One change stuck for nine days is a worse fact
  than ninety queued in the last minute, and a count cannot tell them apart. It reads
  `_min.createdAt` of the PENDING rows.
- **Slow calls are a COUNT over a threshold, not an average.** An average hides a tail:
  99 fast calls and one 30-second call averages fine.
- **Operations sort worst-first, not busiest-first.** An operation failing all 3 of its
  calls is the one to look at, not the one making 26,838 successful ones.

Mutation 1 **failed to apply** on its first form (a quoting bug in the harness) and the

### 4.2 A token that would have been silently dropped

The new stylesheet first used `var(--nds-font-family-mono)`. **That token does not
exist** — the real one is `--nds-font-mono`. DESIGN.md warns that a wrong token name is
an invalid declaration the browser drops in silence, so it was checked by grepping every
token in the new block against the design system's own files before committing. All nine
verified; one was wrong.

### 4.3 And a column type that was not what it looked like

`OutboundSyncQueue.syncType` reads like an enum in Prisma and is **plain `text`** in the
database. The first test seed cast it to `"SyncType"` and the suite reported
`type "SyncType" does not exist`. Read out of `information_schema`, not guessed.

### 4.35 A P1.4 test caught a doubled read, and the CODE was wrong

The first version of the worker hop read the trace in its own query before delegating:

```
FAIL  outbound-sync.shopify.p14.vitest.test.ts > processSingle
AssertionError: expected undefined to match object { product: true, channelListing: true }
```

P1.4's test asserts the shape of the **first** query `processSingle` makes, and mine had
become the first one. The test was right, and the defect was real: **every queue row was
being read twice** — the same waste the P1.3 follow-up was about (a claim check reading
once per row instead of once per chunk, found by the profiles-ON gate).

**The test was not weakened.** The row is now read once, with its `include` intact, and
the trace is bound from that same row before delegating. One query, and P1.4's
proposition is asserted exactly as it was written.

## 5. Still open

1. **Not proven by real traffic.** 48 real calls is the whole population, and no change
   has yet been made through a UI since the trace shipped — so no `traceId` exists in
   any row yet. **The first queued change after the deploy is the proof**, and it is
   one query: `GET /api/cx/trace/<id>`.
2. **Only the queue path carries a trace.** A change pushed straight from a request
   (no queue row) uses the request id, which is right. A change that starts inside a
   cron with no operator behind it has **no trace, by design** — the alternative was a
   tick id pretending to be one.
3. **The screen has no auto-refresh.** It reloads on window change and on mount. "Live"
   in the plan row means the numbers are computed on read, not that the page polls; a
   poll can be added when someone actually watches it.
4. **No per-operation targets.** The target is per metric, applied to every operation.
   A slow-by-nature operation (a feed submit) and a fast one (a stock update) share a
   ceiling, so the operation list is a ranking rather than a pass/fail per row.
