## 1. What was measured first

**No Etsy order has ever entered Nexus, by any route.** Three separate findings, each
with a control.

### 1.1 There is no Etsy receiver

`/usr/bin/grep` for `webhooks/etsy` across `apps/api/src`: **zero hits**. The connector
spec has declared `webhooks: { scheme: 'standard-webhooks' }` since it was written, and
nothing implemented the scheme — a grep for `standard-webhooks` finds the declaration,
one type union and a comment in `utils/webhook.ts` saying Etsy's real order webhooks
"land in CX.6". They had not.

### 1.2 The Etsy order sync has no call site

`services/sync/etsy-sync.service.ts` has a `syncOrders`, and `jobs/etsy-sync.job.ts`
wraps it as `syncEstyOrders`. Nothing calls either:

```
grep -rn 'syncEstyOrders'            -> 2 hits   (its definition, and its export)
grep -rn 'startTrackingPushbackCron' -> 3 hits   (definition, import, call)   <- control
```

### 1.3 And it would have returned immediately anyway

`syncEstyOrders` reads `ConfigManager.getConfig("ETSY")`, which requires `ETSY_SHOP_ID`,
`ETSY_API_KEY`, `ETSY_ACCESS_TOKEN`, `ETSY_REFRESH_TOKEN` **and** `ETSY_WEBHOOK_SECRET`
to be set. Production's variable list contains **no `ETSY_*` entry at all** — the same
shape as the Shopify secret in P2.4. Locally the module logs
`⚠ Etsy configuration incomplete (missing env vars)` on import.

This is the fourth package in a row where a component looked finished, was referenced by
working code around it, and had never once run.

## 2. What changed

| File | Change |
|---|---|
| `services/cx/ingress/standard-webhooks.ts` (new) | The Standard Webhooks scheme: constant-time comparison, a two-sided timestamp tolerance, multiple `v1` signatures for key rotation, and a named reason for each refusal |
| `services/etsy/receipts.service.ts` (new) | Pulls receipts through the account-scoped reader — the connection's own token, through the channel gateway. No environment variables |
| `routes/etsy-webhooks.routes.ts` (new) | The receiver, through the P2.1 ledger: every arrival and rejection recorded, deduped on Etsy's `webhook-id`, retried, replayable |
| `services/cx/ingress/handlers.ts` | Replay handlers for the four order events |
| `index.ts` | Registers the route |

### 2.1 The decisions worth keeping

- **The notification body is a claim; the shop's API is the record.** A webhook says an
  order CHANGED; the handler then asks Etsy what it now looks like. Nothing in the body
  is written as state.
- **The timestamp tolerance is two-sided.** Without any tolerance a captured delivery
  replays forever; with a one-sided check the replay window is as wide as the sender's
  clock skew, and a future timestamp is as much a forgery signal as an old one. The
  ledger's delivery-id dedupe stops a replay being *processed* twice, but that is an
  application guard on a transport problem and it cannot help once the row is archived.
- **A rejected delivery never names itself.** `externalId: null` keys it on the body
  digest, so a forgery quoting a real `webhook-id` cannot occupy the unique slot and
  make the genuine delivery look like a duplicate. Same rule as eBay and Shopify.
- **An event with no handler is recorded and acknowledged, not refused.** Only
  `order.paid` is named by the plan; the other three are marked `assumed`. Recording an
  unknown event with its payload is how a real name and shape get learned — which is
  exactly what P2.2 and P2.3 had to do the hard way.
- **Order ingest is deliberately NOT written.** An Etsy receipt has never been observed
  in this installation. Mapping one to `Order`/`OrderItem` from the documentation would
  be a fixture written to match a belief, which is precisely the defect P2.2 found. The
  receipt is read back and logged; the mapping follows from a real one.
- **A replay gets its account from the LEDGER ROW.** The stored payload is Etsy's own
  body and names no Nexus account. The first draft fell back to "the only connected Etsy
  shop in this workspace" and **the MAP.3 connection-resolver ratchet refused the
  push** — correctly: a site that resolves a connection without being told which account
  it means is how a write lands in the wrong store the day a second one is connected.
  `WebhookEvent.connectionId` was already recorded at arrival; it simply was not being
  asked. The retry worker and the replay endpoint now pass it to the handler, so the
  fallback is gone and the whole class of guess with it.

## 3. The proof

### 3.1 Mutation checks

| # | Mutation | Test that went red |
|---|---|---|
| X | Drop the timestamp tolerance | `refuses a signature that is too OLD, and one from the future` |
| Y | Check only the old side of the window | same test |
| Z | Accept an empty signature | **nothing failed — see below** |
| AA | Leave the delivery id out of the signed content | 3 tests |
| AB | Trust the body instead of reading the receipt back | 3 tests |
| AC | Let a rejected delivery name itself | `is recorded and refused, and never names itself` |
| AD | Treat every duplicate as handled | `short-circuits only a FINISHED event` |

Plus two tests for the ledger-sourced account: it uses the `connectionId` the receiver
recorded, and it refuses rather than guessing when the row names none.

Every file restored byte-for-byte.

**Mutation Z is reported as a negative result, and a claim was corrected because of it.**
Deleting the zero-length guard in the constant-time comparison changed nothing, because
the expected value is always a 32-byte digest and a `v1,` signature already fails on
length. The test's comment claimed to cover a case it does not. The guard is kept — it
protects a future caller that supplies an expectation from elsewhere — but both the code
and the test now say it is unreachable from here rather than implying it is
load-bearing.

A test-harness bug was also found and fixed on the way: the header helper used
`over.id ?? ID`, which swallowed an explicit `undefined` and restored the default, so
the "missing header" case was quietly testing a present one.

## 4. Still open

1. **The done-when is not met: no real `order.paid` has been verified.** Etsy configures
   webhooks in its portal, not by API (`subscriptionApi: false`), so nothing can arrive
   until the Owner points Etsy at `/api/webhooks/etsy` and sets
   `ETSY_WEBHOOK_SIGNING_SECRET`. That is the Owner's step, as the plan says.
2. **Three of the four event names are `assumed`.** Only `order.paid` is named by the
   plan. An event under a different name is recorded with its payload and acknowledged,
   so the real name is learned rather than dropped.
3. **Order ingest is not implemented** — see 2.1. The receipt is read back and logged.
4. **`syncEstyOrders` and `EstySyncService` are left in place**, dead and env-gated.
   Deleting them belongs with the other dead-code sweeps, not inside this package.
5. **The receipts pull has no scheduled caller yet.** `pullEtsyReceipts` exists and is
   bounded at ten pages with `truncated` reported honestly; wiring it to a cron belongs
   with the account lifecycle in P2.6.
