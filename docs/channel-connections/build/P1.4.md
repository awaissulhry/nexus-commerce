## 1. The defects (P1.4a)

- **The queue never reached the native lane.** Both queue loaders loaded `include: { product: true }` only. `syncToShopify` reads `channelListing.platformAttributes.nexusFamilyId` to pick the native lane, so every row fell to the old REST path.
- **The old REST path** (`/admin/api/2024-01`) used the env credentials (`SHOPIFY_SHOP_NAME` + `SHOPIFY_ACCESS_TOKEN`), not the row's account. It took "the first" variant for a SKU and "the first" shop location (`locations.json?limit=1`). It wrote stock with `inventory_levels/set` (no compare-and-set, no idempotency key) and did not read anything back.
- **The native lane's stock write failed on every call.** `offer-sync.service.ts` sent `compareQuantity`, which API `2026-04` removed; the replacement is `changeFromQuantity`, and `inventorySetQuantities` must carry `@idempotent(key:)`.

## 2. Change

- **New `services/shopify/listing-write.service.ts`** — `syncShopifyLinkedListing(row, accountId, work)`, on `shopifyAdmin(accountId)` (the `2026-07` GraphQL client, through the gateway):
  - identity: the ids stored on the listing, else **exactly one** variant with the SKU (two or none → refused, nothing written); then a read-back: the variant must still carry the SKU, the product and the inventory item;

  - stock: the listing's reviewed location (`platformAttributes.inventoryLocationId`; none → refused, **no location is guessed**); read with `inventoryLevel(locationId:)`; write `inventorySetQuantities … @idempotent(key:)` with `changeFromQuantity` = the quantity just read; read back. Already at the target → nothing sent;
  - the shop's circuit breaker (`checkShopifyCircuit` / `recordShopifyOutcome`) is kept from the REST path, per call.

A row naming another account than its listing's → `WRONG_ACCOUNT_WRITE`, terminal (the same consistency check P0.7 gives eBay and Amazon). The native lane (`nexusFamilyId`) stays first;
  - the RT.4 dispatch quantity (listing quantity at dispatch + oversell clamp) moved unchanged into `shopifyDispatchQuantity`;

### 6.1 Part 1 — order actions (refund, cancel, tracking) — BUILT

**The defects.** All three used `ShopifyEnhancedService` with the env credentials (no named account), on `2024-01`, and each sent an operation the API no longer accepts:
- refund: `refundCreate` without `@idempotent` (required since 2026-04) and with `gateway: undefined` on every transaction (`OrderTransactionInput.gateway` is required); the parts were rounded one by one, so they could miss the total by a cent;
- cancel: `orderCancel(input: OrderCancelInput!)` — the 2026-07 form takes top-level arguments; `refund: false` is deprecated;
- tracking: `fulfillmentCreate(input: { orderId, lineItemsToFulfill })` — the 2026-07 input is `lineItemsByFulfillmentOrder`; the job also passed the numeric order id, not a GID. It had no switch of its own ("hits the real API when configured").

**Change.**
- New `services/shopify/order-actions.service.ts` on `shopifyAdmin(<the order's account>)`:
  - `shopifyOrderAccount`: the account recorded on the order; an order with none → the only connected Shopify account; two or more → refused (never "the primary");
  - `refundShopifyOrder`: captured sale / capture transactions with their `gateway`; parts in cents, the last takes the rest (they add up); an amount above the captured total → refused before any write; `refundCreate … @idempotent(key)` with key = return + order + cents;
  - `cancelShopifyOrder`: the 2026-07 top-level form, `refundMethod: { originalPaymentMethodsRefund: false }`, `restock: false` (as before: the operator refunds, Nexus already restocked), staff note capped at 255;
  - `fulfilShopifyOrder`: one `fulfillmentCreate` for the fulfilment orders Shopify can still fulfil (`CREATE_FULFILLMENT`); a retry that finds its tracking number on the order reports it and writes nothing.
  - Every operation validated against the 2026-07 schema (Shopify MCP). No `location { id }` (it needs the `read_markets_home` scope).
- `shopify/admin-client.ts`: the listing publish mode now applies to listing writes only; an order action has its own switch at its caller (P0.1) — the same rule the gateway applies. No existing admin-client caller sends an order action (checked), so nothing else changes.
