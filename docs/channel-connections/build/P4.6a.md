# P4.6a — Etsy gets a publish gate

**Package:** P4.6 (Etsy writes). **Slice:** a of f. **State:** BUILT, local, green.

**Why P4.6 is open at all.** FINAL-PLAN §14.3 recorded `D6 = B` on 2026-09-19 — *"stay
read-only until Shopify is live"* — and every handover since has said "do not re-ask". The
Owner **overrode it on 2026-09-21**: *"I approve you for the ETSY writes."* That is the yes
the P4.6 row (FINAL-PLAN §6) required. Shopify publishing is still `gated`; the Owner's yes
replaces the precondition, it does not claim the precondition was met.

## 1. The measurement, before anything was built

`services/gateway/channels.ts`, `publishModeOf`:

```ts
// Etsy has no publish switch yet: the connected-account client is read-only, and the only Etsy writer
// is the legacy service P1.6 retires (it needs its own env credentials to send anything).
case 'ETSY': return 'live'
```

Every other channel asks a gate. Etsy returned the **literal `'live'`**, and the comment says
why that was safe: nothing could use it. Both halves of that were measured true today:

| Claim in the comment | Measured |
|---|---|
| "the connected-account client is read-only" | `services/etsy/read-client.ts` exports `etsyReader`, whose only method is `get`, and whose only gateway call is `kind: 'read'`. ✅ |
| "the only Etsy writer needs env credentials" | Two write methods exist on `services/marketplaces/etsy.service.ts`. `updateVariationQuantity` **throws** since P0.1 (no caller but its own gate test). `updateReceiptStatus` is live, called twice from `services/sync/etsy-sync.service.ts` (`:506`, `:547`), and reaches the gateway as `kind: 'write'`. It is inert only because `EtsyService`'s constructor needs an `accessToken` + `shopId` production does not have — the boot log says *"Etsy configuration incomplete"*. ✅ (inert, not absent) |

**So the gap is exactly this:** `gatewayFetch({ channel: 'ETSY', kind: 'write' })` passes step 3
of the gateway (`gateway.ts:215`) unconditionally. P4.6 is about to put listing, stock, price
and image writes on the connected account, where a token **does** exist. The first of those
writers would have shipped live the moment it compiled, with no dry-run to rehearse in.

**This slice is therefore the precondition for every other P4.6 slice**, and it is built first
on purpose.

## 2. What was built

`services/etsy-publish-gate.service.ts` (new, 65 lines), modelled on
`shopify-publish-gate.service.ts`:

- `NEXUS_ENABLE_ETSY_PUBLISH` — master flag, **default off**.
- `ETSY_PUBLISH_MODE` — `live` / `production` reach live; **everything else is dry-run**.
- The master flag wins: off + `ETSY_PUBLISH_MODE=live` is still `gated`.
- `etsyWriteRefusal()` / `assertEtsyWriteAllowed()` / `EtsyWriteRefusedError` for parity with
  the other three gates.

`services/gateway/channels.ts` — `case 'ETSY': return getEtsyPublishMode()`.

### Two deliberate differences from the other three gates

1. **Three modes, not four — Etsy has no sandbox.** eBay's and Amazon's gates carry
   `'sandbox'`; Etsy's Open API v3 is one host (`api.etsy.com`), and `SANDBOX_HOSTS.ETSY` is
   already `[]`. A literal `ETSY_PUBLISH_MODE=sandbox` therefore falls to **dry-run** rather
   than to a `NO_SANDBOX_HOST` refusal — the safer of the two, and a test pins it
   (§3, case 3). Nothing in this repo can be configured into believing Etsy has a sandbox.
2. **No rate limiter and no circuit breaker here.** The other three gates predate the P1.1
   gateway and each carries its own token bucket. Etsy is **born on the gateway**, which
   already owns the rate bucket per account and operation group (`gateway/rate.ts`) and reads
   Etsy's own `x-remaining-today` / `x-limit-per-day` headers onto the call ledger (proven by
   `gateway/etsy.p12.vitest.test.ts`). A second bucket would be a second opinion about one
   quota.

## 3. Proof — `services/etsy-publish-gate.p46.vitest.test.ts`, 18 tests, all green

The table half is 12 cases. The half that matters is the 6 behavioural ones, which drive a
real `gatewayFetch` with `channel: 'ETSY', kind: 'write'`:

| # | Case | Assertion |
|---|---|---|
| 1 | gated (nothing set) | `fetch` never called; `GatewayRefusal` `PUBLISH_GATED` / 503; ledger row `outcome: 'gated'` |
| 2 | dry-run | `fetch` never called; `DRY_RUN` / 200; ledger `outcome: 'would_send'` |
| 3 | `ETSY_PUBLISH_MODE=sandbox` | refused as **`DRY_RUN`**, *not* `NO_SANDBOX_HOST` — the mode never becomes `'sandbox'`, so it is held a step earlier |
| 4 | 🟢 **POSITIVE CONTROL** — live | the same call **is** sent, to `https://api.etsy.com/v3/application/shops/42/listings/7`; ledger `outcome: 'sent', success: true` |
| 5 | 🟢 **POSITIVE CONTROL** — a READ while writes are off | sent; the gate did not switch Etsy's readers off |
| 6 | the refusal sentences | each mode's exact sentence; `live` returns `null` |

Cases 4 and 5 are why cases 1–3 are evidence: an empty `h.calls` from a broken fixture would
fail them.

## 6. The one behaviour change to know about

`updateReceiptStatus` — the legacy "mark an Etsy order shipped" PATCH — is now **gated by
default** where it used to be ungated-live. It is inert in production (no Etsy env token), so
nothing changes there today. But it is the one path whose behaviour this slice alters, and it
is named here rather than discovered later. P4.6's own order-status write will be a
connected-account call on the gateway; the legacy one is a P7a deletion candidate.

## 7. Open

Nothing in this slice. The switches are off, which is the point: **P4.6b–f build the writers,
and the Owner turns the gate on when the package is proven.** Turning
`NEXUS_ENABLE_ETSY_PUBLISH` on is a production variable change and belongs to the Owner.
