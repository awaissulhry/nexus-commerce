# P4.5h — the reconnect landmine, and the stale market that self-heals

State: **BUILT 2026-09-21**, committed locally. Owner approved the desk item
*"one stale row: an Ads profile stored as `IE` that Amazon says is `BE`"* — this is
that fix, plus the much larger defect found while checking how to make it.

## 1. What the desk item turned into

The approved item was a one-row data repair. Checking **which column** to repair found
a defect that would have broken **every Amazon ads write** on the first reconnect.

### 🔴 The column every reader matches on was about to be filled with a different vocabulary

| side of the join | value shape | measured |
|---|---|---|
| `AmazonAdsConnection.marketplace` (what readers **match**) | country code | `IT, DE, FR, ES, NL, PL, SE, UK, IE` — 9 rows |
| `Campaign.marketplace` (what callers **pass**) | country code | `IT` (150), `DE` (38), `FR` (22), `ES` (10) |
| `ads-profile-resolver.fromRow` | — | `where: { marketplace, isActive: true }` |
| **what the connect callback WROTE** | **Amazon marketplace id** | `marketplace: marketplaceStringId` → `APJ6JRA9NG5V4` |

The join works today only because **no reconnect has happened since that line was
written**. The first one would rewrite all nine rows from `IT` to `APJ6JRA9NG5V4`,
after which `adsProfileFor('IT')` returns null and `checkAdsWriteGate` refuses every
market with *"no active Amazon Ads profile for marketplace=IT"*.

**A reconnect is meant to repair a connection, not disable advertising.**

🟢 **And this is a second, independent reason for the Owner's decision #1 (do not
reconnect).** P4.5g's reason was the 365-day clock. This one is worse and would have
been immediate.

**The right value was three lines away.** `const country = profile.countryCode ??
marketplaceCountry(marketplaceStringId)` is computed just above the upsert and was
already used for the scope label and the scope's own `metadata.marketplace`. The
correct value was in hand and the wrong one was stored — the same shape as P4.4b,
where a listing id sat four lines above the code that sent no listing.

### The stale row itself

Profile `4392237479209848`: `AmazonAdsConnection.marketplace = 'IE'`, scope says `BE`.
Amazon says BE — `AMEN7PMS3EDWL`, `timezone: Europe/Brussels`. `utils/marketplace-code.ts`
was corrected on 2026-08-29; **the stored row never was.**

## 2. Changes

1. `routes/amazon-ads-auth.routes.ts` — the upsert stores `marketplace: country` on
   **both** branches. Amazon's id is not lost: it continues to go onto the scope as
   `marketplaceStringId`, beside the country code. One column, one meaning.
2. `jobs/p45b-ads-region-reconcile.job.ts` — the daily reconcile now also corrects a
   **stale market** from the scope's own `metadata.marketplace` (which discovery writes
   from the profile's `countryCode`, so it is the channel's current answer).
   - region and market are corrected in **one** update, not two;
   - an absent, blank or non-string market **corrects nothing** — absence is not
     evidence, and blanking a working market to satisfy a missing one would be P4.3b's
     mistake (*"we could not check" is not "it is wrong"*);
   - the report gained `marketCorrected`, so a repair is visible rather than silent.

**This is why no production `UPDATE` was needed.** The repair runs itself on the next
daily tick (`35 4 * * *`), on production, through code that is tested and logged —
rather than a one-off statement typed against a live database.

## 3. Proof

- `jobs/p45b-ads-region-reconcile.vitest.test.ts` grew from 16 to **21**: the callback
  stores the country code on both branches and never the id; the id still reaches the
  scope; the measured `IE → BE` case is corrected; region + market correct in one
  update; and an absent / blank / non-string market corrects nothing.
- **Mutation check** (made, run, restored, compared):
  | Mutation | Tests that failed |
  |---|---|
  | the callback stores Amazon's id again (the landmine) | **1** |
  | the reconcile stops correcting the market | **2** |
  | an absent market **blanks** the stored one | **1** *(see below)* |
  | region and market become two separate updates | **1** |

### 🔴 The mutation that survived, and what it found

The blanking mutation **passed 21/21 at first**. Re-running it with an assertion that
the pattern was actually replaced confirmed it had applied — so it was a real hole, not
[a mutation that does not mutate](../../..).

The cause was in **this slice's own code**: the "nothing to do" guard read
`if (!data.region && !data.marketplace)`. An empty-string market is **falsy**, so a
change that blanked a market took the *unchanged* branch and became invisible. The
guard was quietly neutralising the very defect the test aimed at.

Fixed to `Object.keys(data).length === 0` — presence, not truthiness. The mutation now
fails 1 test. Same family as the banked `Array.isArray([])` trap: a check that reads as
*"is there one"* when it means *"was one set"*.

- `tsc --noEmit` (apps/api): 0 errors.
- `jobs/p45b` + `routes/amazon-ads` + `services/advertising` + `services/ads-core`:
  **2025 passed, 138 files**. Clustered-cron guard ✓.

## 4. Production proof — the job reports it itself

After the deploy, the daily line gains `marketCorrected=`. Expect:

- **`marketCorrected=1`** on the first run — profile `4392237479209848`, `IE → BE`,
  with a `[p45b-ads-regions] corrected a profile stored under the wrong market` warning
  naming both values. That is the approved repair, applied.
- **`marketCorrected=0`** on every run after. A number that keeps rising means
  something else is rewriting the column between ticks.
- `regionCorrected=0` throughout, as before.

If production's stale row is a different profile, or there are several, the log names
each one — which a one-off `UPDATE` targeting a single id would have missed.
