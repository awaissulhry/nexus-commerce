### 1.1 Two traps inside the measurement itself

- **A literal-only regex UNDER-COUNTS.** `studio-publication-ebay.ts:224` passes
  `plan.itemId ? 'ReviseFixedPriceItem' : 'AddFixedPriceItem'`. A census matching
  `callTradingApi\('([A-Za-z]+)'` misses it and reports 13. The census now reads
  the whole first argument and fails if any call's operation cannot be read —
  a hole in the denominator is not a pass.
- **`ebay-presentation-publication.service.ts` already has the value.** Its
  `Target` type carries `listingId: string`, set from `snapshot.listing.id`, and
  it simply never reaches the Trading context. The data was in hand at the call
  site; nothing was missing but the wiring.

## 2. What was built

**Not fourteen edits.** Editing every call site fixes it until the fifteenth is
written, and the fifteenth is the one that matters. The rule went where every
eBay write already passes: `callTradingApi` resolves the listing from what the
call already carries — the `<ItemID>` in its request XML (a revise) or in eBay's
answer (an add), plus the account already in its context.

| File | What |
|---|---|
| `services/listing-issue-recorder.service.ts` | `resolveEbayListingIds`, `itemIdOfTradingXml`, `recordEbayTradingRejection`. The recorder was already "the only writer besides the pre-check"; the resolution joins it there. |
| `services/ebay-trading-api.service.ts` | The failure path files through the resolver instead of requiring `ctx.listingId`. The gateway ledger gets a `listingId` too, resolved before the send. |

### The four rules, and why each one is a rule

1. **A listing the caller named wins outright** — and the database is not asked
   at all. Explicit beats inference: a caller that knows more than the ItemID
   must not be overruled by a query.
2. **Never resolve without the account.** The lookup is keyed on
   `externalListingId` **and** `channelConnectionId`. The MAP.3 ratchet once
   refused a push for falling back to "the only connected Etsy shop"; the same
   mistake here files one seller's rejection on another seller's listing.
3. 🔴 **A shared eBay item is MANY listings, and the rejection is about all of
   them.** One ItemID carries every product in a shared listing. `findFirst`
   would file a real rejection on an arbitrary member and leave the rest showing
   a healthy listing — and shared listings are the whole reason this Trading
   module exists. Every member gets the issue.
4. **"Filed on none" and "never asked" must not look alike.** The count comes
   back, so a zero is a measurement.

**The ledger takes one, the issues take many.** `OutboundApiCallLog.listingId` is
a single column, so the ledger records a listing only when exactly **one**
resolves; the issue path, which can hold many rows, files on all of them. One is
a column, the other is the truth, and they are not made to agree by pretending.

A non-numeric `<ItemID>` is refused. `DRYRUN-AddFixedPriceItem` is the dry-run
sentinel this very module returns, and taking it would query for a listing that
cannot exist — producing "no listing is linked" where the truth is "nothing was
sent".

## 3. The proof

**18 tests, all green** (`services/ebay-listing-rejection.p41.vitest.test.ts`),
with the census derived inside the test rather than typed out.

**7 mutations, 7 named tests failed, every file restored byte for byte.**

```
✅ rule 1: a query overrules the listing the caller named
✅ rule 2: resolve without the account (MAP.3 refusal)
✅ rule 2b: resolve with no account at all
✅ rule 3: a shared item files on the FIRST listing only
✅ itemId: a dry-run sentinel is accepted as an item number
✅ honesty: a failed lookup throws instead of counting
✅ wiring: filing goes back to needing ctx.listingId
7 guarded, 0 not guarded
```

🔴 **A guard of mine was FALSE and the test caught it.** The first version
claimed "there is exactly one sender of eBay Trading XML". Five other files carry
`X-EBAY-API-CALL-NAME`. Three of them genuinely send:

| File | Why it is fine |
|---|---|
| `services/contract/channel-contracts.ts` | P1.8's nightly contract run: `VerifyAddFixedPriceItem` against a deliberately minimal item that is not a listing. Off by default. |
| `services/marketing/ebay-listing-index.service.ts` | Reads only — `GetMyeBaySelling`, `GetItem`. |
| `services/reviews/adapters/ebay-feedback.adapter.ts` | Feedback, not listings — `RespondToFeedback`, `GetFeedback`. |

(The other two mention the header in a comment.) The temptation was to relax the
guard until it passed. Instead the claim was **narrowed to what is true** — no
Trading listing **write** is sent outside `callTradingApi` — the three exemptions
were written down with reasons, and a second test **checks each reason** rather
than trusting it: if `ebay-listing-index` ever adds a `ReviseFixedPriceItem`, it
fails. The exemption list also fails on a **stale** entry.

**Gates**

- `tsc --noEmit` — clean.
- Full API suite — `Test Files 2 failed | 812 passed | 15 skipped`, `Tests 6 failed | 10142 passed`. The 6 are the documented baseline, attributed at clean `HEAD` earlier today in `build/P5.1.md` §3.
- Gateway ratchet — `{"EBAY":0,...}` (exempt 47). Unchanged.
- Push-lock gate — 1 missing guard, the pre-existing `studio-publication-amazon.ts:164`.

## 4. What is still open

1. **No real eBay rejection has landed yet**, because this is a write path and
   the last real eBay traffic is a test artefact (`PROGRESS.md` §4's honest
   denominator: of 395 gateway calls, only 48 Shopify ones are real). The
   done-when is one real `ReviseFixedPriceItem` failure appearing on its listing.
2. **`ChannelListing.externalListingId` must actually hold the eBay ItemID** for
   the resolution to find anything. It is indexed and the studio publication
   writes it, but no count of "how many eBay listings carry one" has been taken
   on production. That is one query and it belongs with the first real rejection.
3. **The Amazon half of P3.2's open item 2 is untouched.** See §5 — the
   handover is wrong about that one too, and in a more interesting way.

## 5. 🔴 The handover is also wrong about Amazon put/patch

`PROGRESS.md` §3.1 item 2 says:

> *`putListingsItem` / `patchListingsItem` are **0 occurrences in
> `apps/api/src`** — Amazon content goes out as `JSON_LISTINGS_FEED`.*

Measured: **28 occurrences of `putListingsItem`** and 5 of `patchListingsItem`.
The claim is true only of the **SDK operation string** (`operation:
'putListingsItem'`), which appears in 2 places, both tests. But
`AmazonSpApiClient.putListingsItem()` is a real method at
`clients/amazon-sp-api.client.ts:801` that sends its own HTTP request, and it
**has a live call site**: `routes/marketplaces.routes.ts:1038`, complete with
P1.7's `amazonContentRefusal` preview in front of it.

So the true statement is: *Amazon single-item content publishing exists and runs;
what is missing is that its `issues` are returned to the caller and never written
to `ListingIssue`.* The route maps them straight into its HTTP response
(`spResult.issues?.map(...)`) and files nothing.

That is the next slice, and it is the same shape as this one: the recorder
exists, the issues exist, nobody joins them.

## 6. For the Owner

Nothing here needs a decision. No switch, no migration, no live call. The change
only fills in a value that was already accepted and already used — an eBay
rejection that used to reach the call ledger now also reaches the listing the
operator is looking at, which is what the flat-file grid's health chip has been
waiting for since P3.2 made `ListingIssue` live.
