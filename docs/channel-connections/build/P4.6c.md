# P4.6c — stock and price on Etsy

**Package:** P4.6. **Slice:** c. **State:** BUILT, local, green.

Stock and price are **one** slice because on Etsy they are one endpoint:
`PUT /listings/{id}/inventory` carries both, and it is a **full replace**.

## 1. Measured before building — Etsy's own OpenAPI document

Not a blog post and not our own belief: `etsy.com/openapi/generated/oas/3.0.0.json`, 908 KB,
downloaded and read 2026-09-21. Three traps, all confirmed there.

### Trap 1 — the GET answer cannot be sent back as it arrived

Etsy strictly interprets the JSON; an extra key is a 400,
`"Array contains invalid keys: product_id,is_deleted"`.

| level | GET returns | PUT accepts | stripped |
|---|---|---|---|
| product | `product_id`, `sku`, `is_deleted`, `offerings`, `property_values` | `sku`, `property_values`, `offerings` | `product_id`, `is_deleted` |
| offering | `offering_id`, `quantity`, `is_enabled`, `is_deleted`, `price`, `readiness_state_id` | `price`, `quantity`, `is_enabled`, `readiness_state_id` | `offering_id`, `is_deleted` |
| property value | …, `scale_name`, … | `property_id`, `value_ids`, `values`, `scale_id`, `property_name` | `scale_name` |

Those four stripped keys are exactly the ones Etsy's error names.

### Trap 2 — `price` changes TYPE between the read and the write of one field

The GET returns a **Money object** (`{amount, divisor, currency_code}`); the PUT wants a
**number**. Sending the object is a 400; sending `amount` is a **hundredfold overcharge** on the
money path. `moneyToNumber` divides and rounds to the divisor's own precision.

The divisor being a power of ten is *not assumed*: a power of ten rounds to its own decimals, and
anything else falls back to six — enough to erase a float artefact without inventing precision.

### Trap 3 🔴 — a correct, successful write can destroy a price, and it cannot be predicted

A shop with **domestic + international pricing** loses its domestic price on any inventory PUT:
the feature is switched off and the field blanked. On Etsy's board since 2023, **still open in
August 2026**, and Etsy staff do not read that board.

**It cannot be avoided** (the PUT requires a price even for a quantity-only change) and **it
cannot be seen coming**:

- The API never exposes it. Verified by searching the **whole** document, with a positive control:
  `price` appears **110** times, so the search works; `regional` appears **0** times; and all
  **16** hits for `domestic` / `international` are about **shipping** — upgrades, handling fees and
  mail classes. Not one is about product pricing.
- A country allowlist would be a lie. The feature is offered in some shop regions and not others,
  and a hardcoded list of them is the banked *"a list of members is a SET CLAIM"* trap: stale
  within months, and reading as a measurement.

So this slice does not pretend to predict it. It does three things instead, and §2 decision 1 and
§2 decision 2 are the two that matter.

## 2. What was built

| File | What |
|---|---|
| `services/etsy/inventory.ts` | **new, pure** — the transform, the change application, the read-back comparison |
| `services/etsy/inventory-write.service.ts` | **new** — the order those happen in, and the two decisions between them |
| `services/cx/channel-alerts.service.ts` | **new alert kind** `channel-write-drift` + `writeDriftAlert` |

### 🔴 Decision 1 — a change that would change nothing is NOT sent

Not an optimisation. **Every** PUT carries trap 3's risk, so a PUT that sets the quantity to the
value Etsy already holds takes that risk **for nothing at all**.

The comparison is structural — the body we would send against the body just derived from Etsy's
own answer — not on the caller's intent, which cannot see what Etsy holds.

### 🔴 Decision 2 — the read-back is part of the write

The quality bar (§7.1.12) asks for one, and here it is the **only** instrument that can see trap
3: the PUT answers **200** while having blanked a price it was never asked about. Banked: *a
claim must match its measurement, and a write's RESPONSE is not what it wrote.*

- Drift → a **danger** alert on the bell (P3.4's path), keyed on the listing **and the fields that
  moved**, so a price drift and a later quantity drift are two facts, not one notice repeated.
- Drift is **reported, never repaired.** A second PUT to fix a price Etsy moved is another full
  replace — the thing that went wrong is exactly what a retry would do again.
- A read-back that cannot be read returns `drift: null, confirmed: false` — **never `[]`**.
  *"We could not check"* and *"we checked and it matched"* are different facts, and only one is a
  pass.
- The read-back waits (default 2 s, injectable) because Etsy is not read-your-writes, and an
  immediate read returning the old value is indistinguishable from the write not landing.

### And one more: a price is never invented

Every offering the caller did not name is sent back with **the price Etsy itself just returned**.
The minimum-damage write.

## 3. Proof — 57 tests across two files, all green

`inventory.p46.vitest.test.ts` (44) — the fixture is the shape Etsy's OpenAPI document defines,
carrying all four banned keys, so the strip is tested against the real thing:

- 🔴 **the 400 case**: a deep key scan proves none of `product_id`, `offering_id`, `is_deleted`,
  `scale_name` survives **at any depth** — with a 🟢 positive control that the scanner does find
  all four in the input
- the exact PUT body, field for field; the four `*_on_property` arrays echoed (dropping one
  flattens a variation listing into a single price)
- deleted products and deleted offerings dropped; a missing `is_enabled` **refused**, because
  defaulting it to false hides the offering from buyers
- a SKU that matches nothing is an **error**, never a quiet no-op; a no-SKU change on a
  multi-product listing is refused rather than applied to all
- `applyOfferingChanges` does not mutate its input — the original is the record of what Etsy held

`inventory-write.p46.vitest.test.ts` (13) — the orchestration:

- the whole inventory is sent with one quantity changed, and the untouched offering carries
  **Etsy's own price**
- 🔴 nothing to change → **no PUT and no read-back at all**; 🟢 positive control: one different
  unit and the PUT is sent
- 🔴 trap 3 simulated: a price we never touched comes back blank → drift, `confirmed: false`, and
  the danger alert with the operator sentence
- 🔴 an unreadable read-back → `drift: null`, and **no alert**, because we cannot claim drift we
  did not see

## 4. Mutation tables — 21 applied, **21 killed**, with the harness itself controlled

Transform (14): keep each banned key (×3), send the raw amount, echo deleted products, echo
deleted offerings, default `is_enabled` to false, drop `*_on_property`, unmatched SKU becomes a
no-op, no-SKU change hits all products, mutate the input in place, drift's price check off,
unreadable read-back returns `[]`, negative quantity allowed. **All killed.**

Orchestration (7): no-op guard removed, read-back skipped, unreadable → `[]`, drift never alerts,
`confirmed` ignores drift, listing-id guard off, changes never applied. **All killed.**

🟢 **The harness was controlled**, because 21 green verdicts from a broken detector would be
worthless: a **null mutation** (a comment only) reported **SURVIVED**, and a sanity mutation
(`price → 0`) reported **KILLED**. So the verdicts above are the tests' work, not the script's.
