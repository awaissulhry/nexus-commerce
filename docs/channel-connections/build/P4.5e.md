# P4.5e — a disconnect removes the Amazon Ads secrets it used to leave behind

State: **BUILT 2026-09-21**, committed locally. Part of P4.5 (advertising).

Plan row (FINAL-PLAN.md §6, P4.5): *"disconnect removes the old Ads secrets"*.
Plan §4.1: *"Disconnect calls the channel only for eBay. For Ads, the old per-profile
secrets stay, and with profiles OFF the Ads client falls back to them — **Ads calls
continue after a disconnect** (`services/advertising/ads-api-client.ts:463-491`)."*

## 1. Evidence — the row is true, and it is worse than "the secrets stay"

Traced in the source, end to end:

1. `services/cx/token.service.ts:revoke()` nulls **eight** token columns — all of them
   on `ChannelConnection` — and sets `isActive: false`.
2. `ads-api-client.credentialsFromCore()` calls
   `resolveConnection({ channel: 'AMAZON_ADS', primary: true })`. For an **inactive**
   row that throws `NoConnectionError`, which the function catches and turns into
   `return null` — correctly, since "no Ads grant on the core" is the ordinary
   pre-adoption state.
3. `resolveCredentials` then falls through to
   `prisma.amazonAdsConnection.findFirst({ where: { isActive: true } })` and reads that
   row's intact `credentialsEncrypted` — `{ clientId, clientSecret, refreshToken }`.

🔴 **The disconnect does not merely fail to revoke at the channel. It creates the exact
condition under which the legacy fallback fires.** The fallback is doing precisely what
it was written to do — a failure path whose premise stopped being true, which is the
shape P4.3e, P4.3b, P4.1e and P4.4c all had.

On the development database, **9 rows** carry a credential blob, and all 9 are
`isActive: true`. (Measured 2026-08-29 on production: the nine rows carry **one**
distinct blob between them.)

**Amazon Ads is the only channel with this shape.** A derived census of
`credentialsEncrypted` in `schema.prisma` finds three columns: `AmazonAdsConnection`,
`Carrier` and `CarrierAccount` — the last two are shipping carriers, not channels. A
test asserts that set, so a fourth appearing is news.

**Not a gap:** Amazon Ads has no `revokeUrl` on its spec, so `revokedAtChannel` is
always false for it. LWA revocation is done in the seller's own Amazon console; the
plan records it as "disconnect calls the channel only for eBay" and that stays true.

## 2. Changes

1. **New** `services/cx/legacy-channel-credentials.ts` —
   `clearLegacyChannelCredentials(channelKey)`. For `AMAZON_ADS` it nulls
   `credentialsEncrypted` on every row that carries one, and writes a sentence into
   `lastError` saying why the row has none. Every other channel: nothing.
2. `services/cx/token.service.ts:revoke()` calls it **after** the connection row is
   cleared, and records the result on the `disconnect` ledger event. Order matters:
   sweeping first and then failing the connection update would leave an account with no
   credentials and no disconnect.
3. Its failure is logged as an **error**, not a warning, and the disconnect still
   completes. This is the one place "best effort" is uncomfortable — a failure leaves a
   live secret — but an operator who has decided to disconnect must not be told it
   failed *and* left with a connected account.

### Why it clears the secret but does NOT deactivate the rows

With the blob gone and `isActive` untouched, `resolveCredentials` reaches
`if (!conn?.credentialsEncrypted) throw` and every ads call **refuses, loudly, naming
the profile**. That is what a disconnect should produce.

Deactivating as well would be quieter, and it would make a disconnect **irreversible
from the connect flow**: P4.5b deliberately stopped the reconnect callback reasserting
`isActive`, because that switch is the operator's and a reconnect is a credential
event. Telling "the operator switched this off" from "a disconnect switched this off"
would need a marker on the row — machinery for no gain, when the refusal already stops
the calls and a reconnect re-fills the blob on its `update` branch.

## 3. Proof

- **New** `services/cx/legacy-channel-credentials.p45e.vitest.test.ts` (10): the blob is
  nulled on every row carrying one; a sentence is left saying why; `isActive` is **not**
  in the update; every other channel is untouched; a database failure logs an error and
  does not fail the disconnect; a no-op run says nothing; `revoke()` calls it and calls
  it **after** the connection update; and the schema census.
- 🟢 **A positive control on the premise itself.** One test asserts the legacy fallback
  and its `no credentials for profileId` throw are **still in the client**. If the
  fallback were ever removed, this whole slice would be dead code — and a test that
  passes for that reason is the worst kind.
- **Mutation check** (made, run, restored, compared):

## 4. Production proof — OPEN

This can only be proven by **disconnecting the Amazon Ads account**, which is an
operator action on a live channel and needs the Owner's yes. It is not done here.

When it is: after `POST /api/accounts/:id/disconnect`, the `disconnect` connection
event carries `legacy: [{ table: 'AmazonAdsConnection', cleared: N }]`, every
`AmazonAdsConnection.credentialsEncrypted` is NULL, and the next ads job logs
`[ADS-LIVE] no credentials for profileId=…` instead of calling Amazon. A reconnect
restores all of it.
