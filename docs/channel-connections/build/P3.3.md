### 1.1 Two things that look like defects and are not

Both checked before being written down, because "sometimes it already works" (P2.6) is
as real a result as a finding.

- **eBay reports no headroom: 0 of 345.** `services/cx/rate-readings.ts` returns `null`
  for eBay unless the answer is a 429, and that is **correct** — eBay does not put
  quota on a call. It publishes remaining counts through a separate Analytics call
  (`getRateLimits`), which this installation has never made (0 occurrences in `src`).
  So the gap is a missing *source*, not a broken parser.
- **Amazon SP reads `x-amzn-RateLimit-Limit`**, which is a RATE, not a remaining count.
  A "how many left" for Amazon cannot be derived from it.

### 1.2 And a correction to a reading made earlier in the session

The eBay rows looked like a per-account gap — 6 of 345. They are not real traffic:

```
trading.AddFixedPriceItem  connectionId=null   statusCode=null  success=false
trading.VerifyAdd…         connectionId=conn-1 statusCode=null  success=false
developer/key_management…  apiz.sandbox.ebay.com   210 / 42 / 42
```

`statusCode` null, a `conn-1` account, a **sandbox host**, and counts that repeat in
multiples of 42 — these are local test runs writing to the development database.

**Of the 395 post-gateway calls, only the 48 Shopify ones are real.** The gateway ledger
is one day old and three channels send nothing until the switches in PROGRESS §5 are
thrown. That is the honest denominator for everything below.

## 3. The three rules that are really about not lying

The memory rule is "100% honest UI", and this screen has three places it could quietly
mislead.

### 3.1 A success rate over zero calls is `null`, never 100%

`successRate: total === 0 ? null : …`, and the tile renders `—`. A green **100%** on an
account that has made no calls is exactly the false green this programme keeps finding.

### 3.2 Unknown headroom says WHY, in the channel's terms

`rateHeadroom.note` is **always** a sentence, including when the number is known. For
eBay it reads:

> eBay does not report its quota on a call. It publishes the remaining counts through a
> separate Analytics call, which Nexus does not make yet.

A blank tile reads as "zero left" or as a broken panel. Both are wrong, and the second
costs someone an hour.

### 3.3 Headroom comes from the last call that REPORTED, not the last call

Shopify reports headroom on its GraphQL calls and not on every REST one. Reading "the
most recent call" would show *unknown* for an account Shopify is answering perfectly,
the moment a quiet endpoint answered last. The query filters
`rateLimitRemaining: { not: null }` and the reading carries its own `asOf`.

### 4.15 A gate caught this package on the way in

`scripts/check-route-prisma-ratchet.mjs` refused the first push:

```
❌ route-prisma ratchet: 1 route file(s) gained direct DB access:
   apps/api/src/routes/cx-connections.routes.ts: 3 → 4
```

The route looked the connection up itself (`channelConnection.findUnique`) before
calling the service. The gate's reason is the right one — *"business logic in an HTTP
handler cannot be extracted into a service later, the handler IS the coupling"* — so the
lookup moved into `accountCallsById`, which returns `null` for an unknown id and lets
the route answer 404 without knowing the table exists. The baseline was **not** touched.

## 5. The other half of the done-when — and why it is a handoff, not a build

The plan row's "Your yes" column says **"Studio side is the studio programme's"**, so
this package does not touch it. What it does do is report the one fact that side needs.

`_studio/channel-ops/syncQueue.ts` already names `ListingIssue`, in a list called
`DORMANT_SOURCES` — *"sources this console would show if they ever held data — named so
silence is not read as none"* — with the file header recording why:

> Measured on prod 2026-09-01: 37,846 rows, **2,553 dead** — while `ListingIssue`,
> `AmazonSuppression` and validation failures are all at ZERO. A four-pane console would
> have been three empty panes.

That measurement was right, and it matched this session's: `ListingIssue` held 0 rows.

**P3.2 changed it.** Amazon feed rejections, suppression, issue notifications, eBay
Trading failures and Shopify `userErrors` all write there now. So the studio console's
`rejections` source is **no longer dormant**, and its first pane can be built on real
rows rather than an empty table. That is the handoff, and it belongs to the studio
programme.
