# P4.2b — an eBay Inventory-API offer rejection reaches its listing

**Date** 2026-09-20 · **Package** P4.2 (Images), second slice · **Size** S

`build/P4.2a.md` §4 named this as measured-and-not-built, because it needed a
decision first. The decision is below, and it was decidable from P3.2's own
contract rather than by guessing.

---

## 1. The decision

`pushVariationGroup` — the Inventory-API publisher shared by the flat-file push
**and** the image publish — has **12 `results.push` sites**. They are two
different kinds of thing:

| Kind | Examples | Belongs on a listing? |
|---|---|---|
| **eBay's verdicts** | `inventory_item PUT 400: …`, `offer create 400: …`, `offer update 400: …` | **yes** |
| **Our validation** | *"No images found for this SKU"*, *"No `DE` price set for …"*, *"No existing offer — run Full Publish first"* | **no** |

P3.2's contract is *"a rejected change shows on the listing **in the channel's
words**"*. Our own validation is not the channel's words, and it already reaches
the operator as a per-row result in the push response. Filing it would dress our
message up as an eBay rejection on a screen whose whole point is "what did the
channel say".

**So four sites file and eight do not**, and the split is derived from source in
the test so it cannot quietly drift.

One site was judged and left out deliberately: *"eBay already has an offer for
this SKU at quantity 0 and the automatic quantity-raise failed …"*. It describes
eBay **state** plus an instruction of ours, not an eBay rejection of a change.

---

## 2. And a retryable answer is not filed

P3.1's rule, quoted in the recorder: *"a 429 or a socket reset is our problem to
retry, not a defect in the operator's listing, and filing them would bury the
four real rejections under a thousand throttles."*

`classifyChannelAnswer` marks a 5xx and eBay's own retry errorIds retryable, and
`recordVerdictOnListing` drops those. **The same file already marks `25604` and
`25001` `isTransientItemErr` and retries them itself**, so filing them would
contradict its own behaviour.

The answer is **classified**, not pasted: a raw JSON body on a listing row is not
"the channel's words" to an operator.

---

## 3. What was built

| Piece | What |
|---|---|
| `resolveEbayListingIdsBySku` | The Inventory API has **no ItemID** when an offer create is refused, so P4.1a's ItemID resolver cannot serve. The key is SKU + market + **account**, exactly as for Amazon. |
| `recordEbayOfferRejection` | classify → drop if retryable → resolve → file on **every** listing the SKU holds. |
| 4 call sites | The ones that hold an eBay HTTP answer, passing eBay's own `status` and `body`. |

The same three rules as every slice in this package: a named listing wins, never
resolve without the account, and a SKU may hold several listings so all are
filed. Filing is **in addition** to the per-row result, never instead of it — the
push response is what the operator is looking at when they press Publish.

**This covers the flat-file push too**, because both callers share
`pushVariationGroup`. One home, as in P4.1a, P4.1c and P4.1d.

## 4. The proof

**14 tests green** (`services/ebay-offer-rejection.p42.vitest.test.ts`), mostly
behavioural, with the four-site split derived from source.

**7 mutations, 7 named tests failed, every file restored byte for byte.**

```
✅ retryable answers are filed too (throttles bury real rejections)
✅ resolve without the account
✅ the market is dropped from the key
✅ only the first listing is filed
✅ the raw body is pasted instead of classified
✅ a filing call is removed from a verdict site
✅ our own validation is filed as an eBay rejection
7 guarded, 0 not guarded
```

The last one is the decision itself, guarded: adding a filing call beside *"No
`DE` price set"* fails the test that asserts our validation never reaches a
listing.

The retryable tests carry a **positive control** in the same block — the same
path DOES file a 400 — because "drops everything" would otherwise pass both.

🔴 **One mutation's label was wrong and the harness said so.** Replacing the
classifier with a hand-made verdict was expected to fail *"does not paste the raw
body"*; it actually failed **three** tests, led by *"files eBay's code and
message on every listing for the SKU"*. The rule was guarded; the label was not
accurate. It was corrected rather than the mutation being dropped — `mentions`
is checked precisely so a red that convicts the wrong thing is visible.

**Gates**

- `tsc --noEmit` — clean.
- Full API suite — `Tests 6 failed | 10222 passed | 127 skipped`; the documented baseline, attributed at clean `HEAD` in `build/P5.1.md` §3.
- Gateway ratchet — `{"EBAY":0,...}` (exempt 47), unchanged.
- Push-lock gate — 1 missing guard, the pre-existing `studio-publication-amazon.ts:164`.
