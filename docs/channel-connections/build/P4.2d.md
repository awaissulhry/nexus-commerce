# P4.2d — the image read-back sweep actually runs

**Date** 2026-09-20 · **Package** P4.2 (Images), correction to P4.2c · **Size** XS

---

## 1. 🔴 I reproduced the exact defect I was fixing

P4.2c's finding was that Amazon and Shopify had a read-back **function** and no
**habit**: nothing scheduled it, so drift stayed invisible until somebody opened
a screen.

P4.2c then shipped the sweep into `CRON_REGISTRY` **only**. A registry entry is a
**manual trigger** — that is the state P4.2c had just called the defect.

And it was reported to the Owner as:

> *"One variable, your call: `NEXUS_ENABLE_IMAGE_READBACK_SWEEP=true` starts
> detecting image drift on Amazon and Shopify, the way eBay already does."*

**That was wrong.** The variable alone would have changed nothing, because
nothing called it. The sweep would have sat there, switched on, never running —
and the switch would have read as "drift detection is on".

Caught while grounding the recommendation the Owner asked for, by checking what
actually schedules it. `readbackAllEbayLiveImages` has **both** a registry entry
and `ebay-image-readback.job.ts`; mine had only the first.

## 2. What was built

`jobs/image-readback-sweep.job.ts`, on eBay's shape so the two can be read side
by side, started at boot next to `startEbayImageReadbackCron()`.

**One switch, not two.** The cron is gated on the same
`NEXUS_ENABLE_IMAGE_READBACK_SWEEP` the sweep itself checks. Two switches for one
fact is the drift shape this programme keeps finding, and here it would produce
the worst outcome available: **a job that runs every six hours and returns "off"
every time.** A mutation invents a second flag and the test convicts it.

**Schedule `25 2,8,14,20 * * *`** — a different minute *and* different hours from
eBay's `45 */6 * * *`, so a deploy does not start both sweeps at once.

---

## 3. The proof

**7 tests green** (`jobs/image-readback-sweep.p42.vitest.test.ts`).
**5 mutations, 5 named tests failed, every file restored byte for byte.**

```
✅ the cron is never started at boot (registry-only again)
✅ a SECOND switch is invented for the cron
✅ it collides with eBay's schedule
✅ unconfigured is dropped from the summary
✅ the run is not recorded
5 guarded, 0 not guarded
```

The first mutation is the defect itself: remove the boot call and the sweep goes
back to registry-only, which is what P4.2c shipped.

**Gates** — `tsc` clean; API suite `Tests 6 failed | 10280 passed | 127 skipped`,
the documented baseline.

---

## 4. The recommendation the Owner asked for

**Turn it on.** `NEXUS_ENABLE_IMAGE_READBACK_SWEEP=true`.

The reason it shipped off was spend, and the spend is small. Measured on the
development database, parents and standalone only:

```
AMAZON : 13 products, 29 listings  → 29 getListingsItem reads per sweep
SHOPIFY:  1 product,   1 listing   →  1 read per sweep
```

⚠️ **That is the development database, not production** — production will be
larger, and nobody has counted it. But the shape is what matters: this is tens of
reads four times a day, against a `getListingsItem` quota of 5 requests a second,
bounded by `NEXUS_IMAGE_READBACK_MAX_PER_RUN` (default 400) and asking only for
the marketplaces a product is actually listed in. eBay's equivalent has been
running every six hours all along.

Against that: with it off, **image drift on Amazon and Shopify is invisible**
until somebody opens a product's images panel. That is the asymmetry P4.2c was
about, and leaving it off keeps the asymmetry.

**Env is the Owner's authority**, so the variable is theirs to set. It is one
line and it takes effect on the next deploy.

---

## 5. The lesson, banked

**Registry-only is a manual trigger, not a habit.** When the finding is *"nothing
runs this"*, the fix is not a registry entry — it is a schedule, and the check is
`grep` for something that CALLS it, not for something that DEFINES it. This
programme has now found that shape in Etsy's sync (P4.3a), in Amazon's and
Shopify's read-back (P4.2c) — and in P4.2c's own fix.
