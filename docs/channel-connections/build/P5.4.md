# P5.4 — Amazon buyer data: we do not ask for it, so we do not hold it

State: **COMPLETE 2026-09-21** — answered by measurement, with a guard to hold the
answer. Committed locally.

Plan row (FINAL-PLAN.md §6, P5.4): *"Amazon buyer data: use a Restricted Data Token
where we read buyer personal data — **or stop reading it if we do not need it**."*
Driver: **Policy**. Size S.

## 1. Evidence (measured 2026-09-21, development database)

Amazon redacts buyer personal data from `getOrders` / `getOrder` unless the call
carries a **Restricted Data Token** (`POST /tokens/2021-03-01/restrictedDataToken`).

**Nexus has never minted one.** A census of the whole `apps/api/src` tree finds
`createRestrictedDataToken` **once**: inside the gateway's `READS_SENT_AS_WRITES` set
(`services/gateway/amazon-sdk.ts:24`), which classifies the operation as read-shaped.
It is a name in a `Set`. There is **no call site**.

And the data agrees. Across **4,464** Amazon orders:

| column | rows with a value |
|---|---|
| `customerEmail` | **0** |
| `customerId` | **0** |
| `customerName` | 4,464 — **every one the literal string `'Amazon customer'`** |
| `shippingAddress` present | 3,908 |
| `shippingAddress` containing `AddressLine1` | **0** |

The stored address keys, by frequency:

| keys | orders |
|---|---|
| `City, CountryCode, PostalCode, StateOrRegion` | 2,879 |
| `City, CountryCode, PostalCode` | 1,013 |
| `City, CountryCode, County, PostalCode` | 13 |
| (three more, 1 each, adding `CompanyName`) | 3 |

That is exactly the **non-personal** subset Amazon returns without an RDT — city,
country, postcode, region — and it is what shipping cost and tax need. No street, no
name, no email, no buyer id.

**So the row is answered by its second branch: we do not read buyer personal data, and
we do not need to.** Nothing had to be built.

🟢 A counterweight, and the cleanest kind: the question was *"are we handling PII
correctly?"* and the answer is *"we are not handling it at all."*

## 2. 🔴 The risk runs the other way, and that is what was built

Three readers are written as if PII will arrive: `pickCustomerName`,
`pickCustomerEmail` (`services/amazon-orders.service.ts:125-136`) and the
`ShippingAddress` store. They look like an unfinished mapping.

If an RDT is ever added — for a genuine reason, or by someone "completing" those
readers — `Order.customerEmail` **silently starts filling with real buyer email
addresses**, into a column with no retention rule, no field-security decision and no
operator awareness. Nothing today would notice.

So the decision is written down twice and held once:

1. `services/amazon-orders.service.ts` — the readers carry the measurement and the
   reason. They were **kept rather than deleted**: they are the only place in the code
   that says we deliberately do not request restricted data, and deleting them leaves
   the question open for the next person to "fix".
2. **New** `services/amazon-buyer-pii.p54.vitest.test.ts` — a census over every
   non-test `.ts` file asserting that nothing mints an RDT, with the gateway's single
   operation-name occurrence as the one written exemption. Its failure message says
   what to do if it is intentional: give the data a retention rule first.

## 3. Proof

- **New** `services/amazon-buyer-pii.p54.vitest.test.ts` (6): nothing mints an RDT;
  nothing passes one as `x-amz-access-token`; the `'Amazon customer'` fallback (the
  real source of all 4,464 stored names) is intact; the email reader still yields `''`;
  the decision is written where the readers are, not only in a document.
- 🟢 **A positive control on the census itself** — that the gateway *does* still name
  the operation exactly once. Without it, the census passes just as well if the string
  vanished and the pattern matched nothing at all: `could not measure` wearing
  `measured empty`'s clothes, which this programme has now paid for three times.
- The census reads **code lines only**, so a comment naming the operation is
  documentation rather than a violation.
- **Mutation check** (made, run, restored, compared):
  | Mutation | Tests that failed |
  |---|---|
  | something mints an RDT | **1** |
  | the gateway's allowed occurrence disappears | **1** (the positive control) |
  | the email reader starts returning a value | **1** |
  | an RDT passed as `x-amz-access-token` | **1** |
- `tsc --noEmit` (apps/api): 0 errors.

## 4. Production proof — OPEN

Nothing changes: no behaviour was altered, only a comment and a new test.

The one open question is whether **production** matches dev. The dev database is a
copy, and the relevant measurement — `customerEmail` non-empty on 0 of 4,464 — would
be worth re-running there before this row is called closed for good. If production
holds buyer emails that dev does not, an RDT is being minted somewhere this census
cannot see (an env-driven SDK option, for instance), and that is news.
