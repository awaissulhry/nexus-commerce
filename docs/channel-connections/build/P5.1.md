## 1. What the plan said, and why it was not enough

> *P5.1 — Amazon Orders v0 → v2026-01-01 (`searchOrders`, `getOrder`). Set the
> version on every library call so it never falls back to the oldest one.*

The measurement found the plan's own instruction is close to a no-op, and that
the real job is four times bigger. Every number below is reproducible.

### 1.1 🔴 The version pin moves ONE operation, silently

`amazon-sp-api@1.2.1` defaults `version_fallback: true`. Walking the library's
own resolver (`_validateAndGetVersion`):

```
TODAY (no endpoints_versions)        endpoints_versions {orders:'2026-01-01'}
  getOrders           -> v0            getOrders           -> v0   ← still v0
  getOrder            -> v0            getOrder            -> 2026-01-01
  getOrderItems       -> v0            getOrderItems       -> v0   ← still v0
  confirmShipment     -> v0            confirmShipment     -> v0
  updateShipmentStatus-> v0            updateShipmentStatus-> v0
  getOrderBuyerInfo   -> v0            getOrderBuyerInfo   -> v0
  getOrderAddress     -> v0            getOrderAddress     -> v0
  getOrderRegulatedInfo->v0            getOrderRegulatedInfo->v0
  updateVerificationStatus->v0         updateVerificationStatus->v0
  getOrderItemsBuyerInfo->v0           getOrderItemsBuyerInfo->v0
  searchOrders        -> 2026-01-01    searchOrders        -> 2026-01-01
control listingsItems.getListingsItem -> 2021-08-01
```

Nine of eleven fall back to v0. **No error, no warning, no log line.** Of the
three Amazon Orders operations our source actually calls — `getOrders`,
`getOrder`, `getOrderItems` — the pin fixes exactly one.

### 1.2 🔴 The version has to go in `options`, not at the top level

`SellingPartner.callAPI` reads `req_params.options.version`
(`SellingPartner.js:618,623`). A top-level `version` key is accepted by the
object and **dropped on the floor**: 2026-01-01 query parameters would go to the
`/orders/v0/orders` path. The first draft here had it at the top level and
TypeScript caught it only because the library's `ReqParams` happens to be a
closed type. This is "an API can accept a flag it IGNORES" in its purest form,
and it now has its own guard.

### 1.3 🔴 2026-01-01 is not a rename — it is a different object model

| v0 | 2026-01-01 |
|---|---|
| `AmazonOrderId` | `orderId` |
| `PurchaseDate` / `LastUpdateDate` | `createdTime` / `lastUpdatedTime` |
| `OrderStatus` (`Shipped`, `Canceled`) | `fulfillment.fulfillmentStatus` (`SHIPPED`, `CANCELLED`) |
| `FulfillmentChannel` (`AFN`/`MFN`) | `fulfillment.fulfilledBy` (`AMAZON`/`MERCHANT`) |
| `OrderTotal` | `proceeds.grandTotal` |
| `MarketplaceId` | `salesChannel.marketplaceId` |
| `BuyerInfo` / `ShippingAddress` | `buyer` / `recipient.deliveryAddress` |
| `IsPrime` / `IsBusinessOrder` | membership of `programs[]` |
| `NextToken` | `pagination.nextToken` |
| a separate **`getOrderItems`** call | `orderItems` **on the order** |

And **three envelopes in one migration**: v0 wraps in `payload`, `searchOrders`
puts the list at the top level under `orders`, and `getOrder` wraps a single
order in `order`. Reading the wrong one gives an object whose every field is
`undefined` and no error — the P3.1 double-encoding failure in a new place.

### 1.4 🔴🔴 The money defect this would have shipped

Amazon's own example response, quoted:

```
quantityOrdered: 2
product.price.unitPrice.amount           = "49.99"   ← PER UNIT
proceeds.breakdowns[type=ITEM].subtotal  = "99.98"   ← the LINE total
```

v0's `ItemPrice.Amount` is the **line total**. `upsertOrderItem`
(`amazon-orders.service.ts`, comment DA-RT.15) **divides it by
`QuantityOrdered`** because of exactly that, and says so:

> *"SP-API's ItemPrice.Amount is the LINE TOTAL across QuantityOrdered units,
> NOT per-unit. … Divide by quantity to get the per-unit price before storing."*

So the obvious mapping — `ItemPrice ← product.price.unitPrice` — makes the
ingest divide an already-per-unit price a **second** time. Fuel, measured on the
development database:

```
OrderItem rows: 4,591 · quantity > 1: 38
  qty 2: 36 lines   qty 4: 1 line   qty 8: 1 line
```

Those 38 lines would have been stored at half, a quarter and an eighth of their
real price, and `DailySalesAggregate` and the forecasting tier read that column.
Nothing would have thrown.

`lineTotalOf` therefore takes the **ITEM proceeds breakdown** first, falls back
to `unitPrice × quantityOrdered`, and returns **nothing** rather than a bare
unit price.

The second line of Amazon's example is quantity 1, where the unit price and the
line total are the same number — the coincidence arm. A rule proven only on that
line looks right while being wrong, so the two arms are kept apart in the test.

### 1.5 🔴 The status vocabulary falls into a silent `default`

`mapStatus` switches on the v0 spelling and ends `default: return 'PENDING'`.
v0 says `Shipped` / `Unshipped` / `Canceled` (one L); 2026-01-01 says `SHIPPED` /
`UNSHIPPED` / `CANCELLED` (two L). Passing the new strings through would have
turned **every shipped and every cancelled order into a pending one**, without a
word. Converted at the boundary, with a case per status.

### 1.6 🔴 P2.2 re-armed under a new name

P2.2 found `fulfillmentType` reading `'MFN'` on **1413/1413** real payloads when
the truth was AFN on 1071. In 2026-01-01 the same fact is spelled
`AMAZON`/`MERCHANT`. Left unmapped, that defect comes straight back.

### 1.7 A screen was already claiming the work was done

`services/cx/connectors/amazon-sp/spec.ts` reported
`apiVersion: 'orders-2026-01-01 · …'` while every Orders call went to v0. The
CX connections screen showed the operator a version we did not use. It is a
getter now and reports `orders-v0` until the switch is on — a switch that is off
must not read as work that is done.

## 2. What was built

| File | What |
|---|---|
| `services/marketplaces/amazon-orders-2026.ts` **(new)** | The whole migration in one file: the 2026-01-01 wire types, the two vocabulary maps, and the conversion **back into the v0 `AmazonOrderRaw` shape**. |
| `services/marketplaces/amazon.service.ts` | `fetchOrders` → `searchOrders`; `fetchOrderById` → `getOrder` 2026-01-01; `fetchOrderItems` reads the items that came with the order. Each arm behind the switch. |
| `services/channel-reconciliation.service.ts` | The hardcoded `/orders/v0/orders` walk reads whichever version is on. |
| `services/cx/connectors/amazon-sp/spec.ts` | The reported API version is derived, not asserted. |
| `test-support/amazon-orders-2026-example.json` **(new)** | Amazon's own `200` examples, copied verbatim from the published model. |

**The design choice: normalise at the boundary, do not spread the new shape.**
Fourteen files read the v0 shape and every historical `Order.raw` row in the
database holds a v0 payload. One file knows both vocabularies; nothing
downstream changes, and the stored history stays readable.

`includedData` asks for `PROCEEDS, FULFILLMENT, RECIPIENT, BUYER` — exactly what
the v0 shape needs, and no wider than what Orders v0 already returns today.
(`BUYER` is buyer personal data; the Restricted Data Token is P5.4.)

**Nothing invents a value.** A section left out of `includedData` is "not
asked", not "empty": an absent `fulfillment` gives no `OrderStatus`, an absent
`programs` leaves `IsPrime` **unset** rather than `false` — `false` would read as
"Amazon says this is not a Prime order", which it never said.

## 5b. ✅ THE PROBE RAN — 2026-09-21, and it found a real defect

The Owner chose option B below (*"one captured live read before the switch goes on"*) and asked
for it to be run in the browser. It was, against the **Xavia Racing** profile — the legacy

### 🔴🔴 The finding: page 2 was broken

Amazon's answer to the second page, live:

> **"The input you have submitted is not valid. One and only one of `createdAfter` or
> `lastUpdatedAfter` must be provided."**

`amazon.service.ts` sent page 2 as `{ paginationToken, includedData }` and **nothing else** — the
probe sent byte-for-byte the same shape, which is why the answer convicts production and not the
probe. **The window is not remembered by the cursor; it must be repeated on every page.**

So with the switch on, an order sync would have fetched page 1 and then **failed on page 2**.
`nextTokenPresent` was `true` on the very first call, so a second page genuinely exists.

**Why nothing caught it:**

- **Production never could** — the switch has never been on.
- **No test could** — every existing stub returns a **single page with no
  `pagination.nextToken`**, so the pagination branch was **unreachable in tests**. *The arm that
  would have failed is the one never run.*

**Fixed:** page 2 is now `{ ...query2026, paginationToken: nextToken }`. New test
`amazon-orders-pagination.p51.vitest.test.ts` drives two real pages against a stub that
**enforces Amazon's own rule** (and a 🟢 positive control proves the stub enforces it, so the test
cannot pass against a permissive fake). Restoring the exact original defect as a mutation:
**KILLED**. The probe was updated too — it must keep sending what production sends, or it stops
being a control.

### ✅ THE MONEY QUESTION IS SETTLED — live, on a real 4-unit order

```
chosenHasMultiQty: true
qty: 4   ItemPrice: 72.08 EUR   wouldStoreUnitPrice: 18.02
```

**72.08 ÷ 4 = 18.02.** `ItemPrice` carries the **LINE TOTAL**, exactly as v0 did and exactly as
`upsertOrderItem` assumes when it divides by the quantity. The mapping is correct.

Had it been wrong — `ItemPrice ← unitPrice` — the same order would have read
`ItemPrice 18.02, qty 4, wouldStore 4.505`: **a quarter of the real price**, which is precisely
the failure P5.1 §4 was built around (38 dev-database lines at ×2, ×4 and ×8).

### 🔴 It took three attempts, and the two failures are the lesson

| window | orders | with items | **with qty ≥ 2** | verdict |
|---|---|---|---|---|
| 7 days | 9 | 9 | — *(not yet measured)* | qty 1 → **unanswerable** |
| 14 days | 20 | 20 | **0** | **unanswerable**, and it said so |
| **30 days** | 20 | 20 | **1** | ✅ **answered** |

1. **The first answer looked clean and proved nothing.** `qty 1, ItemPrice 81.15,
   wouldStoreUnitPrice 81.15` — equal under **both** the correct mapping and the defect. At
   quantity 1 a line total *is* the unit price. That is *a fixture PINS a dimension* arriving in
   **live data**: the order the probe happened to pick held constant the very thing the claim was
   about.
2. **Only 1 order in 20 had a multi-quantity line, and none in 14 days.** This seller sells
   one-at-a-time almost always. A probe that reported "the newest order" would never have answered
   this, however many times it ran.

So the chooser prefers a **quantity ≥ 2** order and reports `chosenHasMultiQty: false` when it
cannot find one — *"still unanswered"*, never *"answered and fine"*. That distinction is what
turned attempt 2 from a false pass into an honest miss.

### A suspicion checked and cleared

Attempt 2 returned `qty: 0` on the chosen line, which would divide by zero on the money path.
It does not: `upsertOrderItem` reads `const qty = item.QuantityOrdered || 1` and then
`qty > 0 ? lineTotal / qty : 0` — two guards. Checked rather than assumed, and clean.

### 🔴 What the probe did NOT settle, and why (superseded above — kept as the record)

**The money.** `ItemPrice` must be the **line total** (v0's meaning), because `upsertOrderItem`
divides by quantity — the finding this whole slice was built around.

It could not be checked: the probe reports items for **the first order of a moving 7-day window
only**, and across nine calls that order had **no `orderItems`** in the response — so our mapper
correctly produced none. An early call *did* show `orderItems[].product.price` in the paths, which
is how the calls after it were worth making, but by then the first order had changed.

⚠️ **A wrong conclusion was drawn and corrected here:** one call's path list was read against a
later call's item count, and the two came from **different orders**. The check that caught it was
comparing both numbers *in the same response*. A claim must match its measurement, and two calls
are two measurements.

**So the money question stays open**, and the switch stays **off**. What would close it: a probe
that reports the first order **that has items**, rather than the first order. That is a small
change to the probe and needs no new permission — it is not done here because the Owner's
instruction was to run the probe, not to rebuild it, and ~9 live Amazon calls in two minutes is
already more than this question deserved in one sitting.

## 5c. ✅ THE MONEY QUESTION IS ANSWERED — 2026-09-21, live

**`ItemPrice` is the LINE TOTAL. The mapping is correct and the money path is safe.**

Measured in the browser against **Xavia Racing** (the legacy workspace), on build `0adbf6e8`,
`GET /backend/api/admin/amazon-orders-2026-probe?days=30`. Every number below comes from **one
response and one order** — the correction §5b had to make.

| field | value |
|---|---|
| `SellerSKU` | `normal-knee-slider-yellow` (`B0C3YT5BM5`) |
| `QuantityOrdered` | **4** |
| mapped `ItemPrice.Amount` | **72.08 EUR** |
| `wouldStoreUnitPrice` | **18.02 EUR** |
| mapped `OrderTotal.Amount` | **87.94 EUR** |

### Why this is decisive, where §5b's answer was not

`OrderTotal` is an **independent field** — `proceeds.grandTotal`, not the item breakdown — so it
arbitrates between the two readings, and the two hypotheses are a **factor of four** apart:

```
ItemPrice is the LINE total   72.08 × 1.22 (IT VAT 22%) =  87.94   ← OrderTotal, to the cent
ItemPrice is the UNIT price   72.08 × 4 × 1.22          = 351.75   ← refuted
```

72.08 ÷ 4 = **18.02** exactly, which is what `upsertOrderItem` would store per knee slider. A
knee slider at €18.02 is an ordinary price; at €72.08 it is not. The arithmetic, the independent
total and the plausibility all agree.

**Amazon's published model is now confirmed by Amazon's own traffic.** §1.4 read the semantics off
the published example (`quantityOrdered: 2`, `unitPrice 49.99`, `ITEM subtotal 99.98`). This is the
same rule holding on a real order at a quantity the model never showed.

### What made the difference, and it is the generalisable part

**The dimension the claim is about must be the one that VARIES.** Nine live orders answered
"quantity 1", where a line total and a unit price are the same number — consistent with the
correct mapping *and* with the defect. The probe was not broken; it was **reporting on the one
arm that cannot discriminate**. One order in twenty carried a quantity of 4, and that single
order settled a question nineteen others could not touch.

`ordersWithMultiQty: 1` of 20 is the measurement that makes the answer readable: it says the find
was **rare, not routine**, so a future run that reports `chosenHasMultiQty: false` is *"ask again
later"*, not *"something regressed"*.

### The second open question, also closed

**Page 2 works.** `answered.page2 = { attempted: true, ok: true, orders: 20 }` — the
`createdAfter`-on-every-page fix from §5b, proven on live Amazon data rather than on a stub. And
`marketplaceIdsAccepted: true`, as before.

## 6. For the Owner — two options, and a pick

Both are one line of configuration. Nothing else in the system changes.

**A. Turn the switch on in production and let the nightly order sync prove it.**
Set `NEXUS_ENABLE_AMAZON_ORDERS_2026=true`. The next Amazon order poll calls
`searchOrders`. If the mapping is wrong anywhere, orders ingest with a wrong
status or a wrong total — the money path. Reversible by unsetting the variable,
but rows already written stay written.

**B. Leave it off. Come back to it before 2026-12-15 with one live read first.**
A single `searchOrders` call against the real account, its response captured, and
the mapping checked against a real payload instead of Amazon's example. That is
a live channel call and needs your yes.

**I would take B.** The deadline is 2027-03-27 and the target is 2026-12-15 —
there is no time pressure, and the two open questions in section 4 are exactly
the kind a single captured response answers for good. The whole migration is
built and guarded; what it lacks is one real payload. Turning it on blind puts
order totals and order statuses at risk to save three months of waiting.
