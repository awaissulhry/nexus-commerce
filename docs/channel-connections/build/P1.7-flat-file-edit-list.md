## 2. The two changes proposed

**Change 1 — NOT NEEDED (see the correction above).** The original text follows for the record: the push lock (safety, no cost). After the wrong-account guard, read the controls for the submitted SKUs (`readPushControls({ channel: 'AMAZON', skus, allowAbsent: true })`) and refuse the rows whose listing is paused, closed or ended, exactly as `channel-batch/amazon-batch-feed.service.ts:279` already does. Refused rows join the existing `skippedRows` list with the refusal sentence, so the operator sees which rows and why.

**Change 2 — Amazon's own dry run per row.** Before the feed document is created, run `amazonContentRefusal` (`services/amazon/validate-before-send.ts`, built in P1.7) for each message the route already built, with that row's `sellerId`, `sku`, `productType` and attributes. A row Amazon refuses joins `skippedRows` with Amazon's own sentence; the other rows are submitted as before.

**Cost of change 2:** one extra API call per row, before the feed. Amazon's Listings Items API allows about 5 calls a second, so a 500-row sheet adds roughly a minute and a half before the feed starts. A 20-row sheet adds about 4 seconds.

## 3. Your options

- **A — both changes.** The safest: no row reaches Amazon that Amazon itself would reject, and the push lock finally covers this route. Big sheets take longer to submit (see the cost above).
- **B — change 1 only.** The push lock costs nothing and closes the safety gap; the preview stays off here, and this route keeps the P1.7 exception.

**My pick: A**, with the preview skipped automatically for a sheet above a row count you choose (suggested: 200 rows, where the wait passes half a minute). That keeps every ordinary sheet fully checked and never makes a big submission unusable.
