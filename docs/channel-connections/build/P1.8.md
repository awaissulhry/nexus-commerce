# P1.8 — the nightly contract run

State: **BUILT (2026-09-20), committed locally (not pushed, not deployed). OFF until the Owner turns it on.**

Plan row (FINAL-PLAN.md section 13.7, P1.8): *A nightly contract run against each channel's sandbox (Amazon SP-API sandbox, eBay sandbox, a Shopify development store, the Amazon Ads test account). One read and one dry-run write per gateway operation. Etsy has no sandbox: use a test listing on the real shop, marked "test". Done when: runs every night; a channel change turns it red before it reaches a live listing.*

## 1. Why it exists

Our fixture tests replay answers we recorded ourselves. A field a channel renames, or an error vocabulary it changes, stays green in those tests and turns red on the seller's account. This run asks the real channel, on its sandbox, and reads the **shape** of the answer.

## 2. Change

- `services/contract/channel-contracts.ts` — what is checked, one entry per operation: eBay inventory read, eBay `VerifyAddFixedPriceItem` (the channel's own dry run), Amazon marketplace participations, Amazon Ads profiles. Each entry owns its assertion sentence, so a failure says what changed, not "it broke".
- `services/contract/contract-run.service.ts` — the runner, with two rules it enforces itself:
  1. **every call goes out as `kind: 'read'`** (a read or the channel's own dry run), so a contract run can never change a listing anywhere;
  2. **the URL must resolve to a sandbox host** (`sandboxUrlOf`); a channel with no sandbox host is reported as *not configured* with its reason, never as green.
- A gateway refusal (account needs sign-in, rate bucket, publish gate) is a **failed** check: the run says "this could not be proven tonight" rather than passing quietly. Green needs at least one check to have actually run.
- `jobs/channel-contract.job.ts` — nightly at 03:20 (`NEXUS_CHANNEL_CONTRACT_SCHEDULE`), recorded through `recordCronRun`, so a red run is red in the cron record too. Also runnable from the sync-logs hub as `channel-contract-run`.

**Off until the Owner turns it on:** `NEXUS_ENABLE_CHANNEL_CONTRACT_RUN=true` and one sandbox account per channel — `NEXUS_CONTRACT_ACCOUNT_EBAY`, `…_AMAZON_SP`, `…_AMAZON_ADS`, `…_SHOPIFY`, `…_ETSY` (plus `NEXUS_CONTRACT_AMAZON_SELLER_ID`). With the switch off nothing is scheduled and nothing is sent.

## 3. Proof

`services/contract/contract-run.p18.vitest.test.ts` (10) and `contract-run.sandbox-host.p18.vitest.test.ts` (1):

- every call is a read, on a sandbox host, as the named sandbox account, with a `contract.*` ledger name;
- a channel with no account named: not configured, nothing sent for it, and the sentence names the variable to set;
- nothing configured at all: `not-configured`, never green, zero calls;
- Shopify and Etsy are reported with their reason, not silently missing;
- a renamed field (eBay `inventoryItems` → `items`), an HTTP 503, a gateway refusal, and a Verify answer with no `<Ack>` each turn the run red with a sentence naming the check;
- **a channel with no sandbox host is refused and nothing is sent to the live host** (proven with a stood-in contract list, so the rule is exercised rather than the current list).

Mutation checks **7/7 caught**: a check sent as a write; the production host used when there is no sandbox; an unconfigured channel run anyway; "nothing configured" reported as green; a gateway refusal passed quietly; the eBay answer shape unchecked; a renamed inventory field accepted.

`tsc` clean. Gateway ratchet 0.
