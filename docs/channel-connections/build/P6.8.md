## 2. What was built

`callbackReadinessAlert` in `services/cx/channel-alerts.service.ts`, raised by the
existing 15-minute alert sweep:

- **no redirect URI at all** → *"has no sign-in callback registered"*;
- **every redirect URI is a development tunnel** → *"…is a development tunnel"*, naming
  the host;
- **a real URI beside a dev one** → nothing. A tunnel kept for local work is not a
  production problem, and an alert nobody can act on is noise;
- **sandbox** → nothing, ever. A sandbox app *should* point at a tunnel.

It knows ngrok, `loca.lt`, localhost, `127.0.0.1`, trycloudflare and serveo.

### 🔴 The bug this slice caught in its own first draft

The alert sweep's query was `where: { secretExpiresAt: { not: null } }`, which P6.2 had
just widened to an `OR` with `signingKeyExpiresAt`.

**Shopify and Etsy have both dates NULL** — so the rows this check exists for would
**never have been selected**, and the alert would have been dead on arrival. It is the
same defect P6.2 had found in the same query an hour earlier, in a new shape:
*selecting on the presence of a date is how a row with nothing set stays invisible.*

The filter is now `where: {}` — five rows, read them all — and each alert keeps its own
guard, so removing the filter cannot fire a secret-expiry alert on a null date.

**Why an alert and not a gate:** this is **data**, not source. A pre-push check reads
files; it cannot see a `ChannelApp` row.

### 🔴 This CONTRADICTS §1 above, and the live reading wins

§1's table says production holds a `ChannelApp` row for **ETSY** (with an ngrok redirect URI) and
one for **SHOPIFY** (with an empty `redirectUris`). It cannot be both.

`oauthConfiguration` raises that exact sentence from **one** place — the `catch` around
`getChannelApp(channelKey, environment)` — and `getChannelApp` throws
`ChannelAppConfigurationError` from **one** place: the `else` branch, reached only when there is
**no row** *and* `envSeed(key)` returns null. The other `channel_unavailable` in that function
says *"connect is not available yet"* and both specs carry `available: true`, so it is not that
one. **There is no row.**

§1 says *"measured 2026-09-21"* and does **not name the database** — where `build/P5.2.md` §1 and
`build/P5.1.md` §1.4 both say *"development database"* explicitly. The most likely reading is that
§1's table describes the **development** database. It is left standing above rather than edited,
because a record that quietly changes its own evidence teaches nothing; this section is the
correction. **Name the database in every row count.**

### What actually unblocks it — and it is one step, not two

`getChannelApp` reads the `ChannelApp` row **first** and falls back to **environment variables**;
`seedChannelApps()` runs at boot and creates the row from those variables for any channel that has
them and no row yet. So setting the variables on the `@nexus/api` service and restarting does both.

| channel | variables `envSeed()` requires |
|---|---|
| **ETSY** | `ETSY_API_KEY` (Etsy's *Keystring*) · `ETSY_SHARED_SECRET` |
| **SHOPIFY** | `SHOPIFY_APP_CLIENT_ID` · `SHOPIFY_APP_CLIENT_SECRET` · *(optional)* `SHOPIFY_APPROVED_SCOPES` |

Both names are **exact**, and neither matches what `ConfigManager` looks for — that is a separate,
legacy reader, and satisfying it does not satisfy this one.

**Then, and only then, §4's portal registration applies:** the redirect URI Nexus sends is
`callbackUrlFor(key)` = `${NEXUS_PUBLIC_API_URL || PUBLIC_API_URL}/api/cx/callback/<key>`. The API
service answers on two hosts — `api.xavia.it` (custom) and
`nexusapi-production-b7bb.up.railway.app` — so the value registered at Etsy and Shopify must match
whichever one `NEXUS_PUBLIC_API_URL` holds, **character for character**, or consent succeeds and
the return trip fails.

🔴 **Railway variable VALUES cannot be read from a session here** (the auto-mode classifier refuses
it), so `NEXUS_PUBLIC_API_URL` is named, not quoted. Confirm it before registering.

### 🔴🔴 Shopify refused two of our own scopes

Pasting `SHOPIFY_REQUIRED_SCOPES` into the version form, Shopify answered:

> **Contains invalid scopes: `read_payment_mandate`, `write_payment_mandate`**

and **accepted the other 91 in the same submission**. That is the vendor validating the entire set
at once — evidence no test here could have produced.

It is the dashboard's **invalid** message, not its separate *"Some scopes require Shopify
permission"* one, so these are **not review-gated**. They do not exist.

🔴 **Why it mattered before anyone pressed Connect.** These travel in the `scope` parameter of
`/admin/oauth/authorize`. One name a channel does not recognise can refuse the **whole** consent
request — which is the 2026-09-16 eBay outage exactly: two plausible-looking scope names off the
keyset broke **every** eBay connect for **nineteen days**. The same trap, a second vendor, caught
this time by the vendor's own form before a single seller saw it.

Both removed. **4 mutations killed, 1 null control survived**, and the tests pin **no count** — a
hardcoded total goes stale the first time a scope is legitimately added, and then it is either
bumped without thought or deleted. What is pinned is the shape of the mistake: the refused pair
absent, their accepted neighbours present as the control, no duplicates, and no review-gated scope
promoted into the required set.

⚠️ Two of the mutation patterns matched **0 places** on the first attempt and reported 14 passed —
