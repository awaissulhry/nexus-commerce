**Date** 2026-09-20 · **Package** P4.2 (Images), first slice · **Size** S

## 1. What was measured

The P4.2 row includes *"Image rejections into `ListingIssue`"*. Measured, per
image publish service — the count is calls to any recorder:

```
images/amazon-image-feed.service.ts          0
images/ebay-inventory-image-publish.ts       0
images/ebay-shared-image-publish.ts          0
images/shopify-live-images.service.ts        0
```

**No image publish on any channel filed a single issue.** And P3.2's feed
recorder, `recordFeedReportIssues`, had exactly **one** caller —
`amazon-flat-file-feed.service.ts`.

Meanwhile the image feed **already builds a structured per-SKU receipt** carrying
Amazon's own codes and messages (`IA.3`, `PerSkuReceipt { sku, asin, accepted,
errors[] }`), and stores it on `AmazonImageFeedJob.resultSummary.perSku` for a
drill-down screen.

So an image rejection was parsed, structured, stored — and visible only to
somebody who opened that one job row. **Third time in two packages: the recorder
existed, the issues existed, nobody joined them.**

Two of the four are already answered:

- `ebay-shared-image-publish.service.ts` sends through `callTradingApi`, whose
  failure path **P4.1a** now resolves the listing for. Covered, and a test here
  asserts it must **not** grow its own recorder call.
- `shopify-live-images.service.ts` is a READ (a refresh), not a publish. Nothing
  to file. (It is also the P5.3 file that has almost certainly never run in
  production — no `SHOPIFY_*` variable exists there.)

## 2. What was built

One call, from where the receipt is built, into the recorder that already exists.

| Rule | Why |
|---|---|
| `recordFeedReportIssues`, **not** a fourth copy of the lifecycle | It already resolves one SKU to MANY listings, files on all of them, and reports the ones it could not place. |
| Source `amazon-feed` — a **MERGE** source | An image feed speaks only about the images it carried. `listings-api` REPLACES and would close content rejections the feed never mentioned. The test reads P3.2's `REPLACE_SOURCES` to confirm, rather than assuming. |
| `marketplace` added to the job's `select` | It is what joins a rejected SKU to its listing. Without it the receipt can be built and never filed. |
| Only the **rejected** SKUs | An accepted SKU has nothing to say. |
| 🔴 **Amazon's `attributeNames` are carried through** | `ListingIssue` is keyed on `code + sorted attributeNames`. With the attribute empty, distinct rejections on one SKU share one fingerprint and the rest vanish — P3.2 measured exactly that: **140 real rejections would have collapsed to 60 rows**. The receipt flattens the attribute away, so it is re-indexed from the raw report by code. |
| Unmatched SKUs are **logged** | `AmazonImageFeedJob.marketplace` may be the literal string `'ALL'`, which matches no `ChannelListing.marketplace`. Every SKU then comes back unmatched — and that must be a **measurement**, not a silence. |
| Never throws | An issue row reports on a publish; it is not part of one. |

## 3. The proof

**14 tests green** (`services/images/amazon-image-issues.p42.vitest.test.ts`).

**6 mutations, 6 named tests failed, every file restored byte for byte.**

```
✅ the filing call is removed
✅ files as a REPLACE source (closes content rejections)
✅ accepted SKUs are filed too
✅ the attribute is dropped (140 issues collapse to 60)
✅ unmatched SKUs become a silence
✅ the marketplace is not selected
6 guarded, 0 not guarded
```

### 🔴 3.1 The attribute rule was NOT guarded at first

The first mutation run reported **5 guarded, 1 not**:

```
❌ the attribute is dropped (140 issues collapse to 60)   ran=true failed=false
```

The assertion was `toContain('attrsByCode')` and `toContain('attributeNames')`.
Replacing the expression with `attributeNames: []` leaves both names in the file,
so the rule was removed and the test stayed green — the **same weakness P4.1e
found** the hour before, in a different file.

A shape test cannot carry this rule, because this rule is about a **value**. The
adapter was exported and given a **behavioural** test: three distinct rejections
on one SKU, each with its own Amazon attribute, asserted to produce **three
distinct fingerprints** rather than one. The mutation convicts now.

That is the discriminator stated plainly: without the attribute, `90220::`,
`90221::` and `90222::` are still three codes — it is the *collapse within one
code* that loses rows, so the test asserts the attribute **per issue**, not merely
that some attribute exists.

## 4. What is still open — P4.2b, measured and NOT built

**eBay's Inventory-API image publish has the same gap**, and closing it needs a
design decision this slice deliberately did not guess.

`images/ebay-inventory-image-publish.service.ts` publishes through
`pushVariationGroup`, which returns `{ sku, market, status: 'PUSHED' | 'ERROR',
message }`. There are **12 `results.push`** sites in that function and they are
**two different kinds of thing**:

- **eBay's verdicts** — `offer update 400: …`, `inventory_item …` — which are
  genuine listing rejections and belong on the listing;
- **our own refusals** — *"No images found for this SKU"*, *"No `DE` price set"*,
  *"No existing offer — run Full Publish first"* — which are our validation, not
  eBay's.

Filing all `ERROR` rows would put our own validation messages on the listing as
channel rejections. P3.1's classifier already draws this line for the gateway
path; the question is whether these in-function messages should go through it, or
whether the two kinds should be separated at the `results.push` sites.

**That is a design decision, so it is recorded rather than guessed.** The same
change would cover the flat-file push too, since both callers share
`pushVariationGroup` — which is the "one home" pattern P4.1a, P4.1c and P4.1d all
used, and the reason it is worth doing properly rather than quickly.

Also still open for P4.2 as a whole: the R-5 census, the eBay Media-API decision
(our own URLs vs eBay-hosted copies, R-1), and read-back per channel.
