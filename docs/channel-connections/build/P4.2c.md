## 1. The census row, and it is a COUNTERWEIGHT

P4.2 opens with *"Finish the census (R-5). One image publish per channel, through
the gateway and the gate."* Measured: **every image publisher already goes
through the gateway and a publish gate.** The proof is the gateway ratchet
standing at `{"EBAY":0,"AMAZON_SP":0,"AMAZON_ADS":0,"SHOPIFY":0,"ETSY":0}` —
zero channel sends outside the gateway, with 47 written exemptions.

🔴 **My own first census said otherwise, and it was wrong.** A grep for a
hand-written list of gateway and gate names reported
`images/amazon-media-publish.service.ts` as `gateway-ish:0 | gate-ish:0`. It
reaches both through `amazon-media-client.ts` (`amazonMediaClient`,
`amazonMediaWriteRefusal`), which my pattern list did not name. **A census built
from a hand-written pattern list is a set claim, and that one was false.** The
ratchet — which is derived, not hand-written — was right all along.

## 2. The real gap: read-back has the capability, not the habit

| Channel | Function | Scheduled | On demand |
|---|---|---|---|
| eBay | `refreshEbayLiveImages` + `readbackAllEbayLiveImages` | **yes**, every 6 h | yes |
| Amazon | `refreshAmazonLiveImages` | **no** | yes — a route, and the adopt service |
| Shopify | `refreshShopifyLiveImages` | **no** | yes — a route |

**A read-back that only runs when somebody opens a screen cannot detect drift.**
It confirms what the person is already looking at. Drift is precisely the case
where nobody is looking: the channel changed and we did not.

So Amazon and Shopify had the capability and no habit.

## 3. What was built

`services/images/live-image-readback.service.ts` — sweeps for both channels on
eBay's shape (parents and standalone only, sequential, a countable summary), plus
an `image-readback-sweep` cron-registry entry.

Two deliberate differences from eBay's:

1. 🔴 **Amazon reads per SKU per MARKETPLACE.** An unbounded sweep multiplies by
   the number of markets, so it asks only for the marketplaces a product actually
   has an Amazon `ChannelListing` in — never the whole list of five — and a cap
   bounds the run. The summary reports `eligible` (products) beside `scanned`
   (reads), so the multiplier is visible rather than hidden.
2. 🔴 **`unconfigured` is counted separately from `empty`.** Shopify's refresh
   self-skips with `NO_CREDS`, and P2.4 measured that production has **no
   `SHOPIFY_*` variable at all** — so in production that is the expected outcome,
   and it must not read as a clean sweep. Amazon reports it too when the profile
   has no seller account, which is the shape of the mistake I made earlier today.
   *"It ran and found nothing"* and *"it could not run"* are different answers.

A truncated run says `capped`, so a partial sweep cannot look complete. One
product failing is counted and the sweep carries on.

### Off by default — and why

`NEXUS_ENABLE_IMAGE_READBACK_SWEEP=true` turns it on. It ships **off** because it
is **new recurring API traffic on the Owner's own seller accounts** — the same
reason P1.8's contract run, P6.1's rotation and P3.2's suppression pull all ship
off. Nothing here is unverified; the switch is about **spend**, not doubt.
`NEXUS_IMAGE_READBACK_MAX_PER_RUN` bounds a run (default 400, hard ceiling 5000).

## 4. The proof

**18 tests green** (`services/images/live-image-readback.p42.vitest.test.ts`),
behavioural, with stubbed channel clients so the arms are real.

**8 mutations, 8 named tests failed, every file restored byte for byte.**

```
✅ NO_CREDS counted as empty (a blind run reads clean)
✅ Amazon with no account is silent instead of counted
✅ the sweep reads every marketplace, not only the listed ones
✅ the cap is removed (a sweep can run away)
✅ a truncated sweep no longer says it was capped
✅ the hard ceiling is removed
✅ the switch is ignored and the sweep always runs
✅ one failing product ends the sweep
8 guarded, 0 not guarded
```

🔴 **The ceiling rule was NOT guarded at first**, and the harness said so. The
behavioural arm used 6 products with the cap set to 999,999 and asserted
`capped === false`. Removing `Math.min(raw, 5000)` changes nothing at that size,
so the rule was gone and the test stayed green. **A behavioural test that cannot
discriminate is not a test of the rule** — it would take 5,000 fixtures to tell
5,000 from 999,999. `readbackCap()` is exported and asserted as a **value**,
with a positive control that a sane value is still honoured.

That is the third time today the same lesson has arrived: P4.1e (a `toContain` on
part of a condition), P4.2a (a name instead of a value), and now a behavioural
arm too coarse to see the change.

## 6. For the Owner

One line, and it is the only thing P4.2 asks of you:

**`NEXUS_ENABLE_IMAGE_READBACK_SWEEP=true`** starts detecting image drift on
Amazon and Shopify, the way eBay already does. It is a read-only sweep, bounded
to 400 products a run. Left off, image drift on those two channels stays
invisible until somebody opens the product's images panel.
