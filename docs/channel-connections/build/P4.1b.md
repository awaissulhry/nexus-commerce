## 1. The handover's claim, and the measurement

> *Amazon put/patch issues have no producer. `putListingsItem` /
> `patchListingsItem` are **0 occurrences in `apps/api/src`** — Amazon content
> goes out as `JSON_LISTINGS_FEED`. That part of the P3.2 plan row is P4.1's to
> build.*

Measured:

```
putListingsItem      : 28 occurrences (non-test)
patchListingsItem    :  5
submitListingPayload : 15
deleteListingsItem   : 10
control getListingsItem : 67

as an SP-API operation STRING (operation: 'putListingsItem'):
  2 occurrences, BOTH in services/gateway/amazon-sdk.p12.vitest.test.ts
```

🔴 **The "0" is true of one spelling and false of the thing it was taken to
mean.** `operation: 'putListingsItem'` really is test-only — but
`AmazonSpApiClient.putListingsItem()` is a real method at
`clients/amazon-sp-api.client.ts:801` that builds and sends its **own** HTTP
request, and it has a live call site:

```
routes/marketplaces.routes.ts:1038   const spResult = await amazonSpApiClient.putListingsItem({
```

with P1.7's `amazonContentRefusal` dry run immediately in front of it. Four more
client methods write the same way: `submitListingPayload`, `patchListingPrice`,
`patchPurchasableOffer`, `deleteListingsItem`.

**So the gap was never "there is no producer."** Amazon's `issues` array is
parsed (`parseErrors`, `parseWarnings`), logged, and handed back to the caller —
and the route maps it straight into its HTTP response:

```
issues: spResult.issues?.map((i: any) => ({ message: i.message ?? String(i), severity: 'ERROR' })),
```

Nothing writes it to `ListingIssue`. The operator sees a rejection **once**, in
the answer to the request that caused it, and never again on the listing.

Same shape as P4.1a: the recorder exists, the issues exist, nobody joins them.

## 2. What was built

Same shape of fix, too. The rule went inside the client, where all five write
methods already pass, rather than at each call site.

| File | What |
|---|---|
| `services/listing-issue-recorder.service.ts` | `resolveAmazonListingIds`, `recordAmazonListingIssues`. |
| `clients/amazon-sp-api.client.ts` | `fileListingIssues`, called from **both paths** of `putListingsItem` and `submitListingPayload`. |

### The rules

1. **A named listing wins outright**, and nothing is looked up.
2. 🔴 **Never resolve without the marketplace — and the fallback is a STRING.**
   `normalizeMarketplaceCode` never returns null: an id it does not know becomes
   the literal `'UNKNOWN'`. Querying for that reads as a clean "no listing carries
   this SKU" while the truth is "we could not tell which marketplace this was",
   and it would match any row that really does store `'UNKNOWN'`. The fallback is
   made empty and refused explicitly. (P3.2's notification path already did this;
   the convention is followed, not re-invented.)
   The marketplace is part of the key because **one SKU is listed in several
   marketplaces at once and Amazon rejects it per marketplace** — resolving on the
   SKU alone files Italy's rejection on the German listing.
3. **One SKU in one marketplace can still be several listings** (accounts,
   aliases). All of them are filed.
4. **An accepted write records an EMPTY set on purpose.** `listings-api` is a
   REPLACE source, so this is what CLOSES a rejection once the listing is fixed.
   Without it a stale issue sits on a healthy listing for ever — the false-red
   twin of a false green.
5. **Offer patches are deliberately NOT filed.** `patchListingPrice`,
   `patchPurchasableOffer` and `deleteListingsItem` answer about the offer, and
   because the source REPLACES, filing their answer would **resolve content
   rejections the call never spoke about**. Named in the code and guarded by a
   test, not left to be rediscovered.
6. **The marketplace id is reused, not recomputed.** `submitListingPayload`
   already computes `marketplaceId` for the request URL; the filing uses that
   same variable. Two names for one fact is the shape of every drift defect here.

An HTTP-level failure (a 4xx with a top-level `errors[]` rather than `issues[]`)
is **not** filed: that is Amazon refusing the request, not a verdict on the
listing, and the gateway ledger already records it.

*new* method (`patchListingPriceUnused`) carrying the call, so the guard's
`not.toContain('patchListingPrice')` still passed — the harness reported a red
whose message did not match, which is how it was caught. The mutation was moved
**inside** the real method and then convicted properly. A mutation that does not
mutate the thing under test is not evidence.

## 4. What is still open

1. **No real rejection has landed yet.** ~~The production logs say Amazon is not
   connected.~~ 🔴 **That was WRONG** — corrected 2026-09-20 after the Owner said
   Amazon was connected. Those cron lines come from ONE of TWO business profiles;
   the same boot log says `persisted Amazon authorization exists` and
   `PUBLISH MODES at boot — Amazon=live`. A per-profile skip is not a fact about
   production. See `PROGRESS.md` §2 for the full correction. The done-when is
   unchanged: one real `putListingsItem` rejection appearing on its listing.
2. **`recordNotificationIssues` still uses `findFirst`** (P3.2's code, line ~343).
   It is the same "arbitrary member" shape this package fixed for the write path.
   It is very likely fine — a SKU plus a marketplace usually is one listing — but
   it is not guaranteed, and it belongs to P3.2's author to decide. **Named, not
   changed**, because it is not this package's file to alter quietly.
3. **The 140 real Amazon rejections P3.2 found** came from feed reports, not from
   this path. This package adds the single-item path beside it; neither has been
   exercised by live traffic since.
