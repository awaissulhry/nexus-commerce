## 1. Evidence (measured 2026-09-21, development database, `127.0.0.1:55439`)

**The row is half a counterweight and half worse than it says.**

**The counterweight.** Three-region discovery already exists and already runs.
`services/cx/connectors/amazon-ads/spec.ts:discoverScopes` sweeps all three hosts, and
`jobs/cx-heartbeat.job.ts:78` calls it on **every successful heartbeat** (15 min). It
has found and recorded **14 profiles**:

| Region | Profiles |
|---|---|
| EU | 9 — IT, DE, FR, ES, NL, PL, SE, UK, BE |
| NA | 3 — US, CA, MX |
| FE | 2 — AU, JP |

**What is worse than the row says.** `AmazonAdsConnection` — the table that
**25+ jobs, routes and services** read to answer "which profiles do we have" — holds
the **9 EU rows**. US, CA, MX, AU and JP are invisible to every ads job: no metrics,
no reports, no bid engine, nothing.

🔴 **Two builders, two answers, and the one that is right has no callers.**
`services/advertising/ads-profile-resolver.ts:listAdsProfiles()` reads the scopes and
therefore already returns all 14. A census of the whole `apps/api/src` tree finds
**zero callers** of it. The accessor that would have made this visible exists, is
surrounded by working code, and has never run — the pattern this programme has now
met in eight packages.

**🔴 And the region is load-bearing, not a label.**
`ads-api-client.ts` picks the API host from `ctx.region` (`REGION_ENDPOINT[region]`),
and `routes/amazon-ads-auth.routes.ts:238` wrote **`region: 'EU'` for every profile it
saved**. The first NA row created under that rule would have had its calls sent to the
EU host. That is an authorization failure rather than a wrong number, which is the one
mercy in it.

**The region → host fact was written out FIVE times:**

## 2. Changes

1. **New** `services/ads-core/ads-regions.ts` — the one definition: `ADS_REGION_HOSTS`,
   `ADS_REGIONS`, `ADS_CONSENT_HOSTS` (used by P4.5c), `asAdsRegion`, and `adsHostFor`
   which **refuses** an unknown region rather than falling back to EU. P4.4a's rule.
2. The three full copies now import it; the CX spec re-exports it so nothing that
   imported `ADS_REGION_HOSTS` from there breaks.
3. `routes/amazon-ads-auth.routes.ts`
   - `discoverProfiles()` sweeps the regions and **tags each profile with the region it
     answered in**. A non-EU region that does not answer contributes nothing and does
     **not** fail the connect (an account with no Far-East profiles is the normal
     case); EU's failure is still the connect's failure.
   - The saved row records `region: profile.region`.
   - **The `update` branch no longer reasserts `isActive: true`.** A reconnect is a
     credential event, not a decision to advertise in every market again. This is the
     rule CX.3a already learned for scope metadata: discovery must not overwrite what
     discovery cannot see.
4. **New** `jobs/p45b-ads-region-reconcile.job.ts` — mirrors the discovered scopes into
   the legacy table. **Scheduled daily** (`35 4 * * *`) through the clustered wrapper,
   not registry-only: P4.2d paid for that lesson once.

### The two gates, and why they differ

| What | Gate | Why |
|---|---|---|
| Correcting a row's region | **always on** | Costs no API call and is pure correctness. Today it corrects **nothing** — which is exactly why it ships *before* the first NA row exists rather than after. |
| Creating the 5 missing rows | `NEXUS_ADS_ALL_REGIONS=1`, **off** | Spend, not doubt. A row is picked up by every read job filtering `isActive`, so five rows means five more profiles' worth of report and metrics calls against the Ads quota, for markets nothing in Nexus is set up for. |

A created row is **`isActive: false`, `mode: 'sandbox'`, `credentialsEncrypted: null`**
— recorded and visible on the Channels page, doing nothing until an operator decides
otherwise. The credential is deliberately not copied: the nine existing rows already
share one blob, `resolveCredentials` asks the connection core first, and spreading a
secret to five more rows is the opposite of what P4.5e does next.

The report distinguishes `createsSkippedOff` from `unchanged`, so "nothing to do" and
"two profiles waiting on a variable" cannot look the same.
