# P4.3d — the oversell clamp is capped by the ROUTED locations

**Date** 2026-09-20 · **Package** P4.3 (Stock), fourth slice · **Size** M

The plan row: *"The Amazon clamp uses all warehouse rows, not the routed ones."*

---

## 1. What was measured

### 1.1 The row is true, and it is true of all three channels

The send-time oversell clamp took its ceiling from `sellableAvailable`
(`services/stock-pool/sync-ledgers.ts:188`): **Σ available over every warehouse
row the product's ledger holds**, with no routing filter at all.

The quantity being clamped came from `resolveIntendedQuantity`, which **does**
route — `locationServes(row.syncRoutes, channel, marketplace)` plus the
listing's own `sourceLocationCodes` pins.

So the number a listing was allowed to promise was routed, and the cap on it was
not. **Two derivations of one number, in two files** — and the cap was the
**wider** of the two, which is the direction that catches nothing.

The plan names Amazon. It is **all three lanes**, identically:

| Lane | Line | Ceiling |
|---|---|---|
| Amazon | `outbound-sync.service.ts:1085` | `sellableAvailable` − buffer |
| eBay | `outbound-sync.service.ts:1336` | `sellableAvailable` − buffer |
| Shopify | `outbound-sync.service.ts:2152` | `sellableAvailable` − buffer |

Fixing only the one the plan names would have re-created the exact drift this
package keeps finding. All three now share one helper.

### 1.2 🟡 On the development database the gap is LATENT, not active

| Measurement (dev DB, `127.0.0.1:55439`) | Value |
|---|---|
| `StockLocation` rows | 3 — `AMAZON-EU-FBA`, `GB-MAIN`, `IT-MAIN` |
| locations with a non-empty `syncRoutes` | **0** |
| `ChannelListing` rows pinning `sourceLocationCodes` | **0** of 1,003 |
| `ChannelListing` rows with `stockBuffer > 0` | **0** |

An empty `syncRoutes` routes **everywhere**, so today the routed sum and the
whole-warehouse sum are the same number and the wrong ceiling caps identically.
**This is a counterweight in effect and a real gap in the rule** — say both.

⚠️ **Production is unmeasured.** Railway reads are blocked for this session (the
auto-mode classifier refuses `list-variables` under *Production Reads*), so the
dev numbers are what is claimed and nothing more. There are already **two**
warehouses, and Sync Control exists precisely to route them; the first
`syncRoutes` entry anyone sets makes the old ceiling wrong.

### 1.3 The arm that had to be got right: "nothing routed" is not "zero"

The resolver already keeps these two facts apart:

```ts
if (routed.length === 0) {
  return i.uncountedIsZero ? { kind: 'FOLLOW', quantity: 0, … } : { kind: 'UNCOUNTED' }
}
```

- an **own-stock** product (`uncountedIsZero: true`) that routes nothing to a
  market genuinely has 0 there — pushing 0 is honest;
- a **pooled** product (`uncountedIsZero: false`) that routes nothing is
  **unknown** — the resolver pushes nothing at all.

A clamp cannot decline; it can only cap. Capping an unknown to 0 and sending it
is the **scoped Zero** — the incident behind D9, where 302 market-scoped zeros
blanked an entire storefront. So the clamp reports the fact and its caller
refuses, exactly as P4.3b made the EU guard do.

## 2. What was built

### 2.1 One routing filter, two readers

`services/sync-control-core.ts` now exports `routedLedgerRows()` — the filter
itself — and `routedAvailable()` — `{ available, routed, locationCodes }`.
`resolveIntendedQuantity` was **refactored onto it**, so the promise and its cap
share the literal same code rather than agreeing by inspection.

`routed: false` is a separate field from `available: 0` on purpose. They are
different facts and the whole failure path turns on telling them apart.

### 2.2 One ceiling, three lanes

`OutboundSyncService.routedCeiling()` loads the ledger the product **follows**
(own warehouses or the pool, via `loadSyncLedgers` + `ledgerInputs`), routes it
by the listing's market and source pins, subtracts the listing's buffer, and
returns `{ available, routedAvailable, locationCodes, refusal }`.

**`refusal` is decided in the helper, not in each lane** — one place decides,
three lanes report — so a fourth lane cannot learn half the rule. It is raised
when `!routed && !uncountedIsZero`, and the lanes answer `NO_ROUTED_LOCATION`,
terminal, naming the market.

**Two nullable fields, not an `ok` union:** `apps/api` sets `"strict": false`, so
a discriminated union never narrows there and `ceiling.refusal` would be a
compile error after the guard. (Banked trap, applied.)

### 2.3 Two selects that would have made the pin arm dead

The Amazon and eBay `cl` selects did not fetch `sourceLocationCodes`, so
`cl?.sourceLocationCodes ?? []` would have been **`[]` forever** — an always-empty
field, and the source-pin arm silently dead while every test passed. Both selects
now fetch it. *A fingerprint built from an always-empty field is not an identity.*

## 3. Proof

**`routed-oversell-ceiling.p43.vitest.test.ts` (13 tests)** — the arithmetic,
pure. A two-market ledger (IT-MAIN 10, GB-MAIN 40): Italy may promise 10 of the
50, not 50. The buffer comes off the routed number. An empty `syncRoutes` routes
everywhere (today's state). Nothing routed → `routed: false`. And the agreement
table: for five (market, buffer) pairs, `resolveIntendedQuantity`'s FOLLOW
quantity and the ceiling are the **same number** — the property the old code
could not have had.

It also states the defect as an assertion: the old ceiling (50) let a stale row
promising 40 through on the Italian listing; the routed ceiling holds it to 10.
And a **PINNED** quantity of 40 — which the resolver deliberately does not route,
because it is the operator's number — is capped by the routed ceiling, which is
the only thing that can hold it to the truth.

**`routed-ceiling-dispatch.p43.vitest.test.ts` (11 tests)** — the helper the
lanes actually call, with `loadSyncLedgers` mocked:

- caps to the routed market, not the whole ledger;
- the buffer comes off the routed number and floors at 0;
- a source pin narrows further, and a **pooled** product's pin is correctly
  ignored (`ledgerInputs` drops it — the pool decides);
- 🔴 a pooled product with nothing routed is **refused**, not capped to 0;
- positive control: an own-stock product with nothing routed is a **true zero**,
  not a refusal — `uncountedIsZero` is the discriminator;
- a routed market genuinely holding nothing is a zero, not a refusal;
- **no ledger at all** (the arm a database hiccup lands in) is a refusal;
- each channel names itself in its own sentence.

Plus a **derived census**: every `this.routedCeiling({` call site must have
**exactly one** line whose trimmed form starts `if (ceiling.refusal)` within its
block, with at least 3 sites. A fourth lane is covered without editing the test.

**Mutation checks — 8 of 8 convicted**, each asserting its edit landed, was
restored byte-for-byte, and that the runner actually ran:

| Mutation | Red test |
|---|---|
| the routing filter dropped | `sums only the locations routed to this market` |
| the source pin ignored | `the listing's own source pin narrows it further` |
| "nothing routed" reported as a plain zero | `NOTHING routed is reported as routed:false` |
| the refusal never raised | `a POOLED product with nothing routed is REFUSED` |
| `uncountedIsZero` ignored | `positive control: an OWN-stock product … is a true zero` |
| the buffer off the whole ledger again | `the listing's buffer comes off the ROUTED number` |
| the Amazon lane stops reading its refusal | `each routedCeiling call site checks ceiling.refusal` |
| the Shopify lane stops reading its refusal | the same census |

🔴 **The Amazon-lane mutation passed GREEN on the first run**, and it is the
banked trap in a new place: the census matched the substring `ceiling.refusal`,
which survives inside `if (false) { … message: ceiling.refusal … }`. *A
`toContain` on part of a condition does not test that condition.* The census now
matches the **whole trimmed condition** and demands **exactly one** such line per
call site.

**Gates.** `tsc --noEmit` clean. Gateway ratchet
`{"EBAY":0,"AMAZON_SP":0,"AMAZON_ADS":0,"SHOPIFY":0,"ETSY":0}`, queue rows
outside `outbound-rows.ts`: 0. `check-push-lock.mjs`: still exactly 1 FAIL, the
pre-existing `studio-publication-amazon.ts:164`.

**Full API suite: 6 failed / 10,332 passed** — the documented baseline
(`amazon-validation-preview` 5 + `amazon-classifications` 1), unchanged. No
existing test needed editing for this slice.

## 4. What this does NOT do

- **It changes no number on the dev database**, where every location routes
  everywhere. The behaviour change begins with the first `syncRoutes` entry.
- **It does not route the FBA pool.** FBA is excluded from the clamp entirely
  (Amazon owns that quantity), unchanged.
- **It is not proven against production data** — production reads are blocked
  for this session. The done-when is a listing whose market is routed to one
  warehouse, clamped to that warehouse's stock rather than the company total.
- **It does not add a `catch`.** If the ledger cannot be read, the load throws
  and the sync fails, exactly as `sellableAvailable` did. A rule's `catch` is
  where it goes to die; this one has none to die in.
