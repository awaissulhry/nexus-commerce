# P4.5a — an eBay Promoted Listings write goes to the campaign's OWN account

State: **BUILT 2026-09-21**, committed locally. Part of P4.5 (advertising).

Plan row (FINAL-PLAN.md §6, P4.5): *"eBay Promoted Listings: full check first (not
done today), then through the gateway."*

**The gateway half of that row is a counterweight — it was done in P1.2.** Every eBay
Marketing call already goes through `ebaySend` (`ebay-ads-api.service.ts:118`), and
the ratchet holds `{"EBAY":0,…}`. The *full check* is what had not been done, and it
found the row P0.7 had deliberately left behind.

## 1. Evidence (measured 2026-09-21, development database, `127.0.0.1:55439`)

**P0.7's own census names this row and defers it here, in these words:**

> "Not changed: … eBay Promoted Listings writes (ads, not listings; **P4.5**)."

**The defect.** `EbayCampaign.channelConnectionId` is a **required column with a
relation** (`schema.prisma:13837-13838`), so every campaign records its account. Every
ads write threw that away:

| Where | Sites | What it did |
|---|---|---|
| `services/marketing/ebay-ads-write.service.ts` | **13** | loaded the campaign, then asked `getActiveEbayAdsAuth()` for the **primary** account's token |
| `routes/ebay-ads.routes.ts` | 6 | 1 of them (`keyword-bid-suggestions`) loads the campaign first |
| `services/marketing/ebay-ads-reports.service.ts` | 2 | report tasks |
| `services/marketing/ebay-ads-entity-sync.service.ts` | 1 | the sweep |
| **Total** | **22** | |

**Why it had not bitten — and why that is the dangerous part.** On the development
database: **two active eBay connections** (`cmr4aaqb…` primary, `cmt142bli…` not
primary, both `authStatus: connected`) and **13 campaigns, all 13 on the primary**. So
"the primary" was the right answer every time.

🔴 **It was right every time because of the SECOND defect.** `syncEbayAdsEntities`
also resolved the primary, visited that one account, and reported `connections: 1`.
A second account's campaigns **could not enter the database at all**, so no row could
ever contradict "the primary".

**That is why both land in one change.** Fixing the sweep alone would have made every
second-account campaign visible to a write layer that still sent its changes to the
first account — converting a latent misroute into a live one. Producer and consumer
ship together.

**A third thing asking for "the primary" can never do:** refuse. The primary is by
definition active, so a write aimed at an account that has since been **disconnected**
silently became a write to a different, live account. Resolving by id refuses it.

## 2. Changes

1. `services/marketing/ebay-ads-api.service.ts`
   - **New** `getEbayAdsAuthFor(connectionId)` — the token of ONE named account,
     through `resolveConnection({ accountId })`, which refuses an inactive account.
     Also refuses a connection of another channel.
   - **New** `listEbayAdsAccounts()` — every active eBay account, primary first. One
     account without a usable token is logged and skipped; it does not hide the rest.
   - `getActiveEbayAdsAuth()` kept, with its purpose written down: only for a call
     with genuinely no account of its own (account-level eligibility, a suggestion
     made before any campaign exists).
2. `services/marketing/ebay-ads-write.service.ts` — new `authForCampaign(c)`; all 13
   sites use it. `createCampaign` is the one site with no campaign row yet (it is the
   one that creates it) and now takes its token from the **same** connection it writes
   into the row, instead of resolving the primary twice.
3. `services/marketing/ebay-ads-entity-sync.service.ts` — `syncOneAccount()` extracted;
   the sweep runs it per account and counts what it reached. A campaigns fetch that
   fails now returns from the **account**, not from the sweep: the difference between
   "account 2 was skipped" and "account 2 was never tried".
4. `routes/ebay-ads.routes.ts` — `keyword-bid-suggestions` asks the account that owns
   the campaign; the primary account does not know that campaign id.

**Deliberately NOT changed:** `suggest/max-cpc`, `suggest/keywords`, `suggest/bids`,
`builder/budget-suggest` and `account-health`. These have no campaign row — they are
account-level or pre-campaign — so the primary is the correct and documented answer.

## 3. Proof

  account's token is returned and is **not** the primary's; the primary through the
  same door still works (control); a disconnected account is refused; another
  channel's connection is refused; an unknown id is refused; the sweep returns both
  accounts and no other channel; one account with no token does not hide the others;
  and a 4-part census derived from the source.

  the sentence that explains the fix. Each census check carries its own positive
  control (`sites.length >= 13`, `listEbayAdsAccounts() === 1 occurrence`) so an

  | one write path goes back to `getActiveEbayAdsAuth()` | **2** |

- `tsc --noEmit` (apps/api): 0 errors.
- `services/marketing/` + `routes/ebay-ads`: **115 passed, 10 files**.

(`NEXUS_MARKETING_WRITES_EBAY`) is **not measured**. Every number above is from the
development database.

Open on production:

1. How many eBay connections are active per business profile? The dev database has
   two active in one workspace; the deploy logs record one connection per profile
   across two profiles. If production really has one active account per profile, this
   fix changes nothing observable — which is exactly the proof that shipping it is
   safe.
2. After the deploy, `[E2][ebay-ads] entity sync complete` should report
   `connections: N` matching the number of active eBay accounts, not `1`.
3. A write to a campaign whose account is disconnected should now refuse with
   *"ChannelConnection … is not active"* rather than reaching a different account.
