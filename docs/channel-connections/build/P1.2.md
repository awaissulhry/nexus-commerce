## 1. The ratchet

`apps/api/scripts/channel-gateway-ratchet.mts` (TypeScript AST, read-only), run by `.githooks/pre-push` after the MAP.3 check.

- Counts every `fetch(`, `https.request(`, `axios…(` and `new SellingPartner(` that talks to eBay, Amazon SP-API, Amazon Ads, Shopify or Etsy, outside `services/gateway/`. Channel: a host in the call, else the hosts in its file, else the channel in its file path, else an eBay `apiBase` argument.
- A send that is not a channel API call carries `// gateway-exempt: <reason>` (an OAuth token exchange the gateway depends on, a pre-signed storage URL, our own CDN, a connector heartbeat). It is listed, not counted. No reason = counted.
- `--check` fails when a channel's count is above its baseline (in the script). `--list` prints every site.
- **Correction (P1.2b fix):** the first rule counted a send by its file's hosts before its own API path. `outbound-sync.service.ts` holds both eBay and Shopify code, and 10 eBay sends there were counted as Shopify, so "eBay 0" was not true. The API path in the call now decides first (`/sell/…` = eBay, `/variants.json` = Shopify; test with a mixed fixture file); the 10 sends moved (`ebaySend`, the account the function already holds).

## 3. What changes for the Owner

1. **Every Amazon call now writes one ledger row** (before: only SDK calls; the listings client and the direct sends wrote none). The 90-day retention job already prunes the table.
2. **An Amazon write can no longer skip the publish mode.** Production is `live`, so nothing changes there. In a dry-run or gated environment every Amazon write is refused with a sentence, including paths that never checked the mode. A listings `VALIDATION_PREVIEW` is a read and is still sent.
3. **Connection setup is not publishing.** Notification subscriptions, destinations and the app-secret rotation (`kind: 'setup'`) are sent in every publish mode — otherwise a switched-off channel could never connect or receive events.
4. **A write that could apply twice is no longer retried.** The old listings client retried every POST on a 5xx (a label purchase could be bought twice). Now only reads and writes that are safe to repeat (PUT, DELETE, the listings PATCH) retry after a network error or 5xx.
5. **P1.6 candidate found:** `amazon-catalog.service.ts` `fetchFromAmazonAPI` calls a path that is not an SP-API endpoint with a static env token. Moved unchanged; it goes on the P1.6 delete list you approve.

## 5. P1.2b — eBay on the gateway

| Path | Change |
|---|---|
| `ebayFetch` (CX connector client, 20 callers) | Sends through `ebayGatewayFetch` (signing, token, state, ledger in the gateway). |
| `callTradingApi` (Trading XML, 83 call sites in 20 files) | Sends through the gateway with the Trading Ack read as the outcome (`answerOk`), eBay's XML error codes classed (931 → auth_revoked, 518 → rate_limited, …). **`TradingCallContext.connectionId` is now required**: every Trading call names the account its token belongs to; TypeScript listed every caller and each one passes the account it took the token for. A call without one is refused (`ACCOUNT_REQUIRED`), never sent on "the primary". |
| 80 direct `fetch` sends in 25 files | `ebaySend` / `ebayTransport` (a `fetch`-shaped sender bound to one account: same headers, body and token), `ebayTradingSend` for Trading XML. Files with their own retry loop turn the gateway's retries off (no double retries). |
| 11 exempt | OAuth token exchanges / revoke (6), connector identity and heartbeat (2), two identity reads with a bare token and no caller (P1.6 candidates), one Amazon pre-signed upload in a mixed file. |

New gateway pieces in this step:

1. **`kind: 'action'`** — P0.1 decided the eBay publish mode is for LISTING writes; order actions (refund, shipment, cancellation, label, feedback, message) and marketing (promotions, markdowns, ads) have their own switches (`NEXUS_ENABLE_*_SHIP_CONFIRM`, `…_ORDER_CANCEL`, `…_BUY_SHIPPING`, `NEXUS_EBAY_MARKDOWN_LIVE`, `…_VOLUME_LIVE`). The gateway now follows that: `action` calls skip the publish mode, keep the account check, rate bucket and ledger. The Amazon rule (P1.2a) was corrected the same way (orders, MFN labels, messaging, FBA shipments → action).
2. **Token-to-account memory** (`gateway/token-accounts.ts`) — the CX token service records every access token it hands out (a SHA-256, never the token) with its account. A call site that holds only a token (marketing, Trading helpers) is recorded and checked against the exact account; a token Nexus did not hand out is refused. No guessing of "the primary".
3. **One row per send** — a moved call can still sit inside an old `recordApiCall` wrapper (12 files). The gateway row takes the wrapper's operation name and product/order links and the wrapper writes nothing (AsyncLocalStorage claim). Proved on the real database.
4. **File bodies** — FormData / bytes go through; the ledger keeps only `{ __binary, bytes }`. A signed call with a file body is refused.
5. **Caller deadlines** — a call's own `signal` (e.g. the 15 s policy read) is combined with the gateway timeout; it was dropped in the first cut and a test caught it.
6. **`marketHeaders: 'caller'`** — moved eBay calls keep the language headers they send today (many `en-US`). P1.5 switches them to the Marketplace-row headers in its own step, with its own test.

Behaviour changes to note:

- **The eBay Feed upload now follows the eBay publish mode** (it did not — a listing write outside P0.1). Production is `live`: no change there.
- **A read retries once after a 5xx or a network error** (the category service test modelled an outage as ONE 503; it is now two).
- **P1.6 candidates found**: `marketplaces/ebay.service.ts` (the app-token service; moved as app-level calls), `providers/ebay.provider.ts` (static env Trading token; moved as app-level), `ebay-auth.service.ts` `getSellerInfo` / `getSellerIdentity` (no caller).

## 6. P1.2c — Shopify on the gateway

| Path | Change |
|---|---|
| `shopify/admin-client.ts` (the connected-account GraphQL client, 17 callers) | Sends through `shopifyTransport(accountId)`. Its own checks stay (assertWritable, mode for mutations, per-shop limiter). |
| Env-credential paths (outbound-sync REST 2024-01 ×5, the two old Shopify services, live images, setup route) | `shopifyTransport(null)`: the token is **exactly** the env credential → an app-level call; P1.4 moves them to the connected account. No env token exists in production, so these send nothing there today. |
| Bulk mutation | The token's account if the token service handed it out, the env credential as app-level, anything else refused. |
| 4 exempt | 2 staged uploads to Shopify's storage (pre-signed targets), the connector heartbeat, the OAuth code exchange (all channels). |

- **Shopify's rule** (`gateway/shopify.ts`): GraphQL — a query is a read; a mutation by its root field: `webhookSubscription*` setup, `fulfillment*` / `order*` / `refund*` / `return*` action, `stagedUploadsCreate` / `bulkOperationRunQuery` read, anything else a listing write (publish mode). REST — webhooks setup; orders / fulfilments / refunds action; GET read; the rest write.
- **Buckets:** GraphQL (cost-based, ~10 mutations/s) and REST (leaky bucket of 40 at 2/s) have their own.
- **No redirects:** every gateway call now refuses to follow a redirect. Node keeps custom token headers (`x-amz-access-token`, `X-Shopify-Access-Token`) on a redirect to another host; the old Shopify client had `redirect: 'error'` and the first cut of this step dropped it. Proved with a real local server: the token reached only the first host.

Proof (P1.2c): `services/gateway/shopify.p12.vitest.test.ts` — **20 tests** (12 kind cases, root field with alias and comment, account token → account, env token → app-level, other token refused with 0 calls, gated listing write refused while a webhook subscription is sent, bucket sizes, `redirect: 'error'` on the request, real redirect not followed); one existing test registers its fixture token as an account's token. Mutation checks 5/5 caught (any token treated as env, env rule removed, setup mutations removed, redirects followed, one Shopify bucket). Full API suite: 9673 passed, 6 failed (the two known files).
