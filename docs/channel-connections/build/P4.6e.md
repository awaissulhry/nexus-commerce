# P4.6e — the Etsy lane, and Etsy's six-hour rule

**Package:** P4.6. **Slice:** e. **State:** BUILT, local, green. **Carries a migration.**

P4.6a–d built the writers. Nothing could reach them, because **`SyncChannel` had no `ETSY`**.

## 1. The migration

`20260921b_p46e_sync_channel_etsy` — `ALTER TYPE "SyncChannel" ADD VALUE IF NOT EXISTS 'ETSY'`.

The enum held `AMAZON`, `EBAY`, `SHOPIFY`, `WOOCOMMERCE`, `GOOGLE`, `META`, `TIKTOK` — and no
`ETSY`, although Etsy has been a connected channel since **P2.5**. So no `OutboundSyncQueue` row
could name an Etsy destination.

**Additive**: it changes no existing row and no existing read, and nothing selects on it until the
lane deploys with it.

Applied to the **local** database only, with `DATABASE_URL` passed explicitly — the trap the
handover names is real and was re-measured here:

| file | database |
|---|---|
| `apps/api/.env` | `127.0.0.1:55439/nexus_development` ← the one apps/api uses |
| `packages/database/.env` | `localhost:5432/nexus_commerce` ← a **different** database |

Verified after applying, by reading `pg_enum` on the database the API actually uses:
`AMAZON, EBAY, SHOPIFY, WOOCOMMERCE, GOOGLE, META, TIKTOK, ETSY`.

## 2. The lane

`syncToEtsy`, in the same order as the Shopify lane, **because the order is the safety**:

push lock → publish mode → destination account → wrong-account guard → listing id → the change.

| step | what is specific to Etsy |
|---|---|
| wrong-account guard | Etsy listing ids are **per shop**, so the same number is a different listing in another shop |
| listing id | `ChannelListing.externalListingId`, falling back to `Product.etsyListingId` |
| quantity | `linkedDispatchQuantity` — never the raw payload number |
| price | `priceRefusalFor` first (P4.4c: refuses, never clamps) |
| content | a **different call**, because Etsy's content body is form-encoded and partial |

### One builder, not two

`shopifyDispatchQuantity` became **`linkedDispatchQuantity(queueItem, sku, channel, channelLabel)`**,
and both lanes call it. The three steps it performs — re-read the committed quantity, apply the
routed ceiling, clamp — are exactly the ones a copy would drift on, and the drift would be a
**silent oversell** on whichever channel was not updated. Banked: *two column builders drift, and
the drift is silent*.

So Etsy gets the same routed ceiling as Amazon and eBay (P4.3d) for free. **Etsy never receives a
raw payload number** — P4.3a is the reason from the other direction: `syncInventoryFromEtsy` wrote
Etsy's quantities straight into `ProductVariation.stock`, past the resolver and the pool.

### 🔴 Drift is a SUCCESS with a warning, not a FAILED row

When P4.6c's read-back does not match, the row is `SUCCESS` with a sentence, not `FAILED`.

The change **was** accepted. Marking it FAILED would invite a retry, and on a full-replace
endpoint **a retry is precisely what would make it worse** — it would send the whole inventory
again, taking the regional-pricing risk a second time to "fix" the damage the first one did. The
operator has already been alerted by name (P4.6c); the queue's job is not to have a second opinion
about it.

## 3. Etsy's six-hour rule — measured, and it is not met

FINAL-PLAN §13 records it as **required**: *"Etsy's terms: listing content at most 6 hours
stale… Must be met once we write or show Etsy data."* P4.6 is that moment.

### 🔴 Three independent reasons it has never been met

| # | fact |
|---|---|
| 1 | `etsy-sync` is **registry-only** — a manual "Run now", **never scheduled**. (The sync-logs hub page had 0 requests in P1.6's window.) |
| 2 | its client needs **env credentials production does not have** — the boot log says *"Etsy configuration incomplete"* |
| 3 | and its `x-api-key` is the **OAuth access token** (P4.6b) — Etsy would refuse the call even with credentials |

Each is sufficient alone. That is itself the finding: **a path can look present in three places
and be dead in all of them.**

### What was built, and what deliberately was not

**Built**: `services/etsy/freshness.ts` — the six-hour constant, `etsyContentIsStale` and a
census; a new alert kind `channel-data-stale`; and the census wired into the channel-alerts sweep
so the producer and its consumer land together.

- **`null` is stale, not fresh.** "Never synced" is the worst case and the one every Etsy row is in
  today. Reading absence as freshness is P3.6's rule inverted.
- **A future timestamp is stale too** — a clock problem must not read as "very recent", which is
  the one reading that would hide it.
- The sweep queries with **no `where` on the date**, for the same reason P6.8 removed one: a row
  that has never been read has `lastSyncedAt` null, and that is the entire population this exists
  for. Selecting on the presence of a date would have made the whole finding invisible.
- The alert is **`warn`, not `danger`**: nothing is being destroyed, and shouting danger at a
  standing condition is how a real danger stops being read. "All of them" and "some of them" are
  **different `entityId`s**, so a shop that fixes most rows is not folded into the unread notice
  that said "all".

**Not built, on purpose**: a job that pulls Etsy's values back into Nexus. That is P4.3a's ruling
and it is not negotiable here — a refresh written to "fix staleness" by copying Etsy's numbers in
would be that defect rebuilt with a better excuse.

**And the write path already meets the rule by construction**: `writeEtsyInventory` reads the
listing from Etsy **immediately before** every write, because the PUT is a full replace and there
is no other way to build the body. Its read is seconds old, not hours. What is left open is the
**display** half (§6).

## 3b. ✅ PRODUCTION ANSWER — and a defect in this slice's own logging

Deployment `8d7e515c`, sweep at **10:30:01 UTC**. The answer is:

> **Production has ZERO Etsy `ChannelListing` rows.**

So the six-hour rule is **vacuously met** today — there is nothing stale because there is nothing.
That was named in §7 as the other possible answer, and it is the one that came back. It also means
P4.6's writers have no production listing to act on yet: Etsy is connected (P2.5) but nothing is
listed through Nexus.

🔴 **And getting that answer took a positive control, because this slice logged it wrong.**

The first version wrapped the log in `if (rows.length > 0)`, so an empty shop produced **silence** —
indistinguishable from the block having thrown. It took reading `[channel-alerts] sweep` (which
**did** run, twice, at 10:30:01 and 10:30:02) to tell the two apart.

That is this package's own standing rule, broken in its own code: **an unwitnessed zero neither
passes nor convicts.** Fixed — the census is logged **always**, including `total: 0`, while the
*alert* still fires only when something is actually stale, because an empty shop is not a breach.

Corroborated on the same deploy: `[ConfigManager] ⚠ Etsy configuration incomplete (missing env
vars)` — the legacy Etsy client is inert in production, exactly as P4.6b measured.

## 4. Proof — 27 new tests plus 9 added to an existing ratchet

- `outbound-sync.etsy.p46.vitest.test.ts` (15) — every gate in order, each `syncType` reaching the
  right writer, the push lock handed **through** to the writer so the gateway checks it again at
  the call, drift as a success-with-warning, and `dispatchSync` routing `ETSY` rather than
  throwing *"Unknown channel"*.
- `etsy/freshness.p46.vitest.test.ts` (12) — the boundary at exactly six hours, null, a future
  date, an unreadable date, the census, and the alert's two shapes.
- 🟢 **`syncToEtsy` was added to `outbound-sync.push-lock.vitest.test.ts`'s `paths` array.** That
  array **is** the parity ratchet: a new lane that forgets the shared push lock fails there. 45 →
  54 tests, all passing, and the mutation below proves the new rows are load-bearing.

**Mutations: 14 applied, 14 killed**, with a 🟢 null control that correctly SURVIVED. Among them:
the Etsy lane skipping the push lock, the publish gate ignored, the wrong-account guard off, a
content row routed to the inventory writer, drift reported as FAILED, `ETSY` removed from
`dispatchSync`, `null` reading as fresh, the six-hour bound becoming six days, and the stale alert
folding "all" and "some" into one id.
