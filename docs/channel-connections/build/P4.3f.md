**Date** 2026-09-21 · **Package** P4.3 (Stock), sixth and last slice · **Size** M

The plan row: *"Shopify read-back."* (§4.3: *"Read-back jobs exist for Amazon

---

## 1. What was measured

### 1.1 🟢 The P5.3 warning does NOT apply to this row — establish that first

The handover said, in as many words: *"⚠️ note P5.3 first: `shopify-live-images`
is guarded by `hasCreds()` and production has no `SHOPIFY_*` variable, so a
Shopify read-back cannot run there today whatever you build. Establish that
before building, or you will build something that cannot run."*

**Established, and the warning is narrower than it reads.** A derived check:
`hasCreds` has exactly **one** definition and **one** call site in the whole API,
both inside `services/images/shopify-live-images.service.ts` — the legacy REST
image reader. Nothing else consults it.

The stock path runs on `shopifyAdmin(accountId)`
(`services/shopify/admin-client.ts`), which takes its token from the **CX
connection** — `getAccessToken(accountId)` — and its domain from the connection's
region. No `SHOPIFY_*` environment variable is read anywhere in it. A read (a
`query`, not a `mutation`) also skips `assertWritable` and the publish-mode gate.

**So a Shopify quantity read-back runs wherever a Shopify connection exists**,
and yields nothing where none does. The thing that cannot run in production today
is the legacy image reader, which is P5.3's row, not this one.

### 1.2 The row is true: there is no scheduled Shopify quantity check

| Channel | Scheduled quantity read-back |
|---|---|
| Amazon | `jobs/amazon-qty-readback.job.ts`, daily 04:15 (P0c) |
| eBay | `jobs/ebay-readback.job.ts`, every 30 min (P5.2) |
| **Shopify** | **none** |

The only scheduled Shopify job is `shopify-linked-automation` (every 5 min), and
it is **content** family automation — `runLinkedAutomation`, shared-content rules
and family links. No stock in it. Checked before building, because five of the
eleven rows in this package so far have been counterweights.

### 1.3 🔴 The counterweight, and why it is not the same thing

**Shopify is not unverified at all — it has the strongest write-time check of the
three channels.** `syncShopifyLinkedListing` reads the variant BEFORE the write,
sends `changeFromQuantity: observed` (a true compare-and-set), reads it back
AFTER, and throws if the two disagree. Neither Amazon nor eBay does that.

**But a read-back that only runs when we push cannot detect drift.** Between two
pushes, a shop-side edit, a third-party app or a Shopify order adjustment moves
the number and nothing notices. That is P4.2c's lesson word for word — *all three
channels had the FUNCTION, only one had the HABIT* — in the stock lane instead of
the image lane. Say both halves: the write is well guarded, the gap is the
absence of a habit.

## 2. What was built

### 2.1 The reader lives beside the writer

`readShopifyAvailable(gql, row)` was added to **`listing-write.service.ts`**, not
to the read-back service, and it calls the write path's own private `identify()`
and `stockLocation()`.

🔴 That placement is the point. A reader that decides "which variant" or "which
location" one line away from the writer is the drift this programme keeps
finding: the read-back would report a mismatch for a listing the writer sends to
a different location, or miss one that it does. `available: null` means "not
stocked at the reviewed location" — **could not read**, never `0`.

### 2.2 The verdict is a value

`readbackVerdict({ shopifyAvailable, resolutionKind, resolutionQuantity })`
returns `COMPARE` / `UNREADABLE` / `SKIPPED`, pure and exported so it is tested
by value rather than by the shape of the code around it.

- **`UNREADABLE` is checked first**, even when the listing is also paused: "we
  cannot see Shopify" is an operational fault and "it is paused" is a choice, and
  they need different fixes.
- **Only `FOLLOW` is compared.** `FBA_EXCLUDED`, `CLOSED`, `PAUSED`, `UNCOUNTED`
  and `PINNED` are `SKIPPED` with the reason. 🔴 **`PINNED` especially:** a pin is
  the operator's number, the shop may legitimately hold another, and silently
  healing it back would overwrite a person's decision.

### 2.3 The loop

`readBackShopifyQuantities()` pages live, linked, account-bearing Shopify
listings (bounded, `NEXUS_SHOPIFY_QTY_READBACK_MAX_PER_RUN`, default 400), opens
**one client per account**, reads Shopify's own number, derives the intended one
through `resolveIntendedQuantity` — the same core the cascade and the dispatch
clamp use — and diffs.

A divergence writes `SyncHealthLog` `CHANNEL_QTY_READBACK`, deduped 24 h per
product, exactly as both siblings do. A bounded heal (default 25) enqueues an
**ordinary queue row that NAMES its listing** (P4.3c), so the dispatch re-read,
the routed ceiling (P4.3d) and the push lock apply to the heal like any other
change. **The read-back never writes to Shopify itself.**

`checked`, `unreadable` and `skipped` are three separate counters. A run that
could not read anything reports `checked=0 unreadable=N`, never a clean-looking
zero.

### 2.4 🔴 It is SCHEDULED, not registry-only

`startShopifyQtyReadbackCron()` in `jobs/shopify-qty-readback.job.ts`, called
from `index.ts` beside its two siblings, every 6 hours (`15 */6 * * *`), ON by
default with `NEXUS_SHOPIFY_QTY_READBACK=0` to opt out — the same shape as
`NEXUS_EBAY_READBACK` and `NEXUS_QTY_READBACK`.

**P4.2c shipped a sweep into `CRON_REGISTRY` only while fixing exactly that
shape, and reported it as working; P4.2d had to add the schedule.** A registry
entry is here too, but only for an on-demand run, and it says so.

**ON by default, and why:** it is a read; both siblings are ON by default; and
making the third channel the only dark one re-creates the inconsistency this
package keeps closing. The spend is bounded per run and the job yields nothing
where no Shopify account is connected.

## 3. Proof

`src/services/shopify/quantity-readback.p43.vitest.test.ts` — **25 tests**:

- **the verdict by value**, including a live `0` and an intended `0` as real
  numbers, `null` as `UNREADABLE`, `UNREADABLE` winning over `SKIPPED`, all five
  non-FOLLOW kinds skipped with their reason, and a non-integer intended
  quantity skipped rather than rounded;
- **the loop**: agreement produces nothing; drift logs once and heals with a row
  naming its listing (`channelListingId`, `channelConnectionId`, payload
  asserted); a 24 h duplicate is not logged but is still healed; an unreadable
  listing is counted apart and never healed; a **thrown** read is unreadable, not
  a silent pass; an unopenable account makes its listings unreadable and is tried
  **once**; a paused listing is skipped; healing can be switched off; the buffer
  is held back, so Shopify showing the unbuffered number **is** drift; and an
  empty candidate set asks Shopify nothing at all;
- **the habit**: `index.ts` calls `startShopifyQtyReadbackCron()`, and the job
  file calls `cron.schedule(` and validates the schedule first — both with
  comments stripped and a positive control that the stripper left the file.

**Mutation checks — 12 of 12 convicted**, each asserting its edit landed, was
restored byte for byte, and that the runner actually ran:

## 4. What this does NOT do

- **It does not verify a write.** The write already verifies itself, better than
  the other two channels do. This detects drift *between* writes.
- **It does not heal a PINNED or PAUSED listing**, by design (§2.2).
- **It has not run against a real shop.** Whether production has a connected
  Shopify account is one of the three things the Owner owns and it is still
  open — the logs cannot answer it, and Railway reads are blocked for this
  session. The done-when is one `CHANNEL_QTY_READBACK` row, or a cron line
  reading `checked=N unreadable=0` with N > 0.
- **It writes no new route**, so no RBAC manifest entry is needed.
