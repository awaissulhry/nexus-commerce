# P4.4d — the eBay price push, through the one queue

**Date** 2026-09-21 · **Package** P4.4 (Price), fourth slice · **Size** S

The plan row: *"Build the eBay price push (today a stub)."* §4.3:
*"eBay price push in `pricing-outbound` is a stub (`NOT_IMPLEMENTED`)."*

---

## 1. What was measured

### 1.1 The stub is real

`services/pricing-outbound.service.ts` — the G.5.1 dispatcher behind
`POST /pricing/push`, which sends a `PricingSnapshot`'s computed price:

```ts
async function pushEbayPrice(…) {
  logger.warn('eBay outbound push: NOT_IMPLEMENTED', { sku, marketplace })
  return { ok: false, …, error: 'eBay ReviseInventoryStatus adapter not yet wired — see TECH_DEBT.' }
}
```

Shopify, WooCommerce and Etsy fall through to a generic *"not yet wired"*. So of
the five channels this endpoint offers, **one worked**.

### 1.2 🔴 The obvious build is the WRONG build — eBay price pushing already works

The row says "build the eBay price push", and the code says
`ReviseInventoryStatus adapter not yet wired`. Both point at writing an adapter
here. **That would be a second eBay price sender.** eBay prices already go out,
three different ways:

| Path | What it prices |
|---|---|
| `syncToEbay` (outbound-sync) | the eBay **OFFER** endpoint — price and quantity live on different endpoints (Phase 0.1) |
| `ebay-variation-push.service.ts` | a variation group |
| `ebay-shared-listing-push.service.ts` | a shared ItemID, through Trading |

What was missing was never an eBay sender. **It was a way for THIS dispatcher to
reach one.**

And P1.1's ratchet says so in numbers: *channel sends outside the gateway* is
held at **0** across all five channels. A `ReviseInventoryStatus` call here would
need its own exemption — and its own idea of the currency, the push lock, the
market and the destination account. That divergence is precisely what the
ratchet exists to prevent, and it is the *two builders, one lesson* shape this
package has now found six times.

**This is the P3.3 / P4.1c counterweight in a new place:** the row describes a
gap, and the honest answer is that the thing exists and is reached differently.
Say so and build the reach, not the duplicate.

## 2. What was built

`queuePriceUpdate()` replaces `pushEbayPrice()` and serves **eBay, Shopify and
WooCommerce**. It resolves the listing for the coordinate, runs the push lock,
and enqueues one ordinary `PRICE_UPDATE` row.

That row inherits, in one place and for free:

- the push lock, the pause gates and the review verdict (`dispatchSync`);
- the market's currency from `Marketplace.currency` (**P4.4a**);
- the operator's pricing floor and ceiling (**P4.4c**);
- the destination account rule (P1.3) and the call ledger (P1.2);
- and it **names its listing** (**P4.4b**), which is what lets all of the above
  apply — an unnamed price row is now refused at birth anyway.

**It refuses rather than guesses.** No listing for the coordinate → refused.
**Two** listings → refused, naming the ambiguity, never "the first" (MAP.3's
ratchet caught exactly that shape once already). A named account or alias
**narrows the query** rather than filtering after it.

**Etsy is refused on its own terms**, not queued: D6 keeps it read-only through
Wave 4 and it has no price sender at all, so queuing for it would put a row in
the queue for nobody. An unrecognised channel gets a plain sentence.

**The answer is honest about what it did:** `ok: true` with `queued: true` and
the `queueId`. Queued is not sent, and `PushPriceResult` now says which.

## 3. Proof

`pricing-outbound-queue.p44.vitest.test.ts` — **12 tests**: the queued row
asserted field by field (listing, account, product, channel, syncType,
externalListingId) and **`payload.price` with `payload.newPrice` asserted
absent** — P4.4b's repricer defect, pinned so it cannot come back here; Shopify
and Woo taking the same road; Etsy and an unknown channel refused with nothing
queued; no listing and **two** listings both refused; a named account narrowing
the `where`; a locked listing refused with the push lock's own sentence; no
snapshot refused **before any listing read**; and a global assertion that **no
outbound `fetch` happens from this module at all**.

Plus a source guard: the dispatcher contains no `ReviseInventoryStatus`, no
`callTradingApi` / `ebayTransport` / `fetch(`, and no `NOT_IMPLEMENTED`.

**Mutation checks — 7 of 7 convicted:** two listings picked instead of refused,
the row un-naming its listing, the payload key reverting to `newPrice`, the push
lock skipped, Etsy queued, the named account no longer narrowing, and a second
eBay sender added back.

🔴 **The un-naming mutation passed GREEN first**, and it is the P4.3e trap in a
new dress: the marker `      channelListingId: listing.id,` (6 spaces) is a
**substring of** an 8-space occurrence earlier in the same file, and
`String.replace` takes the first match — so it mutated the wrong line.
*Anchor a mutation on something unique to the thing you are convicting*, here
the line above it.

**Gates.** `tsc` clean · gateway ratchet still `{"EBAY":0,…}` with 0 rows
created outside `outbound-rows.ts` — the ratchet is the proof no second sender
was built · market-currency ✓ · full suite **6 failed / 10,414 passed**, the
documented baseline.

## 4. What this does NOT do

- **It does not send.** It queues, and says so. The dispatcher sends.
- **It does not touch the Amazon branch**, which still calls
  `amazonSpApiClient.patchListingPrice` directly. That path predates this row,
  is inside the gateway, and works; folding it into the queue too would be a
  larger change with no defect behind it. Worth doing, not worth doing here.
- **It has not been exercised end to end.** `POST /pricing/push` for eBay needs
  a real snapshot and a real listing; the done-when is one queued row from that
  endpoint reaching eBay with its price.
