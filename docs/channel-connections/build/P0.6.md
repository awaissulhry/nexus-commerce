## 2. Changes

1. `services/amazon-sqs.service.ts` — the parser deletes nothing. A message it cannot act on comes back with `unhandled: '<reason>'` (unknown type, no readable payload, unreadable body — the body is kept, capped at 64 KB, as `{ unparsedBody }` with type `UNPARSEABLE`).
2. `jobs/amazon-sqs-poll.job.ts`:
   - The per-message code is moved, unchanged apart from the points below, into an exported `handleSqsMessage(message, tally)` (the 55-second poll loop is not testable; the loop now calls this function).
   - **Ledger first:** every message is recorded (`recordInbound`) before anything else. If the ledger write fails, nothing is handled and nothing is deleted; the message comes back after its visibility timeout.
   - An `unhandled` message is closed `failed` with its reason, then deleted.
   - Every close uses `completeInbound`: `done` on success, `failed` with the reason otherwise (partial FBA inventory failures, the unconfigured MCF adapter and the defensive "unknown shape" branch are now `failed` with their reason, not `processed` with an error text).
   - **Quarantine:** a message no profile owns is recorded in the legacy profile (the platform's own) as `failed`, reason "Not routed to a business profile: …". If Nexus could not act on it anyway, it is then deleted; otherwise it stays on the queue, so connecting that seller later still processes it (each redelivery increments `attempts` on the same row). If the quarantine write fails, the message stays on the queue.
3. `services/amazon-notifications-boot.service.ts` — `ORDER_STATUS_CHANGE` removed from the subscribed types (the parser still reads a stray one). New `runAmazonNotificationSetup()`: with profiles OFF it runs once as before; with profiles ON it visits each active profile and runs the setup only where an active Amazon account exists; a failure in one profile is logged and recorded (CronRun) and does not stop the others. The boot hook calls it.
4. `routes/amazon-notifications.routes.ts` — the admin setup route answers with the canonical list, not a copy.

Not in this package (they are P2.1 / P2.2): dedupe on Amazon's `NotificationId` instead of the SQS message id; payload versions per type; the order-change fields under `Summary`; new subscription types; a nightly reconcile; a retry worker, dead-letter queue and replay button.

## 3. Proof

- **New** `jobs/amazon-sqs-poll.p06.vitest.test.ts` (15 tests). The real parser and the real handler run; the SQS client, the ledger, the seller → profile index and the order sync are stand-ins that write one shared timeline, so "recorded before deleted" is checked in order.
  - Positive control: an MFN order for a connected seller → recorded in its profile, synced, closed `done`, deleted — in that order.
  - Unknown type, account status with no payload, feed finished with no payload, FBA inventory with no items, order with no payload: each recorded in its profile, closed `failed` with the reason, and deleted only after the record.
  - An unreadable body: recorded in the legacy profile as `failed` with both reasons ("Not routed…" + "could not be read"), then deleted.
  - An order for a seller no profile owns: recorded in the legacy profile as `failed`, **kept** on the queue, not synced.
  - Ledger down: 0 handled, 0 deleted.
  - A failed order sync: closed `failed`, kept for retry. An FBA order: recorded first, closed `done`, deleted, no sync. Profiles OFF: the same record-then-delete rule.
  - Subscriptions: `ORDER_STATUS_CHANGE` absent, `ORDER_CHANGE` present; with profiles ON the setup runs only in the profile with an Amazon account (3 visited, 1 ran) and a failing profile does not stop the rest; with profiles OFF it runs once.
- **Mutation check** (each made, run, restored, compared byte for byte): the parser deletes an unknown type silently again → 3 fail; no ledger guard → 1 fails; the quarantine does not record → 2 fail; setup in every profile → 1 fails; `ORDER_STATUS_CHANGE` back → 1 fails.
- `tsc --noEmit` (apps/api): 0 errors. Guards: context boundary, route-prisma ratchet, cron-clustered, MAP.0 connection ratchet — all pass.
- Full API suite, run twice (from `apps/api`, local database): **9524 passed, 6 failed, 46 skipped; 2 failed files**, the two known Amazon local-account files. One of the two runs also printed a runner teardown error (`EnvironmentTeardownError … onUserConsoleLog`) attributed to `services/pim/publish-review-gate.vitest.test.ts`; it is intermittent, moves between unrelated files (P0.3's run named `studio-publication-transports`), and did not change any count.

- `handleSqsMessage` keeps the old per-type code and its deep indentation (moved, not rewritten). P2.1 will replace the per-type branches with a handler table.
