# P4.3c — a quantity push must name its listing

**Date** 2026-09-20 · **Package** P4.3 (Stock), third slice · **Size** M

The plan row: *"Every quantity producer through the resolver (fix the catalog
PATCH first)."*

---

## 1. What was measured

### 1.1 The resolver is real, and the cascade already uses it

`resolveIntendedQuantity` (`services/sync-control-core.ts:169`) is the one place a
quantity is decided: FBA excluded → offer closed → policy paused → listing paused
→ pinned → routed follow, minus the buffer. The stock movement cascade
(`services/stock-movement.service.ts:821`) calls it **per listing** and queues one
row per listing, each naming its `channelListingId`. That is the correct producer
and it was never the problem.

### 1.2 The defect: a quantity row that names no listing turns three guards off

`syncToAmazon` loads the listing **only** from `queueItem.channelListingId`:

```ts
let cl: any = null;
if (queueItem.channelListingId) { cl = await prisma.channelListing.findUnique(…) }
```

With `cl` null, three things that are "ON by default" are silently off:

| Guard | Gate | With no listing |
|---|---|---|
| Send-time re-read (`resolveDispatchQuantity`) | `… && cl && payload.quantity !== undefined` | **skipped** — the enqueue-time snapshot goes out |
| Stock buffer in the oversell clamp | `cl?.stockBuffer ?? 0` | **0** — the buffer is not held back |
| Amazon EU shared-quantity guard (D9) | `AMAZON_EU_SHARED_MARKETS.has(String(cl?.marketplace ?? ''))` | **never runs** — `''` is in no set |

🔴 The third is the one that matters: **P4.3b made that guard fail closed one
slice ago, and this row walks around it entirely.** A guard cannot fail closed on
a check it never reaches.

Shopify has the same shape (`shopifyDispatchQuantity`: `cl` only when
`channelListing?.id`), and its fallback is `payload?.quantity ?? 0` — a quantity
row with no quantity would push **zero**.

🔴 **And it is a drift inside ONE function.** `pushLockListings`, two hundred
lines above `syncToAmazon` in the same file, resolves the listing from
`productId + channel + market` when the row names none. The same file asks "which
listing is this row for" twice and only one of the two answers can cope. That is
the two-builders shape, at a range of two hundred lines.

### 1.3 The producer the plan names, and its twin that got it right

`PATCH /api/catalog/products/:id` (`routes/catalog.routes.ts`) did **both**:

1. `applyStockMovement(...)` → the cascade → correct per-listing rows. ✅
2. `outboundSyncService.queueProductUpdate(id, channel, 'QUANTITY_UPDATE',
   { quantity: totalStock })` → a second, product-level row carrying the
   **gross** total, naming no listing, racing the first. ❌

`queueProductUpdate` sets `productId`, `targetChannel` and `externalListingId`
and nothing else — no listing, no connection, no market. So the row takes
`AMAZON_DEFAULT_MARKETPLACE` (`'IT'`), resolves an account through
`resolveDestinations` step 3 (one account holds the product → it sends), and
pushes gross stock with no re-read, no buffer and no EU guard.

🔴 **The comment 60 lines above it says the opposite of what the code does:**
*"P0/B5 — basePrice + totalStock route through services so the ChannelListing
cascade (Phase 13) + StockMovement audit (H.1/H.2) all fire."* True, and then it
queues the raw number anyway. *A comment can assert a property the code lacks.*

**Its twin already had it right.** `PATCH /api/products/:id`
(`routes/products-catalog.routes.ts:1210`) — the same edit, from the product
drawer — calls `applyStockMovement` and queues **nothing**. One builder learned
the lesson; the other did not.

**This is a live operator path**, not dead code: `ProductDrawer.tsx`,
`VariantCube.tsx`, `VariationMatrix.tsx` and `VariationsTab.tsx` all PATCH
`totalStock`.

### 1.4 The census, and why the first one was wrong

A derived census over `syncType: 'QUANTITY_UPDATE'` literals found 16 sites that
name a listing, 1 shared-eBay Trading site, and **0 bare rows**. That census was
**wrong**, and wrong in the way this file has already recorded twice: *a
literal-only scan under-counts.* The catalog PATCH passes its syncType as a
**ternary argument** to `queueProductUpdate`, so it is invisible to any scan for
the string.

Re-derived over creation *call sites* instead: **74 sites reach
`createOutboundRow` / `createOutboundRows` / `createOutboundRowsAndReturn`.**
Exactly two produce a bare quantity row, both through `queueProductUpdate`:
`routes/catalog.routes.ts` (the plan's row) and `POST /api/outbound/queue`
(`routes/outbound.routes.ts:192`, a manual endpoint the web app never calls —
it only uses the DELETE and retry verbs on an existing queue id).

**The lesson for the next census:** ask what could carry the fact *other than the
spelling you searched for*. Here it was a function argument.

## 2. What was built

### 2.1 The rule, in the engine

`services/outbound-rows.ts` — `quantityRowTarget(row)` returns one of
`NOT_A_QUANTITY_ROW` / `LISTING` / `SHARED_ITEM` / `UNNAMED`.

- **carries a quantity** = `syncType === 'QUANTITY_UPDATE'` **or**
  `payload.quantity !== undefined` **or** a non-empty `payload.updates`. Either
  half alone is not enough: a QUANTITY_UPDATE that re-reads at dispatch carries
  no `payload.quantity`, and a FULL_SYNC can carry one (that is the catalog
  PATCH's price+stock shape).
- **names its target** = a non-empty `channelListingId` in any of its three
  forms (scalar, `channelListing.connect.id` for the checked create,
  `channelListing.id` for a loaded row), **or** the shared-eBay lane
  (`payload.pushVia === 'TRADING'` **and** an ItemID). An ItemID alone is not
  enough — a single eBay listing row must not slip through on one.

`prepareRows` throws `UnnamedQuantityRowError` on `UNNAMED`. **That is the one
place every creation site passes through** (P1.3, and the gateway ratchet holds
it at *"queue rows created outside services/outbound-rows.ts: 0"*), so the rule
cannot be forgotten by a 75th producer. It runs **before** the destination
lookup, so the refusal is never reported as "no account" — a different fact with
a different fix.

### 2.2 The producer

`routes/catalog.routes.ts` no longer puts `totalStock` in the outbound payload
and no longer queues a quantity row; the cascade owns it, as in the twin route.
The syncType is now derived from **what the payload actually carries**, not from
which request fields were present — so a stock-only edit is not still labelled
`QUANTITY_UPDATE`.

### 2.3 The dispatcher, for the rows already in the queue

`dispatchSync` refuses an `UNNAMED` quantity row with `UNNAMED_QUANTITY_ROW`,
terminal (`retryable: false`), before the channel switch. Rows born after this
slice cannot be in that state; this arm is for rows the queue already holds.

**Placement.** It sits **last** of the shared refusals — after the lifecycle
refusal and after the content-review verdict — so neither is masked (P4.1c's
lesson, and a test poses the same row as a `DELETE_LISTING` to prove the older
verdict still answers first). It sits before the channel switch rather than
inside each channel because **every** channel resolves its listing from
`channelListingId` alone and every one loses its re-read without it.

## 3. Proof

`src/services/unnamed-quantity-row.p43.vitest.test.ts` — **28 tests**, four
propositions kept apart:

- **A. the VALUE**, 16 rows through `quantityRowTarget`, including the traps:
  `quantity: 0` counts (the zero-inventory value is the dangerous one), an empty
  and a whitespace listing id do not count as names, and an empty
  `payload.updates` does **not** turn a price row into a quantity row
  (`Array.isArray([])` is `TRUE`).
- **B. the row never exists.** `createOutboundRow` and `createOutboundRows`
  throw, `create` / `createMany` are **never called**, and
  `resolveDestinations` is never reached. Two positive controls: the same row
  with a listing is created, and the shared eBay fan-out row is created.
- **C. dispatch**, per channel: refused, terminal, and **no adapter entered**.
  Plus the masking control and two positive controls (a listing, a shared
  ItemID).
- **D. the producer**: `catalog.routes.ts` assigns no `syncPayload.quantity` and
  names no `QUANTITY_UPDATE`, with comments stripped first (the new comment
  quotes the code it replaced) and a positive control that the stripper did not
  empty the file.

**Mutation checks — 6 of 6 convicted**, each asserting its own edit landed and
that the runner actually ran (`Tests <n>`, no `Startup Error`):

| Mutation | Red test |
|---|---|
| the engine refusal removed | `createOutboundRow throws and writes nothing` |
| the dispatch refusal removed (`if (false && …)`) | `AMAZON: refused, terminal, and no adapter is entered` |
| an empty listing id counts as a name | `empty string listing id → UNNAMED` |
| `payload.quantity` no longer counts | `FULL_SYNC carrying a quantity → UNNAMED` |
| an ItemID alone passes as the shared lane | `externalListingId without pushVia → UNNAMED` |
| the catalog PATCH puts the gross quantity back | `never puts a quantity in the outbound payload` |

**Gates.** `tsc --noEmit` clean. Gateway ratchet
`{"EBAY":0,"AMAZON_SP":0,"AMAZON_ADS":0,"SHOPIFY":0,"ETSY":0}` and *"queue rows
created outside services/outbound-rows.ts: 0"*. `check-push-lock.mjs` still the
one pre-existing FAIL (`studio-publication-amazon.ts:164`), unchanged.

**Full API suite: 6 failed / 10,308 passed**, which is exactly the documented
baseline (`clients/amazon-validation-preview` 5 + `services/marketplaces/
amazon-classifications` 1, both reading a local Amazon account).
`services/assortment/copy-preview` failed in a full run and **passes alone** —
the known under-load flake, not this change.

**Two existing tests had their FIXTURES corrected, not their propositions.** In
both, the proposition is untouched and the fixture was unrepresentative:

- `outbound-sync.lifecycle.vitest.test.ts` — its positive control ("an ordinary
  row of each syncType reaches its adapter") used a `QUANTITY_UPDATE` with no
  listing. It now names one, as every real row of that type does.
- `outbound-rows.p13.vitest.test.ts` — its ambiguous-destination case used a
  product-level `QUANTITY_UPDATE`. It is a `PRICE_UPDATE` now; the proposition
  (an ambiguous destination writes no account) is unchanged, and it can no
  longer be posed with a quantity because that shape no longer exists.

## 4. What this does NOT do

- **It does not change how a quantity is computed.** The resolver and the
  cascade were already right. This closes the path that went around them.
- **It does not fix the Amazon clamp's location scope** (the clamp still uses
  every warehouse row rather than the routed ones). That is the next P4.3 row.
- **It does not resolve a listing for a legacy row.** A bare row is refused, not
  repaired. Refusing is the fail-closed answer: a product-level row can match
  several markets, and pushing one gross number to all of them is the EU
  incident D9 exists to stop.
- **It cannot be proven by real traffic yet** — same as every P4 slice. The
  done-when is an operator stock edit from the product drawer producing only
  per-listing rows in `OutboundSyncQueue`, each with a `channelListingId`.

## 5. 🔴 Measured here, belongs to P4.4 (price) — already done, do not re-measure

**`syncPayload.price` in the same catalog PATCH is the identical defect for
price, and it is still there.** `masterPriceService.update`
(`services/master-price.service.ts:264`) cascades `PRICE_UPDATE` rows **per
listing** inside the same transaction, exactly as the stock cascade does — and
then the route queues a second, product-level price row beside them.

It was left in place on purpose: price is P4.4, and this slice is P4.3. Take it

is the same: delete the producer's duplicate, and consider whether
`quantityRowTarget`'s rule should widen to any row that carries a **price**.
