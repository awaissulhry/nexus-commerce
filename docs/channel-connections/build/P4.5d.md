# P4.5d — the Reports v3 media type, and the parity that outlives it

State: **BUILT 2026-09-21**, committed locally. Part of P4.5 (advertising).

Plan row (FINAL-PLAN.md §6, P4.5): *"the v3 report content type in the client"*.
Plan §4.5: *"The client's `fetchReport` sends no v3 content type, while the report
service does (:2153)."*

## 1. Evidence — the row is TRUE, and it is a drift, not a breakage

Both builders POST to the same endpoint, `/reporting/reports`:

| Builder | media type it sent |
|---|---|
| `services/advertising/ads-reports.service.ts:createReportJob` | `application/vnd.createasyncreportrequest.v3+json` |
| `services/advertising/ads-api-client.ts:fetchReport` | none → the default `application/json` |

**Measured**, not assumed. 1,197 real `POST /reporting/reports` rows in
`OutboundApiCallLog` (development database, 2026-08-05 → 2026-09-08):

| status | n | what it proves |
|---|---|---|
| 200 | **1,135** | accepted |
| 400 | 47 | `configuration columns includes invalid values: (__nope__)` — deliberate probes |
| 425 | 9 | Amazon's documented *"duplicate of &lt;reportId&gt;"* dedupe |
| 429 | 1 | throttle |
| null | 5 | transport |

🟢 **Zero 415 Unsupported Media Type.** And splitting the failures by builder (the
recorder keeps the request payload on failure, and the two name their reports
differently — `nexus-…` vs `<adproduct>-…`): **10 of the 400s and all 9 of the 425s
were made by `fetchReport`**, the builder *without* the media type. A 400 "invalid
column" and a 425 "duplicate of" are answers Amazon can only give **after parsing the
body**. Amazon accepts `application/json` on this endpoint today.

This is a **counterweight with a real fix inside it** — the eleventh in the programme.
The media type is corrected because Amazon documents it and can enforce it at any
time. The part that matters is the parity test.

🔴 **Two builders on one endpoint is the banked trap**
(`reference_two_column_builders_drift`): *"put the rule in the engine, assert parity in
the gate."* A required header surviving missing in one of two builders for months is
precisely that shape, and nothing would have caught the next divergence either.

**`fetchReport` is not a dead path.** Its callers are
`ads-metrics-ingest.service.ts` (the daily campaigns / adGroups / keywords / productAds
ingest) and `ads-tos-is-ingest.service.ts` (the nightly Top-of-Search job) — the
advertising money path.

## 2. Changes

1. `ads-api-client.ts` — **new exported** `REPORT_V3_MIME`, and `fetchReport`'s create
   now sends `contentType: REPORT_V3_MIME`.
2. `ads-reports.service.ts` — its literal replaced by the same constant.
3. `ads-reports-profiles.vitest.test.ts` — its `vi.mock` of the client gained
   `REPORT_V3_MIME`. **7 tests failed first** with the mock missing the new export;
   that is the honest cost of moving a value into a shared module, the same cost P4.4a
   paid with 19 test doubles. No expectation was changed.

**Deliberately NOT changed:** the status poll (`GET /reporting/reports/:id`) and the
pre-signed S3 download. `…createasyncreportrequest…` describes the CREATE body; putting
it on the poll or the download is the obvious over-application, so a test pins that it
is absent there.

## 3. Proof

- **New** `services/advertising/ads-report-mime.p45d.vitest.test.ts` (5): both builders
  are found (a positive control, because an empty census is not a pass); both send the
  v3 media type through the same constant; the constant's value; neither file spells a
  second literal; and the poll does not carry the create media type.
- The builder finder slices from each `liveCall` to its own closing `})` rather than a
  fixed window. A fixed window failed first: the client's request body is ~1.5 KB of
  columns on its own, so a short window read as *"no media type"* when the truth was
  *"did not look"* — "could not measure" wearing "measured empty"'s clothes.
- **Mutation check** (made, run, restored, compared):
  | Mutation | Tests that failed |
  |---|---|
  | the client goes back to no media type | **1** |
  | the service spells its own literal again (the drift itself) | **2** |
  | the constant's value is wrong | **2** |
- `tsc --noEmit` (apps/api): 0 errors. `services/advertising`: **1471 passed, 110 files**.

## 4. Production proof — OPEN

Nothing should change. The measurement says Amazon already accepts these requests, so
the proof is that the daily ingest keeps returning 200 — and specifically that
`POST /reporting/reports` shows **no new 415** after the deploy.

Open on production: the same status census against production's `OutboundApiCallLog`.
If production shows 415s that dev does not, the media type was doing real damage there
and this slice is a fix rather than a tidy-up.
