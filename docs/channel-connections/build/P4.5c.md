# P4.5c — the Amazon Ads consent page, per region

State: **BUILT 2026-09-21**, committed locally. Part of P4.5 (advertising).

Plan row (FINAL-PLAN.md §6, P4.5): *"Ads: consent page per region"*.
Plan §4.1: *"Amazon Ads uses the North America consent page for every region
(`services/cx/connectors/amazon-ads/spec.ts:189`). Research says the EU page is
`eu.account.amazon.com`."* §13.3 marks sign-in **STANDARD after P4.5**, with the
NA-only consent page as the **GAP**.

## 1. Evidence — and the decision this slice had to make first

**The gap is real as a capability, and is NOT a live breakage.** Two independent
pieces of evidence say the North American page works for this EU account:

1. The grant it runs on **was obtained through `https://www.amazon.com/ap/oa`** — nine
   EU advertising profiles, 469k logged calls, a heartbeat that returns 200.
2. `services/cx/connectors/amazon-ads/spec.ts` says so in its own header, written by a
   session that had already tried the regional hosts:
   > *"The hosts below are the ones the flow that actually works uses today … not the
   > regional ones this file guessed while it was a stub … A catalogue that disagrees
   > with the working flow is worse than no catalogue."*

🔴 **So changing the default would risk a live, working sign-in to close a gap nobody
has hit** — and a broken consent redirect is discovered by an operator, mid-connect,
with no way to tell whether the page or the app is at fault.

This is the **P4.1c / P4.3e shape**: the plan row names a real gap, and the right move
is not the one the row's wording implies. It is also the symmetric case to P4.4c — the
scepticism has to point at "obviously fix it" as hard as at "leave it alone".

**Two call sites** decide a consent host: `routes/amazon-ads-auth.routes.ts:309` (the
live flow) and `services/cx/connectors/amazon-ads/spec.ts:188` (the workspaces flow).
Both said `www.amazon.com`.

**The token endpoint is not regional.** `api.amazon.com/auth/o2/token` serves all three
regions. Making it regional is the obvious next "fix" and would break every exchange,
so a test pins it.

## 2. Changes

1. `services/ads-core/ads-regions.ts` — `ADS_CONSENT_HOSTS` (three pages) and
   **`adsConsentUrl(region)`**, which returns the **North American page for every
   region** unless `NEXUS_ADS_CONSENT_REGIONAL=1`.
   - It cannot refuse an unknown region the way `adsHostFor` does. Refusing here means
     an operator clicking **Connect** gets an error page instead of Amazon. NA is the
     page that demonstrably works, so it is the right floor.
2. `routes/amazon-ads-auth.routes.ts` — `/connect?region=EU|NA|FE` names the region;
   unset means EU (the grant's home). The chosen host is **logged** with the state, so
   a failed sign-in says which page it went to instead of leaving that to be guessed.
   That is the one diagnostic this gap needs when it finally bites.
3. `services/cx/connectors/amazon-ads/spec.ts` — `authorizeUrl: (ctx) => adsConsentUrl(ctx.region)`.
   One decision, shared.

**When to flip it:** when an advertiser whose Amazon account is EU-only or FE-only
cannot sign in at the North American page. That is the symptom this gap produces.

**Source honesty:** the three consent hosts come from the plan's own research
(§4.1, recorded 2026-08-29). They were **not re-verified against Amazon's pages** in
this session, and the comment on `ADS_CONSENT_HOSTS` says so.

## 3. Proof

- **New** `services/ads-core/ads-consent.p45c.vitest.test.ts` (8): OFF by default for
  all five inputs including nonsense; ON gives each region its own page; ON with no
  region floors to NA rather than throwing; three distinct hosts; the token endpoint is
  pinned as non-regional; a census that neither call site spells a host itself, with a
  positive control that both go through the accessor; and that the route logs the host.
- 🟢 **The default-unchanged control was already in the repo.**
  `spec.vitest.test.ts:72` has asserted since CX.3a that
  `authorizeUrl({ region: 'EU' })` is `https://www.amazon.com/ap/oa`. It still passes,
  untouched — which is a stronger statement than a test written today alongside the
  change.
- **Mutation check** (made, run, restored, compared):
  | Mutation | Tests that failed |
  |---|---|
  | the default becomes regional (the change this slice refused to make silently) | **2** — including the pre-existing spec test |
  | the switch is ignored, so the capability is fake | **1** |
  | the route decides the host itself again | **2** |
- `tsc --noEmit` (apps/api): 0 errors. `services/cx/connectors/amazon-ads`: 14 passed.

## 4. Production proof — OPEN

Nothing to observe: with `NEXUS_ADS_CONSENT_REGIONAL` unset, every consent URL is
byte-identical to before, which is the proof that shipping it changed nothing.

The open question is the Owner's and needs a **live channel call** (a connect), so it
is not done here: does `https://eu.account.amazon.com/ap/oa` accept this account's
sign-in? If it does, the variable can go on and the plan's §13.3 row moves to STANDARD
for real. If it does not, the current default is not a gap at all for this account and
the row should be marked as such.
