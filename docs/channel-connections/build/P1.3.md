# P1.3 — The queue carries its destination account

State: **BUILT (2026-09-19).** P1.3a and P1.3b+c committed locally, not pushed. **A second-account row goes to the second account** (test below).

Plan row (FINAL-PLAN.md section 6, P1): add a `channelConnectionId` column to `OutboundSyncQueue` (additive), fill it before queueing, use it at send time; per-account concurrency; limit the 1-minute backup loop; one enqueue function for all sites, so the listing-claim check always runs. Done when: a second-account row goes to the second account; the P0.7 guard is removed.

## 1. P1.3a — every row is created with its account

| Piece | What it does |
|---|---|
| Migration `20260919b_p13_queue_destination` | `ALTER TABLE "OutboundSyncQueue" ADD COLUMN "channelConnectionId" TEXT`. Additive, nullable, no default, no backfill, no index (rows are read by id at send time). Applied to the LOCAL database only. |
| `services/outbound-destination.ts` `resolveDestinations` | The account of each row, batched (a few reads for any number of rows): 1. the account the row names; 2. the account of the listing it names; 3. for a product-only row, the ONE account holding that product in the row's market (UK = GB); 4. else the channel's ONLY account. Two or more candidates → **no account** (`AMBIGUOUS`), never "the primary" (D7). An unreadable account list leaves the row unresolved instead of failing the save. |
| `services/outbound-rows.ts` | The one way to create a queue row: `createOutboundRow` / `createOutboundRows` / `createOutboundRowsAndReturn` — the same arguments and answers as Prisma's `create` / `createMany` / `createManyAndReturn` (typed with Prisma's own create-input types), plus the **listing-claim check** (BP.S3) and the destination account. A light module (no queue import). The claim check's grant read now uses the caller's client, so inside a transaction it takes no second connection. |
| 35 creation sites in 26 files | Each call changed from `x.outboundSyncQueue.create(…)` to `createOutboundRow(x, …)` (and the two batch forms). Sites that already hold the listing pass its account (follow-master, matrix write, master content): no extra read in their transaction loops. |
| Ratchet | `channel-gateway-ratchet.mts` also counts `….outboundSyncQueue.create / createMany / createManyAndReturn / upsert(` outside `outbound-rows.ts` / `outbound-enqueue.ts`. Baseline **0**. |

What changes now: nothing is sent differently yet — the sender still resolves its account as before (P1.3b switches it). The claim check now runs for every row; it only does work with business profiles ON and a **shared** account (one indexed read otherwise), so accounts nobody shares see no change.

## 3. P1.3b — the sender uses the row's account

- `outbound-sync.service.ts` `destinationOf(row)`: the account written with the row; for a row from before P1.3, the same rule (`resolveDestinations`). **No account → refused, terminal, 0 calls** (`NO_DESTINATION_ACCOUNT`, "more than one eBay account holds this product …"). Never the primary.
- eBay (Inventory API path and the shared Trading path) resolve `tryResolveConnection({ accountId: destination })` — the `{ channel: 'EBAY', primary: true }` lookups are gone from the queue. Amazon asks for the seller of the row's account (`getAmazonSellerId(destination)`), not the default seller.
- **P0.7 in the queue:** its stopgap meaning ("refuse anything not on the primary") is gone — the row goes to its own account. The ownership check (`assertWriteAccount`) stays as a consistency check against that account: a row that names account A for a listing of account B is still refused. Outside the queue (flat file, bulk actions, wizard, image publishers) P0.7 stays until those paths name their account (MAP.7, D7).

## 4. P1.3c — per-account concurrency and the backup loop

- **Per-account slots** (`workers/bullmq-sync.worker.ts` `takeAccountSlot`): the worker runs 5 jobs for all channels together; a job whose account already has `NEXUS_OUTBOUND_ACCOUNT_CONCURRENCY` (default **2**) running in this process is postponed ~1 s with BullMQ's own delayed move (not a failure, no attempt used). One account's backlog can no longer take all 5 slots. A row without an account is not limited.
- **Backup loop:** the 1-minute drain now takes the oldest `NEXUS_OUTBOUND_BACKUP_BATCH` (default **200**) pending rows per tick; before, it read every pending row in one tick.
