# P4.5f — nothing creates a deprecated Sponsored Brands entity by accident

State: **BUILT 2026-09-21**, committed locally. Part of P4.5 (advertising).

Plan row (FINAL-PLAN.md §6 deadline table, 2026-07-06): *"Sponsored Brands 'Product
collection' ad entity deprecated in favour of Manual / Auto Collection (**CONFIRMED**).
A full shut-off in January 2027 is reported by a third party only (**NOT CONFIRMED** on
Amazon's pages). **CODE:** Sponsored Brands creation defaults to
`creativeType: 'productCollection'` (`services/advertising/ads-create.service.ts:940`).
→ P4.5: default to Manual Collection."*

## 1. Evidence

**The defect is real and is a silent default.**
`createSbAdLocal` read `const creativeType = input.creativeType ?? 'productCollection'`.
Its **one** caller, `POST /advertising/sb-creatives/create`
(`routes/advertising.routes.ts:8347`), passes the request body straight through as
`never`. So an operator who simply did not mention a creative type got the deprecated
entity, with nothing said.

**The path has never run.** Measured on the development database 2026-09-21:

| | |
|---|---|
| `POST /sb/v4/ads` in `OutboundApiCallLog` | **0** |
| `POST /sb/v4/ads/list` (the read) | 285 |
| `AdProductAd` rows with `adType: 'BRAND_AD'` | **0** |

So the default has never actually produced a deprecated ad — which is what makes this
cheap to fix and impossible to verify against a real Amazon answer.

### 🔴 The line this slice would not cross: renaming the wire value

The plan row says *"default to Manual Collection"*. **The wire value for Manual / Auto
Collection could not be established.**

- Amazon's `POST /sb/v4/ads` API reference renders only with JavaScript — P0.8 hit the
  same wall on the deprecations page — so `WebFetch` returned only the page title.
- Two web checks (2026-09-21) produced third-party write-ups and no enum.
- With 0 stored calls there is no Amazon answer in `OutboundApiCallLog` to derive it
  from either.

Swapping a value Amazon **still accepts** — it deprecated the entity, it did not remove
it, and Amazon's own note carries **no shutdown date** — for a guessed one, on a path
that has never run, is the worse trade. *Predict before you write* cuts both ways: a
change whose correct value cannot be stated in advance is not a fix.

**The same restraint applies to the casing.** Every other enum this client sends on SB
v4 is upper-cased (`state: (…).toUpperCase()`), and `adType: 'productCollection'` is
not. That is a smell recorded in the vocabulary file, **not a finding** — nothing
available can tell "wrong case" from "this endpoint's convention".

**One thing the web check did add, and it is recorded with its status:** two
third-party sources report that since **September 2026** Amazon auto-converts newly
created Product Collection campaigns to Manual Collection. Reported, not confirmed on
Amazon's pages — the same standing as the January 2027 date P0.8 recorded.

## 2. Changes

1. **New** `services/ads-core/sb-ad-types.ts` — the three SB creative types, each with
   its wire value, its label, and its deprecation (date, replacement, shutdown date,
   **source**). `sbAdTypeWire()` refuses a type the file does not name;
   `sbAdTypeNotice()` returns the sentence for a deprecated one.
   - `shutdownDate` is **null**, not January 2027. Storing a third-party date as if it
     were Amazon's is how a rumour becomes a deadline.
2. `ads-create.service.ts` — **no default**. An omitted `creativeType` is refused with a
   sentence that names the deprecation and lists the choices. An explicitly chosen
   deprecated type is still **sent** (refusing would break an operator deliberately
   matching an existing campaign's format) and **logged** as deprecated.
3. `ads-api-client.ts` — `adType: sbAdTypeWire(input.creativeType)`: one vocabulary.

## 3b. ✅ CLOSED 2026-09-21 (later) — and the row was asking the wrong question

§4 below says this needs *"the `adType` enum read off Amazon's **rendered** API reference — the
page needs a JavaScript-capable browser"*. It does not. **The page renders with JavaScript; the
data does not need it.**

Opening the reference in a real browser and reading its **network requests** shows what it
fetches:

```
GET https://d3a0d0y2hgofx6.cloudfront.net/openapi/en-us/sponsored-brands/4-0/openapi.json → 200
```

583 KB of plain JSON, `info.version: 4.0`, downloadable with `curl`. 🔴 **"The docs need
JavaScript" is a claim about the renderer, not about the data — ask what the page fetches.**

### What the document says, with a positive control

| the row assumed | Amazon's 4.0 document |
|---|---|
| a discriminator field `adType` | 🔴 **`adType` appears 0 times** (control: `PRODUCT_COLLECTION` appears 7) |
| one endpoint `POST /sb/v4/ads` | 🔴 **`/sb/v4/ads` is `PUT` only** — `UpdateSponsoredBrandsAds` |
| "Manual Collection" as an enum value | ✅ it is an **endpoint**: `POST /sb/v4/ads/manualCollection` |

**Creation is one endpoint per creative type:** `/productCollection`, `/manualCollection`,
`/autoCollection`, `/storeSpotlight`, `/video`, `/brandVideo`, `/productCollectionExtended`.

So there was never a wire value to find. The creative type chooses the **path**.

### 🔴 The request would have failed on four counts

```
POST /sb/v4/ads  { ads: [{ campaignId, adGroupId, adType, creative, landingPage, state }] }
```

1. `/sb/v4/ads` does not accept POST.
2. `adType` is not a field.
3. `campaignId` is not part of a create-ad item — an ad belongs to its **ad group**.
4. `name` is **required** on every create endpoint and was not sent.

Nobody knew because `/sb/v4/ads` has **0 calls ever** in `OutboundApiCallLog`. This is P4.4d's
shape — *the plan row described the wrong build* — and the original slice's restraint was still
correct: it refused to guess, and the guess would have been wrong in a way guessing could not fix.

### What was built

`services/ads-core/sb-ad-types.ts` — the vocabulary now records, per type, its **`createPath`**,
where the landing page goes, what the headline field is called, and whether ASINs are required.
Those differ **in Amazon's document**, which is why the request is built per type rather than from
one template:

| type | endpoint | landing page | headline field | asins |
|---|---|---|---|---|
| productCollection *(deprecated)* | `/sb/v4/ads/productCollection` | on the **ad** | `headline` | optional |
| **manualCollection** | `/sb/v4/ads/manualCollection` | 🔴 **inside the creative** | 🔴 **`title`** | **required** |
| storeSpotlight | `/sb/v4/ads/storeSpotlight` | on the ad | `headline` | optional |
| video | `/sb/v4/ads/video` | 🔴 **none** | 🔴 **none** | optional |

`sbAdTypeWire` is gone (it returned a value for a field that does not exist) and `sbAdCreatePath`
replaces it. `sbAdCreateRequest` — **pure and exported** — builds the path and body, so every
type's shape is testable without a network; `createSbAd` is now a thin call around it.

**`manualCollection` is now a first-class type**, which is what the plan row wanted. It is *not*
made the default: `createSbAdLocal` still refuses an unnamed `creativeType` (the P4.5f rule that
already shipped), and the deprecation notice for `productCollection` is unchanged — Amazon
deprecated it with **no shutdown date**, and its endpoint is still in the document.

### Proof

- `services/advertising/sb-ad-request.p45f.vitest.test.ts` (**16**, new) — the four old defects
  each asserted absent; every required field of `CreateProductCollectionAd` present, derived from
  the document's own `required` list; and each type's shape, including 🟢 a positive control that
  a type whose schema does **not** require ASINs is still accepted without them.
- `sb-ad-types.p45f.vitest.test.ts` rewritten (**14**) — its source-text assertion about
  `adType: sbAdTypeWire(...)` is gone, because the claim it pinned is no longer true.
- **8 mutations, 8 killed**, with a 🟢 null control that survived: one path restored, `adType`
  returned, `name` dropped, landing page forced onto the ad, landing page removed from the
  creative, the headline field hardcoded, the ASIN guard disabled, and `state` left lower-case.
- `tsc` clean; `src/services/ads-core` + `src/services/advertising`: **137 files, 2019 tests
  passed.**

### Still open

Nothing in this row. The path still has **0 calls ever**, so this is proven against Amazon's
published contract and **not** against Amazon's server — a real `POST` remains a live channel call
and the Owner's to authorise. The difference from before is that the request is now built from
Amazon's own document rather than from a shape nothing had checked.

## 4. Why the row WAS open (superseded by §3b — kept as the record)

**This row is NOT finished, and saying otherwise would be the false green.** To move
Sponsored Brands onto Manual Collection, one of:

1. A captured **200 from a real `POST /sb/v4/ads`** (which is a live channel call and
   needs the Owner's yes), or
2. the `adType` enum read off Amazon's **rendered** API reference — the page needs a
   JavaScript-capable browser, which this session did not use.

Until then the behaviour is: nothing chooses the deprecated entity for you, and
choosing it deliberately says so in the log.

**Production proof:** nothing to observe. The path has never run, so the only visible
change would be a 500 from `/advertising/sb-creatives/create` with the new sentence if
an operator posts without a `creativeType`.
