# P2.4 — Shopify webhooks

**Built 2026-09-20.** Plan row: *register by GraphQL and reconcile per shop; per-shop
secret; add `app/uninstalled`, `app/scopes_update` and the 3 privacy topics; route to the
owning business profile.* Done when: *uninstall flips the account to revoked; a second
update to the same product is processed.*

---

## 1. What was measured first

### 1.1 The Shopify inbound path had THREE independent reasons to deliver nothing

P2.1 found the first: the receivers ran with no business profile, so every ledger write
threw into a catch block. Fixing that was necessary and **not sufficient**.

**Second — the signing secret does not exist in production.** The receivers read
`ConfigManager.getConfig("SHOPIFY").webhookSecret`, which is
`process.env.SHOPIFY_WEBHOOK_SECRET`, and that config object only exists when
`SHOPIFY_SHOP_NAME`, `SHOPIFY_ACCESS_TOKEN` and `SHOPIFY_WEBHOOK_SECRET` are **all** set.

Measured locally, through the real modules:

```
env SHOPIFY_WEBHOOK_SECRET : (unset)
env SHOPIFY_SHOP_NAME      : (unset)
env SHOPIFY_ACCESS_TOKEN   : (unset)
ConfigManager.getConfig("SHOPIFY") -> UNDEFINED  <-- the receiver answers 400
ChannelApp clientSecret    : afaf6fb86c84 (len 38)
SAME SECRET?               : NO — the two checks use different keys
```

And confirmed in production by listing the service's variable names (values redacted):
**there is no `SHOPIFY_*` variable at all.** So every Shopify webhook was answered
`400 "Shopify is not configured"` before its signature was even looked at.

Meanwhile `services/shopify/schema-sync.service.ts` verifies against
`getChannelApp('SHOPIFY').clientSecret` — the secret Shopify actually signs with — and
that receiver worked. **Two secrets for one signature check**, and the working one was
sitting in the same repository.

**Third — nothing ever registered the webhooks.** `ensureShopifySchemaSubscriptions`
registers three metafield topics. `/usr/bin/grep` for `webhookSubscriptionCreate` finds
it and nothing else. Shopify had never been told to send the product, order, lifecycle
or privacy events at all.

### 1.2 Five declared topics had no route

`connectors/shopify/spec.ts` has declared
`lifecycleTopics: ['app/uninstalled', 'app/scopes_update', 'shop/redact',
'customers/data_request', 'customers/redact']` since the connector was written. None of
the five had a receiver. Three of them are the privacy topics every Shopify app is
required to answer.

### 1.3 Two of the plan's done-whens were already met by P2.1

*"a second update to the same product is processed"* and *"route to the owning business
profile"* were both fixed there — the delivery-id key and the shop-domain routing. Said
here so this record is not read as claiming them twice.

### 2.1 The decisions worth keeping

- **A missing credential answers 503, not 400.** The old 400 was wrong twice: it fired
  in production for every webhook, and it told Shopify the *request* was bad when the
  truth is we could not check it. 503 keeps the event on Shopify's retry schedule.
- **`shop/redact` arriving with no shop is the NORMAL case.** It lands about 48 hours
  after the uninstall, by which time `app/uninstalled` has set the connection inactive
  and the database trigger has deleted its routing row. Refusing it would mean Shopify
  retrying a mandatory privacy notice until it flags the app. The lifecycle and privacy
  topics fall back to the platform's own workspace and answer 200 — the same shape as
  the eBay fix in P2.3, arrived at for the same reason.
- **An uninstall revokes the shop the notice NAMES.** `updateMany` is already scoped to
  the routed business profile, but a profile may hold more than one Shopify connection,
  and revoking a still-installed shop because a different one was removed is the worst
  kind of correct-looking write. A match of zero rows is logged at error level.
- **A topic already subscribed to another callback is reported, not repointed.**
  Silently taking over another application's subscription is how one integration breaks
  another.
- **The privacy topics are acknowledged, never carried out.** Erasure deletes real
  customer data; that is the Owner's decision and its own unit. Identical to the position
  this repository already takes for eBay's erasure notice.

### 3.3 A near miss worth recording

While editing, a script's two markers were found in the opposite order to the one
assumed, so `s[i:j]` returned an empty slice and `s[:i] + s[j:]` **duplicated** a 10,917
character region instead of moving it. `tsc` caught it immediately (duplicate function
implementations), the duplicate was removed by asserting the two copies were
byte-identical first, and the move was redone with `assert i < j` plus assertions that
the block held the handlers and did not swallow the receiver. Recorded because the
failure mode — a text edit that silently duplicates instead of moving — is not one a
test suite would necessarily catch, and the guard that caught it was a cheap assertion.

## 4. Still open

1. **Nothing has called the registration yet.** `POST …/webhook-subscriptions` exists
   and is idempotent, but it is operator-triggered per account. Until it runs, Shopify
   still sends nothing. It is a live channel call against a connected shop.
2. **Whether the Admin API accepts the three privacy topics is not established.**
   Shopify may require them in the Partner Dashboard. Rather than guess, the attempt is
   made and Shopify's own answer is recorded per topic as `refused` with its message.
3. **No nightly reconcile for Shopify.** Amazon (P2.2) and eBay (P2.3) have one; Shopify's
   registration is per shop and needs the account list, so it is left as an explicit
   action until P2.6 settles the account lifecycle.
4. **`app/scopes_update` records the scopes, it does not react to them.** Deciding what
   a reduced scope set means per feature is P2.6.
5. **The done-when is not verified end to end**: no Shopify webhook has ever been
   recorded, so "uninstall flips the account to revoked" is proven by test, not by a real
   uninstall.
