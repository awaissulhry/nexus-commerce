**The row is half a counterweight.** The 2024-06-19 path is **already built**:
`syncFinancialTransactions` (`services/amazon-financial-events.service.ts:544`) pages
`/finances/2024-06-19/transactions` **through the channel gateway**, with the account,
the rate bucket and the call ledger, and is reachable today by posting
`{ useV0: false }` to `/amazon/financials/sync`.

**What is not done is the switch** — and nobody has ever run the new path, so nobody
has seen Amazon's answer to it.

### 🔴 The defect its first real run would have produced

The parse was `data.transactions ?? []`.

If Amazon wraps the list, that yields `[]`, the pagination loop ends on page one, and
the sync returns **success** with `orderEventsFetched: 0` and `txCreated: 0`. A
settlement day recorded as *"no transactions"*, indistinguishable from a genuinely
quiet day — on the money path.

P5.1 found exactly this class one package earlier and wrote it down:

> **Three envelopes in one migration.** v0 wraps in `payload`; `searchOrders` puts the
> list under `orders`; `getOrder` wraps one order in `order`. **The wrong one gives
> every field `undefined` and no error.**

And the route's own comment named the risk while leaving it open: *"the parser hasn't
been updated for Amazon's `{payload: {...}}` wrapper yet"*.

## 2. Changes

1. **New exported** `readTransactionsPage(body)` in
   `services/amazon-financial-events.service.ts`:
   - accepts **either** envelope — `{transactions}` or `{payload:{transactions}}` —
     exactly as `fetchReport` already accepts `url` **and** `location` for the same
     reason (ACR.0.2-bis);
   - takes `nextToken` from the **same envelope as the list**, because a token read
     from the root while the list came from `payload` pages a different thing — the
     half-migration that loses rows instead of failing;

     actually sent, and saying *"Nothing was recorded"*. *Could not measure* must not

     the equal and opposite error.

3. `routes/amazon.routes.ts` — the comment no longer claims an un-updated parser (it
   would have become a comment asserting a property the code no longer lacks), and
   records the two facts that matter: **0 calls ever**, deadline **2027-08-27**.

## 4b. ✅ THE PROBE RAN — 2026-09-21 — and then found a reason NOT to proceed

Run in the browser against the **Xavia Racing** profile (the legacy workspace, where the Amazon
seller account lives):

```json
{ "ok": true, "envelope": "payload", "transactionsOnFirstPage": 4,
  "hasNextToken": false, "rootKeys": ["payload","statusCode"],
  "windowStart": "2026-09-20T13:03Z", "windowEnd": "2026-09-21T13:03Z" }
```

### The envelope question is SETTLED: `payload`

Amazon wraps the list, exactly as §4 feared. 🔴 **The old parse — `data.transactions ?? []` —
would have found ZERO of those 4 transactions and returned success.** One day's window, four real
transactions, silently recorded as a quiet day. The finding was not hypothetical.

`readTransactionsPage` already accepts both envelopes and takes `nextToken` from the **same**
envelope it found the list in, so the live shape is handled. That half of the row is closed.

### 🔴🔴 But the NEXT step in §5 is not safe as written, and must not be run

§5 prescribes *"one live `{"useV0": false}` call, a count comparison against v0"*. That call is a
**write**, and the two paths **cannot dedupe against each other**:

| path | what it stores as `amazonTransactionId` |
|---|---|
| **v0** (`processOrderEvent` :169, `processRefundEvent` :229) | `amazonOrderId` — e.g. `404-1234567-1234567` |
| **2024-06-19** (`processTransaction` :525, :561) | `${amazonOrderId}/${sellerOrderItemId}/${postedDate}` |

Both write the same table and both dedupe on `(orderId, transactionType, amazonTransactionId)`.
The new path looks for `404-…/ITEM/2026-09-20`; v0 stored `404-…`. **It will not find v0's row,
and will create a second one.**

Measured, not assumed: every writer and matcher of `amazonTransactionId` was listed (7 sites), and
a search for any `migrat|reconcil|backfill|dedupe` bridging the two formats returns **nothing**.

The finer key is **deliberate** — its own comment says *"so we can ingest multiple
shipments/refunds for the same order"* — so this is a genuine granularity change, not a typo. The
consequence is the problem: **running the new path over a window v0 has already synced duplicates
the money.**

### What this changes about closing the row

1. ✅ **Probe** — done. Envelope is `payload`, and the parse handles it.
2. ❌ **"One live call, then compare counts"** — **withdrawn.** As written it double-writes.
3. **What a safe comparison needs instead**, in increasing order of effort:
   - a **dry-run** mode on the 2024-06-19 path that counts what it *would* write without writing
     (the shape P5.2's own probe already proves is possible); or
   - a window with **no v0 rows at all** — a future window, after the cron flips; or
   - a reconciliation that can recognise a v0 row from a new-path row, which is a migration and
     its own package.
4. **Flipping the cron forward** is a separate, smaller question: going forward only one path
   runs, so there is no overlap except at the changeover window. That is the Owner's call, and it
   needs a decision about the boundary day rather than a comparison run.

🔴 **Nothing was written.** The probe is a read, and the write that §5 asked for was not made
once the duplicate risk was measured. *A plan row is usually not the defect* — and here the plan
row's own next step was.

## 4c. ✅ BUILT 2026-09-21 — the dry-run counting mode

§4b withdrew the plan's next step and named three safe alternatives. **The cheapest one is
built**, and it is a read: `POST /api/amazon/financials/sync {"useV0": false, "dryRun": true}`.

It runs the **real** fetch over the **real** window and the **real** decision path, and writes
nothing. It answers two questions at once:

| field | what it says |
|---|---|
| `txWouldCreate` | how many rows the 2024-06-19 path would add |
| 🔴 `txWouldDuplicateV0` | **how many of those v0 has already recorded** |
| `txCreated` | **0** — because zero rows were created |
| `dryRun` | `true`, so the summary cannot be mistaken for a write |

### Why `txWouldDuplicateV0` is the point

§4b proved the double-write by reading two string formats and finding no bridge. That is an
argument. This is the same fact **as a number, on a real window**: for every row the new path
would create, it also looks for a row under the **bare `amazonOrderId`** — the shape v0 wrote,
and the shape the idempotency check above it cannot see. A non-zero answer is the duplicate
count the Owner would otherwise have discovered by creating them.

### The three things this was built against

1. **The dry run is not a second predicate.** It skips exactly one statement — the `create`.
   The related-id lookup, the order match, the type map, the identifier build and the
   idempotency check all run unchanged. A count produced by a re-derived "equivalent" decision
   is a count of something else, and diverges on the first case that differs.
2. **A zero-change round trip cannot test the write.** Every *"nothing was written"* assertion
   is paired with a **positive control** — the same fixture through the real arm, which must
   create. Otherwise *"the write was disarmed"* and *"the fixture never reached the write"* are
   the same observation.
3. **A claim must match its measurement.** `txCreated` reports **0** on a dry run. Every
   existing reader of that field sums writes; a dry run contributing to that sum would be a
   number that means something it does not.

### The flag is refused where it cannot be honoured

`{"dryRun": true}` **without** `{"useV0": false}` is refused with a `400` naming the reason.
v0 (`syncFinancialEvents`) has no dry-run arm, so accepting the flag there would perform a real
write while the caller believed nothing was at stake — *an API accepting a flag it ignores*, on
the money path. The rule lives in the service as `financialsDryRunRefusal`, **not** in the route,
so there is one predicate with one test rather than a sentence a reader has to trust.

### Proof

**25 behavioural tests** in `amazon-finances-dryrun.p52.vitest.test.ts`, against a mocked
`prisma` and a mocked gateway. **7 mutations, 6 killed, 1 null control survived:**

```
✅ the dry run calls create anyway                          → 4 failed
✅ txCreated reports the would-create count                 → 1 failed
✅ the v0 lookup uses the NEW identifier, not the bare id    → 2 failed
✅ dryRun defaults to true                                  → 8 failed
✅ the dry run skips the idempotency check                  → 4 failed
✅ the refusal lets v0 through                              → 2 failed
🟢 NULL CONTROL: a log message reworded                     → 25 passed, survived
```

⚠️ **One mutation did not apply on the first attempt** — the pattern matched 0 places, and the
run reported 25 passed. That reads exactly like a surviving mutation and is not one. The script
asserts the match count before writing, which is why it was caught rather than recorded as a
hole. *Always verify a surviving mutation actually applied.*

**Full `apps/api` suite: 10,949 passed, 6 failed, 130 skipped** — the six are the two known
Amazon local-account files (`amazon-validation-preview`, `amazon-classifications`) that every
handover has carried. Neither is in this diff.

### What is still the Owner's

**Running it.** It is a read, so it needs no write approval — but it is a **live Amazon call**,
and those are the Owner's under §0c. Pick a window v0 has already synced; a window with no
settlements measures nothing.

**Reading it.** `txWouldDuplicateV0 > 0` means the two paths would double-write that window and
the migration needs a bridge before any comparison run. `0` over a window known to have v0 rows
would mean the opposite, and would be a surprise worth chasing before trusting it.

## 5. 🔴 The row is NOT complete, and this is what is left

**Update 2026-09-21, after the Owner approved settling it:** the probe below is new,
and it changes what the Owner has to approve.

### The probe — a READ, not a write

`POST /api/amazon/financials/sync {"probe": true}` asks the 2024-06-19 endpoint which
envelope it uses and **writes nothing**.

Before this, settling the envelope meant running the real sync, which creates
`FinancialTransaction` rows — a production **write**. As a read it needs no write
approval at all, and the standing rules already allow production reads.

It reads **one page**, keeps **no payload**, and answers:

```json
{ "success": true, "probe": {
    "ok": true, "envelope": "bare" | "payload" | null,
    "transactionsOnFirstPage": 0, "hasNextToken": false,
    "rootKeys": ["transactions","nextToken"],
    "windowStart": "…", "windowEnd": "…", "marketplaceId": "APJ6JRA9NG5V4" } }
```

An unreadable shape is **reported, not thrown** — `envelope: null` plus the top-level
keys Amazon actually sent — because the point of the call is to learn the shape, and a
throw would say less than the keys.

Tests pin all of it: no `prisma.`, no `.create(`, no pagination loop, no payload kept.
Mutations: writing a row → **1 fail**; adding a loop → **1 fail**; removing the route
branch → **1 fail**.

**What to run, and what each answer means:**

| `envelope` | meaning | next |
|---|---|---|
| `"bare"` | `{transactions}` — what the original code assumed | the parser was already right; go to step 2 below |
| `"payload"` | `{payload:{transactions}}` | 🔴 the old code would have written **zero** rows and reported success. The new reader handles it |
| `null` | neither — `rootKeys` says what came instead | stop; the mapping needs more than an envelope fix |

### Then, still the Owner's, and still a write

1. ✅ **The probe** — a read, above. Nothing further needed from me.
2. ~~Compare a real `{"useV0": false}` run's `txCreated` against the same window through
   v0.~~ **WITHDRAWN** — §4b measured that this double-writes. Replaced by the dry run
   built in §4c: `{"useV0": false, "dryRun": true}`, which counts the same rows and
   writes none of them, and reports `txWouldDuplicateV0` besides. **A zero-change round
   trip cannot test the write** — pick a window with known settlements.
3. Flip the cron and `useV0`'s default together, leaving the v0 path for one release as
   the rollback.

**Why it was not flipped blind:** the endpoint has never run, so the envelope was
unverified either way. This slice makes a wrong guess **fail loudly** instead of
silently — but a loud failure on a nightly settlement sync is still a failure. With the
deadline at **2027-08-27** and the plan's target at **2027-03**, there was no reason to
take that trade, and now there is a read that answers it instead.
