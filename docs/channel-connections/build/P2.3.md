## 1. What was measured first

### 1.1 Nothing has ever arrived

`/usr/bin/grep` across `apps/api/src` for `notification/v1/destination`,
`notification/v1/subscription`, `createSubscription` and `getTopics`: **zero hits**, with
the Amazon equivalent found by the same sweep as a positive control. There is no
destination and no subscription, so **no genuine eBay notification has ever reached
Nexus.**

The ledger agrees. All seven EBAY rows are from one afternoon, 2026-08-29, all
`signatureOk = false`, and one of them is named `probe.deploy.wait`. They are this
repository's own test probes.

That is the root cause of everything below: **a wrong name only looks wrong when
something real disagrees with it, and nothing real ever arrived.**

### 1.2 Three of the four topic names are not eBay's

The receiver branched on `marketplace.order.created`, `marketplace.order.cancelled`,
`marketplace.inventory_item.updated` and `ItemRevised`. eBay's Notification API uses
SCREAMING_SNAKE topic ids; the first three are not topic ids in any form, and
`ItemRevised` is a **Trading API** event name from the other, older delivery system.

The old `setup-ebay-notifications` comments record the confusion as it happened: REST
topic names were put into `SetNotificationPreferences` and eBay answered *"Invalid input
data"*; then `ItemRevised` was refused too; and the note concluded that returns and
refunds *"flow through the REST Notification API instead, which we already handle."*
Nothing handled them.

### 1.3 An account-deletion notice was answered with 503

`MARKETPLACE_ACCOUNT_DELETION` carries a `username`, never a seller object, so the
receiver's seller extraction yields `undefined` and `verifiedChannelWorkspace('EBAY')`
is left to choose between however many eBay accounts are connected.

Measured against the real routing index, with a control:

```
routing with NO seller id THREW -> ingress_account_ambiguous
                                   "does not identify one connected seller" | statusCode 503
CONTROL, known seller id RESOLVED to workspace: nexus_legacy_workspace
```

There are two eBay routes, so the throw is certain. **eBay requires a 200 for that
topic, marks an endpoint that fails it as down after 24 hours, and answering it is a
condition of holding production keys.** The more eBay accounts are connected, the more
certainly the erasure notice is refused.

`AUTHORIZATION_REVOCATION` has the same shape and the same problem.

### 2.1 The decisions worth keeping

- **eBay is the authority on its own topic names.** `getTopics` returns the catalogue,
  and a topic we believe in that eBay does not offer is reported as `not_offered` — its
  own outcome, separate from `refused` (eBay knows it, won't give it to us) and `failed`
  (everything else). Collapsing those three into "failed" is what let
  `marketplace.order.created` survive: nobody could tell a wrong name from a missing
  permission.
- **The invented names are kept, apart.** They stay routable because rows carrying them
  are in the ledger and a replay must reach a handler. They live in a separate map from
  the real topic ids so they can never be offered to eBay as a subscription — a test
  asserts exactly that.
- **An unknown topic carrying an order id is still acted on**, and logged by name at
  error level. The real topic id for a sale is the one thing this codebase cannot supply
  for itself; dropping a genuine sale because its topic was not the string we guessed is
  the worse failure, and the order service is idempotent.
- **One accessor for the endpoint and token.** The first draft of the setup read
  `EBAY_NOTIFICATION_ENDPOINT` / `EBAY_VERIFICATION_TOKEN` while the receiver's challenge
  handler read `EBAY_NOTIFICATION_ENDPOINT_URL` /
  `EBAY_NOTIFICATION_VERIFICATION_TOKEN`. eBay computes
  `SHA256(challengeCode + verificationToken + endpoint)` from what the **destination**
  says and we compute it from those variables: two names for one fact means two hashes,
  a failed ownership check, and eBay taking the endpoint down with every topic on it.
  Caught before it shipped, and now impossible — both sides call one function.
- **The legacy Trading sale branch stays.** `AuctionCheckoutComplete`,
  `FixedPriceTransaction` and `ItemSold` still drive an order sync, because delivery
  preferences set in eBay's portal before this may still be live and removing the branch
  would drop real sales. They are deliberately not in the topic table: `ItemSold`
  (Trading) and `ITEM_SOLD` (Notification API) are different strings for different
  systems, and folding them together would make one sale fire two syncs.

### 3.3 A guard caught a stale exemption, and it was right

`write-account-guard.p07` keeps a census of files that pick the primary eBay account,
and a list of those that do so without writing a listing. Deleting the Trading helpers
meant `routes/ebay-notification.routes.ts` stopped picking the primary account at all,
so its exemption became stale and the census failed. Its entry already read
*"notification preferences (P2.3), not a listing"* — written by whoever anticipated this
package. The entry was removed. **The guard was not adjusted to pass; it was correct,
and the code had moved.**

## 4. Still open

1. **The plan's done-when is not met: no real eBay order event has been verified end to
   end.** No genuine eBay notification has ever arrived, and one cannot be made to
   arrive without a real sale. The proof is the first genuine notification after the
   destination exists.
2. **The destination does not exist yet.** `setupEbayNotifications` makes no call until
   `EBAY_NOTIFICATION_ENDPOINT_URL` and `EBAY_NOTIFICATION_VERIFICATION_TOKEN` are both
   set in production. That is the single step that starts live traffic — see the open
   items in `PROGRESS.md`.
3. **Three topic ids are `documented`, not `verified`**: `ITEM_SOLD`,
   `ITEM_PRICE_REVISION`, `ITEM_AVAILABILITY`. `getTopics` settles them on the first
   run, and a wrong one is reported as `not_offered` rather than silently subscribed.
   The payload fallback means a sale is not lost while that is being sorted out.
4. **Shipping and returns topics are not subscribed.** The plan names them by purpose;
   their topic ids are not established and Nexus has no handler for them. Adding them
   before both are known would only fill the dead-letter queue.
5. **`AUTHORIZATION_REVOCATION` is recorded, not acted on.** Marking the account revoked
   and pausing writes is P2.6. It is logged at error level meanwhile, with its payload in
   the ledger, so it is never a silent 204.

## 🔴 2026-09-21 — the status endpoint could not see the thing that is broken

`PROGRESS.md` §4 sends the next session here: *"Check `GET /api/admin/ebay-notification-status`
after it runs."* It was checked, in the browser against production. It answered:

```json
{ "environment": "production", "endpoint": null, "destination": null,
  "subscriptions": [], "catalogueSize": 27 }
```

### What is real in that answer, and what was an artefact

🟢 **The call reached eBay.** `catalogueSize: 27` means the Notification API answered with its
topic catalogue, so the keyset works and the nulls are **not** a transport failure. That is the
positive control, and without it the whole reading would be *could not measure*.

🔴 **`subscriptions: []` is a REAL zero.** The list is mapped, not filtered, so eBay genuinely
holds **no subscriptions** on this environment. **Nothing is subscribed in production.**

🔴 **`destination: null` was an ARTEFACT, and could never have been anything else.**

```ts
const endpoint = process.env.EBAY_NOTIFICATION_ENDPOINT ?? null   // ← the wrong name
const ours = destinations.find((d) => d.endpoint === endpoint) ?? null
```

Every other reader — the challenge handler **eight lines below it in the same file**, the
destination setup, the reconcile job — reads `EBAY_NOTIFICATION_ENDPOINT_URL`. So `endpoint` was
`null`, and `find` compared every real destination against `null`. The endpoint reported
`destination: null` **whether or not a destination existed at eBay**.

`notifications.ts` fixed this exact drift *in itself* and wrote down why:

> *"two names for one fact, which is the shape of every drift defect in this programme"*

and this file's own header says:

> *"A status endpoint that cannot see the thing that is broken is worse than none, because it is
> quoted."*

It was quoted. The fix was applied to the accessor and **missed on the one route that exists to
report on it**.

### What changed

| | |
|---|---|
| the endpoint | read through `ebayNotificationConfig()` — the **same** accessor the challenge handler and the destination setup use. One predicate, not two names |
| `configured` | `{hasEndpoint, hasVerificationToken}` — so a null endpoint reads as *"we did not ask"*, never as *"eBay has nothing"* |
| `destinationsAtEbay` + `destinationEndpoints` | the raw count and the endpoints eBay holds, beside `destination`. **Could-not-measure and measured-empty are now different answers** |
| `catalogue` | every topic id eBay offers, sorted. A wish with `offeredByEbay: false` is answered by **reading** this list — never by inventing a plausible id. P6.7 records that two invented eBay scope names broke every connect for **nineteen days** |
| the vacuous match | `find` is skipped entirely when the endpoint is unset, so a destination whose own endpoint is null cannot be adopted as ours |

### Proof

**12 behavioural tests** against a real Fastify instance (`app.inject`), mocking only the three
eBay reads. **7 mutations, 6 killed, 1 null control survived:**

```
✅ RESTORE THE ORIGINAL DEFECT — the bare variable name   → 4 failed
✅ the vacuous find comes back                            → 1 failed
✅ destinationsAtEbay is a constant                       → 1 failed
✅ configured always reports true                         → 1 failed
✅ the catalogue is not reported whole                    → 1 failed
✅ the subscription list is filtered to ours              → 1 failed
🟢 NULL CONTROL: a comment reworded                       → 12 passed, survived
```

⚠️ The first attempt at mutation 1 matched **two** places (the challenge handler's
`config.endpoint ?? ''` contains the same substring) and so did not apply — and reported 12
passed, which reads exactly like a survivor. The script asserts the match count before writing.
*Always verify a surviving mutation actually applied.* Second time this session.

2. **`ITEM_SOLD` came back `offeredByEbay: false`** against a 27-topic catalogue — §4 predicted
