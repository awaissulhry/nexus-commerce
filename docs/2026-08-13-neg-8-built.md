## 1 · 🔴 The refusals were the point, and they had never been on a screen

`protectConverting` refusals live inside `AutomationRuleExecution.actionResults` JSON — not in
`AdvertisingActionLog` — and they carry the term, the order count, the sales and the market. In a
4,000-execution sample, **60 refusals across 5 terms, every one of them earning**:

| term | | | |
|---|---|---|---|
| `chaqueta moto hombre invierno` | 4 orders | €420.00 | ES |
| `b0cxpp5dbk` | 3 orders | €243.45 | IT |
| `b08hytt4kg` | 2 orders | €166.39 | DE |
| `motorradjacke herren mit protektoren` | 2 orders | €166.38 | DE |
| `saponette moto` | 2 orders | €49.18 | IT |

Two are **ASIN targets**, which nobody predicted — the protection was written for search terms and
is catching product targets too.

**€1,045.40 is what those terms made, not what was saved.** The page says exactly that. What the
account would have lost is unknowable, for the same reason `ads-weekly-digest` counts bid moves and
refuses to price them.

## 2 · 🔴 Three ways to get the ledger wrong, and this page hit two of them

**(a) The join drops the rows that matter most.** A local-only retirement **deletes** the
`AdTarget`. So the two `retire_negative` logs — the only rows in the entire ledger carrying
evidence, each with a real user and a full note — point at targets that no longer exist. Filtering
on `isNegative === true` drops exactly the rows that record a removal: **26 of them**.

**(b) The action type alone is wrong the other way** — 24,972 positive-keyword rows on a negatives
page.

So the action type decides where it is unambiguous, and the join arbitrates only where it is not.

**(c) 🔴 And a pagination artefact that read exactly like a fact.** The first version reported
**`created: 0`**. There are 24,109 `AD_BID_UPDATE` rows against 858 negative ones, so a
`take`-bounded query ordered newest-first filled its whole page with rows it then discarded, pushing
every `create_negative_keyword` off the end. A negative keyword has no bid, so that action type is
excluded outright — and the suite now asserts the read did **not** fill its cap, because a full page
is a silent lie.

🔴 **The cap counter is confirmed broken by measurement.** `automation-rule.service.ts:573` uses
`NOT errorMessage = 'DAILY_CAP_EXCEEDED'`, which in SQL is NULL — not true — for the **236,931**
rows where `errorMessage IS NULL`. It matches **0** of them. Every filter on this page uses the
explicit `OR [{ col: null }, { col: { not: 'X' } }]` form. Not fixed: that file is shared.

## 4 · Notifications extend; they do not multiply

Five event types on the **`NotificationPreference` model that already exists** — it already carried
`inApp` / `email` / `digestCadence`. No new table, no second channel. The two defaulted ON are the
ones that would have mattered: a refusal naming a converting term, and a negative becoming orphaned.

The digest gains **one optional field** on `ads-weekly-digest.service.ts`, built by NEG.8's own
service, so the number on screen and the number in the Monday email come from one builder. It
degrades to `null` on failure rather than to a zeroed object that would read as a quiet week.

**The operator asked for a daily digest; the existing one is weekly.** That is a cadence change on
that builder, not a new system, and it is surfaced as a question rather than answered by building
a second service.

## 5 · Two defects only looking found

🔴 **The marketplace column was an em-dash on every row.** The evidence key is `markets` — an
**array** — and my reader looked for `marketplace`. A column that is always empty is worse than no
column, because it reads as missing *data* rather than a missing *reader*. The payload was
well-formed and the type was satisfied by `null`, so nothing failed.

🔴 **The actor column showed a raw cuid** on the two `retire_negative` rows — the two most important
rows in the ledger. §4 asks for a resolved name; `userId` stores `user:<UserProfile.id>` and
stripping the prefix left the id. Now resolved against `UserProfile`, and asserted: no actor label
may match a cuid shape.

## 6 · Verified on production

- 60 refusals · 861 changes · 4 alerts on. All three tabs, `?record=` in the URL.
- **The write works end to end**: toggling an alert POSTs, reloads, and moves the count 4 → 5;
  toggling back restores it. The preference row it created was deleted afterwards and the suite
  re-runs clean.
- **Contrast**: 384 text nodes across all three tabs, composited — **0 failures, lowest 4.83**.
  Section edges **96 → 1698**, flush. No horizontal overflow. Zero console messages.
- The ledger renders all three delivery words — *local only*, *confirmed at Amazon*, *queued for
  Amazon* — and the honesty line: 2 of 861 rows carry evidence, 1,203 of 2,059 negatives have no log
  at all and are recorded as *unattributed*, never guessed at.

## 7 · Reported, never fixed — all four on screen with their file

1. **`alert_operator` alerts nobody** (`automation-action-handlers.ts:1224`) — calls `logger.warn`
   and never `notifyAutomation`. Five advertising rules use it.
2. **The daily-cap counter cannot see a success** (`automation-rule.service.ts:573`).
3. **Gate denials are not persisted** (`ads-write-gate.ts:358`) — substrate several pages need.
4. **`add_negative_phrase` has no handler** — offered on the tab, categorised, ceilinged.
