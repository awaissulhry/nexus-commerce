## API and scope contracts

Existing registered route plugin `channelMappingRoutes` and the `/api/pim` permission prefix cover these APIs; no new registration or permission patch is needed.

- `POST /api/pim/channel-mapping/:channel/:code/impact`: `expectedToken` plus exactly one of `changes`, `expression`, `categoryChange`, `clone`, `presentationChange`; optional marketplace `category` narrows the field-rule review.
- `expression`: `{ name, expr: string | null, previousName? }`.
- `categoryChange`: `{ categoryId, channelCategoryId: string | null, channelCategoryPath?, browseNodeId? }`; channel/market come from the route.
- `clone`: `{ channel, market, token, addTranslate? }`; another market of the same channel.
- `presentationChange`: `{ id, rule: PresentationRule | null }`. A rule contains `id`, `name`, `version`, `priority` (0–100), `scope`, and `themeId` and/or `order`. Theme `none` means body only. The server increments a standing rule’s version.
- `scope`: optional `accountId`, `familyId` (ProductFamily classification), `sharedCategoryId` (direct membership, falling back to the variant parent’s membership), `marketplaceCategoryId`. Conditions combine with AND. Channel is EBAY and market is the containing mapping. No language, descendant-taxonomy or arbitrary-expression selector is exposed.
- For each property, greatest priority wins. Same-priority rules with different results produce named conflicts; identical results select a deterministic rule ID. There is no implicit specificity score. Future overlaps are checked when records resolve.
- `GET /api/pim/channel-mapping/:channel/:code/presentation` returns rules, mapping token and `orderActivationAvailable: false`.
- `GET /api/pim/channel-mapping/impact/:jobId?page=0` returns the caller’s durable review, destination/language rows, matching counts, changed values, preserved overrides, missing/invalid outputs, conflicts, exclusions, source metadata and input policy. The page index is zero-based; rows are persisted in chunks of at most 100.
- `POST .../impact/:jobId/activate` uses the reviewed snapshot; `POST .../impact/:jobId/assign-once` returns the staged transfer job and URL. Existing `MAPPING_SCANNING`, `MAPPING_REVIEW`, `MAPPING_STALE`, `MAPPING_FAILED`, `MAPPING_APPLIED` states remain.
- `POST /api/ebay/description-preview` accepts `accountId` and `aliasKey`. Omitted account uses Session 1’s primary resolution; named selection must resolve to an active eBay connection. The internal renderer also accepts resolved `channelConnectionId: string | null` and preserves null. Preview remains read-only.

## Review consistency and scale

Product scanning uses keyset batches of 100; listing queries page at 250; saved affected-set pages contain at most 100 rows. Checkpoints and chunks commit together. Existing recovery leases and three-attempt retry behavior are retained. A mapping revision references its originating review ID, whose payload contains the before/after mapping and category snapshots.

Activation requires both mapping CAS and a conservative digest of resolution inputs. The digest pages at 250 across product/listing data, taxonomy and memberships, channel/category schemas, links, value maps, size scales, account identity/active/primary state, attribute/family definitions and themes. Account credentials are excluded. Full row values catch relevant legacy writers that fail to increment versions. This digest runs when explicitly creating/completing/activating a review, never on library load or a keystroke. Any input change during the scan marks it stale; activation checks inputs inside a serializable transaction before claiming the review. Old review jobs without this digest cannot activate. Source mapping changes separately invalidate clones and one-time assignments. Draft resolution bypasses the value-map and size-scale TTL cache.

This is conservative invalidation, not a controlled database performance result. A busy catalog can invalidate a review for an unrelated input change. The complete destination grouping and output work for each 100-product batch are still held in memory; pathological numbers of aliases/fields have not been benchmarked. A 60-second transaction timeout can refuse a large activation. No cross-process derived-value cache or materialization migration was added. Legacy mapping revision rollback alone does not restore the separate category table; use a new reviewed category change, whose prior snapshot is retained in the impact job.
