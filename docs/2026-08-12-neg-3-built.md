## 1 · The routing fix — the trap, caught before it fired

DL.1 fixed the split between keyword ids (`/sp/keywords`) and targeting-clause ids (`/sp/targets`).
It could not know about negatives, because nothing had ever pushed a state to one.

Measured before the fix: **0 of the 23 `AD_ENTITY_STATE_UPDATE` logs are on a negative, 0 negatives
have ever been enqueued for an outbound write, and `orphanedAt` is 0 across every target in the
account.** The trap was latent purely because the feature that springs it did not exist.

The chain, end to end: a negative keyword is `kind = 'KEYWORD'` → archive takes the `/sp/keywords`
branch → its id is not a keywordId there (it lives under `/sp/negativeKeywords`, exactly where
`ads-negative-kw.service.ts:61-65` creates it) → Amazon answers `entityNotFoundError` at
`$.keywords[0].keywordId` → `isEntityGoneError` returns **true**, because the error is
keyword-shaped and the kind genuinely *is* KEYWORD, so DL.3's guard sees no contradiction → the
worker sets `orphanedAt` → which blocks every future non-forced write → and
`isContradictoryOrphan` cannot clear it for the same reason. **Live at Amazon, dead here,
permanently unwritable.**

Routing now decides on `(kind, isNegative, negativeLevel)`, additively — a bare `kind` string still
means POSITIVE, so every pre-existing caller is byte-identical. **And the guard is widened**, which
is the half that makes a future mistake survivable: a positive-shaped miss on a negative row now
suppresses the orphan mark instead of minting one.

**16 tests, all seen to fail first** — reverting the routing and the guard fails exactly 10 of them,
and the 34 pre-existing DL.1/DL.3/WF.1 tests keep passing untouched.

This also repairs the two per-campaign grids that have shipped an Archive button on a negative since
the day they were written (`NegativeTargetsTab.tsx`, `AgNegativesTab.tsx`). The 0 state-update logs
are the proof nobody has ever clicked one.

## 2 · The state vocabulary, checked rather than assumed

The brief required verifying whether `PAUSED` is valid for a negative before offering it. Amazon's
SP v3 accepts **`enabled | paused | archived`** for negative keywords and negative targets (Amazon's
negative-targeting reference and the Python SDK's `edit_negative_product_targets`, which lists the
three). **Archive is terminal** — archived negatives cannot be retrieved, confirmed independently by
Amazon's guidance and by our own `rollback.service.ts:151-156`.

So `PAUSED` is legal, and that matters more than the brief anticipated: **there is a reversible way
to stop a negative blocking**, which the study's §4.0 does not consider. Our own account has 0
paused negatives, so this is documented-valid, not locally proven.

## 3 · What shipped

**Three retirement paths**, because they leave three different records:

| path | rows | what it does |
|---|---|---|
| (a) at Amazon, ad-group | 2,017 | `updateAdTargetWithSync` → outbound → `PUT /sp/negativeKeywords` |
| (b) at Amazon, campaign | **0** | implemented; **no subject exists** — all 22 campaign-level negatives are local-only |
| (c) local-only | 42 → 41 | local delete + audit row; `delivery: 'not_applicable'` |

The 62 already-ARCHIVED rows are **refused**, not no-op'd: they were archived on Amazon and mirrored
in, and a no-op logged as a retirement would be a false record.

**Five outcome classes**, counted separately, with untouched ids named — retired / removed_local /
skipped / refused / failed. A gate refusal stops the rest of the batch rather than retrying silently.

**The record**: `AdTarget.retiredAt` + `retireReason` (additive, applied to prod); an optional
`actionType` override on `updateAdTargetWithSync` defaulted to current behaviour, so a retirement is
`retire_negative` in the ledger rather than an anonymous state update; and **evidence, populated** —
the term's numbers at the moment of removal, taken from `getTermContext` rather than re-derived.

## 5 · 🔴 Stage 2 is structurally blocked, and the reason inverts the plan

The brief's stage 2: archive one negative **in a PAUSED campaign** — inert, so it is safe.

I made it safer still: pause → verify → unpause, a reversible probe that proves the routing at no
irreversible cost. The pause was accepted locally and the worker then **SKIPPED** it:

```
[ADS-WRITE-GATE-DENY] campaign_allowlist: campaign cmpee2e2q09m0oj01xc29lqdk is not on the
live-write allowlist (Campaign.liveBidWritesEnabled=false)
```

**Amazon was never contacted.** Measured across the account:

| | |
|---|---|
| campaigns on the live-write allowlist | **82 of 220** |
| negatives where a retirement could reach Amazon | **1,044** |
| negatives blocked by `campaign_allowlist` | **1,014** |
| of the reachable ones, ENABLED and confirmed at Amazon | **942** |

That 942 is not a coincidence: **every ENABLED campaign holding a negative is allowlisted, and the
1,014 blocked ones are exactly the inert ones.** So the allowlist permits retirement precisely where
it matters and forbids it precisely where it is harmless.

**Stage 2 as designed is impossible.** Its safe subjects are unreachable and its reachable subjects
are all live. Routing around that by picking a live campaign myself would be stage 3 without the
decision stage 3 exists to require, so I stopped.

2. **Name a live negative** you are willing to have archived, and I run stage 3 directly. Terminal.

## 6 · The defect stage 2 found in my own service

`updateAdTargetWithSync` returns `ok: true` when a write is **enqueued**. The gate runs later, in
the worker. My outcome shape said `reachedAmazon: true` at enqueue time — a claim about Amazon made
before anything had been sent, which is the exact defect class this page exists to prevent, written
by me hours after writing the rule.

Replaced with `delivery: 'not_applicable' | 'enqueued' | 'refused' | 'failed'`. `enqueued` says the
gate has not run and names the outbound row to poll.

Note the failure mode it would have had: the local row moves, the gate refuses, and **the next v1
ingest heals the local row back from Amazon's truth** — so the whole episode leaves no trace except
a queue row nobody reads.

**And a second one, mine:** `_neg3-stage2b.mts` printed "passed" while looping over an empty subject
list. A false zero, in the session whose brief warns about false zeros. An empty assertion set is
now a failure.

## 7 · Not shipped, deliberately

- **No UI.** §10 says wire the write actions "last, after the single-row path is proven on
  production". It is not proven (§5), so `NegRemoval.tsx` remains a null stub and
  `NO_WRITE_ACTIONS` is untouched. Shipping a Remove button that would be refused for 1,014 of
  2,058 rows, with no live proof the other 1,044 land, is not a retirement path — it is a promise.
- **No bulk**, for the same reason (§8 is stage 4, gated on stage 3).
- **No un-archive**, ever. **No ceiling** — undecided, and rendering a refusal is not the same as
  inventing a policy.

## 8 · Open

1. **Stage 2 needs a decision** (§5).
2. **`PAUSED` is a legal, reversible way to stop a negative blocking**, and the study's §4.0 does not
   consider it. Whether the page should offer "pause" beside "retire" is a design decision worth
   making before NEG.4 hardens the vocabulary.
3. **`redis.railway.internal` does not resolve from a workstation**, even under `railway run`, so
   `enqueueBullMQJob` always fails locally. The queue row is still created and the Railway drain
   picks it up (`drainAdsSyncOnce`, PENDING, FIFO by `createdAt`), so this is noise rather than
   breakage — but a local script that waits for a BullMQ job will wait forever.
4. 🔴 **The `commit --only` trap fired twice more.** My retire route was swept into another
   session's commit, as NEG.2's CSS was into PLC.0's. Three instances in two days on this shared
   tree; it is now the normal case rather than the exception.
5. **`updateAdTargetWithSync` writes the local row before the gate runs.** For a bid that is
   self-healing; for a retirement it means `status: ARCHIVED` and `retiredAt` can both be set
   locally while Amazon still holds ENABLED, until an ingest heals it. The `delivery` field makes
   that legible but does not fix it. Worth a follow-up.
