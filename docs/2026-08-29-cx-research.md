### B1.2 What this means for the programme
- **Tier 1 — true OAuth, build first:** eBay (exists), Amazon SP-API (**needs the public-app OAuth flow we do not have**), Amazon Ads (route exists, UI does not), Shopify (custom-distribution auth-code or client-credentials), Etsy (PKCE). All five satisfy rule 3 with zero key-paste.
- **Tier 2 — true OAuth, new channels, EU-relevant:** Allegro, TikTok Shop, Google Merchant Center, Meta catalog; OTTO **only** if we register as a Service Partner (else it is a key-paste exception).
- **Tier 3 — documented key-paste exceptions (rule 3 exception list):** Kaufland (HMAC keys), bol.com (client id/secret), Mirakl instances (API key per operator), Cdiscount/Octopia (client id/secret + SellerId), Zalando (invitation + client credentials), ManoMano (API key, unverified), eMAG (Basic auth + IP allowlist). For each the least-friction path is a **deep link to the exact settings page**, key-format validation, and an immediate "test connection" call — documented per channel in R5 §2.
- **Not now:** Walmart (EU eligibility partial, US warehouse), Temu/SHEIN (review-gated, docs unverified), Privalia/Veepee (no public docs), Fnac/Darty (docs behind login).

## B2. Open-source references — what to clone as design, what to skip

### B2.1 Licences (verified)

Airbyte: protocol + Python CDK **MIT**; platform **and connectors ELv2**. Saleor BSD-3. Medusa MIT. Supaglue MIT (archived 2024). Panora AGPL-3 (archived 2025). Revert AGPL-3 (joined Ampersand). `@shopify/shopify-api` MIT.

### B2.2 Nango (R8) — the closest design to what we need
Worth re-implementing (Nango file cited in R8): **(1)** declarative provider catalogue (auth mode, URLs, `authorization_params`/`token_params`/`refresh_params`, `scope_separator`, `token_request_auth_method`, `authorization_code_param_in_callback` — SP-API's `spapi_oauth_code` — `redirect_uri_metadata` — `selling_partner_id` — `token_response_metadata`, typed `connection_config` fields); **(2)** connection health columns (`credentials_expires_at`, `last_refresh_success/failure`, `refresh_attempts`, `refresh_exhausted`) plus our own `refresh_token_expires_at` which Nango lacks; **(3)** refresh-if-needed = buffer (15 min) + in-process in-flight dedupe + `SET NX PX` lock + double-check re-read + keep-old-refresh-token-if-omitted; **(4)** failure cooldown + exhaustion + active-error record cleared on recovery with a recovery event; **(5)** OAuth session **row keyed by `state`** (single-use, holds `code_verifier`, config, who started it), PKCE always unless disabled, state cookie double-submit, provider error params folded into the user-visible error; **(6)** metadata capture from callback query and token response; **(7)** popup → opener protocol: `postMessage` + `BroadcastChannel` + ACK-then-close; **(8)** credentials verification on connect (declarative endpoint or per-provider function) reused as the periodic health test for key-based connections; **(9)** proxy retry decision table with header-driven waits (`at`/`after`, longest wins) and re-fetching credentials per attempt; **(11)** records with `external_id` unique per (connection, model), `data_hash`, `deleted_at` tombstone, single-CTE upsert classifying inserted/changed/unchanged/deleted; **(12)** generation-based delete detection; **(14)** Postgres task table with states, heartbeat, three timeouts, group keys with `group_max_concurrency`, `FOR UPDATE SKIP LOCKED` dequeue, one-active-per-schedule index; **(16)** inbound webhook handler contract on the **raw body**; **(17)** outbound delivery with per-destination circuit breaker; **(18)** egress URL policy for user-supplied hosts; **(19)** AES-256-GCM with iv+tag beside ciphertext and a re-encrypt-on-key-change routine.

Not worth cloning: the multi-tenant control plane, five-service topology, WebSocket+Redis result delivery, `node:vm` sandbox and yaml→zod compile pipeline, 256-way partitions, 982-provider catalogue, 17 auth modes. **Nango's own weaknesses we must not repeat:** no `refresh_token_expires_at` (eBay's 18 months and LWA's 365 days are invisible until failure); `refresh_attempts` counted per calendar day (4 days of failure before exhaustion); state cookie measured but not enforced; `===` HMAC compare; popup posts to `'*'`; no outbound per-connection rate limiter (only reactive retries); **none of its commerce entries carry rate-limit metadata**; `data_hash` key-order sensitive; webhook forwarding fire-and-forget without an outbox.

### B2.3 Airbyte (R9a)
Clone as design: the four verbs (`spec/check/discover/read`) as a connector contract; Catalog vs ConfiguredCatalog (source proposes cursor/pk, operator chooses); per-stream STATE checkpointed every N records with `is_resumable`; `ErrorResolution{action, failure_type}` with `RATE_LIMITED` and `REFRESH_TOKEN_THEN_RETRY` as first-class actions and composable backoff strategies (`WaitTimeFromHeader` for `x-amzn-RateLimit-Limit` = 1/rate, `WaitUntilTimeFromHeader`, exponential with `max_waiting_time` → give up); `DatetimeBasedCursor` windowed slices with lookback; `SubstreamPartitionRouter` (orders → refunds, profiles → campaigns); **`AsyncRetriever`** (create/poll/download + status mapping + job cap + retries + timeout) which is exactly SP-API reports/feeds, Ads reports and Shopify bulk; Shopify bulk adaptive window + cancel-to-checkpoint via `partialDataUrl` + `__parentId` re-nesting; SP-API `ReportCreationRequester` reuse of a recent DONE report; RDT authenticator layered over LWA with 403 fallback; `advanced_auth` four-blob split (user input / oauth output / server input / server output) with rotated refresh tokens flowing back as a CONTROL message; `HttpAvailabilityStrategy` + filtering streams by granted scopes; `continue_sync_on_stream_failure` with explicit STREAM_STATUS. What it lacks: any **write/action** verb (record-only), cross-stream transactions, live lookups in config UI; connector-as-container is unusable in a request path.

### B2.4 Saleor, Medusa, Supaglue/Panora/Revert, Shopify SDK (R9)
- **Saleor:** install handshake (manifest → installer-chosen permissions → token POST → rollback); `AppToken` hashed + `token_last_4`; **three-table delivery log** (`EventPayload` / `EventDelivery` / `EventDeliveryAttempt` with request+response headers, status, duration, capped body); channel-scoped webhooks; sync-call cache + failure sentinel + circuit breaker; `AppProblem` deduplicated problem ledger. Anti-pattern: one fixed-column row per (entity, channel) cannot hold Amazon product-type attributes or eBay aspects; payloads deleted after a period (not an audit trail).
- **Medusa v2:** `createStep(invoke, compensate)` sagas with persisted `WorkflowExecution`, reverse-order compensation, and **external resume by idempotency key** (`setStepSuccess/Failure`) — the shape of "push to Amazon, wait for the feed result, then continue or roll back"; step knobs (`maxRetries`, `retryInterval`, `timeout`, `async`, `noCompensation`, `continueOnPermanentFailure`); module links without FKs; provider classes with `static identifier` + `validateOptions`. Anti-pattern: sales channel = membership only; providers per capability not per marketplace; workflow state in Redis by default.
- **Supaglue / Panora / Revert:** all three keep the raw payload beside the unified row (`_supaglue_raw_data` + `_supaglue_mapped_data` in one row; Panora `remote_data` side table + `events` call ledger + `webhook_delivery_attempts`; Revert `tp_*` + BYO OAuth app) and **all three had to bolt on a field-mapping layer** because the common model could not carry provider fields; two are archived. Lesson: start from the provider's full schema and derive a thin common view, not the reverse.
- **`@shopify/shopify-api`:** signed 60 s state cookie, sorted-query HMAC + 90 s timestamp + `safeCompare`, anchored shop regex as tenant key, `Session.isActive(scopes)` with implied-scope algebra (`write_x ⇒ read_x`), **webhook registration as reconcile-to-desired-state** (query, diff, create/update/delete), `app/uninstalled` → purge, `app/scopes_update` → rewrite scope, token exchange / managed install, client-credentials 24 h tokens. Anti-pattern: online/offline duality leaking into 17 storage columns; scope as a comma string; expiry bolted on later.

### B2.5 The paid tier (R9 §6) — what they do and what they lose
- **Merge:** Common Models + `remote_data[{path,data}]` (paid tiers only, refreshed only when a Common-Model field changes) + Field Mapping + passthrough. Loses: no commerce category; provider-only fields go stale; coverage stops at the model.
- **Rutter:** commerce unified objects with `platform_data` raw field; async writes as Job `{prequeued,pending,success,failure}`; `force_fetch` because reads are served from a cache. Loses: no per-marketplace attribute dictionary; a PIM would reconcile against a stale mirror.
- **Apideck:** Vault owns credentials; connection `state` enum (`available/callable/added/authorized/invalid`) — the reusable idea; Ecommerce = four read-mostly resources; `/proxy` is the only way to reach listing attributes.
- **Paragon / Prismatic:** per-integration workflows (UI ↔ code), Connect Portal user settings, connection ownership types, alert triggers as data (execution failed, connection throttled/failed). Loses: the unit is a workflow, not a per-channel data model.
- **ChannelEngine / Feedonomics / Rithum:** feed-and-optimise — one product feed, vendor-owned per-channel mapping, post-hoc channel errors in a report; Rithum encodes marketplace fields as naming conventions in a flat `Attributes[]` bag with profiles multiplying everything by account × marketplace. Loses: the merchant never sees the marketplace's attribute schema; rejections never land on the product record. (ChannelEngine/Feedonomics docs are behind login/JS — details unverified.)

**Design conclusion for §C:** take Nango's connection/token/OAuth-session/records/task-table mechanics, Airbyte's error-action vocabulary + async-retriever + per-stream state, Saleor's delivery ledger, Medusa's sagas with external resume, Shopify's callback hardening and reconcile-to-desired-state webhooks, Apideck's connection state enum, Rutter's Job object — and **invert the unified-model premise**: the channel's full typed schema is primary, the PIM core is a derived view.

## B3. Things the brief may have missed — evaluation and recommendation

| # | Topic | What the references and channel docs say | Recommendation |
|---|---|---|---|
| 1 | Token encryption at rest | Nango: AES-256-GCM, iv+tag beside ciphertext, re-encrypt on key change; Enterprise adds KMS envelope. Our `crypto.ts` is AES-256-GCM `v1:` with no key-id. | **Adopt (enterprise bar, 2026-08-29):** true envelope encryption — per-blob AES-256-GCM data keys wrapped by an **AWS KMS master key** (annual auto-rotation, CloudTrail audit of decrypts), envelope `v2:<kid>:<wrappedDek>.<iv>.<tag>.<ct>`, decrypt only inside the token service, never returned by the resolver, logger redaction; the env key stays for local dev and documented break-glass only. |
| 2 | PKCE, state, nonce, TTL, one-time use, callback allow-list, popup vs redirect | Nango: session row keyed by `state`, single-use, PKCE always; Shopify: 60 s signed cookie + sorted-query HMAC + 90 s window; Etsy/Allegro require PKCE S256; SP-API `spapi_oauth_code` expires in 5 min. | **Adopt:** `OAuthSession` table (id = state, `codeVerifier`, `channelKey`, `startedByUserId`, `intent` (new/reconnect/adopt), `redirectUri`, `expiresAt` 10 min, `consumedAt`), PKCE by default, session-bound (cookie double-submit **enforced**), callback allow-list from the catalogue, popup-first with same-tab fallback (already right for eBay). |
| 3 | Refresh strategy | Nango: buffer + in-flight dedupe + Redis `SET NX` lock + double-check; keep old refresh token if rotation omits; cooldown 30 s; exhaustion; recovery event. Etsy rotates every refresh; TikTok rotates; Amazon/eBay don't. | **Adopt** with two changes: Postgres advisory lock (we already use them) instead of a non-distributed Redis lock; exhaustion after N **consecutive failures** (not calendar days). Refresh failure → `authStatus = NEEDS_REAUTH`, writes paused, reads continue while the access token lives, operator notified. |
| 4 | Connection lifecycle & health | Apideck `state` enum; Nango health columns; Saleor `AppProblem`; Prismatic alert triggers. Channels: SP-API 403 "Expired or revoked", LWA `invalid_grant`, Shopify `app/uninstalled`, TikTok `SELLER_DEAUTHORIZATION` + `UPCOMING_AUTHORIZATION_EXPIRATION`. | **Adopt:** `authStatus ∈ {connected, degraded, needs_reauth, revoked, disconnected}` + `lastSuccessAt/lastErrorAt/lastError/consecutiveFailures/refreshTokenExpiresAt`; a **per-channel heartbeat call** (SP-API `getMarketplaceParticipations`, eBay `commerce/identity`, Shopify `shop`, Etsy `getMe`, Ads `/v2/profiles`) on a cron; `ConnectionEvent` ledger (grant, refresh, revoke, heartbeat, scope change, who); alerts via existing `alert.service` (email/in-app). |
