## 1 · 🔴 132 is a pair count and 128 is a negation count. Both are right.

The brief, the study and the page all say **132**, and it is correct — as a count of
**(negation × protected term) pairs**. The number of `AdTarget` rows behind them is **128**.

Four negations, all of them the phrase `xavia gale`, contradict **two** protected terms each:

| phrase | protections hit | campaign |
|---|---|---|
| `xavia gale` | gale + xavia | GALE \| IT \| Broad \| Brand |
| `xavia gale` | gale + xavia | GALE \| IT \| Broad \| Brand |
| `xavia gale` | gale + xavia | GALE \| IT \| Phrase \| Brand |
| `xavia gale` | gale + xavia | GALE \| IT \| Auto |

The study's own predicate (`_neg-study.mts:71-83`) has **no `break`**, so it pushed those rows onto
its violations list twice and published the pair count without saying which unit it was. Both
numbers are now in the payload and both are on screen, because the audit is **grouped by protected
term** — so the group sizes sum to 132, and a headline of 128 over groups summing to 132 reads as a
bug. The removal cost is the other number, and that is the one an operator acts on.

`_neg5-reconcile.mts` reproduces the study's predicate verbatim beside the gate's and asserts the
identity `128 distinct + 4 second hits = 132 pairs`, so this is a refinement of the study rather
than a disagreement with it.

**A second unit collision, same shape.** The brief's assertion table expects `xavia` to have **16**
negations; the page shows **60**. Both are right and they answer different questions: 16 is the
count of negations of the *bare phrase* `xavia` (NEG.4's Detector B, the one earning €122.91 on one
order), and 60 is the CONTAINS reach of the *protection* `xavia` — every phrase containing it
(`xavia racing`, `giacca moto xavia`, `xavia gale`…). Both are asserted.

## 2 · 🔴 All 132 are blocking right now

This is what separates NEG.5 from NEG.4. Detector A's zero was zero because every overlapping
negation was ARCHIVED. Here `blocking === contradictions` — every one is ENABLED, confirmed at
Amazon, and in an ENABLED campaign. It is asserted, not assumed.

The classification reproduces exactly, over pairs:

| | | |
|---|---|---|
| own-line brand | **54** | the campaign's own name says it exists to capture the term it negates |
| other-line brand | **45** | a different line's term in a brand campaign — all of them `xavia` |
| non-brand | **33** | Auto campaigns; standard funnel architecture, probably correct |

`own-line` is read off the campaign's own name (punctuation stripped) rather than a hardcoded line
list, so a line added next month classifies with no code change. It is a **sort order and a default
filter, never a verdict** — nothing infers an operator's intent, and no campaign name resolves a
contradiction on its own.

Only **5** of the 10 protections are contradicted at all: `xavia` 60, `aireon`/`airmesh`/`moss` 20
each, `gale` 12, across 12 campaigns — every one of them IT.

## 3 · The mark is a new table, and that was the load-bearing decision

The obvious place is a campaign-scoped row on `AdKeywordProtection`. **Verified 2026-08-12 that it
would be wrong in a way nothing would report.** That table has seven production readers, and two of
them treat a WHITELIST row as *the account's definition of a brand term*:

```
share-of-voice.service.ts:347     select { term, matchType, isPrefix, marketplace }   — never campaignId
keyword-watchlist.service.ts:66   select { term, matchType, isPrefix, marketplace }   — never campaignId
```

So an exemption filed there would be read **account-wide** as "this is one of our brands" by Share
of Voice and by the watchlist classifier. And `ads-write-gate.ts:308-313` ANDs
`campaignId IS NULL OR campaignId = ctx.campaignId`, which **narrows** a protection to one campaign
rather than exempting that campaign from it — the exact inverse of the mark's meaning.

`AdNegativeReview` is additive, at the grain **(protected term × campaign)**. The cost of that
grain is stated on screen rather than hidden: one decision covers every current *and future*
negation of that term there, so the group renders "covers N negations… **and every future one**",
and `newSinceDecision` surfaces later arrivals instead of absorbing them.

## 4 · The panel's three defects

**(a) An API failure rendered as an alarm** — fixed. `.catch(() => setItems([]))` made an outage
show *"No protected terms yet"* **plus** the red *"Nothing is protected"* banner: an empty
whitelist and an offline API were the same pixels, and the more alarming reading was the wrong one.
Now three renderings, plus a fourth guard — zero negations read means the audit refuses to run
rather than reporting a clean account.

**(b) The panel could not create the protection the gate wants** — fixed. All ten live rows are
CONTAINS, seeded by SQL; the POST accepted only `isPrefix`, so **every protection an operator added
was strictly weaker than the ten already there**. There is now a three-way Contains / Starts with /
Exactly control defaulting to Contains, each with a sentence saying what it will and will not
catch. Additive on the API: absent `matchType` falls through to today's behaviour unchanged.

**(c) A protection cannot be edited** — not fixed, per the brief. Said on screen instead of left to
be discovered, and the 409 now names the stored semantics and how it differs.

## 5 · 🔴 The panel could not be deleted, and the brief expected it to be

§4 says to absorb the legacy panel and remove the duplicate render. It assumed this page was its
only caller. **`control-room/GuardrailsTab.tsx:197` mounts it too** — deliberately; its own comment

## 6 · Three defects that every automated check passed

🔴 **The delete control rendered as an empty box.** `.h10-am-btn` carries `padding: 7px 13px` — a
text button's padding — so inside this list's 28px icon-only column the content box collapsed and
the 12px `<Trash2>` was laid out at **width 0, height 12**. A destructive action with no icon and no
label.

Everything passed: the svg was in the DOM, `visibility: visible`, `opacity: 1`, a real stroke
colour, `display: block`, and an `aria-label` on the button. tsc, the DS ratchet, the link-target
guard, the class↔stylesheet sweep in both directions and the full build were all green. A zoomed
screenshot showed four empty boxes; `getBoundingClientRect().width === 0` named the cause. **Only
looking finds this one** — it is the seventh click-only defect on this page and the first that no
probe would have caught, because the element was present and correct in every respect a probe
inspects.

**A dead toggle.** `push` in the client deletes any param whose value is `'all'`
(`NegativeTargetingClient.tsx:129`, so `?market=all` never appears in a URL). The reviewed toggle
was written as `reviewed=all`, so it could never have been set — a button that does nothing, with
no error anywhere. Caught by reading the writer before trusting it.

**Two undefined CSS classes.** `.h10-ngp-fwd` / `.h10-ngp-bwd` are the two halves' containers.
tsc, the ratchet, the link guard and the full build all passed; without them the section renders
unseparated. Only grepping class↔stylesheet **in both directions** finds this.

## 7 · 🔴 The API was down, and not because of this section

Two API deploys landed two minutes apart — NEG.5's `ef3602fbd` at 20:14 and HV.5's `a046a097f` at
20:16. The second crashed with **P1002** on `SELECT pg_advisory_lock(72707369)`, and the lock was
then held by an **idle** pgbouncer-pooled backend. Because the next two commits were web-only and
turbo-ignored, **no further API deploy was even attempted**: the live deployment stayed CRASHED and
every route 502'd for roughly fifteen minutes.

This is the failure mode `railway.toml` already names in its own comment as *"the 2026-08-04
outage"*, and which `migrate-direct.mjs` exists to prevent. It is **not fully prevented**: stripping
the pooler stops the lock being *taken* through pgbouncer, but a crashed deploy can still leave one
held, and a `SKIPPED` web deploy will not retry it.

**Do not `pg_terminate_backend` the holder** — that drops live production traffic
([[reference_pgbouncer_advisory_locks]]). Measured here: the lock cleared by itself and
`migrate deploy` then completed in 2.6s. `_neg5-lockcheck.mts` answers "is it still held" in one
command.
