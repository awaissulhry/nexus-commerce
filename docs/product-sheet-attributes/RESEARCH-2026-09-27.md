# Product sheet — why the attribute count changes per market, and what is missing (2026-09-27)

Branch `study/sheet-attribute-parity` (from `main` 467b6353b). Worktree `/private/tmp/nexus-sheet-attr-parity`.
Nothing is built yet. Every number below was read from the live app (read-only) on 2026-09-27, Xavia Racing.

## Summary

The count changes for 3 reasons. Two are our bugs. One is Amazon's own rule.

| # | Cause | Kind | Example |
|---|---|---|---|
| 1 | Amazon's rules are not downloaded for most markets. The page never downloads them, and the nightly job only refreshes rules we already have. | 🔴 our bug | Amazon · BE shows 5 columns ("All attributes (6)"). Only 28 of 66 market × product-type pairs have rules. |
| 2 | The same product gets a different Amazon product type per market. | 🔴 our bug | GALE-JACKET is `COAT` in IT/DE/FR/ES (its live listings) but `OUTERWEAR` in every market where it is not listed. |
| 3 | Amazon asks for slightly different fields per country. | ✅ correct | DE adds 2 fields and drops 1. UK drops 6 image slots. |

"Fulfillment method" is missing because of a 4th problem:

| # | Cause | Kind |
|---|---|---|
| 4 | Amazon marks some fields as a "selector" (a key field). Our schema reader hides every selector field. 7 of them have more than one choice, so nothing can fill them: fulfillment method (FBA/FBM), product ID type (EAN/GTIN/…), battery type, language type, compliance document type and language, package-contains SKU. | 🔴 our bug |

The older Amazon flat-file editor shows some of these fields (`external_product_id_type`, `apparel_size__size_system`). The product sheet does not. So the two screens disagree.

Decisions for the Owner are in §6. The build plan is in §7. Progress is in §9.

## 2. Cause 1 — Amazon rules are missing for most markets

Amazon product types in use: AUTO_ACCESSORY, COAT, GLOVES, OUTERWEAR, PANTS, SUIT. 11 Amazon markets are active.

| Market | Rules cached | Missing |
|---|---:|---|
| IT | 6/6 | — |
| DE | 6/6 | — |
| FR | 5/6 | GLOVES |
| ES | 5/6 | GLOVES |
| UK | 5/6 | GLOVES |
| NL | 1/6 | AUTO_ACCESSORY, COAT, GLOVES, PANTS, SUIT |
| BE, PL, SE, IE, TR | 0/6 | all 6 |
| **Total** | **28/66** | **38 missing** |

Why the gap never closes:

- A page load is cache-only (`withCachedSchemas`, `studio-sheet.service.ts`). A missing rule set comes back as
  `absent`, and the sheet shows only the fixed columns (`loadAmazonSpec`, `channel-specs/index.ts:72`).
- The nightly job (`jobs/schema-refresh.job.ts`, `collectInUseSchemaTargets`) reads its targets FROM the cached rows.
  It refreshes what exists. It never adds a missing market or product type. Its header says "for every coordinate a
  business uses", but the code does not do that.
- The screen says "Requirements incomplete — Incomplete: OUTERWEAR". It does not say that the rules are not
  downloaded, and it gives no way to download them.

eBay has the same shape of problem. GALE-JACKET on eBay: IT = 52 columns (category 177104 cached). DE, FR, ES and
UK = 32 columns: no eBay category is known there, so only the 29 generic eBay fields show. NL, BE, PL and SE have no
eBay site, so that scope is refused. That refusal is correct.

## 3. Cause 2 — one product, two Amazon product types

The Amazon scope picks the product type per row (`productCategoryContext` → `categoryForListing`):

1. the listing's own `platformAttributes.productType`, if the product is listed in that market;
2. else the category mapping for that market (`resolveCategoriesForProducts`);
3. else the product's own `productType`.

For GALE-JACKET:

- IT, DE, FR, ES: all 21 rows are listed, and the listings say `COAT`.
- Everywhere else: no listing, and no mapping, so the product's own value `OUTERWEAR` is used.
- The Nexus category "Jackets" (8 products) has **no Amazon mapping in any market**.
- Amazon mappings exist only in IT, DE, FR and ES (Accessories, Rainwear, Gloves, Suits — not all in every market).
  NL, BE, PL, SE, UK, IE and TR have none.

Result: the same jacket is described with COAT fields in 4 markets and OUTERWEAR fields in the others. COAT has 152
fields in IT, and OUTERWEAR has 106. That is most of the 249 vs 163 difference.

The catalogue mixes both types for similar jackets: AIRMESH-JACKET's own type is `COAT`, and VENTRA, MOSS, REGAL are
`OUTERWEAR`. AIREON's family holds two types (OUTERWEAR + PANTS), so its sheet shows the fields of both.

## 4. Cause 3 — real Amazon differences (keep them)

Compared field by field against IT, same product type, same day:

| Market | Adds | Drops |
|---|---|---|
| DE | `uvp_list_price` (German RRP), `epr_eco_fee_eubr` (+ its currency) | `ghs` |
| FR, ES, NL | — | — |
| UK | — | `image_locator_ps01` … `ps06` |

I checked the raw DE schema. Amazon's own DE definition has 107 properties, and IT has 106. The difference is in
Amazon's data, not in our reader. The sheet must keep showing these differences. It must also explain them, so a
different number is not a surprise.

## 5. Cause 4 — selector fields are hidden (why "fulfillment method" is missing)

Amazon lists some sub-fields of an attribute as `selectors`. They are the key of each value. The walker removes
every selector from the list of fields a person can edit (`channel-specs/amazon.ts:193`). It keeps one only when
nothing else is left (the "keyed set" case, for example `ghs.classification`).

The writer (`attributesFromCells`, `mapping/schema-requirements.ts:54`) fills a hidden selector only when Amazon allows
exactly one value (or a default). With 2 or more choices, it has nothing to write.

Selectors in the 6 product types in use (IT schemas):

| Selector | Choices | Required | What happens now |
|---|---:|---|---|
| `fulfillment_availability.fulfillment_channel_code` (FBA / FBM) | 2 (`AMAZON_EU`, `DEFAULT`) | yes | No column. The publish path sets it from the listing's fulfillment method, but the operator cannot see or change it on the sheet. |
| `externally_assigned_product_identifier.type` (EAN, GTIN, …) | 4 | yes | "External Product ID" column has no type next to it. |
| `num_batteries.type` | 9 | yes | "Number of Batteries" can be typed, but not the battery type. |
| `language.type` | 15 | yes | Language value without its type. |
| `compliance_media.content_type` | 25 | yes | A compliance document without its type. |
| `compliance_media.content_language` | 124 | yes | A compliance document without its language. |
| `package_contains_sku.sku` | free text | yes | Quantity without the contained SKU. |
| `list_price.currency`, `purchasable_offer.currency` | 1 (EUR) | yes / no | Filled automatically. OK. |
| `purchasable_offer.audience` | 1 (ALL) | no | Filled automatically. OK. |
| `apparel_size.size_system`, `bottoms_size.size_system` | 1 (as6) | yes | Filled automatically. OK. |
| `hazmat.aspect` | 1 | yes | Filled automatically. OK. |

The generic `fulfillmentChannel` field is also removed on the channel scope (`droppedKeys`). So the Amazon scope has
no fulfillment column of any kind. The same is true of the ASIN (`amazonAsin` is dropped too).

Every other Amazon field is there: all 152 COAT properties have at least one column.

Only 12 of the 249 Amazon · IT columns show by default. All 49 Offer columns (price, quantity, handling time,
condition, …) are hidden until the operator opens "All attributes". So a field can look missing when it is only
hidden.

## 6. Decisions for the Owner

**D1 — How to get the missing Amazon rules (38 pairs).**
Getting them reads Amazon's rules API and saves a copy in our database. It does not change any listing.

- **A (recommended):** the nightly job also downloads every missing pair (active market × product type in use), and
  the sheet gets a "Download Amazon rules" button for an urgent case. The gap closes by itself and stays closed.
- B: the button only. The operator must click it for every market and product type.

**D2 — Which Amazon product type to use in a market where the product is not listed yet.**

- **A (recommended):** first use the type the same product already has on Amazon in another market of the same
  Amazon region (GALE → COAT everywhere in Europe). Then the mapping. Then the product's own value. The sheet shows
  where the type came from.
- B: use only the category mapping, and add an Amazon mapping for "Jackets" (and the other categories) in every
  market. Then you must choose COAT or OUTERWEAR for jackets yourself.

## 9. Progress

**2026-09-27 — the Owner chose D1 = A and D2 = A**, and asked to fetch every missing rule set at once.

- **Fetched now (8 of 38)** through the normal `GET /categories/schema` path, on production: NL × AUTO_ACCESSORY,
  COAT, GLOVES, PANTS, SUIT, plus GLOVES for FR, ES and UK. Every call returned HTTP 200. Read back: the glove
  products went from 5 to 160 columns in FR, ES and NL (154 in UK). The knee slider in NL went from 5 to 173. The
  suit in NL went from 5 to 197.
- **Blocked (30 of 38): BE, PL, SE, IE, TR.** Amazon answered "Access to requested resource is denied". Cause:
  `amazonMarketplaceId()` (`services/categories/marketplace-ids.ts`) knew only 10 codes, and passed any other code
  through as itself. So Amazon was asked for marketplace "BE". This is a 5th cause: even the nightly job could never
  have fetched these markets.
- **A 6th finding:** `utils/marketplace-code.ts` mapped South Africa's id `AE08WJ6YKNBMC` to BE. The reverse lookup
  keeps the last id per code, so `marketplaceCodeToId('BE')` returned South Africa's id to the Amazon image routes.
- **Fix = PR #77** (branch `fix/amazon-marketplace-ids-all-markets`): the lookup falls back to the market catalogue
  for a missing code, and South Africa reads as ZA. After it is merged and deployed, fetch the 30 missing rule sets.
- About 45 files keep their own copy of this code → id list. Only the two above were wrong for the markets in use.
  A single shared list is a follow-up, not part of #77.

- **P1 built** (branch `feat/amazon-hidden-fields`):
  - The Amazon schema reader authors a selector when the writer cannot fill it (more than one allowed value, no

    do not change; the new columns are `key__selector` (for example `num_batteries__type`).
  - `fulfillment_availability__fulfillment_channel_code` is shown as **Fulfillment method** with the choices
    "FBA — Amazon stores and ships" / "FBM — you ship". It is visible by default on the Amazon scope.
  - It reads the nested code the FBA guard reads. With no nested code, it shows the method the Matrix tab shows
    (typed column, then the flat mirror, then the product's flag), marked inherited.
  - A save goes through `setFulfillmentMethod`, the one fulfilment door, inside the sheet's own save (like
    prices): the typed column and both mirrors in one write, and FBA → FBM refused while FBA stock is on hand.
  - `setFulfillmentMethod` now starts its stock re-push after COMMIT when it runs inside a caller's transaction.
- **New finding — three rules for one fact.** "What is this listing's fulfilment method" is answered three ways:
  the Matrix (`typed ?? flat mirror ?? product`), the Amazon publish step (`active offer ?? typed ?? product`), and
  the FBA guard (fail-closed: any FBA signal). For a listing Amazon reports as FBA whose typed column is empty and
  whose product flag says FBM, the publish step would send FBM. Not changed — it is publish behaviour, and it needs
  the Owner's word. Recommended: the publish step uses the same rule as the Matrix and the guard.
