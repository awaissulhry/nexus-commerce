## 1 · §3's three corrections, resolved

### 3.3 🔴 A real defect in shipped S2 code — fixed, `4ba32e133`

`AdvertisingActionLog.userId` does **not** hold an operator id. `ads-mutation.service.ts:106`
writes `userId: args.actor`, so the column holds the **actor string** — `user:<id>` for a human,
`automation:<ruleId>` for an engine. `ads-changes.service.ts:70` states it outright: *"the mutation
path stores automation actors in userId"*.

| over 60 days | |
|---|---|
| `AD_BID_UPDATE` rows | 25,139 |
| `parseActor(userId).source === 'automation'` | **25,039** |
| …`=== 'operator'` | **100** |
| `userId IS NULL` | **0** |

S2 selected operator writes with `userId: { not: null }`, which matched nearly every automated
write. **`manual` 12 → 6 · `No bidder` 41 → 47 enabled campaigns.** It under-reported the page's
loudest chip, in the direction that hides work: six campaigns read as looked-after by a human when
nothing has touched them.

**The exact predicate, as requested:**

```ts
parseActor(log.userId).source === 'operator'
  // over: actionType = 'AD_BID_UPDATE' AND createdAt >= now - 60d
  // then AdTarget.id → adGroup.campaignId, because a bid write names a TARGET
  // and the bidder is a property of the CAMPAIGN
```

You measured 5/48 to the corrected 6/47. We still differ by one campaign; the predicate is now in
the code so the difference is inspectable rather than argued. `parseActor` is exported, pure and
unit-tested precisely so every surface classifies an actor identically — reading the raw column was
the second resolver this page promised not to write. It just did not look like one.

### 3.1 The convention is correct. The number was a live sample of a ramp

**Verified: `+300%` means `bid × 4.00`.** The code computes `bidCents × (1 + pct/100)`; the shipped
output €1.35 at +133% ⇒ €3.15 is ×2.33. There is no off-by-one-convention defect.

But neither +400% nor +300% is "the largest". `CampaignBidHistory` audits placement under **lane
names** (`PLACEMENT_TOP` 7,303 rows · `PLACEMENT_REST_OF_SEARCH` 6,556) — S2's probe searched for a
field called `placementBidding` and found zero, which is the wrong-field-name trap for the third
time in this programme. Reading the right field, on the exact campaign S2 quoted:

```
13/08 11:45  PLACEMENT_TOP  350 → 375   all-out — push for the slot
13/08 12:00  PLACEMENT_TOP  375 → 400
13/08 12:15  PLACEMENT_TOP  400 → 425
13/08 12:30  PLACEMENT_TOP  425 → 450
13/08 12:45  PLACEMENT_TOP  450 → 475
13/08 13:01  PLACEMENT_TOP  475 →   0   above Placement — snap to 0% Placement
```

**+25% every 15 minutes to +475%, then zero inside 90 minutes.** Account-wide: **1,050 placement
writes in 24 h, values 0–475.** S2's +400% at 12:02 and the operator's +300% at 20:24 were both
correct readings of a moving value.

🔴 **The consequence is larger than the label.** `Eff. max CPC` is a **15-minute sample, not a
ceiling**. The drawer now says "right now" and explains why; **S5 must not derive a bound from it
without the same caveat.**

### 3.2 Clock, confirmed — and a fourth lane

Re-measured: **164** campaigns with a `placementBidding` array, **162** non-zero, **58 ENABLED**
non-zero, against the operator's 165/58 and S2's 172/68. Same field, same method, different hour.

**`SITE_AMAZON_BUSINESS`** — 7 campaigns, max +10% — was reaching its strategy uplift through a
`?? 0.5` fallback in `LANE_UPLIFT`. The value is right (Amazon's non-top figure is 50%) and it is
now named. A lane that arrives at its number by fallback is a lane nobody has checked.

### The denominator you flagged

**2,539** never-written over T (all 3,154 positive targets) · **2,336** over A (the 2,944 ENABLED).
Both correct. S2 quoted the T figure inside a paragraph whose other numbers were A — the exact
discipline that doc preached, broken in it.

## 2 · The curve — one line and one list, not two lines

The fixture forced this. `_bid-page-chain.mts cmr28mgl50019qq010p4nqnhg` (B072XH2LB2, `GALE | IT |
PAT`) shows **33 recorded cuts of €0.38 → €0.02 between 01 Jul and 02 Aug, one a night, every one
FAILED at Amazon** — not the 19 the brief quotes; 56 rows total, **APPLIED 22 / FAILED 34**. On
03 Aug `automation:dl-requeue` wrote `38 → 38 SUCCESS` after the `/sp/keywords` routing fix, and
every write since has landed.

🔴 **In the failed phase every write's `oldValue` is 38 while the previous write's `newValue` was
2** — because the unaudited hourly resync put it back. A connected "intended" polyline would draw
38→2→38→2 and assert the engine raised it each morning. **It never did.** So:

- **Delivered** — a step line built from `APPLIED` writes only, held forward. Flat at €0.38 through
  all of July.
- **Intended** — one row per write in the log, each stating whether it landed. Never connected.

A cut that never reached Amazon reads as exactly that, and the line above it does not move. Two
connected series would have drawn a keyword falling to the floor when it never left €0.38.

`null` delivery renders **"no record"**, never success.

**Density needed no aggregation.** 56 points across the drawer is legible; the busiest entity in the
account is 118. Default is the raw sequence, per the brief. A toggle hides the nightly cycle
(off by default), and **the two reason strings for that one mechanism are grouped** — *"pause
target → bids floored (no-pause)"* is the pre-MB.1 wording for *"Min bid → bids floored to €0.02"*,
and showing them as two causes would invent a second engine.

### A defect the deployed page exposed

The oldest log row read `1 Jul, 17:35 · **€0.00** · System · not recorded`. That is the
`create_target` operation row, which has no value at all — and it passed the numeric filter because
🔴 **`Number(null)` is `0`, which is finite.** It also put a phantom zero at the left end of the
delivered line and inflated the tally by one. Fixed with an explicit null check; the filter now
reads `c.newValue != null && Number.isFinite(Number(c.newValue))`.

## 6 · What S1 and S5 need from this

1. 🔴 **`No bidder` is 47 enabled campaigns, not 41.** S1's band must quote the corrected number.
   Anything published before `4ba32e133` is 6 campaigns short.
2. 🔴 **`Eff. max CPC` is a sample with a 15-minute half-life.** S5 must not materialise a bound
   from it onto `Campaign.maxBidCents` without stating when it was read.
3. **Out-of-band is growing** — 56 on 12 Aug, **105 on 16 Aug**. Bids move nightly and ceilings do
   not, so this population only grows until someone lowers a bid or raises a ceiling. A test that
   pinned it to a range rotted in four days; assert the invariant, report the count.
4. **`parseActor` is the only actor classifier.** Do not read `userId` raw. It cost this page a
   wrong number on its loudest chip for four days.
5. The drawer owns `?target=`. S4's editing controls belong **in the drawer's overlay slot**, not as
   a nested modal.
