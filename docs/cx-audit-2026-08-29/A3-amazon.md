## 2. LWA access-token caching in the hand-rolled client

`api/clients/amazon-sp-api.client.ts`:
- **Cache location:** process memory, one field per singleton — `accessToken`/`tokenExpiresAt` (`:119-120`), and a per-scope `Map` for grantless tokens (`:122`). Nothing in DB.
- **Expiry margin:** fixed `now + 50 min` (`:191`, `:238`), ignoring `expires_in` (LWA issues 3600 s → 10 min margin; if Amazon ever shortens it the cache serves dead tokens).
- **Concurrency lock:** none. Two concurrent callers seeing an expired cache both POST to LWA (`:155-205`). Contrast the Ads client, which dedupes in-flight refreshes (`ads-api-client.ts:202-247`).
- **401 / invalid_grant:** `fetchWithRetry` explicitly does not retry 401/403 (`:345-348`, `RETRYABLE_STATUSES` `:358-360`); a 401 does **not** evict the cached token; `getAccessToken` logs and rethrows on LWA failure (`:199-204`). grep `invalid_grant` finds only post-hoc classifiers (`api/jobs/latency-watchdog.job.ts:63`, `api/services/outbound-sync.service.ts:112`), no handling in the client.
- **Refresh failure → connection status:** none. No code writes `ChannelConnection` for Amazon (grep above). The env row's `lastSyncStatus='SUCCESS'` set at boot (`api/index.ts:380`) never changes.
- The `amazon-sp-api` npm library instances (14 of them, each with its own token cache) handle their own LWA via `auto_request_tokens` — internals unverified.

## 3. Rate limiting and retries

**Hand-rolled SP client (`api/clients/amazon-sp-api.client.ts`):**
- Global fixed 200 ms spacing (`REQUEST_DELAY_MS` `:124`, `applyRateLimit` `:324-335`) — one bucket for every operation, not per-operation as SP-API's limits are.
- `fetchWithRetry` `:357-415`: retries 429/500/502/503/504 and network errors with fixed delays 1 s/2 s/4 s (3 retries), no jitter, **does not read `Retry-After` or `x-amzn-RateLimit-Limit`** (grep for the header returns nothing repo-wide). Final attempt returns the raw response.
- Quota-exceeded (`QuotaExceeded` code) is not distinguished from any other 429.

**`amazon-sp-api` library instances:** rely on `auto_request_throttled: true` (all 14 constructions). `amazon.service.ts:1010-1013`, `:1186`, `:1225` add a 250 ms courtesy sleep, `:1743` 2100 ms for financial-events pagination. `amazon-batch-feed.service.ts:311-328` wraps calls in `withTimeout` (25 s at `:352-356`) because `auto_request_throttled` can block for the whole window (getFeedDocument ~1 req/45 s). Feeds: no explicit quota handling beyond the library; a timed-out `getFeed` is "simply retried on the next tick" (`:316`). Reports: `sp-api-reports.service.ts:183-272` polls until DONE/CANCELLED/FATAL with `POLL_INTERVAL_MS`; no 429-specific branch (grep).

**`api/services/channel-batch/rate-limit.ts`** is not an Amazon client; it is a detector for the bulk-action worker: `RateLimitError` (`:24-34`), `isRateLimitError` string/structural match on 429 / "rate limit" / "throttled" (`:43-62`), `extractRetryAfterMs` (`:69-87`), and a 1→30 s backoff ladder `defaultRateLimitBackoffMs` (`:96-99`). Its consumer pauses the loop and retries the same item (header comment `:19-21`).

**Publish gate (`api/services/amazon-publish-gate.service.ts`):** a per-(seller, marketplace) token bucket, 2 req/s burst 20 (`:55-60`, `acquireAmazonPublishToken` `:104`), and a circuit breaker (3 failures / 5 min → open 10 min, `:19-22`, `checkAmazonCircuit` `:193`, `recordAmazonOutcome` `:224`), single-process state (`:24-27`).

**Ads client (`api/services/advertising/ads-api-client.ts`):** regional hourly quota ledger keyed `amz:ads:<region>`, budget `NEXUS_AMAZON_ADS_REGION_BUDGET ?? 9000`/3600 s (`:278-282`), Redis-backed with memory fallback, reads fail-open / writes fail-closed (`:259-276`), bypass `NEXUS_AMAZON_ADS_QUOTA_MODE=off` (`:284`), one unit per outbound request including retries (`:316-323`). `fetchWithRetry` `:340-383` retries 429/423/5xx, honours `Retry-After` (`:370-371`), exponential ≤8 s with full jitter (`:372-376`), 3 rate attempts / 5 lock attempts.

## 4. Notifications (SP-API → SQS) and AMS

**Subscribed types** — `api/services/amazon-notifications-boot.service.ts:157-169` `NEXUS_SP_API_NOTIFICATION_TYPES`: `ORDER_CHANGE`, `ORDER_STATUS_CHANGE`, `FBA_OUTBOUND_SHIPMENT_STATUS`, `FBA_INVENTORY_AVAILABILITY_CHANGES`, `ANY_OFFER_CHANGED`, `FEED_PROCESSING_FINISHED`, `ACCOUNT_STATUS_CHANGED` — **seven**, though the code and admin response still say "8" (`:172`, `api/routes/amazon-notifications.routes.ts:186-203`, which also lists `LISTINGS_ITEM_STATUS_CHANGE` that was removed at `:163-166` of the boot service). `amazon-sqs.service.ts:276-308` still parses `LISTINGS_ITEM_STATUS_CHANGE` — dead branch.

**Destination / queue ARN:** derived by string-splitting `AMAZON_SQS_QUEUE_URL` into region/account/name and rebuilding `arn:aws:sqs:…` (`boot.service.ts:191-195`). Destination is looked up by that ARN via grantless `GET /notifications/v1/destinations` (`:204-207`) and created if absent (`:209-219`), using `getGrantlessToken('sellingpartnerapi::notifications')` (`api/clients/amazon-sp-api.client.ts:213-241`). Region slug for grantless calls: `mapAwsRegionToSpApiSlug(AMAZON_REGION || 'eu')` (`:199`).

**Verification / self-heal at boot:** `ensureAmazonNotificationSubscription()` (`:340-363`) is called from `api/index.ts:1190`, fire-and-forget, gated on `isSqsConfigured()` **and** `NEXUS_ENABLE_AMAZON_SQS_POLL=1` (`:341-342`), records its result as a `CronRun('amazon-notifications-setup')` row (`:349-356`). Per type it GETs the existing subscription, returns early only if active **and** pointed at our destinationId (`:60-73`); a foreign-destination subscription is deleted (grantless DELETE) and recreated (`:74-93`). A full destination recycle is triggered by a DB directive `CronRun{jobName:'amazon-notifications-recycle-request', status:'RUNNING'}` (`:234-284`). `ORDER_CHANGE` needs a `processingDirective.eventFilter` and other types reject it (`:103-123`). **Polling job** — `api/jobs/amazon-sqs-poll.job.ts`: scheduled `* * * * *` (`:535`) only when `NEXUS_ENABLE_AMAZON_SQS_POLL=1` and SQS configured (`:520-525`); each tick drains for a 55 s budget using 20 s SQS long-polls (`:37-47`, `pollSqsMessages` `amazon-sqs.service.ts:189-209`, `MaxNumberOfMessages ≤10`), guarded by a `running` flag (`:23-30`), wrapped in `recordCronRun('amazon-sqs-poll')` (`:32`). **Not in `cron-registry.ts`** (grep: 0 hits) — cannot be manually triggered from the registry.

**Deletion:** `deleteSqsMessage` after success (`:111`, `:177`, `:212`, `:263`, `:308`, `:353`, `:503`); on handler failure the message is **not** deleted so SQS redelivers after the visibility timeout (`:333`, `:397`, `:499-500`). Payload `SellerId` is not compared with ours except for the buy-box winner heuristic (`job :230-235`). See Security #4.

**AMS (Ads Marketing Stream) — `api/jobs/ams-sqs-poll.job.ts`:** `* * * * *` (`:99`), self-gated on `NEXUS_AMS_SQS_QUEUE_URL` (or derived from `NEXUS_AMS_DESTINATION_ARN`, `ams-sqs.service.ts:27-31`) + AWS keys (`:40-42`); in `cron-registry.ts:255`. ## Security findings (ranked)

1. **Ads OAuth callback has no state/CSRF binding — PUBLIC route accepts any `code`.** `api/routes/amazon-ads-auth.routes.ts:302-332` proceeds without `state`; `PKCE_STORE` lookup is optional; no cookie/session tie. Manifest `permissions-manifest.ts:82` makes `/api/amazon-ads/auth/*` PUBLIC. An attacker who completes consent on *their own* Ads account and sends the operator (or simply requests themselves) `…/auth/callback?code=<theirs>` gets their profiles upserted as `isActive:true` connections (`:399-425`), potentially replacing the operator's rows for colliding `profileId`s and pointing bid automation at a foreign account. Also: in-memory store breaks on restart / multi-instance (`:19-21`).
2. **Public write-capable probe gated by a guessable key.** `GET /api/admin/amazon-auth-probe?k=<last 6 of AMAZON_SELLER_ID>&write=1` is PUBLIC (`permissions-manifest.ts:56`); the seller/merchant id is exposed in Amazon storefront URLs, and the endpoint performs a live `patchListingsItem` (`amazon-auth-probe.routes.ts:137-159`), leaks the env topology (`:65-82`) and logs it at warn (`:166`). Marked TEMPORARY (`:2`).
3. **Debug endpoint exposes credential material and fires live report jobs.** `/api/amazon-ads/debug/test-auth` returns stored `clientId`, a 15-char refresh-token prefix, token prefixes (`amazon-ads-auth.routes.ts:135-147`, `:162-169`, `:256-262`) and POSTs three real `/reporting/reports` jobs per call (`:176-225`). Only `adsView` is required (`permissions-manifest.ts:234`), and only if `NEXUS_RBAC_MODE=enforce` (`api/lib/auth/rbac-hook.ts:30`; prod mode unverified).
4. **SQS/SNS payloads are trusted without signature verification.** `amazon-sqs.service.ts:218-219`, `ams-sqs.service.ts:79-86`; no `SellerId` check on order/inventory notifications. The documented queue policy allows `aws:SourceArn: arn:aws:sns:*:*:*` (`docs/IS-SETUP.md:30-46`) — any SNS topic in any AWS account may publish. Forged `FBA_INVENTORY_AVAILABILITY_CHANGES` create `ChannelStockEvent` drift rows (`amazon-sqs-poll.job.ts:279-336`); forged `ACCOUNT_STATUS_CHANGED` triggers the global banner (`:92-120`). Actual queue policy in AWS: unverified.
5. **Single plaintext seller refresh token in env, no tenant isolation, no rotation, no revocation path** (§1, §7). Captured at module load in `amazon-sp-api.client.ts:131-134` and `amazon-ads-auth.routes.ts:31-37`. `tokenIssuedAt` for the SP-API token is not tracked anywhere (the 365-day expiry countdown exists only for Ads, `schema.prisma:3034-3052`).
6. **LWA app secret copied into every `AmazonAdsConnection` row** (`amazon-ads-auth.routes.ts:376-382`, `advertising.routes.ts:12272-12274`): secret rotation requires re-encrypting/re-consenting every row; DB compromise + `NEXUS_CREDENTIAL_ENC_KEY` yields the app secret. Deleting a connection does not invalidate the token at Amazon (`:12299-12307`).
7. **Hard-coded production URLs** — redirect URI default `https://nexusapi-production-b7bb.up.railway.app/...` (`amazon-ads-auth.routes.ts:35-37`), web link `:455`, EU-only Ads base `:42` and `region:'EU'` `:404` (silently mis-files NA/FE accounts).
8. **Access-token prefix rendered in the callback HTML** (`:431-445`) and logged `state` (`:297`). Low.
9. **`GET /api/admin/amazon-notification-status` returns the raw SQS queue URL incl. AWS account id** (`amazon-notifications.routes.ts:256`) — `adminView` gated (`permissions-manifest.ts:404`). Low.
10. **AMS ingest shared secret compared with `!==` and optional** (`advertising.routes.ts:8406-8407`); PUBLIC path (`permissions-manifest.ts:79`). Low-medium.
11. **No secret logging found** — grep for logger calls containing `refresh_token|access_token|client_secret|Bearer` returned nothing; the hand-rolled client logs only expiry metadata (`amazon-sp-api.client.ts:160-162`, `:193-196`). `marketplaces/amazon-sync.service.ts:148-150` logs the whole outbound payload (no secrets, but prices/titles at info level).
