# Product management and PIM audit

Audit date: 11 September 2026. Scope: the current product Studio, Shared product, Amazon, eBay, Shopify, Etsy, category taxonomy, and the services that resolve, validate and publish their values.

## Decision

**Keep the architecture and finish the operating workflows. The current implementation is not yet ready for an AAA end-to-end product management claim.**

The family-driven shared dictionary, common channel sheet, inherited values, typed channel adapters and explicit destination guards are the right foundation. The largest remaining problems concern the quality of family definitions, language correctness, scoped publishing, and the distinction between locally complete and actually live. Adding more channel columns alone will not solve them.

The lowest-effort model is: define facts once on the shared product, inherit them into variants, translate eligible content once, apply reusable category/channel mappings, and create listing overrides only for deliberate exceptions. Review changes against their exact destination before delivery, then reconcile the provider's actual result.

## Evidence and limits

This audit combines current source tracing, read-only database inspection, browser inspection of the actual local editor and category page, targeted automated tests, two executable resolver reproductions, and current primary provider documentation. It does not certify every product/category/account combination, live publication, storefront output, or WCAG AAA conformance.

- Browser sample: GALE-JACKET and its 20 variants across the five requested scopes; category administration and taxonomy status. Column chooser counts include structural columns and must not be confused with distinct editable business attributes.
- Database sample: all 338 nondeleted products in the connected workspace, 37 roots, family definitions, category defaults, translation counts, active markets and taxonomy sources. Only selected catalog metadata was read. [Database evidence](workspace-evidence.json).
- Fresh automated results: **233 passed, 1 skipped** across 23 test files. The skipped case starts an opt-in isolated scope browser fixture. These are unit/service contract tests, not proof of successful provider mutations. [Verification record](verification.json).
- [Executable reproductions](reproduce-resolver-gaps.mts) and [recorded results](resolver-gap-results.json) demonstrate a language fallback gap and an Amazon conditional validation gap without external writes.
- [Shared attribute review](shared-attribute-review.md) accounts for all 198 effective family definitions in the sampled Jackets family. Its recommendations are proposed schema curation, not changes to stored data.

No catalog values, category assignments, refresh requests, listings, source application code or deployments were changed by this audit. Existing workspace edits were preserved. Earlier audit documents were used as background and checked against the newer common-sheet implementation; their superseded gap lists are not treated as current facts.

## How the current model works

| Layer | Current purpose | Intended ownership |
| --- | --- | --- |
| Product family | Defines the shared attribute template, types, applicability, requiredness and inheritance | Product model: Jackets, Gloves, Boots, etc. |
| Internal category tree | Organizes products and supplies inherited channel category defaults | Catalog classification; may differ from the family hierarchy |
| Shared product and variants | Canonical facts, localized content and variant-specific differences | Brand/model facts on the parent; SKU/GTIN/color/size and relevant measurements on variants |
| Channel category/schema | Amazon product type, eBay leaf category, Etsy taxonomy, Shopify standard category and store definitions | The selected provider, market and store capabilities |
| Mapping | Reads shared facts, applies transformations/value mappings/defaults | Reusable account/market/category rules |
| Listing override | Changes a particular listing's values and exceptions | The exact account, listing alias, market and supported language |
| Provider synchronization | Delivers changes and reads results | A durable reviewed operation with explicit ownership and status |

The current shared sheet is built from the family dictionary through [family-sheet-schema.ts](../../../apps/api/src/services/pim/family-sheet-schema.ts), with universal fields and preserved historical saved keys. It is not currently generated by combining every Amazon/eBay/Shopify/Etsy schema. However, many provider-shaped definitions have already entered that dictionary; the data configuration still makes it excessively broad.

[workspace-destination.ts](../../../apps/api/src/services/pim/workspace-destination.ts) checks account, channel, market, family and listing ownership. Studio remounts on scope changes, and the current Activity and Needs attention channel surfaces carry destination identity. These are meaningful strengths. The remaining identity gaps are specific downstream paths described below.

The family/channel/locale approach also matches established PIM practice: completeness is defined against relevant family requirements and destination language, rather than the total number of possible fields. [Akeneo completeness](https://help.akeneo.com/187-serenity-follow-your-products-completeness?kb_language=en_US).

## Prioritized findings

Priority 0 means a release blocker for the affected workflow. Priority 1 means necessary for the requested low-effort, multi-market product management. Priority 2 means a subsequent usability or scale improvement.

### F01 — P0: the new editor does not yet have a complete, exact-destination publishing path

In [AliasPublishControl.tsx](../../../apps/web/src/app/products/[id]/edit/_studio/sheet/channel/AliasPublishControl.tsx), the preview request contains only product IDs, channel and marketplace. It omits account, alias/listing identity and locale. Selecting an alias changes which variant IDs are included, but does not identify that alias's overrides to the preview service. [sheet-publish.service.ts](../../../apps/api/src/services/pim/sheet-publish.service.ts) uses the older sheet preview path.

The Amazon action is explicitly a stub: clicking its send control produces “The per-alias send is not wired yet”. The generic preview directs eBay toward flat-file export and reports no Etsy sheet publishing route. The Studio header's review action opens Information; its shared action opens the legacy wizard without a bound account/listing handoff.

Real Amazon, eBay and Shopify publishers exist in [channel-publish.service.ts](../../../apps/api/src/services/listing-wizard/channel-publish.service.ts), and Shopify has a newer scoped review/synchronization workflow. This finding is about the missing common editor-to-publication contract, not a claim that Nexus has no publishing code.

**Required result:** expand Needs attention into Readiness & publishing. Carry product/family, account, provider market or market resource, listing/alias, locale, schema version and reviewed draft revision through preview, queue, execution, retries and readback. Show the actual changed values and affected variants. Keep create/update/end or archive operations explicit. Make duplicate prevention, interrupted requests and partial successes visible. A remote acknowledgement must not automatically mean Live.

### F02 — P0: eBay can remove regulatory data after an unrelated offer error

[ebay-publish.adapter.ts](../../../apps/api/src/services/listing-wizard/ebay-publish.adapter.ts), around lines 659–689, attaches the resolved regulatory payload. If `createOffer` returns any unsuccessful response and regulatory data exists, it deletes that payload and retries. The error is not first established to be caused by regulatory data. A subsequent success can continue toward publication, with a warning.

**Required result:** preserve the reviewed payload and fail with a useful correction action. Any permitted change to regulatory intent must be explicitly reviewed. Build on the existing [compliance resolver](../../../apps/api/src/services/compliance-resolver.service.ts), which already resolves manufacturer/responsible-person information, certificates and product safety facts. This is a source-confirmed behavior; it was not exercised against a live listing.

### F03 — P0 for required-language delivery: fallback content is not reliably identified as untranslated

[attribute-resolver.ts](../../../apps/api/src/services/pim/attribute-resolver.ts) falls back from a requested locale to English localized content and, for some content fields, shared legacy columns. [resolve-channel-field.ts](../../../apps/api/src/services/pim/resolve-channel-field.ts) sets `needsTranslation` for an explicit translation link or transform, rather than the effective language of the resolved value.

The reproduction requests German with only an English title. The result is the English title, `source: catalogRule`, and `needsTranslation: false`. A useful display fallback therefore has no reliable missing-translation signal in this path.

There is also a second translation store: the Studio uses `Product.localizedContent`, while the older Locales page and translation route use `ProductTranslation`. Their default-language assumptions differ. The database contains two populated Italian localized-content records and one legacy English translation record. This does not prove that channel overrides contain no other translations.

Finally, [scope-readiness.service.ts](../../../apps/api/src/services/pim/scope-readiness.service.ts), its route and the readiness query in [contracts.tsx](../../../apps/web/src/app/products/[id]/edit/_studio/contracts.tsx) do not accept/key on the selected locale. The header percentage is consequently not a reliable completeness result for the language currently being edited. The visible language picker is currently available in Shared and Shopify, not in Etsy's global scope.

**Required result:** one canonical locale contract; requested and effective locale provenance; explicit missing, fallback, draft, reviewed and outdated states; source-change detection; and readiness evaluated for the actual locale. Allow preview fallback where useful, but enforce the destination's translation policy before delivery. Preserve and reconcile both existing translation stores during migration.

### F04 — P1: the shared family template is too broad and does not define meaningful completeness

The sampled Jackets family inherits **198 definitions, zero required**, and 57 are marked localizable. Its shared column chooser offers **227 columns**, while only 17 saved attribute-bag keys are populated across the example's 21 rows. Irrelevant-looking defaults include flavor, scent, ring, lens and trousers-specific properties. Battery attributes can be valid for heated garments, but should be conditional extensions.

Across 338 nondeleted records, the canonical manufacturer, description, keywords, item weight and three item dimension columns are empty. Twenty-three of 37 roots have no family. Some roots may be imported shells or channel identities, so classification and identity reconciliation must precede any bulk family assignment. Channel overrides and custom bags may contain values absent from these native columns.

The shared Ready 100% result is currently much easier to achieve than a complete sellable product. The family configuration is the main weakness; merely hiding columns would not fix missing requiredness or field semantics.

**Required result:** curate each family's core, optional and conditional attributes; define relevant publish requirements; normalize duplicate concepts; and show focused presets such as Essential, Variants, Content, Technical and Missing. Preserve unused historical values in their existing additional-attributes area. Review automatically proposed source definitions before adding them broadly to families.

### F05 — P0 for Amazon readiness: standard JSON Schema validation misses Amazon vocabulary constraints

[schema-requirements.ts](../../../apps/api/src/services/pim/mapping/schema-requirements.ts) correctly evaluates standard conditional schema constructs. It initializes Ajv with unknown-keyword strictness disabled, but does not register Amazon's additional validation vocabulary. [amazon.ts](../../../apps/api/src/services/pim/channel-specs/amazon.ts) extracts some leaf byte/cardinality limits; that does not enforce all condition-dependent constraints.

The reproduction applies a three-byte `maxUtf8ByteLength` only when a mode is selected. A six-byte value produces no issues. Amazon's vocabulary includes UTF-8 limits and selector-based uniqueness constraints. [Amazon meta-schema](https://developer-docs.amazon/sp-api/docs/product-type-definition-meta-schema).

**Required result:** validate the exact serialized provider payload using the supported Amazon vocabulary, including conditional constraints, selectors and repeated structured values. Retain the existing explicit block where nested repetitions require a structured editor. Include schema version/freshness in preflight. Generic cached product-type schemas are useful; request seller-specific requirements where capabilities require them, since the current cache fetch deliberately omits `sellerId`. [Amazon product type definition retrieval](https://developer-docs.amazon.com/sp-api/docs/retrieve-a-product-type-definition).

### F06 — P1: Shopify store and language support is stronger than Shopify Markets support

The current common sheet has typed native/store-definition editors, product/variant ownership checks, category constraints, metafields/metaobjects, publication operations, translations and durable draft recovery. The sampled chooser has 72 columns. The latest Shopify coverage audit documents 39 store definitions with editing paths; some native fields have legitimate derived or API capability restrictions.

However, the current scope is `GLOBAL`, and [information-translations.ts](../../../apps/api/src/services/shopify/information-translations.ts) selects translations whose market is null and writes without `marketId`. I did not find a connected Shopify Markets catalog/price-list workflow in the inspected product services. This supports base store language editing, not complete per-Market content, assortment and pricing control.

**Required result:** add a store → Shopify Market → locale view, respecting which fields are shared and which support contextual values. Use actual Market/catalog IDs. Shopify supports market-specific translations through `TranslationInput.marketId`, while market catalogs connect publication and pricing. [Translation input](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/TranslationInput), [Market catalogs](https://shopify.dev/docs/apps/build/markets/build-catalog).

The existing native synchronization reads before and after writes; several native mutations still lack atomic compare-and-set protection. Existing tests and real reads are valuable, but controlled provider write/readback and storefront verification remain release work.

### F07 — P0 for an Etsy launch: field authoring is ahead of listing management

The Etsy adapter exposes base fields and category properties with stable IDs, supported values, multiplicity and scales. The sample chooser has 56 columns. With no selected Etsy category, the sample showed eight required columns and 105 missing required cells across five columns and 21 rows. Fresh taxonomy availability does not automatically assign the product's category.

The common sheet supports local authoring, but the common publisher/wizard has no Etsy branch. The older [etsy-sync.service.ts](../../../apps/api/src/services/sync/etsy-sync.service.ts) still uses legacy model assumptions and can copy imported channel title/price/stock into canonical product fields. It should not become the modern write path without ownership and identity reconciliation.

**Required result:** a scoped Etsy lifecycle adapter covering draft/create/update/activate/deactivate, listing inventory offerings, category property serialization, profiles/policies, translations, media and applicable digital files. Expose shop-owned profile names and selectable resources rather than making operators manage numeric IDs.

Support three variation axes and preserve the full inventory structure. Etsy now accepts up to 2,500 inventory products for three-axis listings, with a 400-product limit when any variation-dependent field uses all axes. Sending fewer axes can delete omitted variations. [Etsy third variation guide](https://developers.etsy.com/documentation/tutorials/third-variation/). Personalization should use the current structured question model rather than relying only on older scalar fields. [Etsy personalization migration](https://developers.etsy.com/documentation/tutorials/personalization-migration/).

### F08 — P1: completeness, validation and publication status need clearer separation

Observed examples include Shared Ready 100%, Amazon Blocked 100% with 457 affected cells across 24 columns and 20 rows, and eBay Ready 100% for the counted required fields. The current service calculates a filled-required-value percentage and separately assesses errors. Its explanatory notes acknowledge some limitations, but the prominent percentage still invites a stronger interpretation.

**Required result:** report distinct states for content completeness, local validity, destination eligibility, pending changes, remote processing and confirmed live status. Derive completeness from applicable family/channel/locale requirements. Group repeated errors by root cause: one unmapped color affecting 20 variants should offer one mapping correction with an impact preview, not require 20 individual edits.

### F09 — P1: automation is not equally available to additional accounts and aliases

[cell-formula.service.ts](../../../apps/api/src/services/pim/mapping/cell-formula.service.ts) explicitly rejects named aliases or account-specific requests. Formula storage lacks those dimensions, and the Studio excludes primary-account formulas for a nonprimary account. Ordinary shared mapping and literal listing overrides still exist; the gap is formula parity.

**Required result:** either extend formula identity, dependency tracking and writes to the full destination, or offer equivalent reusable scoped mapping rules in the same workflow. Operators should not have to replace automation with repeated manual overrides when adding a second account.

### F10 — P1/P2: classification governance and scale need finishing

The taxonomy page initially returned a temporary failure, including after retry. It recovered during this audit. The final browser and direct repository read show **all 18 supported sources ready**: 11 Amazon markets, five eBay markets, Etsy and Shopify. Taxonomy tables exist. An older “migration missing” diagnosis is not current evidence. The error's original cause was not established.

All 12 stored category-to-channel defaults have a null review timestamp. Review these for destination category suitability and applicable requirements; a populated taxonomy cache does not validate the mappings. The existing taxonomy architecture already provides snapshots, refresh jobs and impact review. Improve operational observability/recovery and complete assignment review rather than adding a second taxonomy page.

The current channel resolver processes only the first 250 family product IDs; additional IDs are reported as unresolved. This is honest but limits large variant families. Paginate resolution and measure end-to-end load, edit and delivery performance against actual supported catalog sizes.

## Shared attributes: what belongs here

Keep the shared dictionary provider-neutral in meaning. A provider-shaped spelling is not by itself a defect if the fact is reusable, but duplicate facts and ambiguous types create maintenance work. The [complete family review](shared-attribute-review.md) proposes a disposition for each currently effective definition.

| Attribute group | Recommendation | Main improvement |
| --- | --- | --- |
| Identity | Family, internal categories, brand, manufacturer, model name/number, parent and variant SKU, GTIN and relevant identifiers | Reuse existing fields; define parent/variant ownership and meaningful requirements |
| Content | Localized title, description, features, care, warranty prose and relevant search/SEO content | Reconcile translation storage; add short copy or SEO defaults only where a distinct business need exists |
| Variant facts | Canonical color, manufacturer color, size, size system, fit, gender/age where applicable | Stable option codes with translated display labels; map to provider enums/IDs |
| Technical apparel | Composition, lining, closure, pockets, water/weather resistance, season/use, dimensions | Structured facts and measurements; expose only relevant optional groups |
| Logistics | Item measurements and weight, package measurements and weight, quantities, origin and customs classification | Package fields already exist; preserve the distinction between item and shipping package |
| Safety/compliance | Applicable safety classification, manufacturer/responsible-person references, documents, languages, dates and expiry | Compose existing compliance services; add typed document/reference editing where needed |
| Merchandising relationships | Accessories, replacements, bundles/components, compatible items and size guide | Stable references and reusable resources rather than unvalidated strings |
| Commercial data | Currency-aware price sources, availability and fulfillment authority | Reuse pricing/stock systems; show resolved offer values and explicit overrides |

Specific corrections: `care_instructions`, `fabric_type` and `manufacturer_warranty` are currently not localizable even though their present representation can hold prose. For composition, prefer structured material codes and percentages with localized labels, with optional localized marketing text. Keep a stable canonical color code distinct from the branded color name and each channel's standardized color. Define size system/scale explicitly; do not translate a SKU's identity accidentally.

Family reference/asset attributes currently become read-only in the common family builder. A generic column cannot substitute for a typed size-guide, certificate or related-product picker. Extend shared DS controls and the appropriate domain workflow when these are implemented.

Prices and stock deserve an authority review before broad market rollout: current default mappings can read `basePrice` and `totalStock`. Verify pricebook/currency/tax treatment and sellable stock/location/buffer rules. This audit did not trace every outbound monetary payload and does not claim a demonstrated currency-conversion or overselling incident.

Production control should combine local validation with submission outcomes and later listing issues. [Amazon listing issues](https://developer-docs.amazon.com/sp-api/docs/manage-listings-issues).

## Product editor sub-sidebar

Add three substantial workspaces and expand an existing one. The scope selector should continue deciding the owner/destination; the sidebar should decide the task.

| Page | Action | What it should do |
| --- | --- | --- |
| Information | Keep and focus | Canonical or channel fields, useful presets, origin and override state; family/category summary with links to central administration |
| Variants & relationships | Add a unified workspace using existing capabilities | Variant axes/matrix, SKU/GTIN, inheritance, create/remove impact, channel inclusion/grouping; related products, bundles and compatibility as applicable |
| Languages & markets | Add | Side-by-side content, coverage, fallback/missing/outdated state, source-change review, enabled destinations, Shopify Markets and channel-supported locale behavior |
| Media | Keep and extend where needed | Shared gallery with scoped order/selection, language-specific media/alt text, variant associations and delivery status; contextual digital files |
| Compliance & documents | Add using existing compliance services | Relevant product facts and reusable manufacturer/brand defaults, document versions/expiry/languages, exact destination issues and evidence |
| Readiness & publishing | Expand Needs attention | Family and destination requirements, grouped fixes, reviewed value diff, provider operations, partial failures, retries and live verification |
| Activity | Keep | Who changed what, effective owner, destination, source/draft revision and provider outcome; link back to affected values |
| Performance | Keep, lower priority | Listing/channel performance with clear data coverage; does not block correct product management |

Channel-specific navigation should be contextual. Preserve eBay Description themes and Variation order and Shopify Product family while consolidating overlapping variant tasks deliberately. Etsy Personalization can be a contextual workflow; Digital files should appear only for relevant products. Avoid a permanent page for every provider API resource.

Offer price, currency, availability, stock authority, fulfillment and policies should have a clear channel-scoped panel or subsection linked to the existing Pricing and Stock owners. Promote this to an Offers page only if the workflow becomes too substantial for the publishing review; do not create a second authoritative pricing/inventory model merely to fill the sidebar.

## Recommended implementation order and acceptance

1. **Make release-critical behavior trustworthy:** preserve eBay regulatory intent; fix locale provenance and locale-keyed readiness; implement Amazon custom validation; replace ambiguous completeness labels; close the exact-destination publishing contract.
2. **Reduce daily data entry:** curate family templates, requirements and code lists; review category defaults; reconcile canonical content; make repeat mapping failures fixable once; extend automation to additional accounts/aliases.
3. **Deliver the missing product workspaces:** Languages & markets, Variants & relationships, Compliance & documents, and the expanded Readiness & publishing. Build Shopify Markets and Etsy lifecycle support against these contracts.
4. **Prove release quality:** controlled provider mutation/readback, failure recovery and storefront/listing checks, followed by catalog-scale and accessibility verification.

Release acceptance should include:

- Editing one shared fact updates every intended inherited destination in preview, while a pinned exception is preserved. Clearing the exception restores inheritance; explicit zero, false, empty list and intentional removal remain distinguishable.
- Changing source text marks dependent translations outdated. Selecting German cannot show English fallback as a reviewed German value or retain another locale's readiness.
- Two accounts on the same marketplace and two aliases of one family retain separate previews, drafts, formulas/rules, writes and history. Switching scope during a slow request cannot apply stale results to the new destination.
- Category changes preview newly required fields, incompatible values, variation effects and mapping changes while retaining saved data. Schema freshness and seller/store capabilities are checked where relevant.
- A publish timeout preserves intent and operation identity; retry does not create a duplicate listing. Provider partial failures are attached to the correct variant/field, and Live requires a meaningful provider result/readback.
- Etsy inventory edits preserve all existing axes and offerings unless their removal is deliberately reviewed. Shopify market-specific edits show the Market resource and effective locale/currency.
- Compliance data survives all error paths. Price/currency and stock authority are explicit for each destination.
- Keyboard-only operation, focus return, validation announcements, screen-reader grid use, responsive light/dark presentation, zoom, contrast and reduced motion are verified against the agreed accessibility target. “AAA quality” is currently a product quality objective, not an established WCAG conformance result.
- Load/edit/review/synchronize performance is measured on representative large families, including more than 250 products, rather than inferred from grid virtualization alone.

Future UI work must use the Nexus design system, read the relevant component source, keep feature styling to layout/domain content, and mirror shared DS changes into Factory with catalog/changelog and DS-GAPS updates. This audit adds documentation and reproductions only, so it does not introduce a new design-system control or claim fresh type/token/accessibility guard results.
