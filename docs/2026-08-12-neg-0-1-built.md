## 1 · NEG.0 — the two safety fixes

### (a) `protectConverting` has a reader

`_shared/RuleBuilder.tsx:851` renders a switch, **on by default**, promising *"Never create a
negative for a term that converted (≥1 order) in the last 30 days in any campaign."*
`ads-rule-adapter.service.ts:174` wrote it into every negation rule's action JSON.
`grep -rn protectConverting apps/api/src` returned exactly one hit: the adapter that writes it.

`ads-protect-converting.ts` is the reader. It is split deliberately:

- `convertedTermsIn(days)` — one grouped read of `AmazonAdsSearchTerm`, **account-wide, no
  marketplace filter**, because the promise says "in ANY campaign" and a market-scoped check would
  be a weaker sentence than the one on the screen.
- `decideNegation()` — pure. No clock, no database. Which is what makes "a test that fails if the
  branch is removed" something other than an aspiration.

One normalisation, `normaliseNegTerm` (case-folded, whitespace-collapsed), used on both sides of the
comparison — Amazon's search terms arrive lower-case and our negatives do not (`AIRMESH pant`,
`giacca MOSS`). Comparing raw strings would have let exactly the brand terms through.

**Absent means ON.** Every seeded rule predates the switch and carries no key. Defaulting those to
OFF would have protected only rules built after the switch shipped — the same half-protection the
fix exists to end.

Wired into **three** handlers, one more than the fix pack named:

| path | why |
|---|---|
| `add_negative_exact` | named in the brief |
| `applyHarvest` | named in the brief — and enforced *inside the service*, not at its five callers, for the reason the write gate gives about itself: a protection only some callers honour is not a protection. The five are the rule engine, the POST route, `ads-auto-harvest` (which wrote the 22 engine-attributed rows) and two recommendation-accept paths. |
| `sync_negatives_across_campaigns` | **not** named in the brief. Taken deliberately: it negates ONE term across every enabled campaign — 74 on IT per execution, the widest blast radius in the section — and a converting term is precisely the one for which that is the worst outcome. Flagged here so it can be vetoed. |

**Measured on production** (`scripts/_neg1-protect-probe.mts`):

- 45 protected terms at 30 days, 87 at 60, 127 at 120. The read costs 55–316 ms.
- **273 of the 2,059 negatives that already exist would be refused today**, over 12 terms; **82 of
  those are blocking right now.**
- 🔴 **The default 30-day window does not protect the study's Detector B cases.** `xavia`,
  `chaqueta moto verano hombre` and `giacca pelle moto` each earned an order 120 days ago and
  nothing in the last 30, so at `protectDays=30` all three are ALLOWED. At `protectDays=120` all
  three are refused. That is the toggle's own promise working as written, not a defect — but
  "protected" and "protected under this rule's setting" are different sentences, and the operator
  should know which one they have.

🔴 **One conflict the literal reading creates.** `applyHarvest`'s H.3 isolation negation targets a
term that just graduated *because* it converted, so every isolation negation is refused. Applied as
written and counted separately (`protectedTerms[].path = 'isolation'`) so the effect is legible
rather than showing up as an unexplained zero. It is unreachable today — the only caller that has
ever run this service passes no `destinations`. **If isolation should be exempt** — the argument
being that the term is routed rather than blocked, since the same term is created as EXACT in the
destination campaign in the same transaction — **that is an operator decision, and it is open.**

### (b) The gate is reachable

`createNegative` needs `marketplace`. Three callers omitted it behind `as never`. The gate's first
substantive check is `if (!ctx.marketplace) return { allowed:false, deniedAt:'connection' }`
(`ads-write-gate.ts:165-171`) — **before** the protected-terms whitelist at `:304`. So those three
paths were denied at the connection check and the whitelist never ran. All 22 campaign-scope
negatives in the account carry no Amazon id, which is that defect's fingerprint.

`marketplace` is passed, the casts are deleted, and three honesty defects in the same lines went
with them:

- a gate **denial** was reported as `ok: true` — the return value was discarded entirely;
- `applyHarvest` wrote its **local mirror after a denied push** (`createNegativeKeywordCampaignLocal`
  has no gate of its own) — that pair is how the 22 rows were minted;
- 74 attempts reported **one number**; per-campaign outcomes are now counted separately.

**Nothing arms as a result.** All seven rules are PROPOSE; `levelActs` is AUTO-only
(`ads-autonomy.ts:60`), so `dryRun` is true and every handler returns before `createNegative`.
Verified before writing the fix, because fixing (b) without checking this would have been the
change that armed 74 writes per execution.

**18 tests, seen to fail first.** Deleting the `protectConverting` branch fails 2; restoring the
`as never` fails 1.

## 2 · NEG.1 — the page

Route `/marketing/ads/rules-automation/negative-targeting`. Read-only on the ads data: creates no
negative, retires none, changes nothing at Amazon.

`GET /advertising/negatives` in **`advertising-intel.routes.ts`**. The path was free (verified 404
on prod before writing it) and resolves through the generic ads read rule at
`permissions-manifest.ts:214`, so it needs no manifest entry and answers 401 unauthenticated.

**Not** a variant of `GET /advertising/targets?negative=1`: that route selects `externalTargetId` to
filter with and then drops it from the row it returns, and caps at 2,000 against a base of 2,059 —
so it can say neither "did this reach Amazon" nor "show me the account". Both are the page.

### The four decisions, as pure tested functions

Each has already gone wrong silently somewhere in this codebase.

1. **`normaliseMatchType`** — read-time only. See §3.
2. **`isBlockingNow`** — an intersection of three conditions. **942**, not the study's 1,045.
3. **`attributionOf`** — four values, never blank.
4. **`resolveNegScope`** — five grains, most specific wins.

### The census, and the one number the study got wrong

| | study said | measured |
|---|---|---|
| negatives | 2,059 | 2,059 ✓ |
| terms | 258 | 258 ✓ |
| in an ENABLED campaign | 1,045 | 1,045 ✓ |
| **blocking now** | *"≤ 1,045"* | **942** |
| never confirmed at Amazon | 42 | 42 ✓ |

The study's 1,045 is only the third condition of three. **942** excludes the 62 ARCHIVED targets as
well as the 42 rows Amazon has never confirmed. Per market: IT 906, DE 21, ES 14, **FR 1**.

Every census count is computed over the full filtered set in the route, never in the client from a
page of rows — and **every cell applies the filter that reproduces its own number** (see §4).

### The scope spine — five grains

Market · product line · portfolio · campaign · **ad group**. Ad group is the fifth because 2,037 of
2,059 negatives live at it and nothing coarser can address one. Its picker appears once a campaign
is chosen and is filled from the same read that fills the grid, so it can never offer an ad group
holding no negative — verified on prod, every option's count > 0.

Market is **not** in the bar: `AdsPageHeader` already renders that picker and `showMarket` does not
exist. `market=all` is accepted here and refused on the Keyword Tracker for a real reason —
everything this page counts is a count of rows, and rows sum honestly across markets.

A campaign from another market resolves to **nothing**, not to an override. Verified on prod: an IT
campaign under `market=DE` returns 0 rows and still reports `boundBy: 'campaign'`.

A portfolio view states its blind spot out loud: **916 of 1,542 IT negatives (59%)** sit in
campaigns carrying no `portfolioId`; account-wide it is 1,310 of 2,059 (64%).

### The seam

Seven slot files ship today, in order, each rendering null, all taking one typed contract
(`slot-contract.ts`) — including the `selectionActions` / `onRowAction` injection props NEG.3 and
NEG.4 will supply. A later section is one file and one import line. `ProtectedTermsPanel` and the
rule list moved over rendered exactly as they were; NEG.5 and NEG.7 delete those two interim lines.

## 3 · 🔴 The finding that outranks the rest: `expressionType` **oscillates**

The study called the underscore spellings *"a 62-row fringe, not the majority the tab study
implied"* and corrected the tab study on it. **Both were right, at different times.** The column has
no stable value.

Measured tonight, same script, same account:

| time | EXACT | PHRASE | _EXACT | _PHRASE |
|---|---|---|---|---|
| study, 2026-08-11 | 1,393 | 579 | 32 | 30 |
| 00:47 | 1,184 | 491 | 241 | 118 |
| 00:52 | 915 | 413 | 510 | 196 |
| 00:56 | 759 | 368 | 666 | 241 |
| ~01:25 | 57 | 62 | **1,368** | **547** |
| **02:35** | **1,393** | **579** | **32** | **30** |

It converted fully to the underscore form at roughly **65 rows a minute**, then converted all the
way back, landing on the study's snapshot exactly. Two writers are fighting over one column:

- `ads-keyword-list-sync.service.ts:157` — `(k.matchType ?? '').toUpperCase().replace('NEGATIVE','')`
  turns Amazon's `NEGATIVE_EXACT` into **`_EXACT`**;
- `ads-v1-sync.service.ts:600` — `r.targetDetails?.matchType?.toUpperCase()` writes plain
  **`EXACT`** for the same row.

Both are crons on their own cadence, so the column's value depends on which ingest ran last. That is
why the tab study and the page study disagreed by an order of magnitude about the same column:
neither sampled wrongly.

**The consequence for anyone building here:** a filter written against one spelling returns a
different row set depending on the hour. At 00:56, `WHERE expressionType = 'EXACT'` found 745 rows
and `IN (EXACT, _EXACT, NEGATIVE_EXACT)` found 1,447 — a 702-row gap. At 02:35 the same pair reads
1,393 and 1,447, a gap of 54.

The page is immune: it normalises at read time and never filters on the raw value. Its
`EXACT/PHRASE` facets are invariant while the raw spellings swap underneath. Both are on screen —
the note under the census names every raw spelling with its count — because laundering `_EXACT` into
`EXACT` and forgetting it is how a live rewrite went unremarked between two studies a day apart.

**The writes are still untouched, as the study directed.** Three services carry correct dual-spelling
probes a migration would silently invalidate. But the study's reason ("a 62-row fringe") is not the
real one, and **the one-line fix at `ads-keyword-list-sync.service.ts:157` is worth taking in a
session that owns that file** — `advertising.routes.ts:4881` already carries a workaround comment
naming "334 negative rows" with the malformed spelling, so this has been known, at a tenth of its
current size, for some time.

## 4 · What only clicking the deployed page found

Four defects survived a green pre-push, a clean typecheck, 43 passing unit tests and a 60-assertion
endpoint script. Every one of them was found by loading the page and using it.

**1 · `market=all` 400'd.** The page defaults to All markets; the route rejected it. Self-inflicted:
the `market=all` support was written *after* the API commit and swept up by nothing, so the web half
shipped against an API that had never seen it. Exactly the trap the locks doc names — a commit is
TWO deploys.

**2 · 🔴 A census cell's number did not match the filter it applied.** "Blocking now" read **942**
and its filter returned **1,004**: `state=live&amazon=yes` checks the campaign and the Amazon id but
not the target's own status, so the 62 ARCHIVED targets in enabled campaigns came back. "In a paused
campaign" read 1,014 (paused OR archived) and applied `state=paused`, returning 1,013.

Both now send a filter that runs the **same predicate the count runs** — `blocking=yes` calls
`isBlockingNow`, `state=inert` means "not ENABLED". A cell whose number and whose filter disagree is
worse than no cell: it teaches the operator that the strip is approximate. `_neg1-endpoint.mts` §5d
now asserts every cell against its own filter and keeps the old composition as a regression marker
that **prints** the difference, so if it ever matches by coincidence that is visible rather than
reassuring.

**3 · 🔴 Switching to the Terms grain took the whole page to the error boundary.** A blank screen —
no census, no grid, no message. The grid read its grain from the URL; the URL changes the instant
you click and the rows arrive a second later, so for one render the term columns ran against
negation rows and `num(r.rows)` threw. The grid now renders the grain the **payload** reports; the
toggle still shows what you clicked. Verified afterwards in the exact 300 ms race window, both
directions, plus via the census cell.

**4 · Two CSS defects.** `tone: 'on'` collided with the selected class, so "blocking now" rendered
permanently selected and two of five cells claimed to be the active filter at once. And
`.h10-ng-spread > :first-child` matched the wrong node — the row count is a bare text node, which
CSS cannot select, so `:first-child` matched the `<i>` and beat `.h10-ng-spread i` on specificity;
both lines rendered identically at 12px/800.

### Verified on production, by measurement

- **Geometry:** `.h10-hdr`, `.h10-rules-tabs`, `.h10-ng-scope`, `.h10-ng-said`, `.h10-ng-census`,
  `.h10-ng-note`, `.h10-am-card` and `#protected-terms` all sit at **96→1698** at innerWidth 1728.
  No 24px stagger. `scrollWidth === clientWidth` on both the document and the app shell.
- **The census strip:** five cells, 312px each, equal heights, 10px gaps, flush to both edges.
- **The first column is `#1c2530`, not the shared grid's `#1f6fde`** — overridden at (0,4,1).
- **Contrast:** the selected live cell reads **7.23:1**; every other probed pair is above 4.5:1.
- **Each census cell reproduces its own number:** 942→942, 1,014→1,014, 42→42, 258→258, and exactly
  one cell active at a time.
- **The fifth grain** appears only once a campaign is chosen, and every option holds ≥1 negative.
- **`?tab=negative-targeting` 308s to the page** instead of silently rendering Apply Rules.
- **Zero console messages** on a direct load of the terms view — the URL that used to crash.
