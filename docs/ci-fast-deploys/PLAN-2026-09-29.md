## 2. The new pipeline

```
changes ─┐
verify ──┼──► deploy API (pre-deploy migration, readiness = SHA) ──► worker ║ scheduler ║ web ──► web smoke
images ──┤
eBay ────┘
```

- `images` builds in GitHub **while** `verify` runs. One API image (API, worker and scheduler use it with different
  start commands). One web image (Next.js `standalone`).
- Deploy starts only when `verify`, `images` and the eBay scope check all pass.
- Deploy = tell Railway "run image `ghcr.io/awaissulhry/nexus-api:<sha>`". Railway builds nothing.
- The `changes` job stays: a service that did not change is not restarted. Every release still builds both images,
  so every released SHA can be rolled back to.

### Images

- `apps/api/Dockerfile`, `apps/web/Dockerfile`: multi-stage, `turbo prune --docker`, Node 22 slim.
- BuildKit cache in the GitHub Actions cache (`type=gha`, one scope per image).
- `apps/api/Dockerfile.dockerignore`, `apps/web/Dockerfile.dockerignore` (not a root `.dockerignore`, see §9): `docs/`, `output/`, `outputs/`, `obsidian-vault/`, `apps/factory`, `**/.env*`, `node_modules`, `.next`,
  test output, `.git`.
- API image: writes `apps/api/.release-sha` from the SHA, so readiness still shows the build.
- Web image: `NEXT_PUBLIC_*` as build args. Also `NEXUS_API_PROXY_TARGET`: in `standalone` mode Next freezes rewrites at
  build time, so the `/backend` proxy target must be known then. The build reads these values from the `nexus-web`
  service on Railway (like the eBay check reads its values). Railway stays the one place for production values.
  Nothing is copied into GitHub.
- `standalone` only when the Docker build asks for it (`NEXT_OUTPUT=standalone`). CI's smoke build stays as it is.
- `apps/web/scripts/start.mjs` starts `server.js` when it exists, else `next start`. The Railway start command
  does not change.
- **No secrets in any image:** no secret goes in as a build arg. Before the push, a gate lists the image's files and
  fails on any `.env*`, key file or connection string with a password.
- Push to GHCR, public, tag = full commit SHA.

### Deploy

- New `scripts/ci/railway-deploy-image.sh`: `railway service source connect --image <ref>`, then follow that
  deployment to SUCCESS / FAILED (the same follow logic as `railway-up.sh`).
- API first. Pass = Railway says SUCCESS **and** `/api/health/ready` shows the expected SHA (as today).
- Then worker, scheduler and web in parallel, same SHA. Then the web smoke.
- If anything fails, Railway keeps the previous build serving (pre-deploy and health check still gate traffic).
- The deploy job no longer needs `npm ci` (≈ 45 s saved). The eBay check runs in its own job, beside `verify`.

### One service at a time

A GitHub repository variable `RAILWAY_IMAGE_SERVICES` lists the services that deploy by image. The others keep
`railway up` as today. Merging the code changes nothing until this variable names a service.

## 4. Leave Vercel

- **Now:** remove the dead `TURBO_TOKEN` / `TURBO_TEAM` setup. Keep turbo's local cache in the GitHub Actions cache.
  2026-09-30: the Owner chose the small version (PR 3): no turbo cache is kept between runs. Keeping it safely needed a new
  guard for every file a typecheck reads, and it saved almost no time on deploys.
  Key the Playwright cache by Playwright version, not by `package-lock.json` (frees ≈ 3.3 GB of the full cache).
- **Only after the web cutover:** remove `vercel.json`, `.vercelignore` and `VERCEL_AUTOMATION_BYPASS_SECRET` in
  `prod-smoke.yml`. Reason: while Vercel's Git link is live, `vercel.json` (`turbo-ignore`) stops Vercel building every
  push. Without it, Vercel builds every commit, and builds were the Vercel cost (2026-09-28).

## 5. Rollback

`gh workflow run rollback.yml -f sha=<commit>` — runs in GitHub, not on this machine. It checks that both images exist
for that SHA, deploys API → worker, scheduler, web with that tag, and runs the smokes. It shares the `deploy-api`
queue. Migrations do **not** roll back: the old code runs on the new schema (safe for additive migrations only).
Railway's own "Rollback" button on a deployment also works for image deploys. Runbook in
`tasks/architecture-operations.md`.

### Incident after the merge (2026-09-29)

PR 1 first shipped a root `.dockerignore`. Railway's builder (Railpack) applies a root `.dockerignore` to its own
builds too ("Found .dockerignore file, applying filters"). It left `apps/api/.release-sha` out of the API build, so
readiness reported build `unknown`. Deploy run 36636596664 then failed its check after 12 minutes, and the worker,
scheduler and web were not shipped. The API itself was healthy and served the new code.

Fix: the allow-list moved beside each Dockerfile (`apps/api/Dockerfile.dockerignore`,
`apps/web/Dockerfile.dockerignore`). BuildKit reads those; Railpack does not. Railway builds see the whole upload again,
as before PR 1. Proven with Docker: planted `.env`, `docs/`, `services/` and `apps/api/.release-sha` files stay out of
both image contexts; with the file removed, the planted `.env` gets in (control).
