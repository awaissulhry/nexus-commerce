## 2. Saleor — Apps, webhooks, channels

**Licence:** BSD-3-Clause — https://raw.githubusercontent.com/saleor/saleor/main/LICENSE ("Copyright (c) 2020-2023, Saleor Commerce", BSD 3-Clause).

### 2.1 The App model (`saleor/app/models.py`)
Source: https://raw.githubusercontent.com/saleor/saleor/main/saleor/app/models.py

- `App`: `uuid` (unique, uuid4), `name` (60), `created_at`, `is_active` (default True), `removed_at` (null), `type` (choices `AppType`, default `LOCAL`; the other value is THIRDPARTY), `identifier` (256, blank), `permissions` M2M→`Permission`, `about_app`, `data_privacy`, `data_privacy_url`, `homepage_url`, `support_url`, `configuration_url`, `app_url`, `manifest_url` (2048), `version`, `audience`, `is_installed` (default True), `author`, `brand_logo_default` (ImageField). Methods `get_permissions()`, `has_perms()`, `has_perm()`.
- `AppToken`: `app` FK, `name` (128, default ""), `auth_token` (128, **unique**), `token_last_4` (4). `set_auth_token()` hashes the token via Django's `make_password()` — i.e. the token is stored **hashed**, only the last four characters remain readable for display.
- `AppExtension`: `app` FK, `label`, `url`, `mount` (256), `target` (128, default `DEFAULT_APP_TARGET`), `permissions` M2M, `http_target_method` (deprecated), `settings` JSON, `identifier` (256, null) — `UniqueConstraint(app, identifier)` + `CheckConstraint(identifier != "")`.
- `AppInstallation`: `uuid`, `app_name`, `manifest_url` (2048), `permissions` M2M, `brand_logo_default`; `set_message()` — a job record that lives while the install is in flight.
- `AppProblem` (newer): `app` FK, `message` (2048), `key` (128), `count` (default 1), `is_critical`, `dismissed`, `dismissed_by_user_email`, `dismissed_by_user` FK; `MAX_PROBLEMS_PER_APP = 100`. A per-app **deduplicated problem ledger** (key + count) that the dashboard surfaces — worth noting for connection health.

### 2.2 Install flow (`saleor/app/installation_utils.py`)
Source: https://raw.githubusercontent.com/saleor/saleor/main/saleor/app/installation_utils.py

`install_app()`: `manifest_data = fetch_manifest(app_installation.manifest_url, max_retries=2)` with timeout `settings.COMMON_REQUESTS_TIMEOUT` (a `(connect, read)` tuple, connect timeout grows per retry: `timeout=(connect_timeout + attempt, read_timeout)`); permissions granted are those on the `AppInstallation` (`manifest_data['permissions'] = get_permission_names(assigned_permissions)`) — i.e. the installing user chooses, the manifest only requests; `clean_manifest_data(..., raise_for_saleor_version=True)` validates against `requiredSaleorVersion`; the `App` row is created; a token is created **only if the manifest has `tokenTargetUrl`** (`app.tokens.create(name='Default token')`) and `send_app_token()` POSTs `{'auth_token': token}` with headers `AppHeaders.DOMAIN`, `AppHeaders.API_URL` (= absolute `/graphql/` URL), `AppHeaders.SCHEMA_VERSION` (plus deprecated `X-` twins). If that POST fails the install is **rolled back** (app deleted). Webhooks from the manifest are `bulk_create`d together with their `WebhookEvent` rows; extensions likewise.

Manifest shape (docs): https://docs.saleor.io/developer/extending/apps/architecture/manifest — top-level `id`, `version`, `name`, `author`, `about`, `requiredSaleorVersion`, `appUrl`, `configurationUrl`, `tokenTargetUrl`, `dataPrivacyUrl`, `homepageUrl`, `supportUrl`, `permissions[]`, `brand`, `extensions[]`, `webhooks[]`; each webhook: `name`, `identifier` (stable app-defined key), `asyncEvents[]` or `syncEvents[]`, `query` (GraphQL subscription that **defines the payload**), `targetUrl`, `isActive`; each extension: `label`, `identifier`, `mount` (e.g. `PRODUCT_OVERVIEW_CREATE`), `target` (`POPUP` | `APP_PAGE`), `permissions`, `url`. Condensed example from the docs:
```json
{ "id": "example.app.wonderful", "version": "1.0.0", "name": "My Wonderful App",
  "permissions": ["MANAGE_USERS"], "appUrl": "http://localhost:3001/app",
  "webhooks": [{ "identifier": "order-created", "asyncEvents": ["ORDER_CREATED"],
                 "targetUrl": "https://example.com/api/webhooks" }] }
```

App-side persistence (APL) in `@saleor/app-sdk`: https://raw.githubusercontent.com/saleor/app-sdk/main/src/APL/apl.ts — `AuthData { token, saleorApiUrl, appId, jwks? }`; interface `APL { get(saleorApiUrl), set(authData), delete(saleorApiUrl), getAll(), isReady?(), isConfigured?() }`. The key of the store is the **Saleor API URL** (one app can serve many Saleor instances — multi-tenant by URL).

### 2.3 Webhooks (`saleor/webhook/`)
Models — https://raw.githubusercontent.com/saleor/saleor/main/saleor/webhook/models.py: `Webhook { name, app FK (related_name webhooks), target_url (WebhookURLField 255), is_active, secret_key (255, null), subscription_query (Text, null), custom_headers (JSON), filterable_channel_slugs (ArrayField, GIN index), identifier (256) }` with `UniqueConstraint(app, identifier)`; `WebhookEvent { webhook FK, event_type (128, indexed) }`. Note `filterable_channel_slugs` — a webhook can be **scoped to channels**.

Event vocabulary — https://raw.githubusercontent.com/saleor/saleor/main/saleor/webhook/event_types.py: `WebhookEventAsyncType` has 113 entries (incl. `ANY`) — e.g. `PRODUCT_CREATED/UPDATED/DELETED`, `PRODUCT_VARIANT_CREATED/UPDATED/STOCK_UPDATED`, `PRODUCT_VARIANT_OUT_OF_STOCK_IN_CHANNEL`, `PRODUCT_MEDIA_CREATED`, `ORDER_CREATED/PAID/FULFILLED/CANCELLED`, `CHANNEL_CREATED/UPDATED`, `APP_INSTALLED`; `WebhookEventSyncType` has 21 — payment authorize/capture/refund/void/confirm/process/list-gateways, `CHECKOUT_CALCULATE_TAXES` / `ORDER_CALCULATE_TAXES`, transaction charge/refund/cancel requested, `SHIPPING_LIST_METHODS_FOR_CHECKOUT`, checkout/order filter-shipping-methods, payment-gateway/transaction session init/process, tokenization, stored-payment-method list/delete. Each event maps to a required permission (`PERMISSIONS` dict); async `EVENT_MAP` flags `is_deferred_payload`. Both classes expose `CHOICES`, `ALL`, `PERMISSIONS`.

Signing — https://docs.saleor.io/developer/extending/webhooks/payload-signature: when no `secretKey` is set Saleor uses "the JWS signature using RS256 with payload detached", sent in `Saleor-Signature` as `header..signature` (RFC 7515 detached), verifiable against `/.well-known/jwks.json`; "If `secretKey` was set for a webhook" it falls back to "the HMAC SHA-256 header based on it and the payload" (deprecated). Other headers (https://raw.githubusercontent.com/saleor/saleor/main/saleor/webhook/transport/utils.py): `Saleor-Event-Type`, `Saleor-Domain`, `Saleor-Signature`, `Saleor-Api-Url` (and deprecated `X-Saleor-*`: "X- headers will be deprecated in Saleor 4.0"). Transport dispatches on the `target_url` scheme: http(s) POST with `settings.WEBHOOK_TIMEOUT`, **AWS SQS**, **Google Pub/Sub** — the same webhook row can target a queue instead of a URL.

Delivery log — https://raw.githubusercontent.com/saleor/saleor/main/saleor/core/models.py: `EventPayload { payload (Text), payload_file (FileField on private storage, null), created_at }` (big payloads go to a file); `EventDelivery { created_at, status (EventDeliveryStatus), event_type, payload FK, webhook FK }`; `EventDeliveryAttempt { delivery FK, created_at, task_id, duration (Float), response, response_headers, response_status_code, request_headers, status }`. Response bodies are capped at `EVENT_DELIVERY_ATTEMPT_RESPONSE_SIZE_LIMIT` with `"..."` appended (transport/utils.py). Async retries — https://raw.githubusercontent.com/saleor/saleor/main/saleor/webhook/transport/asynchronous/transport.py:
```python
@app.task(queue=settings.WEBHOOK_CELERY_QUEUE_NAME, bind=True,
          retry_backoff=10, retry_kwargs={"max_retries": 5})
def send_webhook_request_async(self, event_delivery_id, *, telemetry_context)
```
`countdown = retry_backoff * (2**retries)`; 3xx/4xx responses **do not retry** (only 5xx / network), `MAX_WEBHOOK_RETRIES = 5`, `WEBHOOK_ASYNC_BATCH_SIZE = 100`, per-app batching task `send_webhooks_async_for_app`, deferred payload generation task with `max_retries=12`. Every attempt is reported to an observability buffer (`observability.report_event_delivery_attempt`). Sync webhooks — https://raw.githubusercontent.com/saleor/saleor/main/saleor/webhook/transport/synchronous/transport.py: `settings.WEBHOOK_SYNC_TIMEOUT` (docs: 2 s connect + 18 s read, https://docs.saleor.io/developer/extending/webhooks/overview), response `json.loads`ed and returned only on `SUCCESS`; responses cached under a key of (cache_data, url, event, app) for `WEBHOOK_CACHE_DEFAULT_TTL`; a failure stores `SYNC_WEBHOOK_FAILURE_SENTINEL` for `SYNC_WEBHOOK_FAILURE_CACHE_TTL` ("Prevent sending webhook if the previous one failed recently"); sync calls are wrapped by a `breaker_board` **circuit breaker**; EventDelivery/Attempt rows are still written for sync calls. Retention — https://raw.githubusercontent.com/saleor/saleor/main/saleor/core/tasks.py: `delete_event_payloads_task` deletes payloads (and their files) whose deliveries are older than `EVENT_PAYLOAD_DELETE_PERIOD`, `BATCH_SIZE = 1000` ("tested on db with 1mln payloads and deliveries").

### 2.4 Channels and channel listings
`Channel` — https://raw.githubusercontent.com/saleor/saleor/main/saleor/channel/models.py: `ModelWithMetadata` + `name`, `slug` (unique), `is_active`, `currency_code`, `default_country`, `allocation_strategy`, `order_mark_as_paid_strategy`, `default_transaction_flow_strategy`, order settings (`automatically_confirm_all_new_orders`, `allow_unpaid_orders`, `expire_orders_after`, `delete_expired_orders_after` …), checkout settings (`automatically_complete_fully_paid_checkouts`, `checkout_ttl_before_releasing_funds` …). One currency per channel.

Listings — https://raw.githubusercontent.com/saleor/saleor/main/saleor/product/models.py: `ProductChannelListing { product FK, channel FK, visible_in_listings, available_for_purchase_at, currency, discounted_price_amount, discounted_price_dirty }`, `unique_together (product, channel)`, `is_available_for_purchase()`; `ProductVariantChannelListing { variant FK, channel FK, currency, price_amount, cost_price_amount, prior_price_amount, discounted_price_amount, promotion_rules M2M (through VariantChannelListingPromotionRule), preorder_quantity_threshold }`, `unique_together (variant, channel)`; `CollectionChannelListing { collection, channel }`. `Product` itself keeps only channel-independent fields (`name`, `slug`, `description`, `category`, `weight`, `rating`, `tax_class` …). Docs confirm the scope list — products (visibility/availability/publication), variant prices, vouchers, promotions, orders ("contextualized to a channel and required channel permission for access"), warehouses/shipping zones availability, shipping rates, tax config, payment flow settings: https://docs.saleor.io/developer/channels/overview. `ChannelContext(node, channel_slug)` wrapper in GraphQL resolvers — **unverified** (fetch of `saleor/graphql/channel/__init__.py` returned no content).

Pre-App extension pattern — https://raw.githubusercontent.com/saleor/saleor/main/saleor/plugins/models.py: `PluginConfiguration { identifier (128), name, channel FK (null), description, active (default False), configuration (JSON) }` with `unique (identifier, channel)` — a plugin's config is **per channel**. Generic escape hatch: `ModelWithMetadata` gives every entity `metadata` and `private_metadata` JSONB (`db_default={}`) with `store_value_in_metadata` / `get_value_from_metadata` helpers (core/models.py).

### 2.5 What Saleor gets right / loses
- Right: the **install handshake** (manifest → permissions chosen by installer → token POSTed to `tokenTargetUrl`, rollback on failure); **payload-by-subscription-query** (the receiver chooses fields, so payload schema drift is the app's problem, not the core's); **three-table delivery log** (payload / delivery / attempt) with per-attempt request+response headers, duration and status; **channel-scoped webhooks**; sync webhooks with cache + failure sentinel + breaker.
- Loses: apps are **outbound receivers only** — there is no inbound "connector sync" concept, no cursor/state model, no rate-limit vocabulary; channel listing is **one row per (entity, channel) with a fixed column set** — a channel cannot carry arbitrary per-channel attributes (Amazon product-type attributes, eBay item specifics) except via untyped `metadata`; `metadata` is an untyped JSON bag with no schema or validation; delivery payloads are deleted after `EVENT_PAYLOAD_DELETE_PERIOD` so the log is not an audit trail.

### 3.2 Workflows engine (saga with compensation)
Composer — https://raw.githubusercontent.com/medusajs/medusa/develop/packages/core/workflows-sdk/src/utils/composer/create-step.ts: `createStep(nameOrConfig, invokeFn, compensateFn?)`; the first arg may be `{ name, maxRetries, ... }` (any `TransactionStepsDefinition` field except `next`/`uuid`/`action`); `new StepResponse(output, compensateInput)` — the second arg is what the compensation receives (defaults to the first); `StepResponse.permanentFailure(message, partialData)` hands partial progress to the compensation (docs caveat for loops: https://docs.medusajs.com/learn/fundamentals/workflows/compensation-function). Compensation runs only on error and **in reverse order** of completed steps (same page). Doc example (≤10 lines):
```ts
return new StepResponse(
  `Hello from step one!`,
  { message: "Oops! Rolling back my changes..." }
)
// compensation: async ({ message }, { container }) => { console.log(message) }
```
Step definition knobs — https://raw.githubusercontent.com/medusajs/medusa/develop/packages/core/orchestration/src/transaction/types.ts: `continueOnPermanentFailure`, `skipOnPermanentFailure` (bool | string), `noCompensation`, `maxRetries` (default 0), `autoRetry` (default true), `retryInterval` (s), `retryIntervalAwaiting`, `maxAwaitingRetries`, `timeout` (s), `async` ("Workflow will not wait for the response of this step"), `nested`, `backgroundExecution`, `compensateAsync`, `noWait`, `saveResponse` (default true), `store` (checkpoint). Orchestrator events: `BEGIN, RESUME, COMPENSATE_BEGIN, FINISH, TIMEOUT, STEP_BEGIN, STEP_SUCCESS, STEP_SKIPPED, STEP_FAILURE, STEP_AWAITING, COMPENSATE_STEP_SUCCESS, COMPENSATE_STEP_FAILURE`. The `TransactionState`/`TransactionStepStatus` enum values themselves live in `@medusajs/utils` — **unverified** (not fetched).

Long-running workflows — https://docs.medusajs.com/learn/fundamentals/workflows/long-running-workflow: a step with `async: true` that does not return a `StepResponse` parks the transaction; `run()` returns `transaction.transactionId`; the external system later calls `workflowEngineService.setStepSuccess({ idempotencyKey: { transactionId, stepId, workflowId }, stepResponse })` or `setStepFailure(...)` (which triggers compensation of earlier steps); `subscribe()` streams `onFinish` / `onStepFailure`. Persistence — https://raw.githubusercontent.com/medusajs/medusa/develop/packages/modules/workflow-engine-redis/src/models/workflow-execution.ts: `WorkflowExecution { id, workflow_id, transaction_id, run_id, execution, context, state, retention_time }`, composite PK `(workflow_id, transaction_id, run_id)`, indexes on `state`, `(state, updated_at)`, `(retention_time, updated_at, state)` for retention sweeps, all with `deleted_at IS NULL`.

### 3.3 Modules & Module Links
https://docs.medusajs.com/learn/fundamentals/module-links: `defineLink(ProductModule.linkable.product, BlogModule.linkable.post)`; one-to-many by wrapping a side in `{ linkable, isList: true }` (both sides for many-to-many); `deleteCascade`; link rows created/removed with `link.create` / `link.delete`; cross-module reads go through `query.graph({ entity: "product", fields: ["id", "featured_post.*"] })`. Isolation rule: "you can't access another module's data models to add a relation to it" — links are separate tables with **no FK constraints** across modules. Extra columns on link tables exist (`database.extraColumns`) but the page fetched only references the chapter — **unverified** detail. This is the mechanism by which a plugin could hang per-channel data off a product without touching the product module.

### 3.6 What Medusa gets right / loses
- Right: **compensating sagas with persisted state and external resume** (`setStepSuccess` with an idempotency key) — exactly the shape of "push to Amazon, wait for the feed result, then continue or roll back"; **module links** as a way to attach data across bounded contexts without FKs; providers as classes with a static `identifier` + `validateOptions` + constructor-time client init; event grouping tied to the transaction.
- Loses: sales channel is **membership-only** — no per-channel title/price/attributes; providers are per **capability** (fulfillment/payment/notification), not per **marketplace**, so a "Shopify provider" has no home; no inbound connector/sync/cursor/rate-limit model at all; workflow engine state in Redis by default (a separate module for Postgres/in-memory exists — not verified here).

- Status: not archived, last push 2025-04-07, 1,012 stars, AGPL-3.0 — https://api.github.com/repos/revertinc/revert; README says "Revert has joined Ampersand" and directs users there — https://raw.githubusercontent.com/revertinc/revert/main/README.md. - Model: proxy-style unified API with "automatic OAuth token refresh" and "API retry mechanism" (README); no sync engine. Lost: no commerce at all, and the team pivoted.

### 4.4 Cross-cutting lesson
All three keep the raw payload (Supaglue inline `_supaglue_raw_data`; Panora in a `remote_data` side table; Merge as `remote_data[]` — §6.1) and all three had to bolt on a **field-mapping layer** (Supaglue `entityMappings`, Panora EAV `attribute/value`, Revert `fieldMappings` + per-account override policy) because the common model could not carry provider-specific fields. Two of three are archived. A PIM that needs 100% channel coverage should **start** from the provider's full schema and derive a thin common view, not the reverse.

## 5. Shopify — OAuth, sessions, webhooks, scopes, token exchange (`@shopify/shopify-api`)

**Licence:** MIT — https://raw.githubusercontent.com/Shopify/shopify-app-js/main/LICENSE.md ("Copyright (c) 2022-present, Shopify Inc."). The Remix template's licence file was not readable at `/LICENSE.md` or `/LICENSE` (404) — **unverified** (repo metadata says MIT).

### 5.1 `begin()` / `callback()` — https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/auth/oauth/oauth.ts
- `begin({shop, callbackPath, isOnline})`: `nonce()` → state; state stored in a **signed** cookie `STATE_COOKIE_NAME` (`shopify_app_state`) with `sameSite: 'lax'`, `secure: true`, `expires: new Date(Date.now() + 60000)` (60 s), path = callback path; authorization URL query = `client_id: config.apiKey`, `scope` (comma-joined), `redirect_uri`, `state`, and `grant_options[]: 'per-user'` for online tokens; bots (`isbot(userAgent)`) get HTTP 410.
- `callback()`: `await cookies.getAndVerify(STATE_COOKIE_NAME)` then delete it; `validQuery()` = `await validateHmac(config)(query)` **and** `safeCompare(query.state!, stateFromCookie)`; `sanitizeShop(config)(query.shop)`; `POST https://${cleanShop}/admin/oauth/access_token` with `client_id`, `client_secret`, `code`, `expiring: '1' | '0'`; `createSession()`; for non-embedded apps a `SESSION_COOKIE_NAME` cookie (`lax`, `secure`). Errors: `InvalidOAuthError` (HMAC/state), `CookieNotFound`, `BotActivityDetected`.
- HMAC — https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/utils/hmac-validator.ts: drop `hmac` and `signature` keys, sort keys, stringify (`ProcessedQuery` for admin, `key=value` joined for app-proxy), HMAC-SHA256 hex with the API secret, `safeCompare`; `timestamp` must be within `HMAC_TIMESTAMP_PERMITTED_CLOCK_TOLERANCE_SEC` = 90 s.
- Shop regex — https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/utils/shop-validator.ts: `^[a-zA-Z0-9][a-zA-Z0-9-_]*\.(domain)[/]*$` with domain ∈ `myshopify.com | shopify.com | myshopify.io | shop.dev` (+ configured `domainTransformations`); `sanitizeShop` also rewrites `admin.{domain}/store/{shop}` to the legacy form and returns `null` or throws `InvalidShopError`; `sanitizeHost` base64-decodes and checks the suffix.

### 5.2 Session model — https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/session/session.ts

### 5.3 Webhooks
- Register — https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/webhooks/register.ts: queries `webhookSubscriptions` (250/page), diffs existing vs configured handlers with `handlerIdentifier()` and `areHandlerFieldsEqual()` (`includeFields`, `metafieldNamespaces`) into create / update / delete; mutation prefix by delivery method — HTTP `webhookSubscription…` (`callbackUrl`), EventBridge `eventBridgeWebhookSubscription…` (`arn`), PubSub `pubSubWebhookSubscription…` (`pubSubProject`, `pubSubTopic`); returns `{[topic]: [{deliveryMethod, success, result, operation}]}` with success = `userErrors.length === 0`; privacy topics skipped; leftovers deleted. **Reconciliation, not append** — the desired set is the source of truth.
- Process — https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/webhooks/process.ts: requires headers Hmac, Topic, Domain, WebhookId, ApiVersion; "base64 HMAC-SHA256 with apiSecretKey" over the raw body + safeCompare; handler lookup `webhookRegistry[topic]`; 401 "Could not validate request HMAC", 404 "No HTTP webhooks registered for topic", 400 missing headers/body, 500 on handler error; callback gets `(topic, domain, rawBody, webhookId, apiVersion, context)`.
- Template — https://raw.githubusercontent.com/Shopify/shopify-app-template-remix/main/shopify.app.toml: `[access_scopes] scopes = "write_products"`; `[webhooks] api_version = "2024-10"`; `[[webhooks.subscriptions]] topics = ["app/uninstalled"] uri = "/webhooks/app/uninstalled"` and `["app/scopes_update"] → "/webhooks/app/scopes_update"`; commented examples for `products/update` with `filter = "variants.price:>=10.00"` and compliance topics. App-level subscriptions in TOML are created by Shopify at deploy for **every** shop; API-registered ones are per shop. Handlers: uninstall — https://raw.githubusercontent.com/Shopify/shopify-app-template-remix/main/app/routes/webhooks.app.uninstalled.tsx:

### 5.4 Scopes — https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/auth/scopes/index.ts
`AuthScopes` accepts string/array/instance; trims and drops empties; computes implied scopes — every `write_(.*)` implies the matching `read_`, preserving an `unauthenticated_` prefix; keeps three sets (compressed = non-implied, expanded, original); `has()`, `equals()` (compare compressed), `toArray()`, `toString()`. No `_orders` special case seen in this file.

### 5.5 Token exchange, managed install, client credentials
- Token exchange — https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts and https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/token-exchange: `RequestedTokenType` = `urn:shopify:params:oauth:token-type:online-access-token` | `…:offline-access-token`; body `client_id, client_secret, grant_type=urn:ietf:params:oauth:grant-type:token-exchange, subject_token=<App Bridge ID token>, subject_token_type=urn:ietf:params:oauth:token-type:id_token, requested_token_type, expiring`; the JWT is validated first (`decodeSessionToken`); "Embedded apps … use this grant to exchange an ID token for an access token, without redirecting the merchant"; "ID tokens are short-lived, so request one per exchange instead of caching it"; a stale token yields 400 → fetch a fresh one and retry.
- ID (session) token claims — https://shopify.dev/docs/apps/build/authentication-authorization/session-tokens: `iss` (admin host), `dest` (shop domain), `aud` (client id), `sub` (user), `exp`, `nbf`, `iat`, `jti`, `sid`; HS256 with the app secret; "they expire one minute after they're issued".
- Managed installation — https://shopify.dev/docs/apps/build/authentication-authorization/app-installation: declaring `[access_scopes] scopes` in TOML makes Shopify own the install/consent screen; "If you add scopes later, merchants who already have your app installed approve the new ones the next time they open it"; the app then does token exchange and sends `X-Shopify-Access-Token` on every request.
- Client credentials (own-org apps) — https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/client-credentials-grant: `grant_type=client_credentials` + `client_id` + `client_secret`; `expires_in` "Always 86399 (24 hours)"; cache and refresh ~60 s before expiry.

### 5.6 Rate limits & client
https://shopify.dev/docs/api/usage/rate-limits: GraphQL is cost-based — "Each combination of app and store is given a bucket size and restore rate based on API and plan tier" (100/200/1000/2000 points·s⁻¹ restore), `extensions.cost { requestedQueryCost, actualQueryCost, throttleStatus { maximumAvailable, currentlyAvailable, restoreRate } }`, single query ≤ 1,000 points; bulk operations "don't have the max cost limits or rate limits that single queries have". Client — https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/api-clients/admin-api-client/README.md: `retries` default 0, max 3; retries on 429/503 honouring `Retry-After`; `customFetchApi`; `apiVersion` required, overridable per request.

### 5.7 What Shopify gets right / to avoid
- Right: signed short-lived state cookie + HMAC over the sorted query + 90 s timestamp window + timing-safe compare; a **sanitised shop regex** as the tenant key; `Session` as the single persisted object with `isActive(scopes)` deciding re-auth; webhook registration as **reconcile-to-desired-state**; `app/uninstalled` and `app/scopes_update` as first-class lifecycle topics; token exchange removes the redirect entirely for embedded apps.
- Avoid: online vs offline duality leaks into every storage adapter (17 columns); `scope` stored as a comma string; `expiring` offline tokens now add `refreshToken`/`refreshTokenExpires` — model expiry from day one.

## 6. Commercial platforms — one paragraph each (proprietary; pattern only)

### 6.1 Merge.dev
Pattern: category-scoped Common Models; `include_remote_data=true` returns `remote_data: [{ path, data }]` — the raw third-party response per endpoint, "only available to customers on our Professional or Enterprise plans", not normalised, and refreshed "only if there's a change to Common Model field" (https://docs.merge.dev/supplemental-data/remote-data/). Field Mapping adds target fields on Common Models at integration-wide or Linked-Account level, resolved via `remote_field.field_key` / `field_traversal_path`, surfaced as `field_mappings` and `remote_fields` on responses (https://docs.merge.dev/supplemental-data/field-mappings/overview/). Passthrough: `POST https://api.merge.dev/api/{CATEGORY}/passthrough` with `method, path, base_url_override, data, multipart_form_data, headers, request_format (JSON|XML|MULTIPART), normalize_response`, response `{status, response, headers}`, plus async passthrough (https://docs.merge.dev/merge-unified/supplemental-data/passthrough-request/passthrough-requests.md). Common Model scopes, `/meta/post`, and webhook pages returned 404 — **unverified**.
Loses: no commerce category at all; `remote_data` only refreshes when a Common Model field changes, so provider-only fields go stale; anything outside the model is a paid add-on (Field Mapping, Remote Data, Passthrough are all Professional/Enterprise) — the "unified" layer is where the coverage stops.

### 6.2 Rutter
Pattern: commerce+accounting unified objects; `Product { id, platform_id, name, description, status (active|archived|inactive|draft), variants[], images, tags, created_at, updated_at, platform_data }` — `platform_data` is the raw-payload field; `access_token` per connection as a query param; list params `force_fetch` ("Bypasses sync checks"), `updated_at_min/max`, `cursor`, `limit` (https://docs.rutter.com/rest/2024-08-31/products). Long-running writes return a Job: `status` "One of prequeued, pending, success, or failure", `response`, `request`, polled via `GET /jobs/:id` or delivered by webhook (https://docs.rutter.com/rest/2024-08-31/jobs). Platform-support matrix and webhooks pages 404 — **unverified**.
Loses: the product model has no per-marketplace attribute dictionary (no Amazon product type, no eBay aspects), `platform_data` is opaque, and reads are served from Rutter's cache (`force_fetch` exists precisely because the cache lags) — a PIM would be reconciling against a stale mirror of a stale mirror.

### 6.3 Apideck
Pattern: Unify APIs (Ecommerce = Orders, Products, Customers, Stores; https://developers.apideck.com/apis/ecommerce/reference) over a Vault that owns credentials: headers `x-apideck-app-id`, `x-apideck-consumer-id`, `x-apideck-service-id`; Connection `{ id, service_id, unified_api, auth_type (oauth2|apiKey|basic|custom), state (available|callable|added|authorized|invalid), configuration[] per resource, custom_mappings[], enabled, oauth_grant_type, validation_support, schema_support }`; hosted UI via `POST /vault/sessions` → `session_uri`; custom mappings at `/vault/custom-mappings/{unified_api}/{service_id}/{target_field_id}` with expressions like `$['root']['field']`; per-resource downstream config at `/vault/connections/{unified_api}/{service_id}/{resource}/config` (https://developers.apideck.com/apis/vault/reference). Proxy: single `/proxy` endpoint with `x-apideck-downstream-url`, `x-apideck-downstream-authorization`, `x-apideck-downstream-method`, credentials injected from Vault (https://developers.apideck.com/apis/proxy/reference). `raw=true` / `pass_through` / `downstream_error` — **unverified** on the pages fetched.
Loses: the Ecommerce unified API is four read-mostly resources; the "state machine" of a connection (`callable`/`authorized`/`invalid`) is the reusable idea, but coverage of listing attributes is nil — the proxy is the only way to reach them, at which point Apideck is just an OAuth vault.

### 6.4 Paragon
Pattern: per-integration Workflows built in a UI or in TypeScript ("Paragraph") — "you can switch between the UI and code at any time" (https://docs.useparagon.com/workflows/overview); a Connect Portal where the end user authenticates and sets **User Settings** at integration- or workflow-level (e.g. pick a Slack channel or Salesforce stage), read in workflows via `{{` variables (https://docs.useparagon.com/connect-portal/workflow-user-settings). Field Mapping UI, Task History/replay and the Custom Integration Builder pages 404 — **unverified**.
Loses: the unit is a workflow per (integration, event), not a per-channel data model; user-level field mapping solves "which of *their* fields is our SKU" but not "which of *Amazon's* 400 attributes this product type requires" — coverage is whatever someone drew in the builder.

### 6.5 Prismatic
Pattern: Connections are a config-variable type ("Connections contain the information necessary for the steps in your integration to connect to third-party apps and services") supporting API key, OAuth 2.0 (`authorizeUrl`, `tokenUrl`, `scopes`) and basic auth; four ownership types — Customer, Organization (per-customer), Organization (global), Integration-scoped (on-prem agents); the platform refreshes tokens before expiry; "connection throttled" is an alert condition (https://prismatic.io/docs/integrations/connections/). Each customer deploys an **Instance** through a config wizard ("multiple configuration pages with dynamically generated dropdown menus, toggles, text fields") with data sources for dynamic dropdowns (https://prismatic.io/docs/integrations/config-wizard/). Alert Monitors pair triggers (execution failed, duration exceeded, log level, connection throttled/failed, instance enabled/succeeded) with email/Slack/PagerDuty/webhook groups (https://prismatic.io/docs/monitor-instances/alerting/).
Loses: an iPaaS for shipping many customers' integrations, not a data model — products/listings are just JSON flowing through steps; nothing enforces channel schema completeness; retention of step results not documented on the pages read (**unverified**).

### 6.6 ChannelEngine
Pattern: merchant-side REST API authenticated by an `apikey` (query param or header), tenant base URL `https://{tenant}.channelengine.net/api`, resource groups products, offers, channels, orders, shipments, returns, webhooks, product bundles, notifications; the official PHP client is "no longer supported by ChannelEngine" and users are told to generate from the Swagger spec (https://raw.githubusercontent.com/channelengine/merchant-api-client-php/master/README.md). The product request model (`MerchantProductNo`, `ExtraData[] {Key, Value, Type, IsPublic}`, `CategoryTrail` …) and the per-channel product validation/`ChannelErrors` — **unverified**: apidocs.channelengine.net and developers.channelengine.net both redirect to an OIDC login (fetched 2026-08-29).
Loses: the merchant pushes one feed and ChannelEngine's own channel connectors do the per-marketplace mapping — the merchant never sees the marketplace's attribute schema, so "100% coverage" is bounded by what ChannelEngine chose to map, and errors come back post-hoc per channel.

### 6.7 Feedonomics
Pattern: feed management — "Transform wild product data into optimized listings for 2,000+ destinations", "1.6M+ data governance rules monthly", "100M+ data transformations monthly", AI enrichment/categorisation, monitoring, order orchestration and platform sync (BigCommerce, Shopify, NetSuite, SFCC, Magento) (https://feedonomics.com/). Transformer rule syntax, export mapping UI and the API (`developers.feedonomics.com` / `help.feedonomics.com` — DNS did not resolve on 2026-08-29) — **unverified**.
Loses: it is a *feed* model — flat rows out, per-destination column mapping — with no bidirectional listing state (no "this ASIN is suppressed because attribute X is missing" loop back into the product record); a PIM needs the channel's rejection to land on the product, not in a feed report.

### 6.8 Rithum / ChannelAdvisor
Pattern (from memory of the public developer docs, marked **unverified** because https://developer.channeladvisor.com/* now redirects to a JavaScript knowledge-center shell that returned no article body): application id + shared secret from a developer console; a per-account authorisation grants a long-lived `refresh_token`; `POST /oauth2/token` with Basic auth and `grant_type=refresh_token` yields a ~1 h `access_token`; every entity carries a `ProfileID` (account/marketplace profile); OData conventions (`$filter`, `$expand`, `$top`, `$skip`, `@odata.nextLink`); products carry an `Attributes[] {Name, Value}` bag plus `DCQuantities`, `Labels`, `Images`; bulk via product export/upload jobs. Rebranded Rithum in 2024 (the fetched KB header reads "Welcome to Rithum API documentation").
Loses: marketplace-specific fields are encoded as **naming conventions inside a flat `Attributes` bag** with no schema, so completeness is unverifiable until the listing errors; profiles multiply everything by account×marketplace.

## Patterns worth re-implementing

| Pattern | Source | Why | Complexity |
|---|---|---|---|
| Four-blob OAuth declaration: user-input / server-input / oauth-output / server-output paths | Airbyte `advanced_auth` (R9a) | Separates what the merchant types, what the platform holds, what the token endpoint returns, and what is injected — the same split every marketplace needs | M |
| Rotated refresh tokens flow back as a control message, never as a side effect | Airbyte CONTROL/`refresh_token_updater` (R9a) | Amazon/eBay/Etsy rotate; the connection store must be the only writer | S |
| Error-action vocabulary: SUCCESS/FAIL/RETRY/IGNORE/RATE_LIMITED/REFRESH_TOKEN_THEN_RETRY + WaitTimeFromHeader/WaitUntil/Exponential | Airbyte `HttpResponseFilter` (R9a) | One declarative table per channel instead of per-call try/catch | M |
| Async-job retriever: create → poll → download → status_mapping → abort/delete | Airbyte `AsyncRetriever` (R9a) | Amazon reports/feeds, Shopify bulk ops, eBay feed API all have this shape | M |
| Per-stream state checkpoint + `is_resumable` | Airbyte STATE (R9a) | Resume mid-catalogue after a 429 storm | M |
| Install handshake: manifest → installer-chosen permissions → token POST to `tokenTargetUrl` → rollback on failure | Saleor `installation_utils.py` | Clean, auditable app onboarding; nothing half-installed | S |
| Hashed app token + `token_last_4` | Saleor `AppToken` | Display without exposure | S |
| Three-table delivery log: payload / delivery / attempt with request+response headers, status code, duration, capped body | Saleor `EventPayload`/`EventDelivery`/`EventDeliveryAttempt` | Exactly the "what did we send Amazon and what came back" ledger a PIM needs, in both directions | M |
| Payload defined by a subscription query chosen by the receiver | Saleor `Webhook.subscription_query` | Decouples payload schema from core changes | L |
| Sync-call cache + failure sentinel + circuit breaker | Saleor synchronous transport | Stops hammering a dead channel; a health signal for the UI | S |
| Channel-scoped webhook (`filterable_channel_slugs`) | Saleor `Webhook` | Per-channel fan-out without per-channel endpoints | S |
| Per-app deduplicated problem ledger (`key`, `count`, `is_critical`, dismissed) | Saleor `AppProblem` | Connection health surface without log spelunking | S |
| Retention sweeper for delivery payloads, batch 1000 | Saleor `delete_event_payloads_task` | Keeps the ledger bounded | S |
| Saga steps with `compensate`, persisted transaction, external `setStepSuccess/Failure` by idempotency key | Medusa workflows | Multi-system writes (DB + Amazon + eBay) with rollback and resume after Amazon's feed result arrives | L |
| Step knobs: `maxRetries`, `retryInterval`, `timeout`, `async`, `noCompensation`, `continueOnPermanentFailure`, `saveResponse` | Medusa `TransactionStepsDefinition` | A complete, named retry/timeout policy per step | M |
| Link tables without FKs + `query.graph` cross-module read | Medusa module links | Attach per-channel listing data to a product without touching the product table | M |
| Provider class: `static identifier`, `static validateOptions`, constructor-time client, registered with `{resolve,id,options}` | Medusa providers | A `ChannelProvider` abstraction with the same shape, one per marketplace | S |
| Raw payload beside the unified row: `_raw_data` + `_mapped_data` + `_last_modified_at` + `_is_deleted` in one row | Supaglue postgres writer | Nothing is lost by normalising; diffs are computable | S |
| API-call ledger (`events { direction, method, url, provider, status }`) and webhook delivery attempts with `next_retry`/`attempt_count` | Panora schema | Outbound *and* inbound observability in the same shape | S |
| Provider catalogue as data: `authStrategy`, `scopes`, `urls` (functions of tenant), `options` flags, `active` | Panora `connectors/metadata.ts` | Channel registry driven by one table, UI derived from it | S |
| Bring-your-own OAuth app vs platform app (`is_revert_app`, `app_client_id/secret` on the app row) | Revert `apps` | Merchants with their own Amazon developer profile | S |
| Signed 60 s state cookie + sorted-query HMAC + 90 s timestamp + timing-safe compare + shop regex | Shopify `oauth.ts`/`hmac-validator.ts`/`shop-validator.ts` | The reference OAuth callback hardening | S |
| `Session.isActive(scopes)` + implied-scope algebra (`write_x ⇒ read_x`) | Shopify `Session`/`AuthScopes` | Re-auth decisions become one predicate | S |
| Webhook registration as reconcile-to-desired-state (query, diff, create/update/delete) | Shopify `register.ts` | Idempotent per-shop setup and drift repair | M |
| Lifecycle topics as first-class: uninstalled → purge sessions; scopes_update → rewrite scope | Shopify template | Connection state stays truthful | S |
| Token exchange / managed install (no redirect; short-lived ID token → access token) | Shopify docs | Where a marketplace offers it, skip the redirect dance | S |
| Connection `state` enum (`available/callable/added/authorized/invalid`) | Apideck Vault | A UI can render exactly what the merchant must do next | S |
| Per-connection writable-field discovery (`/meta/post`-style) | Merge (unverified page) | The right idea for "which attributes does this product type require on Amazon DE" | L |
| Alert triggers as data (execution failed, connection throttled, connection failed) | Prismatic | Operators subscribe to channel health | M |
| Job object `{prequeued, pending, success, failure}` + `force_fetch` | Rutter | Honest async write status and an explicit cache-bypass | S |

## Anti-patterns to avoid

| Anti-pattern | Seen in | Why it hurts a 100%-coverage PIM |
|---|---|---|
| Common model first, raw payload as a paid/optional side-car (`remote_data`, `platform_data`) | Merge, Rutter, Apideck | Provider-only fields go stale or unreachable; coverage stops at the model |
| Field-mapping layer bolted on to patch the common model (EAV `attribute/value`, `entityMappings`, `fieldMappings`) | Panora, Supaglue, Revert | Two of three are archived; the layer becomes the product |
| Per-channel data as one fixed-column row (`ProductVariantChannelListing`) | Saleor | Cannot hold Amazon product-type attributes or eBay aspects; falls back to untyped `metadata` |
| Sales channel = membership only | Medusa | No per-channel title/price/attributes at all |
| Providers per capability (fulfillment/payment), not per marketplace | Medusa | A "Shopify provider" has nowhere to live |
| Outbound-only extension model (apps receive, never sync in) | Saleor apps | No cursor/state/rate-limit concept for inbound sync |
| Marketplace-specific fields as naming conventions inside a flat `Attributes[]` bag | ChannelAdvisor | Completeness is unverifiable until the listing errors |
| Feed-out with post-hoc channel errors in a report | ChannelEngine, Feedonomics | Rejections never land on the product record |
| Deleting delivery payloads after a period without an archive | Saleor `EVENT_PAYLOAD_DELETE_PERIOD` | The ledger stops being an audit trail |
| `scope` as a comma string; expiry bolted on later (`refreshToken`, `refreshTokenExpires`) | Shopify session adapters | Model token expiry and scope sets structurally from the start |
| Cache-backed unified reads that need `force_fetch` to be truthful | Rutter | A PIM reconciling against a stale mirror |
| OAuth for Shopify replaced by "paste an Admin API token" | Panora Shopify entry | Skips install/uninstall lifecycle and scope tracking |
| Session-level webhook registration by append (no diff) | (contrast: Shopify reconciles) | Duplicate subscriptions and drift |
| Workflow state only in Redis | Medusa default engine | Long-running channel writes must survive a cache flush |
