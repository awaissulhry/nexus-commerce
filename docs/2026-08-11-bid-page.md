# BID — Bid as its own page

*Rules & Automation, tab 9 of 11. The page study that follows
[the tab study](2026-08-11-bid-study.md).*
**Read-only. Nothing was changed, no application code was written, nothing was committed.**

Measured on production 2026-08-11 with `apps/api/scripts/_bid-page-{writers,chain,bounds,bidder,nobidder}.mts`.

---

## 0 · The one-sentence version

The tab study's headline was wrong: **there is no bid ratchet** — the "19 consecutive cuts,
€0.38 → €0.02" is the *same* €0.38 → €0.02 write issued once a night for nineteen nights, every one
of which **Amazon rejected**, silently reverted each hour by an inbound resync nobody audits. What
the account actually has is the opposite problem: **41 of 86 live campaigns have no bidder at all**,
they carry **23.3% of live ad spend**, and the six rules that claim to bid propose **nothing**
because the engine behind them reads four database columns that are zero on all 3,154 rows.

## 1 · Corrections to the tab study — read these first

I wrote the tab study this morning. Five of its findings do not survive measurement, and one of
them was its headline. Recording each because the wrong version was entirely plausible.

Yes"** — 19 cuts, €0.38 → €0.02 over 433h, ≈ −15%/day, twelve targets in lockstep | 🔴 **No ratchet.** Every one of the 19 steps is the identical `38 → 2`, once a night, reason `rank — pause target → bids floored (no-pause)`. ### The gate, and what it enforces

**authority pins** → **`minBidCents` / `maxBidCents`** → keyword protection → €-value cap. Two
properties are worth stating because both are already right:

- Bounds **deny**, they do not clamp (`:268`) — *"clamping would rewrite an engine's intent without

- 🔴 **The minimum is already exempt for suppression** (`isSuppression`, ADX G1). A `force:true`
  write travels to the gate as `force` in the queue payload (`ads-mutation.service.ts:189`) and
  skips only the floor; the ceiling still binds, because *"a 'suppression' that raises a bid is not
  a suppression"*. **The hardest part of question (e) is already built and shipped.**

## 3 · (b) How it works — and why the optimiser proposes nothing

### `bid_to_target_acos`, step by step

```ts
// ads-bid-optimizer.service.ts
const source = resolveSource(opts.source)          // :55  env NEXUS_BID_OPTIMIZER_SOURCE, default 'legacy'
const where = { status:'ENABLED', isNegative:false,
                suppressedFromBidCents:null,        // :126 ACR.6 — never touch a suppressed target
                bidCents:{ gte:5 },                 // :127 …nor one already under the floor
                spendCents:{ gt:0 } }               // :129 LEGACY: the dead column
if (t.clicks < 5) continue                          // :180 MIN_CLICKS
if (salesCents === 0)      proposed = max(5, bid×0.5)             // cut 50%
else if (acos > target)    proposed = max(5, bid × max(0.5, tgt/acos))
else if (acos < target && orders ≥ 1) proposed = bid × min(1.25, tgt/acos)
```

**Measured on prod, all 3,154 `AdTarget` rows: `MAX(spendCents)=0 · MAX(clicks)=0 ·
MAX(salesCents)=0`.** The legacy `WHERE spendCents > 0` therefore selects **0 rows**, so the
engine's answer to "what should this keyword bid tomorrow" is, and has always been, **nothing**.

`NEXUS_BID_OPTIMIZER_SOURCE` is **unset** on production. Flipping it to `daily` re-points the same
arithmetic at `AmazonAdsDailyPerformance`:

| source | candidates | after `MIN_CLICKS=5` |
|---|---|---|
| `legacy` (today) | **0** | 0 |
| `daily` | 274 | **128** |

**One environment variable moves four AUTO rules from writing nothing to writing on 128 targets.**
The engine's own header says exactly this and it is worth quoting, because it is the single most
consequential sentence in the bid subsystem:

> *"Default is `legacy`, so deploying this changes nothing. The switch is one env var, and it is a
> real switch: this function is the shared upstream of the APPLY path too (`ads-auto-bid`,
> `autopilot/apply`), so flipping it does not merely reveal proposals — it lets four AUTO rules
> start writing bids."*

The same dead columns are read by two more places:

- 🔴 **`suggestBids`** (`ads-bid-suggest.service.ts:44`) filters on `clicks > 0 AND spendCents > 0`.
  The corpus is empty, `accountMedian` is `null`, so **every "data-grounded" bid suggestion in the
  product is the hard-coded 50¢ default** with `basis: 'default'`.
- 🔴 **`bid_up`'s spend estimate** (`:222`) is `spendCents/30 × (new/old − 1)` → always **0** → the
  per-rule daily ad-spend cap it feeds is never consulted. **The one money brake on bid raises is
  computed from a column of zeros.**

Meanwhile `GET /advertising/targets` — the endpoint the *grid* uses — overlays
`AmazonAdsDailyPerformance` correctly. **The screen shows real numbers; the engine deciding the bid
sees zeros.**

### What the rank engine actually does to a bid

`computeStep` (`rank-controller.ts:170`) moves the **placement bias**, not the bid. Bids move by
four discrete directives on the active `RankTarget`:

| directive | effect on bids | compounding? |
|---|---|---|
| `pause` | floor every bid to `floorBidCents` (default 2¢), remember each prior bid | no — idempotent, `atFloorAlready` short-circuits |
| serve | restore each remembered bid exactly | no |
| `bidMode:'deltaPct'` | every bid = **`baseBidFromCents`** × (1±%) | **no, by construction** (BL.7) |
| `bidMode:'absolute'` | ad-group default = a fixed number | no |

**None of the four is a percent of the current value.** That is the structural difference from the
budget ratchet in study 6, and it is deliberate: `applyBaseBidDelta` stamps a stable baseline
precisely *"so repeated ticks NEVER compound"*. Study 6's failure cannot occur on this path.

The other structural difference: `updateAdTargetWithSync` writes the **local value first**
(`ads-mutation.service.ts:1038`) and enqueues after. The budget path's repeat-write loop — where a
`PENDING` outbound write left the local value stale and the next tick re-issued the same cut — has
no analogue here.

## 4 · (c) 🔴 Who is the bidder?

Measured two ways, and they disagree — which is the finding.

### Observed: almost nobody, and never two at once

| | |
|---|---|
| `AD_BID_UPDATE` rows, 60 d | **23,705** — AD_TARGET 22,014 · AD_GROUP 1,691 |
| by origin class | **`automation/schedule` 23,591 (99.5%)** across 45 schedule ids · `operator/manual` 98 · `automation/job` 16 |
| produced by a rule execution | **92 — 0.4%** |
| campaigns that received a bid write | **46** |
| …with exactly **one** writer | **38** |
| …with two | 7 — in every case *one rank schedule + the operator's 2026-08 consolidation* |
| …with three | 1 — `GALE \| IT \| PAT`: its schedule + two one-off repair jobs |

**There is no engine-vs-engine bid contention in this account today.** Not one campaign has two
automated bidders. The tab study's "six overlapping engines, whichever ran last wins" describes a
*declared* risk that has never fired, and the reason it has never fired is that six of the seven
engines cannot propose anything (§3).

### Declared: five unscoped rules that can reach all 220

| | |
|---|---|
| bid rules **enabled AND `levelActs`** | **5** — and **5 of 5 carry no scope at all** |
| enabled `AdSchedule` rows | 33, across 33 campaigns · **0 campaigns hold more than one** |
| ENABLED campaigns **with** a rank schedule | 33 of 86 |

So the declared bidder set for any ENABLED campaign is: *5 account-wide rules + `ads-auto-bid`
(account-wide cron) + its rank schedule if it has one + operators.* The gap between 5-and-a-cron
declared and 0-or-1 observed is held open by exactly one thing — the dead metric source. **That is
not a safety property. It is an accident that a single environment variable ends.**

### Recommendation — one named bidder per campaign

The abstraction already exists and is better than anything in the competitor set: a `RankTarget` is
`{placement + targetIS + ACoS cap + CPC ceiling + bid directive + motion}`, per lane, reusable, with
per-campaign overrides. Do not invent a second one.

1. **Add a `bidderKind` + `bidderRef` to the campaign** (or derive it — see the shared-layer
   requirement). Exactly three legal values: **`schedule`** (a rank group owns it), **`goal`** (the
   target-ACoS optimiser owns it, once it has a live source), **`manual`** (nobody automated).
   Render it on every row of the Bid page and on Apply Rules. Today that column reads
   *schedule* × 33, *manual* × 53.
2. **Rules become declared exceptions, never the default owner.** A rule that can write must name
   a scope; the write gate is where the refusal lands, and it already renders one.
3. **The transition is a five-step order, and it must be in this order:**
   1. name the bidder on all 86 ENABLED campaigns (read-only column first — it needs no schema
      change to compute);
   2. scope the 5 unscoped writing rules, or move them to OBSERVE (which **no rule in this account
      has ever used** — study 10);
   3. set `minBidCents` / `maxBidCents` on every gate-open campaign (§6);
   4. **only then** flip `NEXUS_BID_OPTIMIZER_SOURCE=daily`, and flip it first for one campaign via
      the explicit `source` parameter the function already accepts;
   5. watch the staged tray for one grace window before opening the gate wider.

   Steps 1–3 are reversible and cost nothing. Step 4 is the one that spends money, and it is
   currently one `railway variables set` away from happening with none of steps 1–3 done.

## 5 · (d) The rule-level defects

The tab study named three. There are five, and the one it missed is the worst.

### 🔴 D1 — the Automation toggle is OFF on all five rules that write

`RuleListTab.tsx:38` derives the toggle from `actions[0].control === 'automate'`.
**No rule in the account sets `control` on any action.** So the switch renders **off on all 18
rows** — including `Profit-native bid optimisation`, `Target ACOS setter (from profit)`,
`Weekend budget boost`, `Reduce bids on ACOS spike` and `ACoS convergence`, all of which are
`enabled` and pass `levelActs(resolveAutonomy(rule))`.

The one control on this tab that claims to say whether a rule is automated **reads a field that
does not exist and reports "no" for every rule that can write to Amazon.** Clicking it changes
React state and nothing else.

### 🔴 D2 — `lower_bid_to_floor` is a raise on 152 targets

```ts
const floorCents = Math.max(5, Number(action.floorCents ?? 5))   // :1148
await updateAdTargetWithSync({ patch: { bidCents: floorCents } }) // unconditional
```

There is no `if (current > floor)` and no `suppressedFromBidCents: null` guard. **152 live targets
sit below 5¢** (141 keywords at ≤2¢). On those, "lower to floor" is a **+150% raise**.

Two enabled rules carry this action — `Wasted keyword instant negate` (19,586 executions) and
`Bulk bid floor protection` (4,285). Both are PROPOSE today. **"Turn automation up" moves them to
AUTO and un-suppresses 152 targets on the first tick.** The bid optimiser already has exactly this
guard, added for exactly this reason (ACR.6, `ads-bid-optimizer.service.ts:76`: *"A cut that raises
a bid is not a cut"*). The handler never got it.

**Fix:** `bidCents: Math.min(existing.bidCents, floorCents)`, plus skip when
`suppressedFromBidCents != null`. Three lines, and it is the prerequisite for arming either rule.

### D3 — `bid_down` stores a positive percent

`percent = -Math.abs(Number(action.percent ?? 20))` (`:145`). The stored value is `25` and means
−25%. The behaviour is right; the *sign is not part of the data*, so any renderer that shows
`action.percent` shows `+25%` for a cut. The Criteria cell doesn't currently render it at all
(`summariseRule` only understands the budget builder's `incPct`/`decPct` vocabulary and returns `—`
for every bid rule), so the tab shows nothing rather than something wrong — but the moment the
column is made real, this is the bug it ships with. **Store the sign, or render the verb.**

### D4 — "Weekend budget boost" is a bid rule on AUTO

Enabled · AUTO · `bid_to_target_acos profitMode bayesian` · 5,252 executions · 4,998 SUCCESS.
Its three siblings (`Profit-native bid optimisation`, `Target ACOS setter (from profit)`,
`Daily automation digest`) carry a **byte-identical action**. Four rules, one behaviour, three
misleading names, and one of them names a different dimension entirely.

**Recommendation: keep one, `Profit-native bid optimisation`, scope it, and delete the other
three.** They cannot disagree with each other today — they all propose zero — which makes this the
cheapest moment there will ever be to collapse them.

### D5 — the four zero-execution rules

| rule | created | trigger | verdict |
|---|---|---|---|
| Top-of-Search rank defender | 2026-06-01 | `KEYWORD_ZERO_IMPRESSIONS` | **delete** — `raise_bids_for_rank_defense` on a zero-impression trigger, superseded by the rank engine |
| Aggressive growth: raise bids on low-ACOS winners | 2026-06-01 | `AD_TARGET_UNDERPERFORMING` | **fix or delete** — a *raise on winners* rule bound to an *underperforming* trigger; the same trigger/condition mismatch study 6 found on `Boost budget on profitable campaigns` |
| Cut bids on high ACOS | 2026-08-03 | `CAC_SPIKE` | **delete** — duplicate of the enabled AUTO `Reduce bids on ACOS spike` |
| Bid down on profit breach | 2026-08-03 | `AD_SPEND_PROFITABILITY_BREACH` | **keep, and arm it in OBSERVE** — the only rule in the set that reads the profit signal the account is differentiated on |

### And two live data defects the handlers already refuse

Both refusals are correct and both are invisible on the tab:

- **`AIREON — Target ACoS bidding`** stores `targetAcos: 30`. Read as a fraction that is a 3,000%
  ACoS target — *"spend up to thirty times revenue"*. Refused (`ads-bid-optimizer.service.ts:275`).
  It also stores `campaignIds[11]`, which the handler cannot honour, so it is refused twice.
  **5,640 FAILED executions in 60 days, every one of them this refusal, and the rule row says
  nothing.**
- `ACoS convergence` stores `0.3` — the only one of the seven with a valid fraction.

## 6 · (e) Bounds as a first-class control

### What is set

| control | enforced where | campaigns |
|---|---|---|
| `minBidCents` | gate `:282` (deny, suppression-exempt) | **0 of 220** |
| `maxBidCents` | gate `:275` (deny) | **82** — exactly the 82 with the gate open; values **80¢ · 90¢ · 190¢** |
| `pinBids` | gate `:259` (deny, whole dimension) | **0** |
| `dynamicBidding.maxBidChangePct` | `ads-mutation.service.ts:989` (**clamp**, not deny) | 2 |
| `cpcCeiling` | rank engine `cpcCapPct` | 6 |
| `dynamicBidding.targetAcos` | read by 5 services | **0** |

Three values, three floors, no minimum: **2¢** (`SUPPRESSION_FLOOR_CENTS`, and the retired
console's bid input), **5¢** (`BID_FLOOR_CENTS` in the handlers, `FLOOR_CENTS` in the optimiser and
in `suggestBids`), and `minBidCents`, which is null everywhere. An operator cannot state a floor;
the code states three on their behalf and they disagree.

### 🔴 57 live bids sit above their campaign's ceiling

The gate denies a write *above* `maxBidCents` — it does not pull an existing bid down. The ceilings
were set after the bids:

| campaign | bid | ceiling |
|---|---|---|
| IT-AIRMESH-SP-Competitor-Broad | €2.32 | €0.80 |
| IT-AIRMESH-SP-Competitor-Exact | €2.23 | €0.80 |
| IT-AIRMESH-SP-Brand-Exact | €1.98 | €0.80 |
| …54 more | | |

These bids are **frozen upward and un-lowered**: nothing may raise them, and nothing is trying to
lower them. That is the deny-vs-clamp trade-off made visible, and it is the one place I would
consider the other choice (§8, Perpetua).

*(This also revises the tab study's €2.05 note: exactly **one** keyword sits at €2.05 today.
**95 keywords are above €1.00** — a much larger population than the 35 it reported — and they are
concentrated in the AIRMESH competitor campaigns and the Sponsored Display campaigns, not in a
single SB drift.)*

### Design — how an operator declares a floor and a ceiling

**Grain.** Per **campaign** is the enforced grain and it is the right default: it is where the gate
reads, it is where the write gate and the pins already live, and Perpetua reaches the same
conclusion from the other direction (min/max at *segment* level, never per keyword, §8).
Per-keyword overrides are a Tier-3 item at most; **do not build a per-row min/max field.**

**Where it lives.** On **Apply Rules** (session 11) as the editable Min/Max Bid column — which
already exists as a column, a hover-pencil editor *and* a bulk action, all three writing to
`useState`. It needs an endpoint, not a UI. The **Bid page shows the same two numbers read-only on
every row**, as the band a bid is moving inside.

**How it interacts with the 2¢ policy — already solved, and must be labelled.** `isSuppression`
exempts the minimum and only the minimum (ADX G1). So:

> **A floor is what optimisation may not go below. Suppression is not optimisation, and passes
> through it.**

That sentence should appear on the page, once, next to the floor field. Without it, an operator who
sets a 20¢ floor will reasonably expect their Min-bid windows to stop working, and will not set one.

**What must be distinguishable on screen — three different 2¢ keywords:**

| state | how to tell | label |
|---|---|---|
| deliberately suppressed | `suppressedFromBidCents != null` | **"Suppressed — restores to €X.XX"** |
| in a Min-bid window | `campaign.bidsSuppressedAt != null` + the active `RankTarget` | **"Min bid until 08:00"** |
| 🔴 at 2¢ with no memory | neither — **141 keywords today** | **"At the floor · no restore value recorded"** |

The third bucket is currently the *whole* of the 2¢ population and nothing anywhere says so.

**A refusal must be visible.** `entity_bounds` denials are already generated with an exact reason
string (`bid 194¢ exceeds Campaign.maxBidCents=80¢ on <id>`). They are logged and dropped. The
operator asked for *"at the cap: refuse the write and tell me"* — the refuse half is built; only
the tell-me half is missing, and `pending-writes` already carries `errorCode` + `errorMessage`.

## 7 · (g) The cadence question

**Answered by measurement, and the premise was wrong.** Bid writes by hour of day, Europe/Rome,
60 days:

```
00:00  8,916 ████████████████████████████████████████████   floor
01:00  1,339 ███████
02:00  1,129 ██████
03:00–07:00  ~1,330 combined
08:00  8,300 █████████████████████████████████████████      restore
09:00  1,869 █████████
10:00–20:00  ~230 combined      ← the entire trading day
21:00    502 ██
22:00–23:00      5
```

**53.7% of all bid writes fall between 22:00 and 08:00, and the trading day is empty.** This is not
"hourly bidding by accident". It is a **binary day-shape**: floor at midnight, restore at 08:00, and
the bid restored is *exactly the number it was before* — a value that has not adapted to anything.

| | |
|---|---|
| entities written in 60 d | 659 |
| writes per entity | median **30** · p90 82 · max 116 |
| distinct **days** touched per entity | median **15** of 60 · p90 42 |
| entities averaging >2.5 writes on an active day | **11** |

Median 30 writes over median 15 days = **exactly one floor and one restore per active day.** The
six rules that tick every 15 minutes contribute 92 writes in 60 days between them.

**Recommendation: make daily explicit, and do not build hourly.**

1. **Say what the cadence is.** "This campaign's bids move twice a day: floored at 00:00, restored
   at 08:00" is a true sentence about 33 campaigns and it is not written anywhere.
2. **The 7-day evidence window matches a daily cadence.** Every condition on every bid rule reads a
   7-day window; evaluating it every 15 minutes buys nothing and is the exact mismatch study 6
   identified as the cause of the budget ratchet. **Move the bid rules' triggers to daily.** This
   costs nothing today (they write 92 rows) and removes the mechanism before it is armed.
3. **Hourly is a real product, and we cannot support it yet.** Quartile charges $895+/mo for it and
   Teikametrics rebuilt on Marketing Stream to do it (§8). We *have* Marketing Stream — 24 subs
   ACTIVE — and 17,963 hourly rows. But the loop that would consume them is reading a signal 16 days
   stale (study 5) and Pacvue's own spec excludes the most recent two days for attribution
   settling, which we do not do. **Hourly bidding on a stale feed is worse than daily bidding on a
   fresh one.** Revisit after the SQP recency guard.

### What the screens converge on

1. **A keyword grid with the bid beside its evidence**: keyword · match · ad group · **bid** ·
   suggested bid / bid range · impressions · clicks · CPC · ACoS · **new bid preview**.
2. **Amazon's suggested-bid range as the anchor** — *"the suggested bid range is based on the
   winning bids… for example a suggested bid of $0.70 with a range of $0.40–$1.40"*. Every tool
   shows it; practitioner guidance is to open **20–30% below** it.
3. **Min/max as visible fields on the row that owns them** — and Perpetua's precedence rules are
   worth copying verbatim: *"all bids lower than min\_bid will be raised to min\_bid… higher than
   max\_bid will be capped"*; **a fixed bid overrides max**; **a multiplier is capped by max**; and
   — the one we should not copy — *"placement multipliers may exceed the segment's maximum bid"*.
4. **Bulk edit that persists**, usually including a CSV round-trip.
5. **A staged/approval step** on the agentic tier (Pacvue Agent's *"governed execution"*).

### 🔴 The gap in the whole field

**No platform in this survey documents a per-keyword bid-change history with actor and reason.**
Perpetua states outright that it *does not have access to the bid's history*. Teikametrics
documents hourly bidding in detail and says nothing about showing the user what changed. Quartile's
own positioning is that you should not need to look.

Nexus has **23,705 attributed bid changes with a resolved origin name, a prose reason, delivery
state, the Amazon error, and a working undo** — and renders none of it on this tab.

**That is not catching up. On the axis the operator cares most about — control and legibility —
it is the one place this system can be unambiguously ahead of a $895/mo product.**

### One to steal, one to avoid

- **Steal: Pacvue's Bid Explorer.** *What does +50% cost and buy?* — shown **before** committing.
  We have the substrate (`AmazonAdsDailyPerformance` per target, observed CPC, SoV going rate) and
  the retired console already computes a "new bid" preview column. Forecast-before-commit is the
  single feature that turns a bid grid from a form into a decision.
- **Avoid: Perpetua's placement exemption.** *"Placement multipliers may exceed the segment's
  maximum bid"* is exactly the compounding hole study 3 measured on our own account — one live
  campaign at **+300% Top of Search**. Our ceiling must bind the **effective** CPC
  (`bid × placement × strategy`), not the base bid. `cpcCapPct` already computes this for the rank
  engine; the gate does not.
- **Also avoid: Pacvue's weeks-long onboarding.** *"Flat grid + filters, minimal teaching text"* is
  the right instinct and the research supports it.

## 9 · (f) How the Bid page should be

> **One question: what is each keyword bidding, why is it that number, and who decided?**

### Layout

```
┌ AdsPageHeader — Bid · scope bar (market · portfolio · product line · campaign) ─────┐
├ Bidder strip ──────────────────────────────────────────────────────────────────────┤
│  33 campaigns bid by a schedule · 53 by nobody · 0 by a goal                        │
│  🔴 26 spending campaigns have no bidder — €709.93/30d, 23.3% of live spend         │
│  Bids move twice a day: floored 00:00, restored 08:00 · next move in 4h 12m         │
├ FilterBar — campaign · market · bidder · match · status · bid band · at-floor ──────┤
├ AdsDataGrid ───────────────────────────────────────────────────────────────────────┤
│ Keyword  Match·AdGroup  Bidder   Bid    Band       Suggested  Impr  CPC  ACoS  Last │
│ giacca…  EXACT·GALE     IT GALE  €0.34  0.05–0.80  €0.41      2,481 €0.31 28%  ▁▄▂▂ │
│ moto…    BROAD·GALE     — none   €0.02  — none —   €0.41         12 —     —    ▁▁▁▁ │
│                                                    ↑ at the floor · no restore value│
├ Selection → Set bid · Boost % · Bid to win (N% of going CPC) · Set floor/ceiling ───┤
└ Staged tray (5-min grace) · Refusals · Change log filtered to field=bid ────────────┘
```

### The seven things it must do

1. **🔴 A bid curve per keyword.** The single highest-value addition, and it needs **no backend**:
   `GET /advertising/changes?entityType=AD_TARGET&entityId=<id>&field=bid` already returns actor →
   resolved origin name, old→new, reason, evidence, delivery state, `lastError`, and
   `undoActionLogId`. A sparkline in the row; the full annotated curve in the row drawer.
   **It must plot two series**: what we *intended* and what Amazon *took*. The 2026-07 example is
   the reason — nineteen recorded "cuts" that never reached Amazon, on a bid that never moved.
2. **Unexplained jumps marked as unexplained.** When `AdTarget.bidCents` differs from the last
   audited value, the hourly resync (writer 9) changed it — from Seller Central, or because Amazon
   disagreed with us. Render it as **"changed outside Nexus"**, not as a gap.
3. **One named bidder per row**, from the three-value vocabulary in §4. *"none"* is a value and it
   should be loud on the 53 campaigns that hold it.
4. **The band on the row**: `minBidCents` – `maxBidCents`, read-only here, edited on Apply Rules,
   with the bid's position inside it. **57 bids outside their band** need a state of their own.
5. **Refusals and failures as first-class rows.** `pending-writes` returns them per campaign with
   the Amazon error. Never mix `DAILY_CAP_EXCEEDED` into a health figure — it is a refusal, and it
   is 99% of the execution table.
6. **The staged tray, moved not rebuilt.** Every rule-driven bid write already sits in a
   **5-minute cancellable grace window** (`GRACE_PERIOD_MS`, `ads-mutation.service.ts:34`); only the
   rank engine's suppression writes use `applyImmediately`. `StagedChangesTray.tsx` reads a working
   endpoint and is on the console being retired. **Move it. Do not write a second one.**
7. **The suppression floor labelled as policy** — the three-state vocabulary in §6, so that a 2¢
   bid never reads as collapse and a 2¢ bid with no restore value never reads as policy.

### What it must not do

- **No per-keyword min/max fields.** Perpetua's segment-level conclusion is correct and our
  enforcement grain is the campaign.
- **No second lane/blend or motion editor.** Those live in the Rank & Dayparting builder.
- **No bid-rule builder rebuild.** Five of the eighteen rules should survive; the page's job is to
  show what they *are allowed to do*, and to show that four of them are duplicates.

### The URL contract

```
/marketing/ads/rules-automation/bid
  ?market=IT|DE|FR|ES        scope bar, shared across all eleven pages
  &portfolio=<id> &line=<id> &campaign=<id>
  &bidder=schedule|goal|manual|none
  &state=at-floor|suppressed|out-of-band|unexplained|failing
  &match=EXACT|PHRASE|BROAD  &kind=KEYWORD|PRODUCT|AUTO
  &band=0-5|6-20|21-50|51-100|100+
  &q=<search>                &sort=<col>:<dir>
  &target=<adTargetId>       opens the row drawer — the bid curve, deep-linkable
  &window=7d|30d|60d         the metric window, NOT the history window
```

Every view linkable; `?target=` is the one that matters, because *"why did this bid move"* is a
question asked about one keyword by someone who was sent a link.

## 10 · (i) Requirements on the shared layer

Constraints, not solutions. A twelfth pass reconciles these with the other ten sets.

**Shared with sessions 3 (Placement) and 5 (Rank & Dayparting) — one engine, three pages**

1. `ad-rank-defend` writes **placement, base bids, bid suppression and campaign status**. There must
   be **one identity, one name and one link target** for it, and one resolver from
   `automation:rank-defend-<id>` to a human name. *(Session 3 asks for this in identical terms;
   I am seconding it, not restating it.)*
2. **"Which loop owns this campaign this hour" is one fact with one resolver** —
   `resolveActiveTargetKey` over the Postgres clock, plus events, plus per-scope overrides. Bid
   needs it to render *when the next bid move happens*; three implementations will disagree.
3. **`RankTarget.floorBidCents` is a bid control that lives in the rank builder.** Bid must **read**
   it and must not offer a second floor editor. It is the per-campaign Min-bid floor and it is a
   different thing from `Campaign.minBidCents` — the page has to name both, distinctly, in one
   sentence each.

**Attribution and the change feed**

4. **One change-feed component**, one origin resolver, one evidence renderer — for Bid, Placement,
   Budget and Rank. `listChanges` is the contract; `evidence` is present on **81 of 23,705** bid
   rows, so the component must render *absent evidence as normal*, never as an error.
5. **Intended vs delivered must be one primitive.** A field change and whether Amazon took it are
   two facts, kept apart in `listChanges` on purpose. Every page that shows a value needs the same
   badge for *"queued · delivered · rejected · changed outside Nexus"*. Bid is where the cost of
   conflating them is provable.
6. **The 5-minute grace window and the staged tray must be shared, not per-page.** A bid write and
   a placement write on the same campaign land in the same queue in the same window; two trays
   would show each other's changes and disagree about which to discard.
7. **A change on one page must appear on the others without a reload.** A rank schedule flipping to
   Min-bid at 00:00 changes 12 rows of the Bid grid.

**Refusal and guardrails**

8. **A refusal renders identically everywhere** — `entity_bounds`, `authority_pin`,
   `campaign_allowlist`, `automation_halted`, `keyword_protected`, `value_cap`. The gate already
   writes an exact sentence for each; the page must **display, not paraphrase**.
9. **The spend ceiling per scope the operator asked for on 2026-08-10 cannot be built on
   `estimatedValueCentsEur` as it stands.** `bid_up`'s estimate is derived from `AdTarget.spendCents`
   — zero on all rows — so it is always 0 and the cap it feeds never binds. Whoever builds the
   per-scope ceiling must re-source the estimate from `AmazonAdsDailyPerformance`. **This is a
   shared prerequisite, not a Bid-page task.**
10. **Bounds are enforced per campaign and edited on Apply Rules (session 11).** Bid renders them
    read-only. There must be exactly one editor and one endpoint. Session 11 owns the write.

**Scope and grain**

11. Bid needs all four grains from the shared scope bar, inherited across navigation. It also needs
    the **grain the shared layer does not have**: `expressionType` and `kind`. A bid decision is
    made about EXACT keywords and PRODUCT targets differently; the account holds 1,982 keywords and
    962 non-keyword targets and they cannot share a filter chip.
12. **Rule scope is single-valued** (`scopeCampaignId`). Scoping the 5 unscoped writing rules from
    the Bid page would *move* them, not add. Bid needs `scope*Ids` arrays for the same reason
    session 11 does; until they land, **Bid must be read-only about rule scope.**

**Design system**

13. `AdsDataGrid` + `GridToolbar` + `FilterBar` + all four DS stylesheets; shared frozen-column and
    dropdown-portal behaviour; shared empty state; the sparkline must be a shared DS primitive —
    Bid, Placement and Rank all want one and three implementations will not align.
14. Bid becomes a routed page (`routed: true` in `RULES_TABS`, `tabs.tsx`) — one additive line in a
    file ten other sessions also need. **Sequencing, not design.**
